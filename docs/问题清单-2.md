## 122. 接下来要做什么？

对应旧清单第 118 条（统一异常）。ReturnValueResolver 按用户要求停在当前形态：按 `method.getReturnType()` 区分 String 与 JSON，成功时写 200 和 Content-Type。

**结论：下一步只把异常收成一条出口，不要开 PathVariable，也不要拆 ReturnValueResolver。** 你已经让坏 JSON 能变成 400，但只接住了 `JsonProcessingException`，接在 `DispatcherServlet` 里，没有写正文，其它异常仍会变成 Tomcat 的 HTML 500。

### 现在实际怎样

`ArgumentResolver` / `ReturnValueResolver` 把 `JsonProcessingException` 继续向外抛。`Dispatcher.doService` 也声明抛出它。`DispatcherServlet` 里：

```java
} catch (JsonProcessingException e) {
    resp.setStatus(HttpStatus.WRONG_PARAM.value());
    resp.setContentType(httpResponse.contentType);
    return;
} catch (InvocationTargetException e) {
    throw new RuntimeException(e);
}
```

因此：

| 情况 | 现状 |
| --- | --- |
| 坏 JSON | 能到 400。`contentType` 多半还是 null，没有 body。`curl.exe` 不加 `-i` 看起来像没返回 |
| `IllegalArgumentException`（不支持的类型、缺 body、数字格式不对） | 没人接，容器 500 |
| Controller 里抛出的异常 | 被包成 `InvocationTargetException`，Servlet 再包成 `RuntimeException`，容器 HTML 500 |
| 404 / 405 | `Dispatcher` 已写 `status` 和 body，这条别动 |

`HttpStatus` 已有 `WRONG_PARAM(400)`，够用。

### 这一步只做

把翻译放进 `Dispatcher.doService`，包住 `handlerAdapter.handle(...)`。Servlet 删掉单独的 `JsonProcessingException` 分支，恢复成只写 `HttpResponse`。

解开包装后再分类：

```text
InvocationTargetException → 用 getTargetException()
RuntimeException 且有 cause → 用 cause
```

| 解开后 | status | body | contentType |
| --- | --- | --- | --- |
| `IllegalArgumentException` | 400 | 异常 message | `text/plain;charset=UTF-8` |
| `JsonProcessingException` | 400 | 短句，例如 `bad json` | 同上 |
| 其它 | 500 | `internal error` | 同上 |

不要把堆栈写进 body。404/405 仍走 `failStatus`，不要改成抛异常。启动时的「重复 URL」发生在 `init`，不要放进这个 catch。

参数解析器和返回值处理继续抛，不要在里面直接改 `httpResponse.status`。

### 验收

Tomcat 停在 `await()` 上：

```powershell
curl.exe -i -X POST http://localhost:8080/addUser -H "Content-Type: application/json" -d "{bad}"
curl.exe -i http://localhost:8080/hello
curl.exe -i http://localhost:8080/noSuch
```

坏 JSON 的第一行是 `HTTP/1.1 400`，正文是你写的短句，不是 `<!doctype html>`。`/hello` 仍是 200，`/noSuch` 仍是 404。

### 做完再往后

```text
异常出口（本步）
  → 类级 @RequestMapping 前缀
  → @PathVariable（只加 ArgumentResolver，不改 Adapter 的循环）
  → 启动从测试挪到 main
  → 再加固 IoC
```

### 最终建议

ReturnValueResolver 保持不动。下一步把 Servlet 里那个只设状态码的 catch 挪到 `Dispatcher`，补上正文，并接住参数错误和未预料异常，分别写成 400 和 500。

## 123. `throw e` 和 `throw new RuntimeException(e)` 有什么区别？

出现位置：`Dispatcher.doService` 里对同一个 `InvocationTargetException` 写了两段 catch：

```java
} catch (InvocationTargetException e) {
    throw e;
} catch (InvocationTargetException e) {
    throw new RuntimeException(e);
}
```

**结论：第一段是把原异常原样再抛出去；第二段是新做一个非受检异常，把原异常藏进 cause。** 这两段不能同时存在，第二段编译不过，因为同一种异常已经被上一支接住了。统一异常这一步两种 throw 都还不对：接住之后应写入 `HttpResponse`，而不是再抛。

### 两段分别做了什么

`throw e`：

```text
抛出的对象就是刚才抓住的那个 InvocationTargetException
类型不变，堆栈不变，没有多包一层
```

`throw new RuntimeException(e)`：

```text
新的对象，类型是 RuntimeException
e 变成它的 cause（getCause() 才能看到原来的 InvocationTargetException）
调用方若只 catch InvocationTargetException，接不住这层包装
```

`InvocationTargetException` 是受检异常。方法现在没有 `throws InvocationTargetException` 时，`throw e` 编译失败，必须在方法签名上声明，或者继续包成 `RuntimeException`。`throw new RuntimeException(e)` 不用声明，所以能编译。这是很多人包一层的原因，不是因为两种写法语义相同。

### 为什么第二段写不上去

catch 按书写顺序匹配，一种异常类型只会进第一支。编译器对第二支的判断是：这个异常已经在上面被抓住了，下面这段永远执行不到。必须删掉其中一段，不能两个都留着。

`IllegalAccessException`、`JsonProcessingException` 是另外的类型，可以各自有自己的 catch。和 `InvocationTargetException` 不冲突。

### 和 Servlet 里现有 catch 的关系

`DispatcherServlet` 现在有：

```java
catch (InvocationTargetException e) { throw new RuntimeException(e); }
catch (JsonProcessingException e) { resp.setStatus(400); return; }
```

| Dispatcher 里怎么抛 | Servlet 能接到什么 |
| --- | --- |
| `throw e`（仍是 InvocationTargetException） | 进 Servlet 的 `catch (InvocationTargetException)` |
| `throw new RuntimeException(e)` | Servlet 那个 `catch (InvocationTargetException)` **接不住**；若里面是 JSON 错误，`catch (JsonProcessingException)` 也接不住，因为最外层已经是 RuntimeException |
| `throw new RuntimeException(jsonException)` | 同样接不住 `JsonProcessingException`，400 分支不会走 |

所以在 Dispatcher 里再包一层，会把你刚写的 400 分支绕开，最后仍是 Tomcat 的 500 页。

### 这一步实际该写的

不要在 catch 里 `throw`。`method.invoke` 把 Controller 的异常放在 `InvocationTargetException.getTargetException()` 里。接住后取出那一层，按类型填响应：

```text
Throwable cause = e.getTargetException();
若 cause 是 IllegalArgumentException 或 JsonProcessingException → status 400
否则 → status 500
写上 contentType 和一句 body
```

`JsonProcessingException` 若是解析请求时直接抛出的（没有包进 InvocationTargetException），用它自己的 catch 填 400，同样不要 `throw new RuntimeException(e)`。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 两种 throw 一样，只是写法不同 | 抛出的对象类型不同，外层 catch 对得上的分支就不同 |
| `throw new RuntimeException(e)` 会丢掉原来的异常 | 不会丢，在 `getCause()` 里；但类型变了 |
| 两个 catch 写同一个类型可以分别做两件事 | 编译失败，第二支不可达 |
| 包成 RuntimeException 就算处理完了 | 只是换了个类型继续抛，客户端仍可能看到容器错误页 |

### 最终建议

删掉重复的那段 `catch (InvocationTargetException)`。不要 `throw e`，也不要 `throw new RuntimeException(e)`。用 `getTargetException()` 看真正的原因，把 400 或 500 写进 `httpResponse` 后正常返回。

## 124. 统一异常按讨论的方式写进 Dispatcher

用户要求按前面的方案把异常处理写出来。

**结论：异常不再向外抛。** `Dispatcher.doService` 接住 `handle` 的全部异常，解开 `InvocationTargetException` 后写入 `HttpResponse`。参数错误和 JSON 解析错误是 400，其它是 500。`DispatcherServlet` 删掉了单独的 `JsonProcessingException` 分支，只把已经填好的 status、contentType、body 写回。

### 写法

`catch` 只有一支，避免同一种异常写两次：

```java
try {
    handlerAdapter.handle(...);
} catch (Exception e) {
    writeError(httpResponse, unwrap(e));
}
```

`unwrap` 只剥 `InvocationTargetException`，因为 `method.invoke` 把 Controller 里的异常包在 `getTargetException()` 里。请求体解析抛出的 `JsonProcessingException`、`IllegalArgumentException` 没有这层包装，剥完仍是它们自己。

`writeError`：

| 解开后 | status | body |
| --- | --- | --- |
| `IllegalArgumentException` | 400 | `getMessage()`，没有则 `bad request` |
| `JsonProcessingException` | 400 | `bad json` |
| 其它，含 `IllegalAccessException` | 500 | `internal error` |

三种都写 `contentType = text/plain;charset=UTF-8`。不把堆栈放进 body。404/405 仍在 try 之前用 `failStatus` 返回，不进这个 catch。

`HttpStatus` 增加 `INTERNAL_ERROR(500)`。

Servlet 不再 `throw new RuntimeException`。status 或 contentType 为 null 时不调用对应的 setter，避免 404 没设 contentType 时传入 null。

### 怎么看

测试进程要重新跑过，停在 `await()` 上，再执行：

```powershell
curl.exe -i -X POST http://localhost:8080/addUser -H "Content-Type: application/json" -d "{bad}"
```

第一行应是 `HTTP/1.1 400`，正文是 `bad json`。`/hello` 仍是 200，未知地址仍是 404。

### 最终建议

异常出口就停在 `Dispatcher` 的这两个私有方法上。ArgumentResolver 继续抛，不要在解析时改 status。

## 125. `unwrap` 是解包装的意思吗？

**结论：是。** `unwrap` 不是 Java 关键字，是按英文意思起的方法名：wrap 是包起来，unwrap 是把包装拆开，取出里面那个真正的异常。

### 词

| 英文 | 这里的意思 |
| --- | --- |
| wrap | 在外面再套一层 |
| unwrap | 拆掉外面那层，拿出里面的对象 |

对应代码：

```java
while (cause instanceof InvocationTargetException) {
    cause = ((InvocationTargetException) cause).getTargetException();
}
```

`method.invoke` 不会把 Controller 里抛出的异常原样抛给你。它套一层 `InvocationTargetException`，真正的异常放在 `getTargetException()` 里。例如 Controller 抛了 `IllegalArgumentException`，`catch` 抓到的最外层是 `InvocationTargetException`。不拆开的话，`writeError` 对不上 `IllegalArgumentException`，就会一律写成 500。

循环是因为外面可能套了不止一层。拆到不再是 `InvocationTargetException` 就停，把里面的异常交给 `writeError`。

`JsonProcessingException` 若是解析请求时直接抛出的，本身没有这层包装，`unwrap` 原样返回它，随后写成 400。

### 最终建议

把 `unwrap` 理解成「拆掉 `InvocationTargetException` 这层皮」。它不处理 HTTP，也不决定 400 还是 500；那是后面 `writeError` 的事。

## 126. 异常出口写完之后，接下来要做什么？

**结论：下一步只做类级别的 `@RequestMapping` 路径前缀。** 异常出口可以停在现在的 `unwrap` + `writeError`。不要同时做 `@PathVariable`，也不要先把启动从测试挪到 `main`。

### 为什么是这一步

现在 `@RequestMapping` 的 `@Target` 只有 `ElementType.METHOD`。每个方法都要写完整路径：

```text
GET  /hello
GET  /getUser
POST /addUser
```

类上还不能写公共前缀。Spring MVC 里常见的是：

```java
@Controller
@RequestMapping("/user")
public class UserController {
    @RequestMapping(value = "/hello", requestMethod = RequestMethod.GET)
    public String hello() { ... }
}
```

注册时拼成 `GET /user/hello`。这是 HandlerMapping 注册阶段的字符串拼接，不改参数解析，也不改异常出口。做完后，`@PathVariable` 才有 `/user/{id}` 这种路径可挂。

### 这一步只做

1. `@RequestMapping` 的 `@Target` 加上 `ElementType.TYPE`，让它能标在类上。
2. `HandlerMappingImpl` 注册方法时：若类上有 `@RequestMapping`，把它的 `value` 和 方法上的 `value` 拼成最终 path。方法上的 `requestMethod` 仍是 HTTP 方法，类上的 method 第一版可以忽略。
3. 拼接规则要固定，避免双斜杠或丢掉斜杠。例如类 `"/user"`、方法 `"/hello"` → `"/user/hello"`；类没有注解时，方法路径保持原样，现有 `/hello`、`/getUser`、`/addUser` 行为不变。
4. 查重仍用拼完后的 `RequestMappingInfo(path, method)`。

先不要改 `UserController` 的现有三个 URL，除非你愿意连 curl 一起改。可以另加一个带类前缀的方法来验收，或者把三个路径改成类前缀加短路径，然后 curl 改打新地址。

### 验收

```text
类上没有 @RequestMapping 时，GET /hello 仍然是 hello world
类上是 /user、方法上是 /hello 时，GET /user/hello 命中，GET /hello 为 404
同 path + 同 method 仍在启动时失败
```

### 再往后

```text
类级路径前缀（本步）
  → @PathVariable，只新增一个 ArgumentResolver，不改 Adapter 里挑选 resolver 的方式
  → 启动代码从 PhraseTest4 挪到 main
  → 再回头加固 IoC
```

### 最终建议

异常处理先停住。下一步只让 `@RequestMapping` 能标在类上，注册时把类路径和方法路径拼起来。现有不带类前缀的接口保持能访问。

## 127. 这些是完善 MVC 的步骤吗？后面的思路是什么？

**结论：紧接着的几步仍是在完善 MVC，补的是「路由怎么写」。** 调度主链路已经有了：Tomcat 进来，Mapping 按 path + method 找到方法，Adapter 填参数并调用，ReturnValueResolver 写响应，Dispatcher 把异常写成 400/500，找不到则 404/405。后面不是再造一套 Dispatcher，而是让 URL 的写法更接近 Spring MVC，然后才离开 MVC，去补启动方式和 IoC。

### 已经稳定的 MVC 链路

```text
curl / 浏览器
  → Tomcat
  → DispatcherServlet（Servlet 请求转成 HttpRequest）
  → Dispatcher
       找不到 path        → 404
       path 在、method 不对 → 405
       找到 Handler
         → ArgumentResolver 填参数
         → invoke
         → ReturnValueResolver 写 body / contentType / 200
         → 抛异常则 unwrap 后写成 400 或 500
  → Servlet 把 HttpResponse 写回
```

这条链路可以停住，不要为了「像 Spring」再拆 Resolver，除非下一步的 PathVariable 需要新的参数来源。

### 还缺的 MVC 能力，按顺序

**1. 类级别路径前缀（下一步，只做这个）**

现在每个方法都要写完整路径。类上的 `@RequestMapping("/user")` 加上方法上的 `"/hello"`，注册时拼成 `/user/hello`。这是 Mapping 注册时的字符串拼接，不改异常，也不改参数绑定。类上没有注解时，现有 `/hello`、`/getUser`、`/addUser` 保持不变。

**2. 路径变量 `@PathVariable`**

前缀稳定之后再做 `/user/{id}`。这时路径不再是整段字符串相等，Mapping 要能匹配模板；`id` 从路径里取出来，交给参数解析，而不是从 query 里取。这是路由匹配和参数来源同时变一点，所以放在类前缀之后，单独做。验收时 Adapter 的挑选循环最好不动，只增加一种参数处理。

**3. 可以不做的语法糖**

`@GetMapping`、`@PostMapping` 只是 `@RequestMapping(method=GET/POST)` 的简写。有类前缀和 PathVariable 之后，MVC 的表达力已经够教学使用。组合注解可以以后再加，不占主线。

做到第 2 步，这个项目里的 MVC 就可以视为「小而完整」：能映射、能绑 query 和 JSON、能区分文本和 JSON 响应、能返回 200/400/404/405/500、能被 curl 访问、能写带前缀和路径变量的 URL。

下面这些属于 Spring MVC 的后半本，本项目不必为了完善而做：拦截器、视图解析、文件上传、内容协商、CORS、`@ExceptionHandler` 按 Controller 定制。默认异常出口已经有了。

### MVC 主线结束之后的思路

顺序不要和路由改良插在一起。

```text
MVC 路由补完（类前缀 → PathVariable）
  → 启动类
  → 加固 IoC
  → 工程化
```

**启动类。** 现在 Tomcat 启动写在 `PhraseTest4` 里，靠 `await()` 把测试挂住。这能用，但它是测试，不是程序入口。挪到 `main`：`refresh`、`dispatcher.init`、注册 Servlet、`start` 和 `await`。行为与测试相同，只是换地方。做完可以用 `java` 或 IDE 直接运行，而不是跑一个不会结束的单元测试。

**加固 IoC。** Web 已经在调用容器里的 Controller 和 Service。这时再修容器，问题会从真实请求里冒出来。优先这些，而不是新功能：

```text
BeanFactory 等接口边界，单例 Map 不要对外乱改
构造器注入、多个候选时的 @Primary / @Qualifier
初始化和销毁顺序
循环依赖里提前暴露的对象和最终代理是不是同一个
```

不要在做 PathVariable 的同时改注入。

**工程化。** 功能能跑之后再整理：demo 业务和框架分开、删掉重复类、日志代替 `System.out`、README 写清怎么启动和怎么 curl。这是给别人看的，不是 MVC 的下一步。

### 一条线看完

```text
现在位置：异常出口已有，URL 仍是方法上的完整路径

仍属 MVC：
  类前缀 → PathVariable

MVC 可以收口之后：
  main 启动 → IoC 正确性 → 模块和文档
```

每次只做其中一格。类前缀的完成标准是：类上 `/user`、方法上 `/hello` 时，`GET /user/hello` 命中，原来的 `/hello` 仍可用。

### 最终建议

是在完善 MVC，而且只剩路由的写法。先做类级别路径前缀，再做路径变量。这两步做完，MVC 主线就可以停。后面的思路不再加注解，而是把启动从测试里拿出来，然后回头把 IoC 做成和这条 Web 链路匹配的容器。

## 128. 怎样从 `user/getUser/12345` 里把 `12345` 解析出来？

出现位置：`PatternTest.test2`。

```java
String s = "user/getUser/12345";
Pattern p = Pattern.compile("user/getUser/.*?");
Matcher m = p.matcher(s);
while (m.find()) {
    System.out.println(m.group());
}
```

**结论：用圆括号做成捕获组，再用 `m.group(1)` 取组里的内容。** `m.group()` 不带参数时永远是整段匹配，不是你想单独拿的那一段。末尾的 `.*?` 又是非贪婪的，后面没有别的条件逼它继续吃字符，所以它可以匹配空串，`12345` 甚至不会进整段匹配。

### 为什么现在拿不到 12345

两层原因叠在一起。

**1. `group()` 是整段，不是其中一段。**

`Matcher.group()` 等于 `group(0)`，表示这次匹配到的全部文本。就算模式把 `12345` 吃进去了，打印出来的也是 `user/getUser/12345`。要单独拿到数字，必须用圆括号标出「这一截要留下来」，这叫捕获组。第 1 对圆括号是 `group(1)`，第 2 对是 `group(2)`。

**2. `.*?` 放在末尾会尽量匹配空。**

`.*` 是贪婪，尽量多吃。`.*?` 是非贪婪，尽量少吃。模式后面已经没有别的字符要求它必须再匹配下去，最少就是 0 个字符。于是 `find()` 成功时，整段往往只是 `user/getUser/`，`12345` 留在后面没被这次匹配用掉。

所以既不是「正则没写到 12345 的位置」，也不是 `find` 不会循环。是整段匹配里没有强制包含这段数字，而且没有一个组专门保存它。

### 怎么写

数字 id 用 `\\d+`（Java 字符串里一个反斜杠要写成两个）。圆括号把它收成第 1 组：

```java
String s = "user/getUser/12345";
Pattern p = Pattern.compile("user/getUser/(\\d+)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 12345
}
```

这里用 `matches()` 而不是 `find()`：`matches()` 要求整个字符串都符合模式。路径就这一条时，这比「在字符串里随便找一段」更合适。`\\d+` 是一位以上的数字，空串不行，所以 `12345` 一定被吃进第 1 组。

若 id 不只有数字，例如 `user/getUser/tom`，把数字改成「除了斜杠以外的一段」：

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

`[^/]+` 表示一个或多个不是 `/` 的字符。`group(1)` 仍是 `tom` 或 `12345`。

### 和模板 `user/getUser/{id}` 的关系

`test()` 里的字符串是模板 `user/getUser/{id}`，`test2` 里是真实路径 `user/getUser/12345`。解析 `12345` 时，正则是拿去套真实路径的，不是拿去套 `{id}` 那段模板。

以后做路径变量时，常见两步：

```text
模板 user/getUser/{id}
  → 编译成正则 user/getUser/([^/]+)
真实请求 user/getUser/12345
  → matcher.matches()
  → group(1) 得到 12345，对应名字 id
```

模板上的 `\\{[^{}]*\\}` 只能找出 `{id}` 这个占位符本身。它不负责从 `12345` 里取值。

### 常见误区

| 写法 | 结果 |
| --- | --- |
| `user/getUser/.*?` 然后 `group()` | 非贪婪末尾可以匹配空；`group()` 又是整段 |
| `user/getUser/(.*)` 然后 `group()` | 数字在组里，但 `group()` 仍打印整段；要用 `group(1)` |
| `user/getUser/(\\d+)` 写成 `\d` | Java 字符串里 `\d` 不是正则的 `\d`，要写 `\\d` |
| 用 `find()` 在整段路径上找 | 能找到，但路径匹配更适合 `matches()`，避免只命中中间一段 |

### 最终建议

真实路径用 `user/getUser/(\\d+)` 或 `user/getUser/([^/]+)`，`matches()` 成功后打印 `m.group(1)`。`group()` 只看整段匹配。模板 `{id}` 和取值用的正则是两套字符串，不要用 `.*?` 去扫 `12345`。

## 129. `user/getUser/([^/]+)` 怎么逐步读，尤其是 `[]`？

出现位置：`PatternTest.test2`。

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

Java 字符串交给正则引擎之后，模式就是：

```text
user/getUser/([^/]+)
```

**结论：从左到右先匹配字面量 `user/getUser/`，再匹配「一段不含斜杠的字符」，并用圆括号把这段收成 `group(1)`。** 方括号 `[]` 表示字符集合：集合里写的是「允许出现的一个字符」。`[^/]` 开头的 `^` 表示把集合反过来，于是是「不是斜杠的一个字符」。后面的 `+` 表示这个字符至少出现一次。

### 按片段拆

对字符串 `user/getUser/12345`：

| 片段 | 种类 | 匹配什么 |
| --- | --- | --- |
| `user/getUser/` | 普通字符 | 必须原样出现。这里的 `/` 不是特殊符号，不用写成 `\\/` |
| `(` `)` | 捕获组 | 不匹配字符，只把括号里匹配到的文本存为第 1 组 |
| `[^/]` | 字符集合，取反 | 恰好一个、并且不是 `/` 的字符 |
| `+` | 量词 | 紧挨着它左边的那一截，重复 1 次或更多 |

所以 `([^/]+)` 一起读成：捕获「一个或多个非斜杠字符」。对 `12345`，五个字符都不是 `/`，整段进入 `group(1)`。

若字符串是 `user/getUser/12345/extra`，`[^/]+` 会在下一个 `/` 前停下，`group(1)` 仍是 `12345`。`find()` 只要求能找到这一段；`matches()` 则要求后面不能再剩 `/extra`。

### `[]` 是什么

方括号划出一个字符集合。引擎每次只从输入里看 **一个字符**，问：这个字符在不在集合里？

```text
[abc]     a 或 b 或 c，三选一，只占一个字符的位置
[0-9]     0 到 9 里的一个。减号在集合内部表示范围
[a-zA-Z]  一个英文字母
```

它不是「把括号里的单词当一个整体」。`[abc]` 不会去匹配连续的 `abc` 三个字符，那是外面不加方括号的 `abc`。

集合里大部分符号失去特殊含义，变成普通字符。例如 `.` 在集合外是「任意一个字符」，在 `[.]` 里只是句点。`*`、`+`、`?` 放进 `[]` 里通常也只是星号、加号、问号这三个字符本身。

### `[^/]` 里的 `^` 和行首的 `^` 不是一回事

`^` 放在 `[]` **内部的第一个位置**，意思是「不在这个集合里」：

```text
[^/]      除了 / 以外的任意一个字符
[^0-9]    除了数字以外的任意一个字符
[^abc]    除了 a、b、c 以外的一个字符
```

`^` 放在整个模式的开头，意思才是「行首 / 字符串开头」：

```text
^user/getUser/([^/]+)
```

这是「必须从开头就是 user/getUser/...」。你现在的模式没有这个行首 `^`。不要把 `[^/]` 读成「以斜杠开头」。

`^` 如果不在集合的第一位，就只是一个普通的 `^` 字符。例如 `[a^b]` 是 a、b 或 `^`。

### `+` 管的是谁

量词只修饰紧挨着它左边的那一个单位。

```text
[^/]+
```

左边的单位是整个 `[^/]`，不是仅仅 `/`，也不是前面的 `user`。所以是「非斜杠字符」重复多次，不是「斜杠重复多次」。

| 量词 | 次数 |
| --- | --- |
| `+` | 1 次或更多。`12345` 可以，空字符串不行 |
| `*` | 0 次或更多。空字符串也能过 |
| `?` | 0 次或 1 次 |
| 不加量词 | 恰好 1 次。`[^/]` 只能吃掉 `1`，吃不完 `2345` |

圆括号在 `+` 的外面：`([^/]+)`。先让 `[^/]+` 尽量匹配完这一段，再把整段放进第 1 组。若写成 `([^/])+`，组里只会留下最后重复的那一个字符，例如 `5`。路径变量要的是整段 `12345`，所以 `+` 要放在方括号外面、圆括号里面。

### 和 `\\d+` 的差别

```text
(\\d+)     只收数字。12345 可以，tom 不行
([^/]+)    只要里面没有斜杠。12345、tom、a_b 都可以
```

`\\d` 是「数字」的简写，方括号写法是 `[0-9]`。你这条路径里 id 可能不是纯数字时，用 `[^/]+`。

### 常见误区

| 读法 | 实际 |
| --- | --- |
| `[]` 表示可选 | 可选是 `?`。`[]` 是字符集合 |
| `[^/]` 表示以 `/` 开头 | 集合内开头的 `^` 表示「除外」 |
| `[^/]+` 匹配斜杠本身 | 匹配的是斜杠以外的字符，斜杠会让这一段停住 |
| `[12345]` 匹配数字串 12345 | 只匹配其中一个字符：1 或 2 或 3 或 4 或 5 |
| `([^/])+` 和 `([^/]+)` 一样 | 前者 `group(1)` 只剩最后一个字符 |

### 最终建议

把 `([^/]+)` 读成三层：`[]` 规定一个字符的允许范围，`^` 把范围改成「不要斜杠」，`+` 让这样的字符连着出现，`()` 把连在一起的整段存进 `group(1)`。前面的 `user/getUser/` 只是必须原样出现的前缀。

## 130. `s.replaceFirst("\\{[^\\]+\\}", "123")` 为什么换不掉 `{id}`？

出现位置：`PatternTest.test3`。字符串是 `user/getUser/{id}`，接着：

```java
s.replaceFirst("\\{[^\\]+\\}", "123");
System.out.println(s);
```

注释写的是把字符串里的 `{id}` 替换掉。

**结论：有两处独立的问题。** `String` 不会被原地修改，`replaceFirst` 的结果必须接回去。另外这串正则在 Java 字符串里的反斜杠不合法或没有按「匹配花括号」来写，对不上 `{id}`。要换成 `123`，应写成 `s = s.replaceFirst("\\\\{[^{}]+\\\\}", "123")`。在 Markdown 里反斜杠会再折叠一层；放进 Java 源文件的字面量是 `"\\{[^{}]+\\}"`。

### 1. 返回值被丢掉了

`String` 是不可变的。`replaceFirst` 不改原来的 `s`，它返回一个新字符串。现在没有赋值，下一行 `println(s)` 打出来的仍是 `user/getUser/{id}`。

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
System.out.println(s); // user/getUser/123
```

### 2. 正则没有按 `{id}` 来写

目标是花括号里的名字：`{id}`。引擎要看到的模式是：

```text
\{[^{}]+\}
```

含义：

| 片段 | 含义 |
| --- | --- |
| `\{` | 一个普通的 `{`。花括号在正则里要转义 |
| `[^{}]+` | 一个或多个「既不是 `{` 也不是 `}`」的字符，所以能吃掉 `id` |
| `\}` | 一个普通的 `}` |

Java 字符串里每个正则反斜杠要再写一个，所以源码是：

```java
"\\{[^{}]+\\}"
```

源码里的 `\\{` 交给正则才是 `\{`。

现在这行源码 `"\\{[^\\]+\\}"` 有两个偏差：

- `[^\\]` 读成的是「不是反斜杠的一个字符」。集合在 `]` 处就结束了，后面的 `+` 才是量词。它不是「不是 `}`」。
- `\\}` 若能通过编译，表示的是正则里的 `\}`，但前面的集合已经提前结束，整段对 `{id}` 的结构和 `\\{[^{}]+\\}` 不一样。

`{` 前面写成 `\{` 而不写成 `\\{` 时，Java 字符串里 `\{` 还不是合法转义（合法的是 `\\`、`\n` 这类），这一行本身就可能编译失败。

### 和上面 `([^/]+)` 的差别

`([^/]+)` 是拿去套真实路径 `user/getUser/12345` 的，斜杠是分隔符。`{id}` 是模板上的占位符，分隔符是花括号，所以集合里要排除的是 `{` 和 `}`，写成 `[^{}]`，不是 `[^/]`。

`test3` 里先用 `user/getUser/([^/]+)` 去配 `user/getUser/{id}`，`{id}` 里没有斜杠，`group(1)` 会得到整段 `{id}`，包括花括号。这和 `replaceFirst` 想做的「把占位符换成 123」不是同一步。

### 最终建议

替换时接住返回值，模式用 `"\\{[^{}]+\\}"`，替换成 `"123"`。打印的才是 `user/getUser/123`。不要用 `[^/]` 或 `[^\\]` 去描述花括号占位符。

## 131. `"\\{[.*]\\}"` 为什么还是换不掉 `{id}`？

出现位置：`PatternTest.test3`，字符串仍是 `user/getUser/{id}`。

```java
s.replaceFirst("\\{[.*]\\}", "123");
System.out.println(s);
```

**结论：方括号里的 `.*` 不是「任意多个字符」。** 引擎看到的模式是 `\{[.*]\}`，意思是 `{`、然后恰好一个 `.` 或 `*`、然后 `}`。`{id}` 中间是字母 `i`，对不上，所以一次都不会替换。返回值仍然没有赋回 `s`，就算匹配上了，`println(s)` 也不会变。

### 这串正则实际在匹配什么

Java 字符串 `"\\{[.*]\\}"` 交给正则引擎之后是：

```text
\{[.*]\}
```

| 片段 | 实际含义 |
| --- | --- |
| `\{` | 一个普通的 `{` |
| `[.*]` | 恰好一个字符，这个字符只能是 `.` 或者 `*` |
| `\}` | 一个普通的 `}` |

`[]` 里面，`.` 不再是「任意字符」，`*` 不再是「重复多次」。它们都变成集合里的普通成员。所以 `[.*]` 等于「一个点，或一个星号」，只占一个字符的位置。

`{id}` 的三个字符是 `{`、`i`、`}`。中间的 `i` 既不是 `.` 也不是 `*`，整段失败。`replaceFirst` 找不到匹配，返回的新字符串和原来一样。

能匹配上的是 `{.}` 或 `{*}`，不是 `{id}`。

### 想表达「花括号里的一段」应该怎么写

量词要放在方括号外面。排除花括号本身：

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
```

引擎看到的是 `\{[^{}]+\}`：

```text
{  +  一个或多个「不是 { 也不是 }」的字符  +  }
```

`id` 符合中间这一段，所以 `{id}` 被换成 `123`，结果是 `user/getUser/123`。

`.*` 若真想当「任意字符、任意多次」，必须离开方括号：

```java
"\\{.*\\}"
```

这对只有一个 `{id}` 的字符串也能换成 `123`。它和 `[^{}]+` 的差别是：`.*` 会吃掉换行以外的任何字符，包括另一个 `}`。字符串里如果有两对花括号，贪婪的 `.*` 会从第一个 `{` 一直吃到最后一个 `}`。路径模板用 `[^{}]+` 更稳，一对花括号就停。

### 赋值仍然要做

`replaceFirst` 不修改原来的 `s`。上面正确的模式也要写成：

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
System.out.println(s);
```

### 常见误区

| 写法 | 实际 |
| --- | --- |
| `[.*]` | 一个 `.` 或一个 `*`，不是任意长度 |
| `.*` 写在 `[]` 里面 | `.` 和 `*` 都失去特殊含义 |
| `\\{.*\\}` 配多对花括号 | 贪婪，可能一次吞掉后面的占位符 |
| 调用了 `replaceFirst` 就地改 `s` | 必须用返回值 |

### 最终建议

把 `[.*]` 读成「一个点或一个星号」。替换 `{id}` 用 `"\\{[^{}]+\\}"`，并且 `s = s.replaceFirst(...)`。

## 132. `"\\{.*\\}"` 已经能匹配 `{id}`，为什么打印还是原字符串？

出现位置：`PatternTest.test3`。

```java
s.replaceFirst("\\{.*\\}", "123");
System.out.println(s);
```

字符串是 `user/getUser/{id}`。

**结论：这版正则对得上 `{id}`。** 打印不变，是因为 `replaceFirst` 的返回值没有赋给 `s`。`String` 不会被原地改掉。

### 这版模式在说什么

`"\\{.*\\}"` 交给引擎是 `\{.*\}`：

| 片段 | 含义 |
| --- | --- |
| `\{` | 一个 `{` |
| `.*` | 任意多个字符（换行除外）。点在方括号外面，星号也在外面，所以恢复了「任意」和「重复」 |
| `\}` | 一个 `}` |

`{id}` 符合：`{` + `id` + `}`。`replaceFirst` 会造出一个新字符串 `user/getUser/123`，然后这个新字符串被丢掉了。下一行打印的仍是变量 `s` 里原来的 `user/getUser/{id}`。

接回去即可：

```java
s = s.replaceFirst("\\{.*\\}", "123");
System.out.println(s); // user/getUser/123
```

### 和 `[^{}]+` 的差别先知道即可

当前这个字符串里只有一对花括号，`.*` 和 `[^{}]+` 结果一样。以后模板里有两对，例如 `/user/{id}/order/{no}`，贪婪的 `.*` 会从第一个 `{` 一直吃到最后一个 `}`，一次替换掉中间整段。一对一对换时用 `"\\{[^{}]+\\}"`。

### 最终建议

这一行的模式不用再改就能换掉单个 `{id}`。加上 `s = ` 再打印。

## 133. `replaceFirst` 的替换结果里为什么没有留下 `\`？

出现位置：`PatternTest.test3`。

```java
String s = "user/getUser/{id}";
String s1 = s.replaceFirst("\\{.*\\}", "\\{.*\\}");
System.out.println(s);
System.out.println(s1);
```

注释希望 `{id}` 被换成 `\{.*\}`。

**结论：第一个参数里的 `\\` 是在写正则；第二个参数里的 `\\` 是替换语法里的转义，不会原样进入结果。** `s1` 里看到的是 `user/getUser/{.*}`，反斜杠被替换器吃掉了。`System.out.println(s)` 打的是原字符串，本来就不会变。

### 两个参数不是同一套规则

| 参数 | 谁来解释 `\` | `"\\{"` 实际表示 |
| --- | --- | --- |
| 第 1 个，要匹配的模式 | 正则 | 模式 `\{`，匹配一个 `{` |
| 第 2 个，替换成什么 | `Matcher` 的替换规则 | 一个 `{`。这里的 `\` 只表示「后面那个字符按字面输出」 |

Java 字符串先处理一层：源码 `"\\{.*\\}"` 在两个参数里，变成内存中的同样 6 个字符 `\{.*\}`。后面分道：

模式侧：`\{` 匹配 `{`，`.*` 匹配 `id`，`\}` 匹配 `}`。所以 `{id}` 能被找到。

替换侧只认两个特殊字符：`\` 和 `$`。`$1` 表示第 1 个捕获组。`\` 表示「下一个字符不要当特殊符号，就输出那个字符」。于是：

```text
\{    →  输出 {
.*    →  输出 .*
\}    →  输出 }
```

`s1` 就是 `user/getUser/{.*}`。反斜杠完成了转义任务，自己不留下。

### 想在结果里看见反斜杠

替换文本里要出现一个 `\`，替换串里得写两个 `\\`（表示「输出一个反斜杠」）。Java 源码再把每个 `\` 写成 `\\`，所以一个想留下的反斜杠在源码里是四个 `\`。

目标结果 `user/getUser/\{.*\}`：

```java
String s1 = s.replaceFirst("\\{.*\\}", "\\\\{.*\\\\}");
```

源码 `"\\\\{.*\\\\}"` 经过 Java 字符串后，替换器看到的是 `\\{.*\\}`。替换器再把每一对 `\\` 打成一个 `\`，得到 `\{.*\}`。

也可以避免手写这么多层，让 API 按字面替换：

```java
String s1 = s.replaceFirst("\\{.*\\}", Matcher.quoteReplacement("\\{.*\\}"));
```

`quoteReplacement` 会把替换串里的 `\` 和 `$` 都变成字面量。这里传入的 Java 字符串 `"\\{.*\\}"` 内容已经是 `\{.*\}`，引用之后结果里就会保留这些反斜杠。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 两个参数都写 `"\\{"`，结果里就有 `\` | 模式用 `\` 表示转义；替换串也用 `\` 表示转义，转义完只留下后面的字符 |
| `println(s)` 能看到替换结果 | `s` 没被赋值，要看 `s1` |
| 替换串里的 `.*` 还会按正则再匹配一次 | 不会。替换串不是正则，`.` 和 `*` 就是这两个字符 |

### 最终建议

匹配 `{id}` 继续用第一个参数 `"\\{.*\\}"`。若结果里要保留反斜杠，第二个参数写成 `"\\\\{.*\\\\}"`，或用 `Matcher.quoteReplacement`。看结果打印 `s1`。

## 134. 怎样从 `user/getUser/123` 里提取 `123`？当前模式为什么不行？

出现位置：`PatternTest.test4`。

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/\\{.*\\}");
Matcher m = p.matcher(s);
while (m.find()) {
    destinationString = m.group(1);
}
```

**结论：这个模式在找花括号，字符串里没有 `{` `}`，`find()` 一次都不会成功。** 要提取 `123`，模式末尾改成捕获组 `(\\d+)` 或 `([^/]+)`，再用 `group(1)`。`\\{.*\\}` 是拿去匹配模板 `user/getUser/{id}` 的，不是拿去匹配真实路径的。

### 现在这行在找什么

`"user/getUser/\\{.*\\}"` 交给引擎是：

```text
user/getUser/\{.*\}
```

`\{` 和 `\}` 是普通花括号。整段要求字面量 `user/getUser/` 后面跟着 `{`、若干字符、`}`。`user/getUser/123` 在斜杠后面是数字，没有花括号，匹配失败。`while` 不进入，`group(1)` 不会执行。

即便把字符串改成 `user/getUser/{id}` 让它匹配上，这个模式里也没有圆括号。`group(1)` 会抛 `IndexOutOfBoundsException`，因为第 1 组不存在。`group()` 或 `group(0)` 才是整段匹配。

### 提取 123 的写法

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/(\\d+)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 123
}
```

`(\\d+)` 是第 1 个捕获组，`group(1)` 才是 `123`。`\\d+` 只收数字。若这一段不一定是数字：

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

`group(1)` 仍是 `123`。

### 两套字符串不要混用

| 字符串 | 用什么模式 | 得到什么 |
| --- | --- | --- |
| 模板 `user/getUser/{id}` | `\\{.*\\}` 或 `\\{[^{}]+\\}` | 找到占位符 `{id}` |
| 真实路径 `user/getUser/123` | `user/getUser/(\\d+)` | `group(1)` 为 `123` |

模板负责说明「这里有一个参数」，真实路径负责提供 `123`。用找花括号的模式去扫 `123`，对不上。

### 最终建议

`test4` 的模式改成 `user/getUser/(\\d+)`，`matches()` 成功后打印 `m.group(1)`。`\\{.*\\}` 留在处理 `{id}` 模板的那一步。

## 135. `user/getUser/.*` 配上 `group(1)` 为什么拿不到 `123`？

出现位置：`PatternTest.test4`。

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/.*");
Matcher m = p.matcher(s);
while (m.find()) {
    destinationString = m.group(1);
}
```

**结论：`.*` 已经能匹配 `123`，但它属于整段匹配 `group(0)`，不是第 1 组。** 模式里没有圆括号，`group(1)` 会抛 `IndexOutOfBoundsException`。要单独取出 `123`，把 `.*` 放进括号：`user/getUser/(.*)`，然后用 `group(1)`。

### 这次和花括号那版的差别

`user/getUser/\\{.*\\}` 要求斜杠后面是 `{...}`，对 `123` 匹配失败，循环进不去。

`user/getUser/.*` 里的 `.*` 是「任意字符，零次或多次」，`123` 符合。`find()` 能成功，整段是 `user/getUser/123`。成功之后去调 `group(1)` 才出错：组号从 1 开始，对应第几对圆括号。没有括号就没有第 1 组。`group()` 或 `group(0)` 才是整段，里面夹着前缀，不是单独的 `123`。

### 要提取就加括号

```java
Pattern p = Pattern.compile("user/getUser/(.*)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 123
}
```

括号不匹配额外字符，只把 `.*` 吃到的 `123` 存起来。

`.*` 会吃掉斜杠。路径若是 `user/getUser/123/extra`，`group(1)` 会是 `123/extra`。只要最后一段时，用 `([^/]+)` 或只要数字时用 `(\\d+)`：

```java
Pattern.compile("user/getUser/([^/]+)")
```

### 最终建议

`.*` 外面加上圆括号再 `group(1)`。没有括号时不要调用 `group(1)`。只取一个路径段时，把 `.*` 换成 `[^/]+`。

## 136. 怎样匹配字符串里的 `{}`，并且花括号里必须是字母？

出现位置：`PatternTest.test5`。现在的模式是：

```java
Pattern.compile("user/getUser/\\{[^{}]*\\}")
```

字符串是 `user/getUser/{id}`。

**结论：把 `[^{}]*` 换成 `[a-zA-Z]+`。** `[^{}]*` 的意思是「不是花括号的任意字符，可以一个都没有」，所以 `{id}`、`{123}`、`{}` 都能过。字母用 `[a-zA-Z]`，至少要有一个字母就用 `+`，不要用 `*`。

### 现在这版实际允许什么

`\\{[^{}]*\\}` 交给引擎是 `\{[^{}]*\}`：

| 片段 | 含义 |
| --- | --- |
| `\{` `\}` | 一对普通花括号 |
| `[^{}]` | 一个既不是 `{` 也不是 `}` 的字符 |
| `*` | 这种字符可以出现 0 次或更多 |

因此 `{id}`、`{123}`、`{a_b}`、空的 `{}` 都匹配。它只保证括号里面不再嵌一套花括号，不保证是字母。

### 只要英文字母

```java
Pattern p = Pattern.compile("\\{[a-zA-Z]+\\}");
Matcher m = p.matcher(s);
if (m.find()) {
    System.out.println(m.group()); // {id}
}
```

`[a-zA-Z]` 是一个大小写英文字母。`+` 是至少 1 次，所以 `{}` 失败，`{id}` 成功，`{id1}` 失败（里面有数字），`{a_b}` 失败（里面有下划线）。

还要前缀时：

```java
Pattern.compile("user/getUser/\\{[a-zA-Z]+\\}")
```

只要括号里面的名字，再加一层圆括号：

```java
Pattern p = Pattern.compile("\\{([a-zA-Z]+)\\}");
if (m.find()) {
    System.out.println(m.group(1)); // id
}
```

`find()` 表示字符串里出现即可，不必整段都是花括号。`matches()` 则要求整个 `s` 都符合模式；`user/getUser/{id}` 整段匹配时，模式里必须带上前面的 `user/getUser/`。

### 和相近写法的差别

| 写法 | `{id}` | `{}` | `{123}` | `{id1}` |
| --- | --- | --- | --- | --- |
| `\\{[^{}]*\\}` | 能 | 能 | 能 | 能 |
| `\\{[a-zA-Z]*\\}` | 能 | 能（`*` 允许空） | 不能 | 不能 |
| `\\{[a-zA-Z]+\\}` | 能 | 不能 | 不能 | 不能 |

「必须是字母」用最后一行。

若字母包括中文这类 Unicode 字母，把 `[a-zA-Z]` 换成 `\\p{L}`：`\\{\\p{L}+\\}`。`{id}` 仍然匹配。路径变量名一般是英文，用 `[a-zA-Z]+` 即可。

### 最终建议

判断有没有「花括号里全是英文字母」，用 `"\\{[a-zA-Z]+\\}"` 再 `find()`。要拿出里面的 `id`，写成 `"\\{([a-zA-Z]+)\\}"`，读 `group(1)`。不要继续用 `[^{}]*`，那不是字母限制。

## 137. `while (m.find())` 为什么要加 while？

出现位置：`PatternTest.test5`。

```java
Pattern p = Pattern.compile(".*\\{[a-zA-Z]*\\}.*");
Matcher m = p.matcher(s);
while (m.find()) {
    System.out.println(m.group());
}
```

字符串是 `user/getUser/{id}`。

**结论：`while` 不是 `find()` 的语法要求。** `find()` 每次只找下一处匹配，找到返回 true，找不到返回 false。`while` 表示「有多少处就处理多少处」。只判断有没有一对花括号时，写成 `if (m.find())` 就够。你现在的模式前后都有 `.*`，整段字符串最多成功一次，循环体也只会进一次。

### `find()` 做一次什么

`Matcher` 内部记着上次找到的位置。第一次 `find()` 从开头找。找到就把这次匹配的范围记下来，`group()` 能读到这段文本，并返回 true。再调用 `find()` 时，从上一次匹配结束的后面继续找，不再从头找。后面没有了就返回 false，循环结束。

所以：

```text
if (m.find())     只关心有没有至少一处
while (m.find())  把每一处都走一遍
```

没有 `while` 也可以写 `if`。不调用 `find()`，`group()` 没有当前匹配，不能拿结果。

### 你这段循环实际只会进一次

模式是 `.*\\{[a-zA-Z]*\\}.*`。开头和结尾的 `.*` 会把 `{id}` 前后的字符都吃掉，一次匹配就是整个 `user/getUser/{id}`。匹配结束的位置已经是字符串末尾，下一次 `find()` 为 false。`while` 和 `if` 在这个模式上效果一样：打印一次整段字符串。

若模式收成只匹配花括号本身：

```java
Pattern p = Pattern.compile("\\{[a-zA-Z]+\\}");
```

字符串里有两处时，`while` 才看得出差别：

```text
/user/{id}/order/{name}
第 1 次 find：{id}
第 2 次 find：{name}
第 3 次 find：false，结束
```

用 `if` 就只会看到 `{id}`。

### 最终建议

只判断「有没有」时写成 `if (m.find())`。要把每一对 `{名字}` 都打出来时再用 `while`，并且模式不要用前后的 `.*` 把整段一次吃完，否则循环没有第二次机会。

## 138. 从 Map 里取值时，为什么进不了 `RequestMappingInfo.equals`？

出现位置：`RequestMappingInfo.equals`，调用点是 `HandlerMappingImpl` 里的 `requestMappingInfoMap.get(requestMappingInfo)`。`hashCode` 仍是 `Objects.hash(path, method)`。`equals` 里又用 `regexPath` 对另一个对象的 `path` 做正则。

**结论：`HashMap.get` 先用 `hashCode` 选桶，桶里对不上才不会调用 `equals`。** 请求路径是 `user/getUser/123`，表里的 key 是模板 `user/getUser/{id}` 时，两边的 `path` 不同，`hashCode` 就不同，查找停在选桶，断点打在 `equals` 上不会进来。另外，若拿去 `get` 的就是当初 `put` 进去的同一个对象，`==` 已经成立，`HashMap` 也不会再调 `equals`。

### `get` 实际做了什么

`HashMap` 不是遍历所有 key 调 `equals`。简化后的查找是：

```text
1. h = key.hashCode()，映射到某个桶
2. 看这个桶里已有的 key：
     先比 hash 是否相等
     再看是不是同一个引用（==）
     都不是，才调用 key.equals(...)
3. 桶是空的，或者这条链上没有 hash 相同的 key：直接返回 null
```

所以「进不了 equals」通常是第 1 步就走散了，不是 `equals` 写错了没被调试器看见。

你现在的 `hashCode` 只含 `path` 和 `method`，不含 `regexPath`：

```java
return Objects.hash(path, method);
```

注册时放进 Map 的 `path` 是模板，例如 `user/getUser/{id}`。请求进来时新建的 `RequestMappingInfo.path` 是 `user/getUser/123`。两个字符串不相等，`hashCode` 几乎一定不同，它们不在同一个桶里。`equals` 里的正则根本没有机会跑。

可以在 `hashCode` 里打断点，看两次调用的 `path` 是不是一个模板、一个真实路径。

### 同一个对象取值也不会进 equals

`HashMap` 的比较大致是：

```text
已有key == 传入key    或者    已有key.equals(传入key)
```

`==` 为 true 时，短路，不再调用 `equals`。用 `put` 时的那个实例再 `get`，调试器停在 `equals` 上也进不去。这不表示相等判断失败。要观察 `equals`，必须 `new` 另一个 `RequestMappingInfo`，并且它的 `hashCode` 得和表里的 key 相同。

### 正则不能写进 HashMap 的 equals

就算强行让 `equals` 被调用，这套写法也违反 `hashCode` / `equals` 的约定：

```text
若 a.equals(b) 为 true，则 a.hashCode() 必须等于 b.hashCode()
```

模板对象和 `user/getUser/123` 若靠正则算成相等，它们的 `hashCode` 仍然按不同的 `path` 计算，结果不相等。`HashMap` 允许这种 key，但 `get` 找不到。`HashMap` 适合「path + method 完全相同」这种精确 key。`/user/{id}` 对 `/user/123` 这种一对多的匹配，要自己遍历 `keySet()`，对每个模板做 `matcher.matches()`，不要指望 `map.get`。

`getHandlerMethodForPath` 里已经有一层 `for` 循环，但循环内部又 `requestMappingInfoMap.get(loop)`。那里的 `get` 用的是表里原有的 key 自己去查自己，`==` 成立，同样不会为了正则去跑你新写的 `equals`。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 重写了 `equals`，`get` 就一定会进来 | 先过 `hashCode` 选桶 |
| 断点不进就是 `equals` 返回了 false | 没被调用和返回 false 不是一回事 |
| 把正则放进 `equals` 就能匹配路径变量 | `hashCode` 仍按模板字符串算，桶对不上 |
| `hashCode` 也改成算正则就能修好 | 正则匹配不是稳定的哈希。查找时应遍历模板 |

### 最终建议

精确路径继续用现在的 `hashCode` 和 `map.get`。带 `{id}` 的模板不要放进 `equals` 里用正则比较。`get` 返回 null 时，再遍历 `requestMappingInfoMap.keySet()`，用每个 key 的 `regexPath` 去匹配请求的 `path`。调试「为什么没进 equals」时，先看两次 `hashCode` 的 `path` 是否相同。

## 139. 路径变量也写好了，怎么样？接下来呢？

**结论：一个路径变量的主路径已经接上，类前缀也一起做了。** `GET /user/getUserByPath/123` 这种请求可以命中 `getUserWithPath`，并把 `123` 转成 `Long`。精确路径仍走 `map.get`，模板不走 `equals`。可以停在这一版。下一步把 Tomcat 启动从 `PhraseTest4` 挪到 `main`，不要再加第二种路径变量。

wholeUrl.replaceFirst("\\{.*\\}", "(.*)")

`ArgumentResolver` 里还有 `System.out.println(destinationString)`，验证完可以去掉。

一个 `{id}` 加类前缀可以算写好了。精确匹配和模板匹配分开，这个方向是对的。下一步只把内嵌 Tomcat 的启动挪到 `main`。

## 140. 启动类接下来怎么写？

**结论：把 `PhraseTest4.testWithCurl` 里的启动顺序原样挪到 `src/main/java` 的一个 `main` 方法里。** 不要改 Mapping、Resolver 和异常。测试方法可以留着，但不要再靠它挂住进程。

### 写在哪

放在 `minispring-web` 的 **main** 源码，不要放在 `src/test/java`。测试里的 `main` 也能点运行，但那仍然是测试 classpath 上的类。建议：

```text
minispring-web/src/main/java/com/minispring2/web/MiniSpringApplication.java
```

类上只有 `public static void main(String[] args)`。IDEA 里对这个方法点运行。

### 方法里按这个顺序写

和现在的测试相同，一行都不要改语义：

```java
public class MiniSpringApplication {
    public static void main(String[] args) throws Exception {
        MiniApplicationContext miniApplicationContext = new MiniApplicationContext();
        miniApplicationContext.basicPackages = new String[]{
                "com.minispring2.demo", "com.minispring2.core", "com.minispring2.web"
        };
        miniApplicationContext.refresh();

        Dispatcher dispatcher = new Dispatcher();
        dispatcher.init(miniApplicationContext.defaultBeanFactory);

        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();

        Context context = tomcat.addContext("", new File(".").getAbsolutePath());
        DispatcherServlet dispatcherServlet = new DispatcherServlet(dispatcher);
        Tomcat.addServlet(context, "dispatcherServlet", dispatcherServlet);
        context.addServletMappingDecoded("/*", "dispatcherServlet");

        tomcat.start();
        tomcat.getServer().await();
    }
}
```

四段各自的作用：

| 顺序 | 代码 | 作用 |
| --- | --- | --- |
| 1 | `refresh()` | 扫包、创建 Bean。`Dispatcher` 要用这里的 `defaultBeanFactory` |
| 2 | `dispatcher.init(...)` | 注册 Controller 映射。必须在把 Servlet 交给 Tomcat 之前做完 |
| 3 | `new DispatcherServlet(dispatcher)` 再 `Tomcat.addServlet` | 把已经 init 好的 Dispatcher 传进 Servlet。不要在 `service()` 里再 `new Dispatcher` |
| 4 | `getConnector()`、`start()`、`await()` | 创建 8080 连接器、启动、阻塞主线程。没有 `await()`，`main` 结束进程就退出 |

`throws Exception` 交给 `main` 即可，不用在 `main` 里把异常翻译成 400。那是请求进来之后 `Dispatcher` 的事。

### 跑起来之后怎么验

先停掉还挂在 `PhraseTest4` 上的旧进程，否则 8080 会被占用。然后运行 `main`，另开终端：

```powershell
curl.exe -i http://localhost:8080/user/hello
curl.exe -i "http://localhost:8080/user/getUser?userId=12345"
curl.exe -i http://localhost:8080/user/getUserByPath/123
curl.exe -i -X POST http://localhost:8080/user/addUser -H "Content-Type: application/json" -d "{\"name\":\"Jerry\",\"age\":19}"
```

## 142. 构造器注入和构造器有什么关系？现在只有字段上的 `@Autowired`

**结论：构造器是 Java 创建对象时调用的那个方法；构造器注入是容器把依赖当成这个方法的参数传进去。** 关系就是「在哪一次调用里把依赖交出去」。你现在的字段注入发生在对象已经 `new` 出来之后，用反射给字段赋值，没有经过构造器的参数。

### 构造器是什么

构造器是类里和类同名、没有返回类型的方法。`new UserController()` 或 `getDeclaredConstructor().newInstance()` 执行的就是它。对象在这一步诞生。没有手写时，编译器会补一个无参构造器。

你现在的创建就是无参那一个：

```java
return aClass.getDeclaredConstructor().newInstance();
```

`getDeclaredConstructor()` 不带参数，表示要「没有参数的构造器」。`newInstance()` 也不带参数，所以创建出来的 `UserController` 里，`userService` 还是 null。

### 字段注入发生在诞生之后

`createBean` 的顺序是：

```text
instantiate()              无参构造，对象已存在，依赖仍是 null
populate()                 按 BeanDefinition 填属性
injectAutowiredFields()    看字段上的 @Autowired，再 getBean 并 field.set
```

`UserController` 上的写法是：

```java
@Autowired
UserService userService;
```

容器先空对象，再 `field.set(bean, userService实例)`。构造器从头到尾没有出现 `UserService` 这个参数。所以「只有字段上的 `@Autowired`」和构造器无关：依赖不是创建时传的，是创建后塞进字段的。

### 构造器注入是把依赖挪到参数上

同样是「容器负责找出 UserService 并交给 UserController」，换一个交法：

```java
public UserController(UserService userService) {
    this.userService = userService;
}
```

容器要做的就不是 `getDeclaredConstructor().newInstance()`，而是：

```text
找到参数是 UserService 的那个构造器
先 getBean(UserService)
再 constructor.newInstance(那个 UserService)
```

对象一诞生，`userService` 字段就已经有值。后面不必再 `field.set`。`@Autowired` 若写在构造器上，只是标记「用这个构造器，参数由容器填」。参数只有一个时，很多实现连这个注解都可以省略，因为没得选。

所以：

| | 构造器 | 构造器注入 |
| --- | --- | --- |
| 是什么 | 创建对象的方法 | 用这个方法的参数传递依赖 |
| 谁提供 | Java 语言 | 容器在调用构造器之前把参数准备好 |
| 你现在的代码 | 无参 `newInstance()` | 还没有。依赖在 `injectAutowiredFields` 里 `field.set` |

### 和字段注入比，差在时刻

```text
字段注入：  new 空对象 → 之后改字段
构造器注入：先拿到依赖 → new 的时候作为参数传入
```

字段方式下，对象可以在依赖还是 null 时就已经存在。构造器方式下，没有 `UserService` 就构造不出来。这就是它和「构造器」的关系：依赖成了构造参数，创建和赋值是同一次调用。

### 现在先不用改

上一问的顺序里，构造器注入排在「把 `BeanDefinition` 挪出 demo 包」之后。挪包不改变 `newInstance()` 这行。等包挪完，再把 `instantiate` 从「总是无参构造」改成「看有参构造，先解析参数再 `newInstance(依赖)`」。

### 最终建议

构造器是创建对象的那一下。构造器注入是容器在那一下把依赖当参数传进去。你现在的 `@Autowired` 字段是创建完成之后再赋值，所以和构造器的参数列表无关。

## 143. 类里有多个构造方法时，`getDeclaredConstructor().newInstance()` 会怎样？

出现位置：`DefaultBeanFactory.instantiate`。

```java
return aClass.getDeclaredConstructor().newInstance();
```

**结论：这句不会在多个构造器里挑一个，它只找「参数个数为 0」的那一个。** 无参构造还在，就只用它，其它有参构造不会被调用。类里只写了有参构造、无参构造因此消失时，抛 `NoSuchMethodException`，被你下面的 `catch` 包成 `RuntimeException`。

### 这句在找什么

`getDeclaredConstructor()` 括号里没有 `Class`，等价于「参数类型列表是空的」：

```java
aClass.getDeclaredConstructor(new Class<?>[0])
```

返回的是那一个 `Constructor` 对象，不是「所有构造器里的某一个」。后面的 `newInstance()` 同样不带参数，所以调用的就是这个无参构造。

类里可以同时有：

```java
public UserController() { }

public UserController(UserService userService) {
    this.userService = userService;
}
```

执行到这句时，只会进入第一个。`UserService` 那个构造器对这行代码是看不见的。字段上的 `@Autowired` 仍然在对象创建之后，由 `injectAutowiredFields` 赋值。

### 没有无参构造时

手写了任意构造器之后，编译器不再自动补无参构造。若只剩：

```java
public UserController(UserService userService) { ... }
```

`getDeclaredConstructor()` 找不到 0 个参数的构造器，抛出的是 `NoSuchMethodException`，不是「自动改用剩下的那个」。你的 `catch` 里已经写了这个异常，所以创建 Bean 失败，异常信息里能看到它。

### 和另外两个 API 的差别

| 方法 | 多个构造器时 |
| --- | --- |
| `getDeclaredConstructor()` | 只要无参的那一个。没有就抛 `NoSuchMethodException` |
| `getDeclaredConstructors()` | 返回全部，包括 private。要自己挑 |
| `getConstructor()` | 只要 **public** 的无参构造。无参但是 private 时，它找不到；`getDeclaredConstructor` 找得到，但接着 `newInstance()` 可能因没有 `setAccessible(true)` 抛 `IllegalAccessException` |

这句没有把构造器设成可访问。无参构造是 public（你现在的 Controller 就是这样）时没有问题。无参构造是 private 时，能找到构造器，`newInstance()` 会因访问失败进入同一个 `catch`。

### 以后要做构造器注入时

不能再写死 `getDeclaredConstructor()`。要先 `getDeclaredConstructors()` 拿到列表，按参数类型选出那一个（例如唯一的有参构造，或标了 `@Autowired` 的），先 `getBean` 出每个参数，再 `constructor.newInstance(参数...)`。多个有参构造、又没有标记该用哪一个时，应启动失败，而不是随便挑第一个。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 有多个构造器时，这句会选参数最多的 | 不会。只认 0 个参数 |
| 没有无参构造时，会自动用剩下的有参构造 | 不会。抛 `NoSuchMethodException` |
| `getDeclaredConstructor` 和 `getDeclaredConstructors` 一样 | 前者要指定参数类型，空就是无参；后者才是数组 |
| 找到 private 无参构造就能 `newInstance` | 还要 `setAccessible(true)`，否则是 `IllegalAccessException` |

### 最终建议

把这句理解成「永远调用无参构造」。多个构造器不影响它，只要无参那个还在。只有有参构造时，这句会失败。构造器注入要另写选择逻辑，不能靠这句自动完成。

## 144. 弄清多个构造器之后，然后呢？

`BeanDefinition` 和 `RuntimeBeanReference` 的 import 已经改到 `com.minispring2.core.model`。`DefaultBeanFactory`、`Scan` 和 Phase 测试都不再引用 `demo.model` 里的那两份。挪包这一步可以算完成。`demo.model` 里还留着同名旧文件，已经没有引用，删掉即可，不删也不影响运行。

### 最终建议

## 145. 为什么 `parameterTypes` 必须是数组，`inputObjects` 用 ArrayList 却能传进去？

出现位置：`DefaultBeanFactory.instantiate`。

```java
Class[] parameterTypes = constructor.getParameterTypes();
List<Object> inputObjects = new ArrayList();
for (Class clazz : parameterTypes) {
    inputObjects.add(getBeanForType(clazz));
}
return aClass.getDeclaredConstructor(parameterTypes).newInstance(inputObjects);
```

**结论：两边要的都是数组，不是「一个必须用数组、一个允许用 List」。** `getDeclaredConstructor` 的参数类型是 `Class...`，ArrayList 对不上，所以类型列表只能用 `Class[]`。`newInstance` 的参数类型是 `Object...`，ArrayList 本身是一个 `Object`，编译能通过，但传进去的是这一整个 List，不是里面的每个依赖。运行时对不上 `UserService` 这种参数。

### 两个方法的签名

```java
Constructor getDeclaredConstructor(Class<?>... parameterTypes)
Object newInstance(Object... initargs)
```

`...` 是可变参数，调用时底层就是数组：`Class<?>[]` 和 `Object[]`。没有 `List` 重载。

`constructor.getParameterTypes()` 的返回值也是 `Class[]`。所以 `parameterTypes` 用数组，是因为 JDK 就给你数组，而且下一行正好要这个数组。

### 为什么 List 填不进 getDeclaredConstructor

`getDeclaredConstructor` 要的每个元素都是 `Class`（参数的类型，例如 `UserService.class`）。`ArrayList<Object>` 不是 `Class`，也不是 `Class[]`。写成下面这样不能编译：

```java
List<Class> parameterTypes = new ArrayList<>();
aClass.getDeclaredConstructor(parameterTypes);
```

数组可以：`Class[]` 直接对上 `Class...`。

### 为什么 ArrayList 能写进 newInstance，但意思错了

`newInstance(Object... initargs)` 要的是「构造器的各个参数值」。可变参数的规则是：

```text
传入的如果已经是对应的数组，这个数组就是参数列表
传入的如果是别的一个对象，这个对象只算列表里的一个元素
```

`ArrayList` 不是 `Object[]`，它只是一个普通对象。所以这句：

```java
newInstance(inputObjects)
```

等价于构造器只收到 **一个参数**，这个参数的运行时类型是 `ArrayList`，里面的 `UserService` 并没有被拆出来。

若构造器是：

```java
public UserController(UserService userService)
```

实际传进去的是一个 List，不是 `UserService`。会抛 `IllegalArgumentException`（参数个数或类型不符）。这个异常不在你现在的 `catch` 里，会直接冒出去。

能编译，是因为 List 可以当成一个 `Object`。不是因为 `newInstance` 会遍历 List。

### 要让里面的依赖真正成为参数

把 List 转成数组再传：

```java
newInstance(inputObjects.toArray())
```

`toArray()` 得到 `Object[]`。对 `Object...` 来说，这个数组就是参数列表：第一个元素给构造器的第一个参数，第二个给第二个。一个 `UserService` 时，构造器收到的就是那个实例，而不是装着它的 List。

`parameterTypes` 不要改成 List。`getDeclaredConstructor` 要的是类型数组，`getParameterTypes()` 已经是 `Class[]`。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| `newInstance` 接受集合，所以 ArrayList 会被展开 | 不会展开。整个 List 是一个参数 |
| 能编译就说明参数传对了 | 这里能编译是因为 List 是 Object |
| `getDeclaredConstructor` 也可以改成收 List | 没有这个重载，元素类型必须是 `Class` |
| `toArray()` 之后还是一个参数 | 对可变参数，`Object[]` 会被当成参数列表本身 |

### 最终建议

类型列表继续用 `Class[]`，就是 `getParameterTypes()` 的返回值。依赖值可以先放在 `ArrayList` 里收集，调用时写成 `newInstance(inputObjects.toArray())`。不要把 List 直接交给 `newInstance`。

## 146. 构造器注入写好了，怎么样？接下来呢？

**结论：主路径写对了。** 标了 `@Autowired` 的构造器会先按参数类型 `getBean`，再用 `toArray()` 传给 `newInstance`。没有这种构造器时，仍然走无参构造。字段注入还留着，两种可以并存。下一步做 `@Primary`，不要接着改构造器选择。

### 现在的行为

`instantiate` 遍历 `getDeclaredConstructors()`：

```text
找到带 @Autowired 的构造器
  已经找到过另一个 → 抛「多个构造方法，未指定哪一个」
  否则记下它的 getParameterTypes()
一个都没有 → getDeclaredConstructor().newInstance()
有一个 → 每个参数类型 getBeanForType，newInstance(inputObjects.toArray())
```

`UserController` 同时有无参构造、`@Autowired` 的 `UserController(UserService)`，以及字段上的 `@Autowired UserService`。创建时会走有参构造，`userService` 在 `new` 的时候就有值。之后 `injectAutowiredFields` 还会按字段再赋一次同一个单例。功能上没问题，只是同一依赖走了两遍。

`singletonBeanMap` 已经是 `private`。加上这次的构造器参数，问题 144 里的两件都落地了。

### 先知道的边界

| 情况 | 现状 |
| --- | --- |
| 一个 `@Autowired` 构造器，参数类型只有一个 Bean | 能创建 |
| 没有 `@Autowired` 构造器 | 无参 `newInstance()`，和以前一样 |
| 两个构造器都标了 `@Autowired` | 启动失败。报错文案说的是「多个构造方法」，实际统计的是多个带注解的构造器 |
| 有参构造但没标 `@Autowired`，同时还有无参构造 | 仍走无参，有参那个不会被用 |
| 构造器参数的类型有两个 Bean | `getBeanForType` 已经会抛「该类型匹配多个 Bean」 |
| 构造器要的对象反过来又要当前对象 | 对象还没 `new` 完，不能像字段注入那样先交出一个半成品。这种循环会在 `getBean` 里堆起来 |

字段上的 `@Autowired` 先留着。验证 `/user/hello` 仍然能拿到 `UserService` 即可。

### 接下来

下一件只做 `@Primary`。现在多个同类型 Bean 直接失败，没有「默认用哪一个」的说法。

```text
某个类型找到多个 Bean
  其中恰好一个标了 @Primary → 用它
  没有或不止一个 @Primary → 仍然失败
```

只改 `getBeanForType` / `getBeanNamesForType` 这一条选择，不要改 `instantiate`。构造器注入和字段注入都会走 `getBeanForType`，所以一处改完，两边都生效。

### 最终建议

构造器注入的主路径可以停。`toArray()` 用对了。下一步只在按类型查找时支持 `@Primary`，多个候选里恰好一个首选就用它。

## 147. `@Primary` 写好了，然后呢？

**结论：按类型挑选的主路径写对了。** 多个同类型 Bean 时，恰好一个类上有 `@Primary` 就用它；一个都没有，或不止一个，都失败。只有一个候选时不看这个注解。下一步先不要写初始化、销毁，也不要加 `@Qualifier`。下一件只处理：循环依赖里提前交出去的对象，和最后放进一级缓存的对象，是不是同一个。

### 现在的选择

`getBeanForType` 仍然先 `getBeanNameForType`，再按名字 `getBean`。名字的规则在 `getBeanNameForType`：

```text
按 isAssignableFrom 收集候选
0 个 → 「未找到该类型的Bean」
1 个 → 直接用它，不看 @Primary
多于 1 个 → 只留下类上有 @Primary 的
    0 个 → 「存在多个Bean，未用Primary指定哪一个」
    多于 1 个 → 「存在多个相同类型的Bean使用了Primary注解」
    恰好 1 个 → 用这一个
```

`@Primary` 标在类型上，`@Target(ElementType.TYPE)`，运行时保留。`UserService` 有这个注解，`EmployeeService` 没有。两者都实现 `UserInterface`，也都是 `@Component`。

`getBeanNamesForType` 没有过滤 `@Primary`，仍然返回该类型的全部名字。这是对的。`preInstantiateSingletons` 要创建每一个 `BeanPostProcessor`，不是只要首选的那一个。`@Primary` 只影响「给我这一个 Bean」。

### 哪一次查找真的用到了它

`UserController` 的构造器参数类型是 `UserService`。这个具体类只有一个 Bean，走的是「1 个候选」那条，不会读 `@Primary`。

字段类型是 `UserInterface`。`UserService` 和 `EmployeeService` 都能赋给它，所以字段注入才会进入「多于 1 个」的分支，并选中 `UserService`。创建顺序是先构造器、再字段注入，字段注入会把构造器刚赋上的值再写一次。两边现在都是 `UserService`，所以 `/user/hello` 仍然是 `hello world`，看起来和没加 `@Primary` 一样。

要看见这个注解在起作用，把 `@Primary` 挪到 `EmployeeService` 上再请求 `/user/hello`。`EmployeeService.setName` 是空的，`getName` 固定返回「获取雇员名字」，响应会变成 `hello获取雇员名字`。把两个类上的 `@Primary` 都去掉，启动应在注入 `UserInterface` 时失败，文案是「存在多个Bean，未用Primary指定哪一个」。

### 先知道的边界

| 情况 | 现状 |
| --- | --- |
| 一个候选，类上没有 `@Primary` | 用这一个 |
| 一个候选，类上有 `@Primary` | 同样用这一个，注解不起额外作用 |
| 多个候选，恰好一个 `@Primary` | 用那一个 |
| 多个候选，没有 `@Primary` | 失败 |
| 多个候选，两个以上 `@Primary` | 失败 |
| 注入点想指定「不要默认的那个」 | 还没有。那是 `@Qualifier`，这一步不做 |
| `@Bean` 方法上的 `@Primary` | 注解目标只有类型。现在没有 `@Bean` 方法，够用 |

### 接下来

问题 144 的顺序里，前四步都落地了。最后一步里先只做循环依赖的对象身份，初始化方法和销毁先不动。

`createBean` 现在是：

```text
instantiate 得到原始对象
三级缓存里放一个工厂，工厂返回的就是这个原始对象
populate、字段注入
initialize：BeanPostProcessor 可以返回另一个对象
一级缓存放 initialize 的返回值
清掉二级、三级缓存
```

`LoggingBeanPostProcessor.afterInitialization` 会返回 JDK 代理，不是原来的那个实例。`Phase4Test` 会注册这个处理器。正常没有循环时，别人都是创建结束后才 `getBean`，拿到的是一级缓存里的代理，看不出问题。

循环发生在填充属性或字段注入期间：对方 `getBean` 当前还在创建的这个名字。一级缓存还没有，二级也没有，于是执行三级工厂，把**原始对象**放进二级缓存并返回。创建结束时，一级缓存放的是**代理**。对方字段里仍是原始对象。`==` 不成立，之后打在代理上的逻辑，这条依赖走不到。

做到这一步的标准：A 依赖 B、B 又依赖 A，并且 A 在初始化后会被换成代理。B 里拿到的 A，和最后 `getBean("A")` 得到的对象，是同一个引用。没有人中途来取时，行为与现在一样，仍然只包装一次，一级缓存里是那个代理。

不要在这一步加 `@PostConstruct`、销毁回调，或 `@Qualifier`。那些都是对象已经确定是谁之后的事。

## 148. 这些代理是什么？Spring 容器里一定要放代理吗？

**结论：不必。** 容器里放的是创建流程最后交出来的那个对象。多数 Bean 就是 `new` 出来的原实例。代理只在有人要把原对象换成另一个、外表一样的对象时才出现。你现在的 Web 启动没有注册 `LoggingBeanPostProcessor`，`UserService` 放进一级缓存的就是 `UserService` 自己。上一问把「循环依赖时两边是不是同一个对象」放在代理上讲，是因为你项目里只有这一处会把 Bean 换成另一个对象。没做 AOP 时，这个问题先不存在。下一步改做初始化方法。

### 代理是什么

代理是另一个对象。它实现和原对象相同的接口，里面拿着原对象。别人调用接口方法时，先进入代理，代理可以先做一点额外的事，再转调原对象的同名方法。

你项目里的生成点是 `JdkDynamicProxy.getProxy`：

```java
Proxy.newProxyInstance(
    object.getClass().getClassLoader(),
    object.getClass().getInterfaces(),
    new LoggingProxyHandler(advisorList, object))
```

`Proxy.newProxyInstance` 在运行时做出一个新类的实例。这个实例的类型不是 `UserService`，它只实现 `UserService` 的接口（这里是 `UserInterface`）。`LoggingProxyHandler` 把原来的 `UserService` 记在 `target` 里。

`invoke` 的过程：

```text
别人调用代理.getName()
  → LoggingProxyHandler.invoke
  → 方法名是 getName，命中 NameMatcher，advisor.enhance()（打日志这一类额外动作）
  → method.invoke(target, args)，也就是真正的 UserService.getName()
```

所以调用方手里的引用和 `new UserService()` 不是同一个对象，但 `getName()` 的业务结果仍然来自那个 `UserService`。多出来的只是调用前的那一下 `enhance()`。

`LoggingBeanPostProcessor.afterInitialization` 对每个经过它的 Bean 都执行这件事，返回值是代理，原对象只留在代理内部。`Phase4Test` 会 `addBeanPostProfessor` 注册它。`MiniSpringApplication` 的启动路径没有注册这个处理器，`initialize` 收到什么就返回什么，一级缓存里是原实例。

### Spring 什么时候才放代理

Spring 的一级缓存同样只保存创建流程的最终返回值。`BeanPostProcessor` 可以返回原对象，也可以返回另一个对象。返回原对象时，容器里就是原实例。

会换成代理的典型情况：

| 场景 | 容器里实际是什么 |
| --- | --- |
| 普通 `@Component`，没有 AOP、没有事务 | 原实例 |
| `@Transactional` | 代理。提交、回滚包在业务方法外面 |
| `@Async`、一部分安全注解 | 代理。额外动作在调用前插入 |
| 你自己的 `LoggingBeanPostProcessor` | 代理。`getName` 之前先 `enhance()` |

事务能包在方法外面，是因为调用先到达代理，代理开事务，再调用原对象。原对象自己的方法体里没有事务代码。这是代理存在的原因，不是容器的存储格式。

没有这些需求时，Spring 不会给 Bean 套代理。`getBean` 拿到的就是那个类的实例，字段、构造器注入进去的也是它。

### 和循环依赖那句话的关系

三级缓存在属性填充之前交出的是 `instantiate` 的返回值，也就是原对象。创建结束时，一级缓存放的是 `initialize` 的返回值。

`initialize` 返回原对象时，两边本来就是同一个引用，循环依赖拿早了也没关系。`LoggingBeanPostProcessor` 让 `initialize` 返回代理时，中途拿到的是原对象，最后缓存的是代理，两个引用不同。日志打在代理上，中途注入的那一边调用 `getName` 不会经过 `enhance()`。

因此「提前拿到的和最终缓存的必须是同一个」只在 Bean 会被换成另一个对象时才需要处理。你当前的主程序没有这种替换。上一问把这一步排在初始化前面，是顺着「有代理时身份会裂开」说的，不是说容器必须先学会放代理。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 单例缓存里就该是代理 | 缓存里是最终对象。最终对象经常就是原实例 |
| 注入的接口类型说明容器给的是代理 | `UserInterface` 字段只说明按接口找实现。`UserService` 自己就实现了这个接口，赋的可以是 `UserService` 实例 |
| 没看懂代理就不能继续 IoC | 代理是 AOP 那条线。生命周期回调不依赖它 |

### 接下来

`@Primary` 仍然算写完。代理身份先搁置，等你自己要做事务或日志增强时再回到 `createBean` 里「提前交出的引用」和「`initialize` 的返回值」。

下一件做初始化方法：依赖注入完成之后、放进一级缓存之前，调用 Bean 自己的一个初始化回调。销毁放到再下一步，这次先不写。

```text
instantiate
populate、字段注入
调用初始化回调（依赖已经在，可以在这里做准备）
放进一级缓存
```

回调用一个你自己的接口即可，例如 `InitializingBean`，里面一个 `afterPropertiesSet()`。类实现了它就调用，没实现就跳过。不要在这一步判断是不是代理，也不要改三级缓存。

## 149. `afterPropertiesSet` 写好了，然后呢？

**结论：主路径写对了。** 属性填充和字段注入之后、`addSingleton` 之前，实现了 `AfterPropertiesSet` 的 Bean 会走到 `afterPropertiesSet`。没实现的类直接跳过。`UserService` 在这里给 `name` 加上前缀，并且返回的仍是原来的那个实例，所以一级缓存里还是这个 `UserService`。下一步只做销毁回调。

### 现在的调用

`createBean` 的顺序是：

```text
instantiate
把原始对象放进三级缓存
populate、injectAutowiredFields
initialize（现有的 BeanPostProcessor）
若对象的类能赋给 AfterPropertiesSet → 用返回值换掉 initialize
addSingleton（放进一级缓存，并清掉二级、三级）
```

接口是：

```java
public interface AfterPropertiesSet {
    Object afterPropertiesSet(Object o);
}
```

`UserService` 同时实现 `UserInterface` 和 `AfterPropertiesSet`。方法里把参数转成 `UserService`，在 `name` 前面加上 `(prefix:afterPropertiesSet-`，再把这个对象返回。传入的参数就是当前这个实例，返回的也是它，没有换成另一个对象。

`EmployeeService`、`UserController` 没有实现这个接口，创建时不会进这个分支。

### 和 Spring 的两点差别，先留着

Spring 的 `InitializingBean.afterPropertiesSet()` 没有参数，返回 `void`。准备动作写在 `this` 上，容器不会用返回值替换 Bean。替换对象是 `BeanPostProcessor` 的事。你这份接口把 Bean 当参数传进去，再用返回值作为即将缓存的对象。`UserService` 返回的是同一个实例，所以今天的缓存身份没有变。以后如果某个实现 `return` 了一个新对象，中途从三级缓存拿到的仍是 `instantiate` 的那个，一级缓存里则是新对象。初始化回调继续返回当前实例即可。

Spring 把 `afterPropertiesSet` 夹在 `beforeInitialization` 和 `afterInitialization` 中间。你现在先跑完 `initialize()` 里成对的 before/after，再调 `afterPropertiesSet`。Web 启动没有注册会把 Bean 换成另一个对象的处理器，`initialize` 返回的就是原实例，这一步的结果和「注入完成后、进缓存前调用」一致。先不要为了插进两个处理器中间去拆 `initialize`。

### 怎么看见它跑过

`/user/hello` 看不出来。`hello()` 里有 `userService.setName(" world")`，创建时写上的前缀会被这句盖掉，响应仍是 `hello world`。

前缀留在创建结束、还没有人调用 `setName` 的时候。此时 `UserService.getName()` 是 `(prefix:afterPropertiesSet-`。`getUser` 在 `name` 不为空时会把 `name` 和 `"Tom"` 拼在一起，所以这一段前缀会出现在返回的用户名里。断点打在 `UserService.afterPropertiesSet` 上，启动时每个 `UserService` 只会进一次。

### 接下来

下一件只做销毁。容器关闭时，对单例里实现了销毁接口的 Bean 调用一次销毁方法。没实现的跳过。

```text
void destroy();
```

工厂加一个 `close()`：按单例调用 `destroy()`。一个 Bean 的销毁里还会用到它依赖的 Bean 时，先销毁依赖方，再销毁被依赖的那个。这次不要写 `@PreDestroy`，也不要改三级缓存和代理。

这个「下一件」在 150 里改掉了：销毁是初始化的对称步骤，但现阶段没有必须释放的资源，不必优先写。

## 150. 为什么要销毁？现阶段有必要优先写这个吗？

**结论：现阶段不必优先写。** 销毁是容器关闭时的回调，用来释放初始化里占下的外部资源。你现在的 Bean 没有这类资源，进程退出时内存也会被操作系统收回。`afterPropertiesSet` 已经把「依赖注入之后做一次准备」这条生命周期补上了，IoC 这条线可以先停。

### 销毁在 Spring 里解决什么

`afterPropertiesSet` 发生在创建过程中：依赖已经放进对象，对象还没交给别人使用，适合做准备。销毁发生在容器决定停掉这些单例的时候，适合做准备的逆操作。

Spring 在 `ApplicationContext.close()`，或者注册了 shutdown hook、JVM 收到退出信号时，按创建的大致反序调用：

```text
DisposableBean.destroy()
@PreDestroy
@Bean(destroyMethod = "...")
```

反序是因为 A 的销毁里可能还要调用 B。先关掉 A，再关掉 B，B 在 A 收尾时仍然可用。典型要释放的东西是：连接池、后台线程、临时文件、监听端口。这些不会因为 Java 对象不再被引用就立刻停掉。连接池的线程还在跑，文件句柄还占着。所以才需要一次明确的 `destroy()`。

### 你现在的进程里没有这件事

`UserService.afterPropertiesSet` 只给 `name` 加了一个前缀，没有打开连接，没有启动线程。`EmployeeService`、`UserController` 也没有。工程里没有 `destroy`、`close`、`shutdown` 或 `DisposableBean`。

Web 入口是 Tomcat `start` 然后 `await`，一直停在那里等请求。停进程靠结束 JVM。JVM 退出后，堆上的单例、字符串前缀都会一起消失，没有留在进程外面的资源需要你的 `close()` 去还。

所以现在写 `destroy()`，只能在人为调用 `close()` 时打一行日志。请求路径、注入、`/user/hello` 都不会变。它是教科书上和初始化成对的下一步，不是当前会露出的缺口。

| 情况 | 要不要现在写销毁 |
| --- | --- |
| Bean 只在内存里放数据，进程结束就丢掉 | 不必 |
| `afterPropertiesSet` 里启动了线程、打开了连接或文件 | 要。否则关容器后这些还在 |
| 测试里反复 `new` 容器，上一轮的线程还活着 | 要。否则下一轮和上一轮叠在一起 |
| 想先把「创建完可以准备一下」跑通 | 已经有 `afterPropertiesSet`，够用 |

### 什么时候再写

等某个初始化回调真的占了进程外面的东西，再给工厂加 `close()`，对实现了销毁接口的单例调用 `destroy()`。依赖方先销毁。仍然不必先写 `@PreDestroy`。

### 这条 IoC 线停在哪

问题 144 里列出的内容，现在的落点是：

```text
BeanDefinition 已在 core.model
singletonBeanMap 已是 private
构造器注入已按 @Autowired 构造器传参
多个同类型 Bean 已由 @Primary 选一个
注入之后已有 afterPropertiesSet
```

代理身份、`@Qualifier`、销毁都先搁置。前两个要等你真的把 Bean 换成另一个对象，或某个注入点必须指定「不要默认的那个」。销毁等上面说的资源出现。

若继续改能从请求里看出来的行为，回到之前放下的路径变量：`HandlerMappingImpl` 仍把 `{id}` 换成 `(.*)`，并用 `find()` 判断。一个路径变量、中间没有多余斜杠时能取到值；`(.*)` 会吞掉后面的斜杠，多个 `@PathVariable` 也还都读 `group(1)`。那是路由上的缺口，和销毁无关。

## 151. 后面该优先干什么？

**结论：优先改单个路径变量的匹配。** IoC 停在 `afterPropertiesSet`。销毁、代理身份、`@Qualifier` 都不改变你现在能发出的请求。`/user/getUserByPath/{id}` 已经在用，但 `{id}` 被换成 `(.*)`，再用 `find()` 判断，多出来的路径段也会被当成匹配成功。这一步只把「一段、不含斜杠、整段路径都要对上」写对。多个路径变量、模板路径的 405，留到下一问。

### 为什么是这一件

能从一次请求里看出来的缺口，比容器关闭时的回调优先。当前路由注册在 `HandlerMappingImpl.autoAddHandlerMethod`：

```java
requestMappingInfo.regexPath = wholeUrl.replaceFirst("\\{.*\\}", "(.*)");
```

查找时：

```java
if (m.find() && 方法名相同) { ... }
```

`ArgumentResolver` 里同样 `compile` 这段 `regexPath`，`find()` 之后取 `group(1)`。

`/user/getUserByPath/12` 能工作，是因为这一段里没有多余的斜杠，`group(1)` 正好是 `12`。下面两种也会被 `find()` 判成找到了：

| 请求路径 | `(.*)` 加 `find()` 的结果 |
| --- | --- |
| `/user/getUserByPath/12` | 匹配，`group(1)` 是 `12` |
| `/user/getUserByPath/12/extra` | 也匹配，`group(1)` 是 `12/extra`。后面 `Long.valueOf` 会失败 |
| `/foo/user/getUserByPath/12` | `find()` 不要求整段相等，中间出现这段模式就算找到 |

`(.*)` 里的 `.` 包含 `/`。`find()` 只要求字符串某处出现这个模式，不要求从开头到结尾都是这条映射。

### 这一步只改两处

注册时把唯一的 `{名字}` 换成 `([^/]+)`。`[^/]` 表示「不是斜杠的一个字符」，`+` 表示至少一个。一段路径变量到下一个 `/` 为止。

判断从 `find()` 改成 `matches()`。`HandlerMappingImpl.getHandlerMethod` 和 `ArgumentResolver` 里对这条 `regexPath` 的匹配都要改。`matches()` 要求整段路径符合模式，前后多出来的字符不算成功。

做完后的结果：

```text
GET /user/getUserByPath/12        仍然得到这个用户，id 是 12
GET /user/getUserByPath/12/extra  404
GET /foo/user/getUserByPath/12    404
```

`/user/hello`、`/user/getUser?userId=`、`POST /user/addUser` 保持原样。这些路径没有 `{}`，不会走进 `regexPath`。

### 先不要一起做的

| 内容 | 为什么先不动 |
| --- | --- |
| 两个以上的 `{id}` | `replaceFirst` 只替换第一对花括号。多个变量要按名字各占一个组，和「收紧这一段」不是同一处改动 |
| 模板路径的 405 | 方法不对时，精确路径能返回 405；带 `{}` 的路径对不上精确字符串，现在会落到 404。等这一段匹配稳定后再区分 |
| 销毁、`@Qualifier`、代理身份 | 不改变这次请求的路径和参数 |

### 最终建议

下一件只改单个路径变量：`([^/]+)` 配合整段 `matches()`。`/user/getUserByPath/12` 仍然可用，多一段路径或前面多一段前缀则为 404。

## 152. 代理那块我想调一下，我看 Spring 返回的对象都是代理

**结论：调试器里大量 `$Proxy` 或 `$$EnhancerBySpringCGLIB`，是那些 Bean 被切面增强过。** 没有切面的组件，`getBean` 拿到的就是源码里的那个类。你这份 JDK 代理也不能套到每一个对象上：没有接口的类，`Proxy.newProxyInstance` 会直接失败。这一步只改「谁该被换成代理，初始化回调在换之前调用」。路径变量先停。

### 你在 Spring 里看到的是哪一种对象

类名能区分：

| `getClass().getName()` | 容器里实际是什么 |
| --- | --- |
| `com.minispring2.demo.model.UserService` | 原实例 |
| `com.sun.proxy.$Proxy12` 这一类 | JDK 代理。目标类有接口，切面按接口生成 |
| `UserService$$EnhancerBySpringCGLIB$$…` | CGLIB 子类代理。Spring 在没有合适接口，或指定按类代理时用它 |

会变成代理的，是容器认为「调用要先经过额外逻辑」的 Bean：类或方法上有 `@Transactional`、`@Async`、`@Cacheable`，以及 MyBatis 的 Mapper、Spring Data 的仓库接口。`@Configuration` 在完整模式下也会被 CGLIB 生成子类，为的是拦截 `@Bean` 方法，让多次调用拿到同一个单例。

一个什么注解都没有的 `@Component`，`getBean` 的运行时类就是它自己。业务工程里 Service 几乎个个都挂了事务，所以调试时连续看到的都是代理，容易看成「容器的返回值一律是代理」。

### 你现在的代理实际套在哪

`LoggingBeanPostProcessor.afterInitialization` 对传进来的每一个对象都调用 `JdkDynamicProxy.getProxy`。`Phase4Test` 里手动 `addBeanPostProfessor` 注册了它。`MiniApplicationContext.refresh` 只 `scan` 再 `preInstantiateSingletons`，没有注册这个处理器。Web 启动拿到的 `UserService` 仍是 `UserService`。

`getProxy` 把 `object.getClass().getInterfaces()` 交给 `Proxy.newProxyInstance`。JDK 动态代理必须至少有一个接口。接口数组为空时，JDK 抛 `IllegalArgumentException`。

| 类 | 接口 | 现在这句代理 |
| --- | --- | --- |
| `UserService` | `UserInterface`、`AfterPropertiesSet` | 可以生成，类型不是 `UserService`，只是这两个接口的实现 |
| `EmployeeService` | `UserInterface` | 可以生成 |
| `UserController` | 没有 | 接口数组为空，一调用就失败 |
| `LoggingBeanPostProcessor` 自己若也被这条逻辑处理 | 有 `BeanPostProcessor` | 会套成代理，后面按具体类使用它会出问题 |

所以不能把 `afterInitialization` 写成「返回值一律换成代理」，再挂到启动流程上。第一个没有接口的 Bean 会让整个 `preInstantiateSingletons` 停住。

### 这一步怎么调

`afterInitialization` 里先决定要不要换：

```text
对象没有任何接口 → 返回原对象
对象是 BeanPostProcessor → 返回原对象
否则 → 返回 JdkDynamicProxy.getProxy(...)
```

有接口、需要 `getName` 之前那一下 `enhance()` 的，才放进一级缓存的是代理。`UserController` 仍然是它自己。

调用顺序也要换。现在是先 `initialize()`（其中 `afterInitialization` 已经返回代理），再对这个返回值做 `afterPropertiesSet`。代理一旦实现了 `AfterPropertiesSet`，这次调用进的是代理。`UserService.afterPropertiesSet` 里有 `(UserService) o`，参数却是代理，会 `ClassCastException`。

改成和创建过程一致的顺序：

```text
populate、字段注入
beforeInitialization（仍是原对象）
原对象实现了 AfterPropertiesSet → 对原对象调用 afterPropertiesSet
afterInitialization → 这里才可能换成代理
一级缓存放 afterInitialization 的返回值
```

`afterPropertiesSet` 继续改原来的 `UserService`。缓存里放代理时，代理内部的 `target` 就是这个已经加过前缀的实例。`getName()` 从代理进来，先 `enhance()`，再调到这个 `target`。

注册：在 `preInstantiateSingletons()` 之前 `addBeanPostProfessor(new LoggingBeanPostProcessor())`。不要给这个处理器加 `@Component` 让它和普通 Bean 一起被自己的 `afterInitialization` 再包一层。

`UserController` 的构造器要的是 `UserService` 这个类型。代理的运行时类不是 `UserService`，按具体类注入会对不上。字段类型是 `UserInterface`，代理可以实现它。这一步若要在 Web 里看见代理，构造器参数改成按 `UserInterface` 取，或者这条处理器先不要套 `UserService`、只在 `Phase4Test` 里看类名。二选一，不要两头都改。

### 先不要一起做的

三级缓存里仍是 `instantiate` 的原对象。没有循环依赖时，别人都在创建结束后才 `getBean`，拿到的是一级缓存里的代理，身份不会裂开。等出现「创建 A 的中途就要 A」时再改提前交出的引用。路径变量的 `([^/]+)` 也先停，避免和「返回值是不是代理」混在一次启动失败里。

### 最终建议

Spring 里成片的代理，是切面作用过的那些 Bean。你这次只让有接口、且不是 `BeanPostProcessor` 的对象走 JDK 代理；`afterPropertiesSet` 在换成代理之前，对原对象调用。没有接口的类原样放进容器。

## 153. 写 Tomcat 难度大吗，和 JBoss、Netty 相比呢？

**结论：写一个能用的 Tomcat 是大工程。** 它是 Servlet 容器，要自己把 HTTP 收成请求，再按 Servlet 规范把请求送进应用。JBoss（现在的 WildFly）是应用服务器，里面还要再装一套 Web 容器，以及事务、消息、命名、部署这些服务，范围比 Tomcat 更大。Netty 是网络框架，事件循环和字节缓冲是难点，它不提供 Servlet，范围比 Tomcat 小，难点种类不同。你现在的 `MiniSpringApplication` 是在用嵌入式 Tomcat，不是在写 Tomcat。

### 三样东西各自负责什么

| | 要完成的事 | 调用方拿到什么 |
| --- | --- | --- |
| Tomcat | 监听端口、解析 HTTP、管理 Web 应用、按 Servlet 规范调用 Filter 和 Servlet、会话、每个应用一个类加载器 | `HttpServletRequest` / `HttpServletResponse` |
| JBoss / WildFly | 上面这一层 Web 容器，再加上 EJB、CDI、JTA、JMS、JPA 的集成、JNDI、安全域、模块化类加载、管理端、集群和部署 | 一整台 Jakarta EE 服务器 |
| Netty | 事件循环、连接和管道、`ByteBuf`、协议解码器。HTTP 只是可选的一种解码器 | `Channel` 上的字节或已经解码的 HTTP 消息 |

WildFly 的 Web 层是 Undertow。更早的 JBoss 用过从 Tomcat 分出去的 JBossWeb。所以「写 JBoss」不是「写另一个 Tomcat」，而是「写一台里面含有 Web 容器的应用服务器」。

### 写 Tomcat 难在哪

嵌入式用法只是这几行：`setPort`、`getConnector`、`addContext`、`addServlet`、映射、`start`。连接器、解析、线程都在 `tomcat-embed-core` 里。

自己写，至少要有这些块：

```text
接受 TCP 连接
按 HTTP 报文切出方法、路径、头、体（含 Content-Length、分块传输）
找到对应的 Servlet，构造请求和响应对象
在线程里调用 service
把状态码、响应头、响应体写回
```

教学版做到「一个端口、一个 Servlet、只处理短请求」是可以完成的。真正的 Tomcat 还要扛这些：慢客户端、管道化、HTTP/2、TLS、WebSocket、大文件上传、会话持久化、热部署、JSP 编译、安全约束、同一个进程里多个应用的类加载器隔离。难的是这些边界同时正确，而且在并发下不串请求。Tomcat 是多年持续改出来的容器，不是一份周末能对齐的代码。

### 和另外两个比

**JBoss / WildFly 的范围更大。** Web 请求仍然要有人解析，这一部分 Undertow 已经是一个完整的 Web 服务器。除此之外，提交事务、投递消息、按模块隔离类、把几十个规范装进同一个进程并且能单独升级，是另一类工作。单论「把 HTTP 送进 Servlet」，Tomcat 和 Undertow 是同一档；单论「做出 JBoss」，要比做出 Tomcat 多出一整层平台。

**Netty 的范围更小，并发模型更陡。** 一个能回显的 Netty 服务，比一个 Servlet 容器少了解析 HTTP 规范和 Servlet 生命周期。难在事件循环：回调里不能做阻塞调用，`ByteBuf` 要配对释放，写一半的数据要继续写，协议要拆包。Spring WebFlux、gRPC 站在 Netty 上，它们仍然没有 Servlet 容器。若目标是「和现在的 `DispatcherServlet` 一样能跑」，用 Netty 还得把 HTTP 语义和 Servlet 那一层自己补上，最后的工作量会回到 Tomcat 这一档。

| 问题 | Tomcat | WildFly | Netty |
| --- | --- | --- | --- |
| 教学版最小能跑的内核 | HTTP 解析加一次 Servlet 调用 | 没有有意义的「最小 JBoss」，平台是由很多服务拼起来的 | 事件循环加一条管道 |
| 写完整产品的范围 | Servlet 容器 | 应用服务器，含 Web 容器 | 网络框架，不含 Servlet |
| 最容易写错的地方 | 报文边界、请求隔离、类加载器 | 服务之间的生命周期和类隔离 | 阻塞了事件循环、缓冲区泄漏 |

### 和当前工程的关系

`MiniSpringApplication` 把已经写好的 Tomcat 嵌进来，自己的代码停在 `DispatcherServlet`。容器、连接器都不是这个仓库里的代码。路径变量、代理注册仍然是这个框架里的下一步。写 Tomcat、Undertow 或 Netty 都不会让 `/user/getUserByPath/{id}` 的匹配变正确。

### 最终建议

要理解难度：Tomcat 是大工程；JBoss 比它更大，因为多了整台应用服务器；Netty 更小，难点在事件循环，不能拿它代替 Servlet 容器。当前仓库继续用嵌入的 Tomcat 即可。

## 155. 字符组 `[^/]+` 和捕获组是什么关系？

对应旧清单第 128、129 条。用户这次只点名这两块：字符组、捕获组。

**结论：它们不是一类东西，是套在一起用的两层。** `[^/]+` 回答「这一段允许出现哪些字符、出现几次」；外面的 `()` 回答「匹配成功后把这一段存下来，好用 `group(1)` 取出」。没有 `()`，`[^/]+` 仍能匹配路径里的 `12345`，但取不出单独的值。没有 `[^/]`，`(.*)` 也能捕获，但可能把斜杠后面的更多路径一起吃进去。

出现位置：`PatternTest.test2` 的 `user/getUser/([^/]+)`；`ArgumentResolver` 里 `m.group(1)` 取路径变量；注册时 `HandlerMappingImpl` 目前把 `{id}` 换成的是 `(.*)`，同样是捕获组，只是里面不是字符组。

### 先拆 `([^/]+)`

```text
(      [^/]      +      )
│        │       │      │
│        │       │      └─ 捕获组结束
│        │       └─ 至少 1 个这样的字符
│        └─ 字符组：一个不是 / 的字符
└─ 捕获组开始，整段落进 group(1)
```

对 `user/getUser/12345`：

```text
字面量 user/getUser/   对上前缀
字符组 [^/]+           吃掉 12345（五个都不是 /）
捕获组 (...)           把 12345 存成第 1 组
```

`m.group()` / `group(0)` = `user/getUser/12345`（整段匹配）  
`m.group(1)` = `12345`（捕获组里的内容）

### 字符组：规定「一个字符」的允许范围

`[]` 叫字符组（character class / 字符类）。它每次只描述**一个**字符可以是什么。

| 写法 | 一个字符可以是 |
|------|----------------|
| `[abc]` | `a` 或 `b` 或 `c` |
| `[0-9]` | 一位数字 |
| `[^/]` | 除 `/` 以外的任意一个字符 |
| `[.*]` | 一个点或一个星号，**不是**「任意多个」 |

方括号里开头的 `^` 表示取反，不是「行首」。行首的 `^` 写在模式最前面、方括号外面。

`+` 不是字符组的一部分，它是量词，作用在左边那一整块 `[^/]` 上：这样的字符至少出现一次。所以 `[^/]+` = 一段连续的、中间没有 `/` 的文本，正好对应 URL 里的一节路径。

遇到下一个 `/` 就停。`user/getUser/12345/extra` 里，`[^/]+` 只拿到 `12345`。

### 捕获组：规定「匹配到的哪一段要留下来」

`()` 叫捕获组（capturing group）。它不改变「能不能匹配」，只多存一份子串。

| 编号 | 含义 | 本例 |
|------|------|------|
| `group(0)` / `group()` | 整次匹配 | `user/getUser/12345` |
| `group(1)` | 第 1 对圆括号 | `12345` |
| `group(2)` | 第 2 对圆括号 | 这个模式没有 |

路径变量要的是 `{id}` 对应的那一截，所以必须有捕获组，取值用 `group(1)`，不要用 `group()`。

圆括号和量词的相对位置：

```text
([^/]+)     group(1) 是整段 12345     ← 路径变量要这个
([^/])+     group(1) 是最后一次重复的那个字符，往往是 5
```

`+` 要包在括号里面。

非捕获组 `(?:[^/]+)` 也能匹配同样的字符，但不占 `group(1)`。框架要取值，必须用会捕获的 `()`。

### 两者如何配合，以及和当前代码的差别

匹配「一节路径」：字符组决定停在哪，捕获组决定取哪段。

```java
Pattern.compile("user/getUser/([^/]+)");
//                   字面量     捕获( 字符组+量词 )
```

当前注册代码是：

```java
wholeUrl.replaceFirst("\\{.*\\}", "(.*)");
```

`{id}` 变成 `(.*)`：有捕获组，所以 `ArgumentResolver` 里 `m.group(1)` 能取到值。但里面是 `.*`（任意字符，含 `/`），不是 `[^/]+`。`/user/getUser/123/extra` 时，`.*` 可能把后面也吃进去。Spring 把 `{id}` 编成 `([^/]+)`，就是用字符组把一节路径卡住。

| | 字符组 `[^/]+` | 捕获组 `(...)` |
|--|----------------|----------------|
| 管什么 | 哪些字符、几个 | 匹配成功后存哪一段 |
| 没有它 | 仍可能匹配，但停不准或取不出 | 能匹配，`group(1)` 没有 |
| 路径变量 | 一节里不要 `/` | 把这一节交给 `@PathVariable` |

### 常见误区

| 想法 | 实际 |
|------|------|
| `[^/]+` 本身就是捕获组 | 那是字符组加量词；捕获要靠外面的 `()` |
| `[^/]` 表示以 `/` 开头 | `^` 在 `[]` 里表示「除外」 |
| `group()` 就是捕获到的 id | `group()` 是整段；id 是 `group(1)` |
| `(.*)` 和 `([^/]+)` 当捕获组效果一样 | 都能捕获；字符组不同，后者遇 `/` 会停 |
| `([^/])+` 和 `([^/]+)` 一样 | 量词在括号外时，组里只剩最后一个字符 |

### 最终建议

读 `([^/]+)` 时先看里面的字符组（一节路径），再看外面的括号（留给 `group(1)`）。模板 `{id}` 换成正则时，捕获组不能省；字符组用 `[^/]+` 比 `.*` 更符合「一节路径」。当前 `replaceFirst(..., "(.*)")` 已经有捕获组，若要和 Spring 一样按斜杠切开，把 `(.*)` 改成 `([^/]+)`。

### 再问时的极简记法

把两个词拆开记，不要合成一个概念：

```text
字符组   [ ]     一个字符允许是什么
  [^/]           不是斜杠的一个字符
  [^/]+          这样的字符连成一段（一节路径）

捕获组   ( )     把已经匹配到的某一段存下来
  group(1)       第 1 对括号里的内容
```

合在一起才是路径变量常用的 `([^/]+)`：里面负责「吃一节、遇 `/` 停」，外面负责「把这节交给 `group(1)`」。

## 154. Cursor 适配 Java 需要什么配置？

**结论：Cursor 不自带 JDK，也不自带 Java 语言服务。** 机器上要有 JDK 和 Maven；编辑器里要装 Java 扩展（通常是 Extension Pack for Java）。跳转、补全、红线和测试装订线靠这套扩展；Agent 聊天不装也能改 Java 文件，但没有项目 classpath 时容易瞎补。对本仓库这种 Maven 多模块，打开带父 `pom.xml` 的根目录即可，不必装 Spring Boot / Gradle 扩展。

官方说明：[Cursor for Java](https://cursor.com/for/java)。Cursor 能用 VS Code 扩展市场里的 Java 插件。

### 1. 机器环境（先于 Cursor）

Windows 上先确认：

```text
java -version
javac -version
mvn -version
echo %JAVA_HOME%
```

| 项 | 作用 |
|----|------|
| JDK（建议 17，和父 POM `maven.compiler.source` 一致） | 编译、运行、语言服务器自己也是 Java 进程 |
| `JAVA_HOME` 指向 JDK 根目录，`%JAVA_HOME%\bin` 在 PATH | Cursor 和 Maven 找 javac |
| Maven，`mvn` 能用 | 导入多模块、下依赖。本仓库已在用阿里云镜像 |

只有 JRE、没有 `javac`，扩展会报找不到编译器。本仓库 `minispring-web` 的 POM 还写了 source/target 8，JDK 17 可以编译 8，反过来用 JDK 8 跑语言服务器也行，但和父 POM 17 不一致时容易乱。语言服务器用 17、项目按 POM 的 release 编译即可。

### 2. 扩展（Cursor 里真正「适配 Java」的部分）

扩展面板搜索并安装 **Extension Pack for Java**（发布者 `vscjava` / Microsoft）。它会带上：

| 插件 | 做什么 |
|------|--------|
| Language Support for Java by Red Hat | 补全、跳转、重构、红线（Eclipse JDT Language Server） |
| Debugger for Java | 断点调试 |
| Test Runner for Java | JUnit 方法上的 Run Test |
| Maven for Java | 识别 `pom.xml`、生命周期 |
| Project Manager for Java | Java Projects 视图 |

本仓库用 Maven、JUnit 5，上述四件就够。

**不必装：**

- Gradle for Java（本仓库没有 Gradle）
- Spring Boot Extension Pack（这是迷你 Spring，不是 Spring Boot）
- Kotlin

另一条路是 JetBrains 的 **Java and Kotlin by IntelliJ IDEA**。体验更接近 IDEA，但预览后要 Ultimate 授权，和 Red Hat 包不要同时开，会抢语言服务。学习迷你框架用 Extension Pack for Java 足够。

装完后右下角应出现 Java 项目导入。失败时命令面板执行 **Java: Clean Java Language Server Workspace**，再重载窗口。

### 3. Cursor 用户设置（识别不到 JDK 时才写）

`Ctrl+Shift+P` → **Open User Settings (JSON)**。Windows 文件在 `%APPDATA%\Cursor\User\settings.json`。

语言服务器找不到 JDK 时：

```json
{
  "java.jdt.ls.java.home": "C:\\Program Files\\Java\\jdk-17",
  "java.configuration.runtimes": [
    {
      "name": "JavaSE-17",
      "path": "C:\\Program Files\\Java\\jdk-17",
      "default": true
    }
  ]
}
```

路径改成你机器上 `java.exe` 所在 JDK 的根目录（里面有 `bin\javac.exe`）。不要指向 `bin`。

可选、对本仓库有用：

```json
{
  "java.configuration.updateBuildConfiguration": "automatic",
  "java.import.maven.enabled": true,
  "java.compile.nullAnalysis.mode": "disabled",
  "java.jdt.ls.vmargs": "-XX:+UseParallelGC -Xmx2G -Xms256m -Dsun.zip.disableMemoryMapping=true"
}
```

| 设置 | 含义 |
|------|------|
| `updateBuildConfiguration: automatic` | 改 POM 后自动刷新 classpath |
| `import.maven.enabled` | 按 Maven 导入，本仓库必须开 |
| `nullAnalysis.mode: disabled` | 减少教学代码上的空指针误报 |
| `jdt.ls.vmargs` 里的 `-Xmx` | 语言服务器内存；卡在 Importing Maven 时可加大 |

Maven 私服/镜像用用户目录的 `.m2/settings.xml`，一般不用在 Cursor 里再配；IDE 导入和命令行 `mvn` 读同一份。若 `mvn` 不在 PATH，可设 `maven.executable.path`。

想让 `@RequestParam` 省略 value 时反射拿到参数名，编译还要 `-parameters`（问题 83–86）。那是 Maven/javac 的事，不是 Cursor 专用项。可在 POM 的 `maven-compiler-plugin` 里写 `<parameters>true</parameters>`，并在 Cursor 的 Java Compiler 相关设置里同样打开，避免 IDE 自己编译的 class 没有 `MethodParameters`。

### 4. 怎么打开本仓库

打开 `d:\idea-repository\spring-mini2`（有父 `pom.xml` 的那一层），不要只开 `minispring-web` 子目录。多模块要让语言服务器看到 reactor。

导入成功后，`UserController` 里的 `UserService` 应能 `Ctrl+单击` 跳转，`PhraseTest2` 方法上方出现 Run Test。Agent 改代码不依赖这些；**红线、跳转、方法上的 Run 依赖扩展和导入完成。**

`.vscode/launch.json` 不是第一天必须。有 `main` 时可在方法上点 Run；测试用 Test Runner。要用 Tomcat 嵌入启动类调试，再补一个 Launch 配置即可。

### 5. 和 IDEA 的差别（避免按 IDEA 习惯找）

| IDEA | Cursor + Java 扩展 |
|------|-------------------|
| 自带 JDK 检测、Maven 导入 | 要自己装 JDK + 扩展 |
| Project Structure 里设 SDK | `java.jdt.ls.java.home` / `java.configuration.runtimes` |
| 打开 Maven 项目即索引 | 等 JDT LS 导入，右下角有进度 |
| 自带 Spring 图表 | 迷你框架不需要；Boot 才用 Spring 扩展 |

Cursor 的 Agent、Tab、Chat 是另一层：它们读工作区文件，不代替 JDT。没装扩展时 Agent 仍能改 Java，但补全和「这个类在哪个模块」不如语言服务器准。

### 常见误区

| 想法 | 实际 |
|------|------|
| 装了 Cursor 就能当 IDEA 用 | 还要 JDK、Maven、Java 扩展 |
| 必须装 Spring Boot 扩展 | 本仓库不是 Boot |
| `java.home` 指到 `bin` | 指到 JDK 根目录 |
| 只开子模块目录 | 父 POM 多模块应开仓库根 |
| Agent 能跑就等于 Java 配好了 | 跳转和测试装订线才说明语言服务起来了 |

## 156. `Field.set` 报错：不能把 `$Proxy10` 赋给 `UserService.UserDao` 字段

对应第 152 条。出现位置：`Phase4Test.test` → `getBean("userService")` → `injectAutowiredFields` 第 150 行。

```text
IllegalArgumentException: Can not set com.minispring2.demo.dao.UserDao field
com.minispring2.demo.model.UserService.UserDao to com.sun.proxy.$Proxy10
```

**结论：要注入的字段类型是具体类 `UserDao`，容器里拿出来的却是 JDK 代理 `$Proxy10`。** JDK 代理只实现接口，不是 `UserDao` 的子类，`Field.set` 在写入前做类型检查，对不上就抛这句。根因是 `LoggingBeanPostProcessor` 在 `afterInitialization` 里把每个 Bean 都包成代理，包括没有业务接口的 `UserDao`。

### 调用是怎么走到这里的

`Phase4Test` 注册了 `LoggingBeanPostProcessor`，再 `getBean("userService")`。

```text
createBean(userService)
  instantiate UserService
  populate name
  injectAutowiredFields
    看见 @Autowired UserDao UserDao
    getBeanForType(UserDao.class) → getBean("userDao")
      createBean(userDao)
        instantiate UserDao            ← 这时还是 UserDao 实例
        initialize
          LoggingBeanPostProcessor.afterInitialization
            JdkDynamicProxy.getProxy(userDao)  → 返回 $Proxy10
        addSingleton("userDao", $Proxy10)
    field.set(userService, $Proxy10)   ← 字段声明是 UserDao，失败
```

`getBeanForType` 只看 BeanDefinition 上的 `UserDao.class`，认为类型匹配；真正塞进字段时，值已经是 `initialize` 换过的代理。两套类型对不上。

### 为什么 `$Proxy10` 不是 `UserDao`

```java
Proxy.newProxyInstance(
    object.getClass().getClassLoader(),
    object.getClass().getInterfaces(),
    handler);
```

生成的类继承 `java.lang.reflect.Proxy`，只实现 `getInterfaces()` 里的那些接口。它**不会**变成目标类的子类。

| 对象 | 接口 | 代理 instanceof 谁 |
|------|------|-------------------|
| `UserService` | `UserInterface`、`AfterPropertiesSet` | 这两个接口；**不是** `UserService` |
| `UserDao` | 无 | 不是 `UserDao`。部分 JDK 仍会生成一个不实现业务接口的 `$ProxyN` |

`UserService` 字段写的是：

```java
@Autowired
UserDao UserDao;
```

`UserDao` 是类不是接口。`field.set` 要求 `UserDao.class.isInstance(传入值)`。`$Proxy10` 不通过，异常文案就是 “Can not set … UserDao … to … $Proxy10”。

这和强制转换是同一条 JVM 规则：变量/字段的**声明类型**必须能接住对象的**运行时类型**。代理的运行时类型是 `$Proxy10`，不是 `UserDao`。

CGLIB 代理是目标类的子类，`instanceof UserDao` 为 true，这种字段写得进去。JDK 代理做不到，所以 Spring 对「没有合适接口、却要按类注入」的 Bean 会改用 CGLIB，或者业务代码按接口声明依赖。

### 和「代理一定能注入」的误解

容器按类型查找用的是定义里的类：

```java
clazz.isAssignableFrom(beanDefinition.getaClass())  // UserDao vs UserDao，通过
```

注入用的是 `getBean` 的返回值，可能已经被 `afterInitialization` 换成代理。查找成功不等于 `Field.set` 成功。官方 Spring 的 `getType` 会按最终暴露的类型（接口或目标类）来匹配；迷你容器还没有这一层。

### 这一步该怎么改（先讨论，不改源码）

第 152 条已经定过，这次异常正好验证了那条：

1. **`afterInitialization` 不要无条件 `getProxy`。** 没有接口、或自己是 `BeanPostProcessor` 时返回原对象。`UserDao` 原样进容器，字段就能 set。
2. **需要代理的 Bean，依赖声明写成接口。** `UserService` 若要被代理，别人注入 `UserInterface` 而不是 `UserService`。`Phase4Test` 第 36 行已经按接口接 `getBean("userService")`，这一头是对的。
3. **`afterPropertiesSet` 在换代理之前、对原对象调用。** 否则 `UserService.afterPropertiesSet` 里的 `(UserService) o` 会再炸一次。现在还没走到这一行，是因为先在注入 `UserDao` 时失败了。

不要为了让这次测试变绿去把 `UserDao` 改成接口，也不要在 `injectAutowiredFields` 里把代理强转成 `UserDao`。那是绕过类型模型。该收的是「谁被代理」和「按什么类型注入」。

### 常见误区

| 想法 | 实际 |
|------|------|
| `$Proxy10` 是 `UserDao` 的包装，字段应该能接 | 包装在 handler 的 `target` 里；对外类型是代理类 |
| `getBeanForType(UserDao.class)` 会返回 `UserDao` 实例 | 返回的是一级缓存里 `initialize` 之后的对象，可能是代理 |
| 没有接口就不能生成 JDK 代理，所以不该出现 `$Proxy10` | 有的 JDK 仍生成不实现业务接口的代理；`Field.set` 照样失败 |
| 把字段改成 `Object` 就能注入 | 能 set，但后面当 `UserDao` 用会再出问题 |
| 这是 `@Autowired` 坏了 | 注解没问题；是代理类型和字段声明类型不一致 |

### 最终建议

异常含义是：JDK 代理不能赋给具体类字段。`LoggingBeanPostProcessor` 先跳过没有接口的 Bean（至少跳过 `UserDao`），`UserDao` 字段就能注入。`UserService` 继续按 `UserInterface` 取出。`afterPropertiesSet` 仍按第 152 条，在生成代理之前对原对象调用。

## 157. `Phase4Test` 里这三行，是不是让容器里的 Bean 都变成代理？

```java
DefaultBeanFactory defaultBeanFactory = new DefaultBeanFactory();
LoggingBeanPostProcessor loggingBeanPostProfessor = new LoggingBeanPostProcessor();
defaultBeanFactory.addBeanPostProfessor(loggingBeanPostProfessor);
```

**结论：对这次测试里的这个容器来说，基本是。** 这三行把 `LoggingBeanPostProcessor` 挂进工厂；之后每个走完 `createBean` 的对象都会进 `initialize` → `afterInitialization`，而这个处理器无条件 `getProxy`，所以 `userService`、`userDao` 都会被换成 JDK 代理。不是「凡是 DefaultBeanFactory 里的 Bean 永远都是代理」：没注册这个处理器的容器（例如 `MiniApplicationContext.refresh`）不会包；处理器自己也不是扫描出来的 Bean。真正让「每个对象都变代理」的，是 `afterInitialization` 没有过滤，而不只是 `addBeanPostProfessor` 这句本身。

对应第 152、156 条。出现位置：`Phase4Test` 第 20–22 行。

### 这三行做了什么

`addBeanPostProfessor` 只是把处理器放进 `beanPostProcessorList`。它不立刻改任何已有对象。

每个 Bean 创建末尾都会：

```java
Object initialize = initialize(instantiate);
```

```java
private Object initialize(Object object) {
    for (BeanPostProcessor beanPostProcessor : beanPostProcessorList) {
        object = beanPostProcessor.beforeInitialization(object);
        object = beanPostProcessor.afterInitialization(object);
    }
    return object;
}
```

`LoggingBeanPostProcessor.afterInitialization` 当前是：

```java
return JdkDynamicProxy.getProxy(object, ...);
```

没有「有没有接口」「是不是 PostProcessor」的判断。于是：

| Bean | 这次测试里会不会变代理 |
|------|------------------------|
| `userService` | 会。有 `UserInterface`，代理还能赋给测试里的 `UserInterface` 变量 |
| `userDao` | 也会。创建 `userService` 时注入依赖会先 `getBean("userDao")`，同样走 `initialize` |
| 处理器自己 | 不会。它是 `new` 出来再 `add` 的，没有进 `createBean` |

`userDao` 变成 `$Proxy10` 之后，再 `field.set` 到 `UserService.UserDao` 字段，就是上一问的异常。所以：**不是只有 userService 变代理，依赖链上每个被 createBean 的对象都会变。**

### 不是所有容器、所有 Bean

`MiniApplicationContext.refresh` 只 `scan` + `preInstantiateSingletons`，没有这三行，也没有给 `LoggingBeanPostProcessor` 加 `@Component`。Web 启动拿到的 `UserService` / `UserDao` 仍是原来的类。

`preInstantiateSingletons` 会把 **BeanDefinition 里类型是 `BeanPostProcessor` 的 Bean** 先创建并加入列表。`Phase4Test` 走的是手动 `addBeanPostProfessor`，两条进列表的路不一样，效果都是「之后的 `initialize` 会调到它」。

三级缓存里暂存的仍是 `instantiate` 的原对象。没有循环依赖时，别人 `getBean` 拿到的是一级缓存里 `initialize` 的返回值，也就是代理。

### 两层责任不要混

```text
addBeanPostProfessor          → 这个容器要不要跑这段后置逻辑
afterInitialization 一律 getProxy → 跑到的对象会不会都换成代理
```

只注册、但处理器按条件返回原对象，就不会「全都是代理」。Spring 的 `AbstractAutoProxyCreator` 也是挂在 PostProcessor 链上，但会判断切点、是否已是代理、是否基础设施 Bean，多数对象原样返回。

### 常见误区

| 想法 | 实际 |
|------|------|
| 这三行会把工厂里已经存在的对象当场换成代理 | 只影响之后 `createBean` → `initialize` 的对象 |
| 所有 DefaultBeanFactory 都会变代理 | 只有列表里有这个处理器的那一台 |
| 只有 `getBean("userService")` 返回代理 | 为了注入，`userDao` 也会先被创建并包一层 |
| 删掉这三行代理功能就没了 | 对。测试就是为了看代理才手动挂上的 |
| 处理器自己也会被包成代理 | 这次是 `new` 后 add，不走 `createBean` |

### 最终建议

是：`Phase4Test` 这三行让这个容器的 `initialize` 链上有了无条件包代理的处理器，所以这次测试里创建出来的 Bean 都会变成 `$Proxy`。要修的是 `afterInitialization` 的过滤（第 152、156 条），不是删掉这三行——测试需要处理器在；不需要的是给 `UserDao` 也套 JDK 代理。

## 158. Spring 自动代理不是通过切点来控制吗？

对应第 157 条里「判断切点、是否已是代理、是否基础设施 Bean」。

**结论：是，业务上由切点决定「这个 Bean 要不要增强」。** PostProcessor 只是每个 Bean 初始化后都会走到的挂钩；走到之后先用切点（以及 Advisor）看有没有匹配的通知，没有匹配就不创建代理，原对象返回。基础设施 Bean、已经是代理，是切点之前的跳过条件，防止切面框架自己被切、或包两层。不是「PostProcessor 替代切点」，而是「PostProcessor 里用切点做决定」。

### 两层分别管什么

```text
BeanPostProcessor.afterInitialization
    │  每个 Bean 创建末尾都会进来（挂钩）
    ▼
  跳过？基础设施 / 已是 AOP 代理 / 明确 exclude
    │
    ▼
  收集 Advisor，用切点问：这个类、这些方法要不要增强？
    │
    ├─ 一个都匹配不上 → 返回原对象（多数 Bean 走这里）
    └─ 有匹配 → 创建代理，把匹配到的 Advisor 放进拦截链
```

切点是 **Pointcut**：类过滤器 + 方法匹配器。`@Pointcut("execution(* com.example.service..*(..))")`、`@Transactional` 对应的 Advisor，都在这一步参与。`AbstractAutoProxyCreator.wrapIfNecessary` → `getAdvicesAndAdvisorsForBean`：返回 `DO_NOT_PROXY` 就不动这个 Bean。

「是否已是代理」「是否基础设施」不是第二套业务规则，是防护：

| 判断 | 为什么要有 |
|------|------------|
| 切点 / Advisor 匹配 | 决定要不要增强（主开关） |
| 已经是 AOP 代理 | 避免再包一层 |
| `BeanPostProcessor`、切面自身等基础设施 | 避免自动代理器给自己或 Advisor 再套代理，初始化顺序会乱 |

切点写得很宽时，基础设施仍可能被跳过。所以上一句把三件事并列，容易看成「和切点平级的三种控制」。更准确：切点是正门；后两件是门卫。

### 和当前迷你代码的差别

现在切点（`NameMatcher` 只认 `getName`）用在**调用时**，不是**要不要创建代理**时。

`LoggingBeanPostProcessor`：每个对象都 `getProxy`，不管类上有没有匹配的方法。

`LoggingProxyHandler.invoke`：每次方法调用再 `matcher.match(method.getName())`，命中才 `enhance()`。

```text
Spring：切点在创建代理前过滤 Bean → 多数对象根本没有代理
现在：先给所有 Bean 套代理 → 调用时再看是不是 getName
```

所以 `UserDao` 没有人要拦截它的业务方法，Spring 不会给它代理；迷你框架仍会生成 `$Proxy10`，然后注入失败。`UserService` 有 `getName`，两边都会代理——这才是切点该留下的那个。

Spring 一旦决定创建代理，拦截时仍会再用方法切点：代理上每个方法进来，只有匹配的才走通知。类匹配决定「有没有这层壳」，方法匹配决定「这次调用打不打日志」。

### 常见误区

| 想法 | 实际 |
|------|------|
| 有 PostProcessor 就会全部变代理 | 挂钩会进来；切点不匹配就原样返回 |
| 切点和 PostProcessor 是两套互斥机制 | PostProcessor 里调用切点 |
| 切点只在 invoke 时看方法名 | Spring 创建前先看类能不能匹配，避免无意义的代理 |
| 基础设施跳过等于不用切点 | 切点仍是主逻辑；跳过防止框架自切 |
| `NameMatcher("getName")` 已经和 Spring 一样 | 它现在只在 invoke 里生效，创建代理时没用上 |

### 最终建议

控制「谁成为代理」的是切点（加上 Advisor 列表）。PostProcessor 保证每个 Bean 有机会被问一次。迷你框架要对齐，应在 `afterInitialization` 里先问：这个对象有没有 Advisor 能匹配；没有就返回原对象。`NameMatcher` 从「调用时才看」提前到「创建代理前就看」。

## 159. `LoggingProxyHandler.invoke` 写得对吗？入参 `proxy` 为什么没用到？

出现位置：`LoggingProxyHandler.java` 第 19–33 行。

```java
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    // ... NameMatcher 命中则 advisor.enhance() ...
    return method.invoke(target, args);
}
```

**结论：业务调用写在 `target` 上是对的，`proxy` 不用也正常。** `proxy` 是这次调用落在哪一个代理实例上，不是目标对象。真正干活的是构造时传进来的 `target`。若写成 `method.invoke(proxy, args)`，调用会再进 `invoke`，无限递归直到栈溢出。JDK 规定 `InvocationHandler.invoke` 必须带这个参数，不等于每次都要用它。当前打日志再转发，用不到 `proxy`。Spring 主要在 `equals` / `hashCode`、以及需要「当前代理」暴露给业务时才用。

### 三个参数各是什么

`InvocationHandler.invoke` 的签名是 JDK 定的，少一个都不是这个接口：

| 参数 | 是什么 | 当前代码 |
|------|--------|----------|
| `proxy` | 调用方手里的那一个 `$ProxyN` | 未使用 |
| `method` | 被调用的接口方法 | 用来匹配名字、再 `invoke` |
| `args` | 实参，无参时可能是 `null` 或空数组 | 传给 `target` |

`JdkDynamicProxy.getProxy` 里：

```java
new LoggingProxyHandler(advisorList, object)  // object 存成 this.target
```

调用路径：

```text
userService.getName()
  → 进 $ProxyN
  → LoggingProxyHandler.invoke(proxy=$ProxyN, method=getName, args)
  → enhance（若名字匹配）
  → method.invoke(target, args)   // target 才是原来的 UserService
```

`target` 在 handler 字段里，不需要再从 `proxy` 里拿。代理对象上也没有一份「真实 UserService」字段给你取；真实对象只活在 handler 里。

### 为什么不能用 `proxy` 当 invoke 的接收者

```java
return method.invoke(proxy, args);  // 错
```

`method` 是接口上的方法。用代理当接收者，等于再调一次代理方法，又进同一个 `invoke`。这不是「把调用转给实现」，而是自己调自己。

`method.invoke(target, args)` 走的是目标类上的实现，不再经过 `InvocationHandler`。这才是动态代理的转发。

### `proxy` 什么时候才有用

少数情况需要「这次调用是哪个代理」：

1. **`equals` / `hashCode` / `toString`。** 若转到 `target`，`proxy.equals(proxy)` 可能变成两个不同实例的比较。Spring 的 `JdkDynamicAopProxy` 对这几个方法特殊处理，比较的是代理身份或基于 target 的约定。迷你日志代理可以先不管。
2. **方法返回 `this` 做链式调用。** 业务若 `return this`，`invoke(target)` 返回的是 target，调用方拿到的不再是代理，下一环会绕过切面。需要的话把返回值里的 `target` 换成 `proxy`。
3. **自调用还要走切面。** `this.getName()` 在 target 内部不会进代理。Spring 的 `AopContext.currentProxy()` 用的就是当前这次的 `proxy`。现在没有这种需求。

当前 `enhance()` 只打印日志，然后转发 `getName`，不涉及上面三类，所以参数列表里有 `proxy`、方法体不用，是符合接口、也符合常见写法的。

### 这段还算不算「写对了」

作为「命中方法名就打日志，再调真正的实现」，主路径是对的。和 Spring 完整拦截器链比，仍有几处是现阶段可以接受的简化：

| 点 | 现在 | 说明 |
|----|------|------|
| 转发到 `target` | 对 | 不要转发到 `proxy` |
| `proxy` 未使用 | 对 | 当前不需要 |
| 切点只在 invoke 里判断 | 能跑 | 第 158 条：创建代理前就该先问 |
| `enhance()` 在 `invoke(target)` 之前 | 相当于前置通知 | 没有后置、没有异常通知、没有把 `joinPoint.proceed()` 交给通知控制是否继续 |
| `instanceof NameMatcher` | 能跑 | 有别的 Matcher 时会被跳过 |

这些不影响「`proxy` 为什么不用」。

### 常见误区

| 想法 | 实际 |
|------|------|
| 参数没用到说明方法写错了 | 接口强制三个参数；常用的是 `method` 和 `args` |
| 应该 `invoke(proxy, args)` 才叫走代理 | 那会递归；代理已经走完了，下一跳是 target |
| `proxy` 就是 target | `proxy` 是壳，`target` 是壳里面的对象 |
| 不用 `proxy` 就不是动态代理 | 是不是代理看 `Proxy.newProxyInstance` 有没有把这个 handler 挂上 |

### 最终建议

`invoke` 里对 `target` 做 `method.invoke` 是正确转发。`proxy` 留给「还要拿当前代理实例」的场景，现在打日志用不到，不必为了用而用。不要改成 `invoke(proxy, args)`。

## 160. `UserService` 在 `afterPropertiesSet` 处已经是代理，无法强转怎么办？

对应第 152、156 条。出现位置：`DefaultBeanFactory.createBean` 第 136–138 行；`UserService.afterPropertiesSet` 第 62 行。

```java
Object initialize = initialize(instantiate);
if (AfterPropertiesSet.class.isAssignableFrom(initialize.getClass())) {
    initialize = ((AfterPropertiesSet) initialize).afterPropertiesSet(initialize);
}
```

```text
ClassCastException: com.sun.proxy.$Proxy10 cannot be cast to UserService
```

**结论：不要在代理上做初始化回调，也不要把代理当 `afterPropertiesSet` 的参数。** 先对原对象调用 `afterPropertiesSet`，再 `initialize` 换成代理。栈里方法已经进了真正的 `UserService.afterPropertiesSet`（handler 转到了 `target`），炸的是参数 `o`：外面传入的是 `$Proxy10`，里面却写成 `(UserService) o`。JDK 代理实现 `AfterPropertiesSet` 和 `UserInterface`，不是 `UserService` 的子类，这句强转过不了。

### 栈在说什么

```text
createBean 第 137 行
  ((AfterPropertiesSet) initialize).afterPropertiesSet(initialize)
      initialize 已经是 $Proxy10
  → LoggingProxyHandler.invoke(target=真正的 UserService, args=[proxy])
  → UserService.afterPropertiesSet(o)   // this 是 UserService，o 是 $Proxy10
  → (UserService) o                     // 失败
```

所以不是「代理上调不到 UserService 的方法」。方法已经在原对象上执行了。失败点是 **入参是代理，却按具体类来接**。

`AfterPropertiesSet.class.isAssignableFrom(initialize.getClass())` 为 true，是因为 `getInterfaces()` 含 `AfterPropertiesSet`，代理实现了这个接口。判断通过，不代表能转成 `UserService`。

### 和 Spring 的顺序

官方 `AbstractAutowireCapableBeanFactory` 大致是：

```text
populate
applyBeanPostProcessorsBeforeInitialization
invokeInitMethods          ← afterPropertiesSet，对象仍是原实例
applyBeanPostProcessorsAfterInitialization  ← 这里才可能换成代理
放进单例缓存的是最后这一步的返回值
```

初始化回调看见的 `this` 是 `UserService`。一级缓存里给别人用的才是代理。

现在把 `initialize()`（里面 `afterInitialization` 已经 `getProxy`）放在回调前面，等于让生命周期方法去消化 `$Proxy10`。

### 怎么办：对原对象回调，再换代理

`createBean` 里应改成：

```java
injectAutowiredFields(instantiate);
if (instantiate instanceof AfterPropertiesSet) {
    instantiate = ((AfterPropertiesSet) instantiate).afterPropertiesSet(instantiate);
}
Object exposed = initialize(instantiate);
addSingleton(beanName, exposed);
return exposed;
```

此时：

- `instanceof AfterPropertiesSet` 看的是真正的 `UserService`
- 传入 `afterPropertiesSet` 的是原对象，`(UserService) o` 成立
- `setName` 改的是即将放进 handler 的那同一个 `target`
- `initialize` 再包代理；`getName()` 从代理进来，先打日志，再调到已经加过前缀的 `target`

不要在 136–138 行把 `$Proxy10` 强转成 `UserService`。代理转不成具体类，这是 JDK 代理的类型模型，不是再写一层 `(UserService)` 能解决的。

### `afterPropertiesSet(Object o)` 这个形状本身别扭

Spring 的 `InitializingBean.afterPropertiesSet()` **没有参数**，改的是 `this`。你现在把对象再传进去，调用方一旦传错（传了代理），实现类就会去强转。

即便暂时不改接口，实现里也更稳妥用 `this`：

```java
@Override
public Object afterPropertiesSet(Object o) {
    String prefix = "(prefix:afterPropertiesSet-";
    setName(getName() == null ? prefix : prefix + getName());
    return this;
}
```

通过代理调用时，`this` 仍是 `target`（`method.invoke(target, args)`）。真正可靠的仍是 **在包代理之前调用**，和 Spring 一致。

`UserDao` 注入失败（第 156 条）和这次是同一条生命周期：先包代理，再当具体类用。`afterInitialization` 仍应按切点决定要不要套壳；`UserDao` 没有匹配就不要包。两处都改，`Phase4Test` 才能走完。

### 常见误区

| 想法 | 实际 |
|------|------|
| 代理无法调用 `afterPropertiesSet` | 能调，接口在代理上；炸的是参数强转 |
| 把 `initialize` 再转成 `UserService` | JDK 代理不是子类，转不成 |
| 回调里接收 `UserInterface` 就行 | 前缀逻辑在 `UserService` 上；关键是对原实例调用 |
| 只改 `UserService`、不改 `createBean` 顺序 | 以后别的回调仍可能拿到代理 |

### 最终建议

把 `afterPropertiesSet` 挪到 `initialize` 之前，对 `instantiate` 调用。缓存里仍然放代理。不要试图把 `$Proxy10` 转成 `UserService`。
