## 122. 接下来要做什么？

对应旧清单第 118 条（统一异常）。ReturnValueResolver 按用户要求停在当前形态：按 `method.getReturnType()` 区分 String 与 JSON，成功时写 200 和 Content-Type。

**结论：下一步只把异常收成一条出口，不要开 PathVariable，也不要拆 ReturnValueResolver。** 你已经让坏 JSON 能变成 400，但只接住了 `JsonProcessingException`，接在 `DispatcherServlet` 里，没有写正文，其它异常仍会变成 Tomcat 的 HTML 500。

### 现在实际怎样

`ArgumentResolver` / `ReturnValueResolver` 把 `JsonProcessingException` 继续向外抛。`Dispatcher.doService` 也声明抛出它。`DispatcherServlet` 里：

```java
} catch (JsonProcessingException e) {
    resp.setStatus(HttpStatus.WRONG_PARAM.value());
    resp.setContentType(httpResponse.contentType);
    return;
} catch (InvocationTargetException e) {
    throw new RuntimeException(e);
}
```

因此：

| 情况 | 现状 |
| --- | --- |
| 坏 JSON | 能到 400。`contentType` 多半还是 null，没有 body。`curl.exe` 不加 `-i` 看起来像没返回 |
| `IllegalArgumentException`（不支持的类型、缺 body、数字格式不对） | 没人接，容器 500 |
| Controller 里抛出的异常 | 被包成 `InvocationTargetException`，Servlet 再包成 `RuntimeException`，容器 HTML 500 |
| 404 / 405 | `Dispatcher` 已写 `status` 和 body，这条别动 |

`HttpStatus` 已有 `WRONG_PARAM(400)`，够用。

### 这一步只做

把翻译放进 `Dispatcher.doService`，包住 `handlerAdapter.handle(...)`。Servlet 删掉单独的 `JsonProcessingException` 分支，恢复成只写 `HttpResponse`。

解开包装后再分类：

```text
InvocationTargetException → 用 getTargetException()
RuntimeException 且有 cause → 用 cause
```

| 解开后 | status | body | contentType |
| --- | --- | --- | --- |
| `IllegalArgumentException` | 400 | 异常 message | `text/plain;charset=UTF-8` |
| `JsonProcessingException` | 400 | 短句，例如 `bad json` | 同上 |
| 其它 | 500 | `internal error` | 同上 |

不要把堆栈写进 body。404/405 仍走 `failStatus`，不要改成抛异常。启动时的「重复 URL」发生在 `init`，不要放进这个 catch。

参数解析器和返回值处理继续抛，不要在里面直接改 `httpResponse.status`。

### 验收

Tomcat 停在 `await()` 上：

```powershell
curl.exe -i -X POST http://localhost:8080/addUser -H "Content-Type: application/json" -d "{bad}"
curl.exe -i http://localhost:8080/hello
curl.exe -i http://localhost:8080/noSuch
```

坏 JSON 的第一行是 `HTTP/1.1 400`，正文是你写的短句，不是 `<!doctype html>`。`/hello` 仍是 200，`/noSuch` 仍是 404。

### 做完再往后

```text
异常出口（本步）
  → 类级 @RequestMapping 前缀
  → @PathVariable（只加 ArgumentResolver，不改 Adapter 的循环）
  → 启动从测试挪到 main
  → 再加固 IoC
```

### 最终建议

ReturnValueResolver 保持不动。下一步把 Servlet 里那个只设状态码的 catch 挪到 `Dispatcher`，补上正文，并接住参数错误和未预料异常，分别写成 400 和 500。

## 123. `throw e` 和 `throw new RuntimeException(e)` 有什么区别？

出现位置：`Dispatcher.doService` 里对同一个 `InvocationTargetException` 写了两段 catch：

```java
} catch (InvocationTargetException e) {
    throw e;
} catch (InvocationTargetException e) {
    throw new RuntimeException(e);
}
```

**结论：第一段是把原异常原样再抛出去；第二段是新做一个非受检异常，把原异常藏进 cause。** 这两段不能同时存在，第二段编译不过，因为同一种异常已经被上一支接住了。统一异常这一步两种 throw 都还不对：接住之后应写入 `HttpResponse`，而不是再抛。

### 两段分别做了什么

`throw e`：

```text
抛出的对象就是刚才抓住的那个 InvocationTargetException
类型不变，堆栈不变，没有多包一层
```

`throw new RuntimeException(e)`：

```text
新的对象，类型是 RuntimeException
e 变成它的 cause（getCause() 才能看到原来的 InvocationTargetException）
调用方若只 catch InvocationTargetException，接不住这层包装
```

`InvocationTargetException` 是受检异常。方法现在没有 `throws InvocationTargetException` 时，`throw e` 编译失败，必须在方法签名上声明，或者继续包成 `RuntimeException`。`throw new RuntimeException(e)` 不用声明，所以能编译。这是很多人包一层的原因，不是因为两种写法语义相同。

### 为什么第二段写不上去

catch 按书写顺序匹配，一种异常类型只会进第一支。编译器对第二支的判断是：这个异常已经在上面被抓住了，下面这段永远执行不到。必须删掉其中一段，不能两个都留着。

`IllegalAccessException`、`JsonProcessingException` 是另外的类型，可以各自有自己的 catch。和 `InvocationTargetException` 不冲突。

### 和 Servlet 里现有 catch 的关系

`DispatcherServlet` 现在有：

```java
catch (InvocationTargetException e) { throw new RuntimeException(e); }
catch (JsonProcessingException e) { resp.setStatus(400); return; }
```

| Dispatcher 里怎么抛 | Servlet 能接到什么 |
| --- | --- |
| `throw e`（仍是 InvocationTargetException） | 进 Servlet 的 `catch (InvocationTargetException)` |
| `throw new RuntimeException(e)` | Servlet 那个 `catch (InvocationTargetException)` **接不住**；若里面是 JSON 错误，`catch (JsonProcessingException)` 也接不住，因为最外层已经是 RuntimeException |
| `throw new RuntimeException(jsonException)` | 同样接不住 `JsonProcessingException`，400 分支不会走 |

所以在 Dispatcher 里再包一层，会把你刚写的 400 分支绕开，最后仍是 Tomcat 的 500 页。

### 这一步实际该写的

不要在 catch 里 `throw`。`method.invoke` 把 Controller 的异常放在 `InvocationTargetException.getTargetException()` 里。接住后取出那一层，按类型填响应：

```text
Throwable cause = e.getTargetException();
若 cause 是 IllegalArgumentException 或 JsonProcessingException → status 400
否则 → status 500
写上 contentType 和一句 body
```

`JsonProcessingException` 若是解析请求时直接抛出的（没有包进 InvocationTargetException），用它自己的 catch 填 400，同样不要 `throw new RuntimeException(e)`。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 两种 throw 一样，只是写法不同 | 抛出的对象类型不同，外层 catch 对得上的分支就不同 |
| `throw new RuntimeException(e)` 会丢掉原来的异常 | 不会丢，在 `getCause()` 里；但类型变了 |
| 两个 catch 写同一个类型可以分别做两件事 | 编译失败，第二支不可达 |
| 包成 RuntimeException 就算处理完了 | 只是换了个类型继续抛，客户端仍可能看到容器错误页 |

### 最终建议

删掉重复的那段 `catch (InvocationTargetException)`。不要 `throw e`，也不要 `throw new RuntimeException(e)`。用 `getTargetException()` 看真正的原因，把 400 或 500 写进 `httpResponse` 后正常返回。

## 124. 统一异常按讨论的方式写进 Dispatcher

用户要求按前面的方案把异常处理写出来。

**结论：异常不再向外抛。** `Dispatcher.doService` 接住 `handle` 的全部异常，解开 `InvocationTargetException` 后写入 `HttpResponse`。参数错误和 JSON 解析错误是 400，其它是 500。`DispatcherServlet` 删掉了单独的 `JsonProcessingException` 分支，只把已经填好的 status、contentType、body 写回。

### 写法

`catch` 只有一支，避免同一种异常写两次：

```java
try {
    handlerAdapter.handle(...);
} catch (Exception e) {
    writeError(httpResponse, unwrap(e));
}
```

`unwrap` 只剥 `InvocationTargetException`，因为 `method.invoke` 把 Controller 里的异常包在 `getTargetException()` 里。请求体解析抛出的 `JsonProcessingException`、`IllegalArgumentException` 没有这层包装，剥完仍是它们自己。

`writeError`：

| 解开后 | status | body |
| --- | --- | --- |
| `IllegalArgumentException` | 400 | `getMessage()`，没有则 `bad request` |
| `JsonProcessingException` | 400 | `bad json` |
| 其它，含 `IllegalAccessException` | 500 | `internal error` |

三种都写 `contentType = text/plain;charset=UTF-8`。不把堆栈放进 body。404/405 仍在 try 之前用 `failStatus` 返回，不进这个 catch。

`HttpStatus` 增加 `INTERNAL_ERROR(500)`。

Servlet 不再 `throw new RuntimeException`。status 或 contentType 为 null 时不调用对应的 setter，避免 404 没设 contentType 时传入 null。

### 怎么看

测试进程要重新跑过，停在 `await()` 上，再执行：

```powershell
curl.exe -i -X POST http://localhost:8080/addUser -H "Content-Type: application/json" -d "{bad}"
```

第一行应是 `HTTP/1.1 400`，正文是 `bad json`。`/hello` 仍是 200，未知地址仍是 404。

### 最终建议

异常出口就停在 `Dispatcher` 的这两个私有方法上。ArgumentResolver 继续抛，不要在解析时改 status。

## 125. `unwrap` 是解包装的意思吗？

**结论：是。** `unwrap` 不是 Java 关键字，是按英文意思起的方法名：wrap 是包起来，unwrap 是把包装拆开，取出里面那个真正的异常。

### 词

| 英文 | 这里的意思 |
| --- | --- |
| wrap | 在外面再套一层 |
| unwrap | 拆掉外面那层，拿出里面的对象 |

对应代码：

```java
while (cause instanceof InvocationTargetException) {
    cause = ((InvocationTargetException) cause).getTargetException();
}
```

`method.invoke` 不会把 Controller 里抛出的异常原样抛给你。它套一层 `InvocationTargetException`，真正的异常放在 `getTargetException()` 里。例如 Controller 抛了 `IllegalArgumentException`，`catch` 抓到的最外层是 `InvocationTargetException`。不拆开的话，`writeError` 对不上 `IllegalArgumentException`，就会一律写成 500。

循环是因为外面可能套了不止一层。拆到不再是 `InvocationTargetException` 就停，把里面的异常交给 `writeError`。

`JsonProcessingException` 若是解析请求时直接抛出的，本身没有这层包装，`unwrap` 原样返回它，随后写成 400。

### 最终建议

把 `unwrap` 理解成「拆掉 `InvocationTargetException` 这层皮」。它不处理 HTTP，也不决定 400 还是 500；那是后面 `writeError` 的事。

## 126. 异常出口写完之后，接下来要做什么？

**结论：下一步只做类级别的 `@RequestMapping` 路径前缀。** 异常出口可以停在现在的 `unwrap` + `writeError`。不要同时做 `@PathVariable`，也不要先把启动从测试挪到 `main`。

### 为什么是这一步

现在 `@RequestMapping` 的 `@Target` 只有 `ElementType.METHOD`。每个方法都要写完整路径：

```text
GET  /hello
GET  /getUser
POST /addUser
```

类上还不能写公共前缀。Spring MVC 里常见的是：

```java
@Controller
@RequestMapping("/user")
public class UserController {
    @RequestMapping(value = "/hello", requestMethod = RequestMethod.GET)
    public String hello() { ... }
}
```

注册时拼成 `GET /user/hello`。这是 HandlerMapping 注册阶段的字符串拼接，不改参数解析，也不改异常出口。做完后，`@PathVariable` 才有 `/user/{id}` 这种路径可挂。

### 这一步只做

1. `@RequestMapping` 的 `@Target` 加上 `ElementType.TYPE`，让它能标在类上。
2. `HandlerMappingImpl` 注册方法时：若类上有 `@RequestMapping`，把它的 `value` 和 方法上的 `value` 拼成最终 path。方法上的 `requestMethod` 仍是 HTTP 方法，类上的 method 第一版可以忽略。
3. 拼接规则要固定，避免双斜杠或丢掉斜杠。例如类 `"/user"`、方法 `"/hello"` → `"/user/hello"`；类没有注解时，方法路径保持原样，现有 `/hello`、`/getUser`、`/addUser` 行为不变。
4. 查重仍用拼完后的 `RequestMappingInfo(path, method)`。

先不要改 `UserController` 的现有三个 URL，除非你愿意连 curl 一起改。可以另加一个带类前缀的方法来验收，或者把三个路径改成类前缀加短路径，然后 curl 改打新地址。

### 验收

```text
类上没有 @RequestMapping 时，GET /hello 仍然是 hello world
类上是 /user、方法上是 /hello 时，GET /user/hello 命中，GET /hello 为 404
同 path + 同 method 仍在启动时失败
```

### 再往后

```text
类级路径前缀（本步）
  → @PathVariable，只新增一个 ArgumentResolver，不改 Adapter 里挑选 resolver 的方式
  → 启动代码从 PhraseTest4 挪到 main
  → 再回头加固 IoC
```

### 最终建议

异常处理先停住。下一步只让 `@RequestMapping` 能标在类上，注册时把类路径和方法路径拼起来。现有不带类前缀的接口保持能访问。

## 127. 这些是完善 MVC 的步骤吗？后面的思路是什么？

**结论：紧接着的几步仍是在完善 MVC，补的是「路由怎么写」。** 调度主链路已经有了：Tomcat 进来，Mapping 按 path + method 找到方法，Adapter 填参数并调用，ReturnValueResolver 写响应，Dispatcher 把异常写成 400/500，找不到则 404/405。后面不是再造一套 Dispatcher，而是让 URL 的写法更接近 Spring MVC，然后才离开 MVC，去补启动方式和 IoC。

### 已经稳定的 MVC 链路

```text
curl / 浏览器
  → Tomcat
  → DispatcherServlet（Servlet 请求转成 HttpRequest）
  → Dispatcher
       找不到 path        → 404
       path 在、method 不对 → 405
       找到 Handler
         → ArgumentResolver 填参数
         → invoke
         → ReturnValueResolver 写 body / contentType / 200
         → 抛异常则 unwrap 后写成 400 或 500
  → Servlet 把 HttpResponse 写回
```

这条链路可以停住，不要为了「像 Spring」再拆 Resolver，除非下一步的 PathVariable 需要新的参数来源。

### 还缺的 MVC 能力，按顺序

**1. 类级别路径前缀（下一步，只做这个）**

现在每个方法都要写完整路径。类上的 `@RequestMapping("/user")` 加上方法上的 `"/hello"`，注册时拼成 `/user/hello`。这是 Mapping 注册时的字符串拼接，不改异常，也不改参数绑定。类上没有注解时，现有 `/hello`、`/getUser`、`/addUser` 保持不变。

**2. 路径变量 `@PathVariable`**

前缀稳定之后再做 `/user/{id}`。这时路径不再是整段字符串相等，Mapping 要能匹配模板；`id` 从路径里取出来，交给参数解析，而不是从 query 里取。这是路由匹配和参数来源同时变一点，所以放在类前缀之后，单独做。验收时 Adapter 的挑选循环最好不动，只增加一种参数处理。

**3. 可以不做的语法糖**

`@GetMapping`、`@PostMapping` 只是 `@RequestMapping(method=GET/POST)` 的简写。有类前缀和 PathVariable 之后，MVC 的表达力已经够教学使用。组合注解可以以后再加，不占主线。

做到第 2 步，这个项目里的 MVC 就可以视为「小而完整」：能映射、能绑 query 和 JSON、能区分文本和 JSON 响应、能返回 200/400/404/405/500、能被 curl 访问、能写带前缀和路径变量的 URL。

下面这些属于 Spring MVC 的后半本，本项目不必为了完善而做：拦截器、视图解析、文件上传、内容协商、CORS、`@ExceptionHandler` 按 Controller 定制。默认异常出口已经有了。

### MVC 主线结束之后的思路

顺序不要和路由改良插在一起。

```text
MVC 路由补完（类前缀 → PathVariable）
  → 启动类
  → 加固 IoC
  → 工程化
```

**启动类。** 现在 Tomcat 启动写在 `PhraseTest4` 里，靠 `await()` 把测试挂住。这能用，但它是测试，不是程序入口。挪到 `main`：`refresh`、`dispatcher.init`、注册 Servlet、`start` 和 `await`。行为与测试相同，只是换地方。做完可以用 `java` 或 IDE 直接运行，而不是跑一个不会结束的单元测试。

**加固 IoC。** Web 已经在调用容器里的 Controller 和 Service。这时再修容器，问题会从真实请求里冒出来。优先这些，而不是新功能：

```text
BeanFactory 等接口边界，单例 Map 不要对外乱改
构造器注入、多个候选时的 @Primary / @Qualifier
初始化和销毁顺序
循环依赖里提前暴露的对象和最终代理是不是同一个
```

不要在做 PathVariable 的同时改注入。

**工程化。** 功能能跑之后再整理：demo 业务和框架分开、删掉重复类、日志代替 `System.out`、README 写清怎么启动和怎么 curl。这是给别人看的，不是 MVC 的下一步。

### 一条线看完

```text
现在位置：异常出口已有，URL 仍是方法上的完整路径

仍属 MVC：
  类前缀 → PathVariable

MVC 可以收口之后：
  main 启动 → IoC 正确性 → 模块和文档
```

每次只做其中一格。类前缀的完成标准是：类上 `/user`、方法上 `/hello` 时，`GET /user/hello` 命中，原来的 `/hello` 仍可用。

### 最终建议

是在完善 MVC，而且只剩路由的写法。先做类级别路径前缀，再做路径变量。这两步做完，MVC 主线就可以停。后面的思路不再加注解，而是把启动从测试里拿出来，然后回头把 IoC 做成和这条 Web 链路匹配的容器。

## 128. 怎样从 `user/getUser/12345` 里把 `12345` 解析出来？

出现位置：`PatternTest.test2`。

```java
String s = "user/getUser/12345";
Pattern p = Pattern.compile("user/getUser/.*?");
Matcher m = p.matcher(s);
while (m.find()) {
    System.out.println(m.group());
}
```

**结论：用圆括号做成捕获组，再用 `m.group(1)` 取组里的内容。** `m.group()` 不带参数时永远是整段匹配，不是你想单独拿的那一段。末尾的 `.*?` 又是非贪婪的，后面没有别的条件逼它继续吃字符，所以它可以匹配空串，`12345` 甚至不会进整段匹配。

### 为什么现在拿不到 12345

两层原因叠在一起。

**1. `group()` 是整段，不是其中一段。**

`Matcher.group()` 等于 `group(0)`，表示这次匹配到的全部文本。就算模式把 `12345` 吃进去了，打印出来的也是 `user/getUser/12345`。要单独拿到数字，必须用圆括号标出「这一截要留下来」，这叫捕获组。第 1 对圆括号是 `group(1)`，第 2 对是 `group(2)`。

**2. `.*?` 放在末尾会尽量匹配空。**

`.*` 是贪婪，尽量多吃。`.*?` 是非贪婪，尽量少吃。模式后面已经没有别的字符要求它必须再匹配下去，最少就是 0 个字符。于是 `find()` 成功时，整段往往只是 `user/getUser/`，`12345` 留在后面没被这次匹配用掉。

所以既不是「正则没写到 12345 的位置」，也不是 `find` 不会循环。是整段匹配里没有强制包含这段数字，而且没有一个组专门保存它。

### 怎么写

数字 id 用 `\\d+`（Java 字符串里一个反斜杠要写成两个）。圆括号把它收成第 1 组：

```java
String s = "user/getUser/12345";
Pattern p = Pattern.compile("user/getUser/(\\d+)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 12345
}
```

这里用 `matches()` 而不是 `find()`：`matches()` 要求整个字符串都符合模式。路径就这一条时，这比「在字符串里随便找一段」更合适。`\\d+` 是一位以上的数字，空串不行，所以 `12345` 一定被吃进第 1 组。

若 id 不只有数字，例如 `user/getUser/tom`，把数字改成「除了斜杠以外的一段」：

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

`[^/]+` 表示一个或多个不是 `/` 的字符。`group(1)` 仍是 `tom` 或 `12345`。

### 和模板 `user/getUser/{id}` 的关系

`test()` 里的字符串是模板 `user/getUser/{id}`，`test2` 里是真实路径 `user/getUser/12345`。解析 `12345` 时，正则是拿去套真实路径的，不是拿去套 `{id}` 那段模板。

以后做路径变量时，常见两步：

```text
模板 user/getUser/{id}
  → 编译成正则 user/getUser/([^/]+)
真实请求 user/getUser/12345
  → matcher.matches()
  → group(1) 得到 12345，对应名字 id
```

模板上的 `\\{[^{}]*\\}` 只能找出 `{id}` 这个占位符本身。它不负责从 `12345` 里取值。

### 常见误区

| 写法 | 结果 |
| --- | --- |
| `user/getUser/.*?` 然后 `group()` | 非贪婪末尾可以匹配空；`group()` 又是整段 |
| `user/getUser/(.*)` 然后 `group()` | 数字在组里，但 `group()` 仍打印整段；要用 `group(1)` |
| `user/getUser/(\\d+)` 写成 `\d` | Java 字符串里 `\d` 不是正则的 `\d`，要写 `\\d` |
| 用 `find()` 在整段路径上找 | 能找到，但路径匹配更适合 `matches()`，避免只命中中间一段 |

### 最终建议

真实路径用 `user/getUser/(\\d+)` 或 `user/getUser/([^/]+)`，`matches()` 成功后打印 `m.group(1)`。`group()` 只看整段匹配。模板 `{id}` 和取值用的正则是两套字符串，不要用 `.*?` 去扫 `12345`。

## 129. `user/getUser/([^/]+)` 怎么逐步读，尤其是 `[]`？

出现位置：`PatternTest.test2`。

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

Java 字符串交给正则引擎之后，模式就是：

```text
user/getUser/([^/]+)
```

**结论：从左到右先匹配字面量 `user/getUser/`，再匹配「一段不含斜杠的字符」，并用圆括号把这段收成 `group(1)`。** 方括号 `[]` 表示字符集合：集合里写的是「允许出现的一个字符」。`[^/]` 开头的 `^` 表示把集合反过来，于是是「不是斜杠的一个字符」。后面的 `+` 表示这个字符至少出现一次。

### 按片段拆

对字符串 `user/getUser/12345`：

| 片段 | 种类 | 匹配什么 |
| --- | --- | --- |
| `user/getUser/` | 普通字符 | 必须原样出现。这里的 `/` 不是特殊符号，不用写成 `\\/` |
| `(` `)` | 捕获组 | 不匹配字符，只把括号里匹配到的文本存为第 1 组 |
| `[^/]` | 字符集合，取反 | 恰好一个、并且不是 `/` 的字符 |
| `+` | 量词 | 紧挨着它左边的那一截，重复 1 次或更多 |

所以 `([^/]+)` 一起读成：捕获「一个或多个非斜杠字符」。对 `12345`，五个字符都不是 `/`，整段进入 `group(1)`。

若字符串是 `user/getUser/12345/extra`，`[^/]+` 会在下一个 `/` 前停下，`group(1)` 仍是 `12345`。`find()` 只要求能找到这一段；`matches()` 则要求后面不能再剩 `/extra`。

### `[]` 是什么

方括号划出一个字符集合。引擎每次只从输入里看 **一个字符**，问：这个字符在不在集合里？

```text
[abc]     a 或 b 或 c，三选一，只占一个字符的位置
[0-9]     0 到 9 里的一个。减号在集合内部表示范围
[a-zA-Z]  一个英文字母
```

它不是「把括号里的单词当一个整体」。`[abc]` 不会去匹配连续的 `abc` 三个字符，那是外面不加方括号的 `abc`。

集合里大部分符号失去特殊含义，变成普通字符。例如 `.` 在集合外是「任意一个字符」，在 `[.]` 里只是句点。`*`、`+`、`?` 放进 `[]` 里通常也只是星号、加号、问号这三个字符本身。

### `[^/]` 里的 `^` 和行首的 `^` 不是一回事

`^` 放在 `[]` **内部的第一个位置**，意思是「不在这个集合里」：

```text
[^/]      除了 / 以外的任意一个字符
[^0-9]    除了数字以外的任意一个字符
[^abc]    除了 a、b、c 以外的一个字符
```

`^` 放在整个模式的开头，意思才是「行首 / 字符串开头」：

```text
^user/getUser/([^/]+)
```

这是「必须从开头就是 user/getUser/...」。你现在的模式没有这个行首 `^`。不要把 `[^/]` 读成「以斜杠开头」。

`^` 如果不在集合的第一位，就只是一个普通的 `^` 字符。例如 `[a^b]` 是 a、b 或 `^`。

### `+` 管的是谁

量词只修饰紧挨着它左边的那一个单位。

```text
[^/]+
```

左边的单位是整个 `[^/]`，不是仅仅 `/`，也不是前面的 `user`。所以是「非斜杠字符」重复多次，不是「斜杠重复多次」。

| 量词 | 次数 |
| --- | --- |
| `+` | 1 次或更多。`12345` 可以，空字符串不行 |
| `*` | 0 次或更多。空字符串也能过 |
| `?` | 0 次或 1 次 |
| 不加量词 | 恰好 1 次。`[^/]` 只能吃掉 `1`，吃不完 `2345` |

圆括号在 `+` 的外面：`([^/]+)`。先让 `[^/]+` 尽量匹配完这一段，再把整段放进第 1 组。若写成 `([^/])+`，组里只会留下最后重复的那一个字符，例如 `5`。路径变量要的是整段 `12345`，所以 `+` 要放在方括号外面、圆括号里面。

### 和 `\\d+` 的差别

```text
(\\d+)     只收数字。12345 可以，tom 不行
([^/]+)    只要里面没有斜杠。12345、tom、a_b 都可以
```

`\\d` 是「数字」的简写，方括号写法是 `[0-9]`。你这条路径里 id 可能不是纯数字时，用 `[^/]+`。

### 常见误区

| 读法 | 实际 |
| --- | --- |
| `[]` 表示可选 | 可选是 `?`。`[]` 是字符集合 |
| `[^/]` 表示以 `/` 开头 | 集合内开头的 `^` 表示「除外」 |
| `[^/]+` 匹配斜杠本身 | 匹配的是斜杠以外的字符，斜杠会让这一段停住 |
| `[12345]` 匹配数字串 12345 | 只匹配其中一个字符：1 或 2 或 3 或 4 或 5 |
| `([^/])+` 和 `([^/]+)` 一样 | 前者 `group(1)` 只剩最后一个字符 |

### 最终建议

把 `([^/]+)` 读成三层：`[]` 规定一个字符的允许范围，`^` 把范围改成「不要斜杠」，`+` 让这样的字符连着出现，`()` 把连在一起的整段存进 `group(1)`。前面的 `user/getUser/` 只是必须原样出现的前缀。

## 130. `s.replaceFirst("\\{[^\\]+\\}", "123")` 为什么换不掉 `{id}`？

出现位置：`PatternTest.test3`。字符串是 `user/getUser/{id}`，接着：

```java
s.replaceFirst("\\{[^\\]+\\}", "123");
System.out.println(s);
```

注释写的是把字符串里的 `{id}` 替换掉。

**结论：有两处独立的问题。** `String` 不会被原地修改，`replaceFirst` 的结果必须接回去。另外这串正则在 Java 字符串里的反斜杠不合法或没有按「匹配花括号」来写，对不上 `{id}`。要换成 `123`，应写成 `s = s.replaceFirst("\\\\{[^{}]+\\\\}", "123")`。在 Markdown 里反斜杠会再折叠一层；放进 Java 源文件的字面量是 `"\\{[^{}]+\\}"`。

### 1. 返回值被丢掉了

`String` 是不可变的。`replaceFirst` 不改原来的 `s`，它返回一个新字符串。现在没有赋值，下一行 `println(s)` 打出来的仍是 `user/getUser/{id}`。

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
System.out.println(s); // user/getUser/123
```

### 2. 正则没有按 `{id}` 来写

目标是花括号里的名字：`{id}`。引擎要看到的模式是：

```text
\{[^{}]+\}
```

含义：

| 片段 | 含义 |
| --- | --- |
| `\{` | 一个普通的 `{`。花括号在正则里要转义 |
| `[^{}]+` | 一个或多个「既不是 `{` 也不是 `}`」的字符，所以能吃掉 `id` |
| `\}` | 一个普通的 `}` |

Java 字符串里每个正则反斜杠要再写一个，所以源码是：

```java
"\\{[^{}]+\\}"
```

源码里的 `\\{` 交给正则才是 `\{`。

现在这行源码 `"\\{[^\\]+\\}"` 有两个偏差：

- `[^\\]` 读成的是「不是反斜杠的一个字符」。集合在 `]` 处就结束了，后面的 `+` 才是量词。它不是「不是 `}`」。
- `\\}` 若能通过编译，表示的是正则里的 `\}`，但前面的集合已经提前结束，整段对 `{id}` 的结构和 `\\{[^{}]+\\}` 不一样。

`{` 前面写成 `\{` 而不写成 `\\{` 时，Java 字符串里 `\{` 还不是合法转义（合法的是 `\\`、`\n` 这类），这一行本身就可能编译失败。

### 和上面 `([^/]+)` 的差别

`([^/]+)` 是拿去套真实路径 `user/getUser/12345` 的，斜杠是分隔符。`{id}` 是模板上的占位符，分隔符是花括号，所以集合里要排除的是 `{` 和 `}`，写成 `[^{}]`，不是 `[^/]`。

`test3` 里先用 `user/getUser/([^/]+)` 去配 `user/getUser/{id}`，`{id}` 里没有斜杠，`group(1)` 会得到整段 `{id}`，包括花括号。这和 `replaceFirst` 想做的「把占位符换成 123」不是同一步。

### 最终建议

替换时接住返回值，模式用 `"\\{[^{}]+\\}"`，替换成 `"123"`。打印的才是 `user/getUser/123`。不要用 `[^/]` 或 `[^\\]` 去描述花括号占位符。

## 131. `"\\{[.*]\\}"` 为什么还是换不掉 `{id}`？

出现位置：`PatternTest.test3`，字符串仍是 `user/getUser/{id}`。

```java
s.replaceFirst("\\{[.*]\\}", "123");
System.out.println(s);
```

**结论：方括号里的 `.*` 不是「任意多个字符」。** 引擎看到的模式是 `\{[.*]\}`，意思是 `{`、然后恰好一个 `.` 或 `*`、然后 `}`。`{id}` 中间是字母 `i`，对不上，所以一次都不会替换。返回值仍然没有赋回 `s`，就算匹配上了，`println(s)` 也不会变。

### 这串正则实际在匹配什么

Java 字符串 `"\\{[.*]\\}"` 交给正则引擎之后是：

```text
\{[.*]\}
```

| 片段 | 实际含义 |
| --- | --- |
| `\{` | 一个普通的 `{` |
| `[.*]` | 恰好一个字符，这个字符只能是 `.` 或者 `*` |
| `\}` | 一个普通的 `}` |

`[]` 里面，`.` 不再是「任意字符」，`*` 不再是「重复多次」。它们都变成集合里的普通成员。所以 `[.*]` 等于「一个点，或一个星号」，只占一个字符的位置。

`{id}` 的三个字符是 `{`、`i`、`}`。中间的 `i` 既不是 `.` 也不是 `*`，整段失败。`replaceFirst` 找不到匹配，返回的新字符串和原来一样。

能匹配上的是 `{.}` 或 `{*}`，不是 `{id}`。

### 想表达「花括号里的一段」应该怎么写

量词要放在方括号外面。排除花括号本身：

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
```

引擎看到的是 `\{[^{}]+\}`：

```text
{  +  一个或多个「不是 { 也不是 }」的字符  +  }
```

`id` 符合中间这一段，所以 `{id}` 被换成 `123`，结果是 `user/getUser/123`。

`.*` 若真想当「任意字符、任意多次」，必须离开方括号：

```java
"\\{.*\\}"
```

这对只有一个 `{id}` 的字符串也能换成 `123`。它和 `[^{}]+` 的差别是：`.*` 会吃掉换行以外的任何字符，包括另一个 `}`。字符串里如果有两对花括号，贪婪的 `.*` 会从第一个 `{` 一直吃到最后一个 `}`。路径模板用 `[^{}]+` 更稳，一对花括号就停。

### 赋值仍然要做

`replaceFirst` 不修改原来的 `s`。上面正确的模式也要写成：

```java
s = s.replaceFirst("\\{[^{}]+\\}", "123");
System.out.println(s);
```

### 常见误区

| 写法 | 实际 |
| --- | --- |
| `[.*]` | 一个 `.` 或一个 `*`，不是任意长度 |
| `.*` 写在 `[]` 里面 | `.` 和 `*` 都失去特殊含义 |
| `\\{.*\\}` 配多对花括号 | 贪婪，可能一次吞掉后面的占位符 |
| 调用了 `replaceFirst` 就地改 `s` | 必须用返回值 |

### 最终建议

把 `[.*]` 读成「一个点或一个星号」。替换 `{id}` 用 `"\\{[^{}]+\\}"`，并且 `s = s.replaceFirst(...)`。

## 132. `"\\{.*\\}"` 已经能匹配 `{id}`，为什么打印还是原字符串？

出现位置：`PatternTest.test3`。

```java
s.replaceFirst("\\{.*\\}", "123");
System.out.println(s);
```

字符串是 `user/getUser/{id}`。

**结论：这版正则对得上 `{id}`。** 打印不变，是因为 `replaceFirst` 的返回值没有赋给 `s`。`String` 不会被原地改掉。

### 这版模式在说什么

`"\\{.*\\}"` 交给引擎是 `\{.*\}`：

| 片段 | 含义 |
| --- | --- |
| `\{` | 一个 `{` |
| `.*` | 任意多个字符（换行除外）。点在方括号外面，星号也在外面，所以恢复了「任意」和「重复」 |
| `\}` | 一个 `}` |

`{id}` 符合：`{` + `id` + `}`。`replaceFirst` 会造出一个新字符串 `user/getUser/123`，然后这个新字符串被丢掉了。下一行打印的仍是变量 `s` 里原来的 `user/getUser/{id}`。

接回去即可：

```java
s = s.replaceFirst("\\{.*\\}", "123");
System.out.println(s); // user/getUser/123
```

### 和 `[^{}]+` 的差别先知道即可

当前这个字符串里只有一对花括号，`.*` 和 `[^{}]+` 结果一样。以后模板里有两对，例如 `/user/{id}/order/{no}`，贪婪的 `.*` 会从第一个 `{` 一直吃到最后一个 `}`，一次替换掉中间整段。一对一对换时用 `"\\{[^{}]+\\}"`。

### 最终建议

这一行的模式不用再改就能换掉单个 `{id}`。加上 `s = ` 再打印。

## 133. `replaceFirst` 的替换结果里为什么没有留下 `\`？

出现位置：`PatternTest.test3`。

```java
String s = "user/getUser/{id}";
String s1 = s.replaceFirst("\\{.*\\}", "\\{.*\\}");
System.out.println(s);
System.out.println(s1);
```

注释希望 `{id}` 被换成 `\{.*\}`。

**结论：第一个参数里的 `\\` 是在写正则；第二个参数里的 `\\` 是替换语法里的转义，不会原样进入结果。** `s1` 里看到的是 `user/getUser/{.*}`，反斜杠被替换器吃掉了。`System.out.println(s)` 打的是原字符串，本来就不会变。

### 两个参数不是同一套规则

| 参数 | 谁来解释 `\` | `"\\{"` 实际表示 |
| --- | --- | --- |
| 第 1 个，要匹配的模式 | 正则 | 模式 `\{`，匹配一个 `{` |
| 第 2 个，替换成什么 | `Matcher` 的替换规则 | 一个 `{`。这里的 `\` 只表示「后面那个字符按字面输出」 |

Java 字符串先处理一层：源码 `"\\{.*\\}"` 在两个参数里，变成内存中的同样 6 个字符 `\{.*\}`。后面分道：

模式侧：`\{` 匹配 `{`，`.*` 匹配 `id`，`\}` 匹配 `}`。所以 `{id}` 能被找到。

替换侧只认两个特殊字符：`\` 和 `$`。`$1` 表示第 1 个捕获组。`\` 表示「下一个字符不要当特殊符号，就输出那个字符」。于是：

```text
\{    →  输出 {
.*    →  输出 .*
\}    →  输出 }
```

`s1` 就是 `user/getUser/{.*}`。反斜杠完成了转义任务，自己不留下。

### 想在结果里看见反斜杠

替换文本里要出现一个 `\`，替换串里得写两个 `\\`（表示「输出一个反斜杠」）。Java 源码再把每个 `\` 写成 `\\`，所以一个想留下的反斜杠在源码里是四个 `\`。

目标结果 `user/getUser/\{.*\}`：

```java
String s1 = s.replaceFirst("\\{.*\\}", "\\\\{.*\\\\}");
```

源码 `"\\\\{.*\\\\}"` 经过 Java 字符串后，替换器看到的是 `\\{.*\\}`。替换器再把每一对 `\\` 打成一个 `\`，得到 `\{.*\}`。

也可以避免手写这么多层，让 API 按字面替换：

```java
String s1 = s.replaceFirst("\\{.*\\}", Matcher.quoteReplacement("\\{.*\\}"));
```

`quoteReplacement` 会把替换串里的 `\` 和 `$` 都变成字面量。这里传入的 Java 字符串 `"\\{.*\\}"` 内容已经是 `\{.*\}`，引用之后结果里就会保留这些反斜杠。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 两个参数都写 `"\\{"`，结果里就有 `\` | 模式用 `\` 表示转义；替换串也用 `\` 表示转义，转义完只留下后面的字符 |
| `println(s)` 能看到替换结果 | `s` 没被赋值，要看 `s1` |
| 替换串里的 `.*` 还会按正则再匹配一次 | 不会。替换串不是正则，`.` 和 `*` 就是这两个字符 |

### 最终建议

匹配 `{id}` 继续用第一个参数 `"\\{.*\\}"`。若结果里要保留反斜杠，第二个参数写成 `"\\\\{.*\\\\}"`，或用 `Matcher.quoteReplacement`。看结果打印 `s1`。

## 134. 怎样从 `user/getUser/123` 里提取 `123`？当前模式为什么不行？

出现位置：`PatternTest.test4`。

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/\\{.*\\}");
Matcher m = p.matcher(s);
while (m.find()) {
    destinationString = m.group(1);
}
```

**结论：这个模式在找花括号，字符串里没有 `{` `}`，`find()` 一次都不会成功。** 要提取 `123`，模式末尾改成捕获组 `(\\d+)` 或 `([^/]+)`，再用 `group(1)`。`\\{.*\\}` 是拿去匹配模板 `user/getUser/{id}` 的，不是拿去匹配真实路径的。

### 现在这行在找什么

`"user/getUser/\\{.*\\}"` 交给引擎是：

```text
user/getUser/\{.*\}
```

`\{` 和 `\}` 是普通花括号。整段要求字面量 `user/getUser/` 后面跟着 `{`、若干字符、`}`。`user/getUser/123` 在斜杠后面是数字，没有花括号，匹配失败。`while` 不进入，`group(1)` 不会执行。

即便把字符串改成 `user/getUser/{id}` 让它匹配上，这个模式里也没有圆括号。`group(1)` 会抛 `IndexOutOfBoundsException`，因为第 1 组不存在。`group()` 或 `group(0)` 才是整段匹配。

### 提取 123 的写法

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/(\\d+)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 123
}
```

`(\\d+)` 是第 1 个捕获组，`group(1)` 才是 `123`。`\\d+` 只收数字。若这一段不一定是数字：

```java
Pattern p = Pattern.compile("user/getUser/([^/]+)");
```

`group(1)` 仍是 `123`。

### 两套字符串不要混用

| 字符串 | 用什么模式 | 得到什么 |
| --- | --- | --- |
| 模板 `user/getUser/{id}` | `\\{.*\\}` 或 `\\{[^{}]+\\}` | 找到占位符 `{id}` |
| 真实路径 `user/getUser/123` | `user/getUser/(\\d+)` | `group(1)` 为 `123` |

模板负责说明「这里有一个参数」，真实路径负责提供 `123`。用找花括号的模式去扫 `123`，对不上。

### 最终建议

`test4` 的模式改成 `user/getUser/(\\d+)`，`matches()` 成功后打印 `m.group(1)`。`\\{.*\\}` 留在处理 `{id}` 模板的那一步。

## 135. `user/getUser/.*` 配上 `group(1)` 为什么拿不到 `123`？

出现位置：`PatternTest.test4`。

```java
String s = "user/getUser/123";
Pattern p = Pattern.compile("user/getUser/.*");
Matcher m = p.matcher(s);
while (m.find()) {
    destinationString = m.group(1);
}
```

**结论：`.*` 已经能匹配 `123`，但它属于整段匹配 `group(0)`，不是第 1 组。** 模式里没有圆括号，`group(1)` 会抛 `IndexOutOfBoundsException`。要单独取出 `123`，把 `.*` 放进括号：`user/getUser/(.*)`，然后用 `group(1)`。

### 这次和花括号那版的差别

`user/getUser/\\{.*\\}` 要求斜杠后面是 `{...}`，对 `123` 匹配失败，循环进不去。

`user/getUser/.*` 里的 `.*` 是「任意字符，零次或多次」，`123` 符合。`find()` 能成功，整段是 `user/getUser/123`。成功之后去调 `group(1)` 才出错：组号从 1 开始，对应第几对圆括号。没有括号就没有第 1 组。`group()` 或 `group(0)` 才是整段，里面夹着前缀，不是单独的 `123`。

### 要提取就加括号

```java
Pattern p = Pattern.compile("user/getUser/(.*)");
Matcher m = p.matcher(s);
if (m.matches()) {
    System.out.println(m.group(1)); // 123
}
```

括号不匹配额外字符，只把 `.*` 吃到的 `123` 存起来。

`.*` 会吃掉斜杠。路径若是 `user/getUser/123/extra`，`group(1)` 会是 `123/extra`。只要最后一段时，用 `([^/]+)` 或只要数字时用 `(\\d+)`：

```java
Pattern.compile("user/getUser/([^/]+)")
```

### 最终建议

`.*` 外面加上圆括号再 `group(1)`。没有括号时不要调用 `group(1)`。只取一个路径段时，把 `.*` 换成 `[^/]+`。

## 136. 怎样匹配字符串里的 `{}`，并且花括号里必须是字母？

出现位置：`PatternTest.test5`。现在的模式是：

```java
Pattern.compile("user/getUser/\\{[^{}]*\\}")
```

字符串是 `user/getUser/{id}`。

**结论：把 `[^{}]*` 换成 `[a-zA-Z]+`。** `[^{}]*` 的意思是「不是花括号的任意字符，可以一个都没有」，所以 `{id}`、`{123}`、`{}` 都能过。字母用 `[a-zA-Z]`，至少要有一个字母就用 `+`，不要用 `*`。

### 现在这版实际允许什么

`\\{[^{}]*\\}` 交给引擎是 `\{[^{}]*\}`：

| 片段 | 含义 |
| --- | --- |
| `\{` `\}` | 一对普通花括号 |
| `[^{}]` | 一个既不是 `{` 也不是 `}` 的字符 |
| `*` | 这种字符可以出现 0 次或更多 |

因此 `{id}`、`{123}`、`{a_b}`、空的 `{}` 都匹配。它只保证括号里面不再嵌一套花括号，不保证是字母。

### 只要英文字母

```java
Pattern p = Pattern.compile("\\{[a-zA-Z]+\\}");
Matcher m = p.matcher(s);
if (m.find()) {
    System.out.println(m.group()); // {id}
}
```

`[a-zA-Z]` 是一个大小写英文字母。`+` 是至少 1 次，所以 `{}` 失败，`{id}` 成功，`{id1}` 失败（里面有数字），`{a_b}` 失败（里面有下划线）。

还要前缀时：

```java
Pattern.compile("user/getUser/\\{[a-zA-Z]+\\}")
```

只要括号里面的名字，再加一层圆括号：

```java
Pattern p = Pattern.compile("\\{([a-zA-Z]+)\\}");
if (m.find()) {
    System.out.println(m.group(1)); // id
}
```

`find()` 表示字符串里出现即可，不必整段都是花括号。`matches()` 则要求整个 `s` 都符合模式；`user/getUser/{id}` 整段匹配时，模式里必须带上前面的 `user/getUser/`。

### 和相近写法的差别

| 写法 | `{id}` | `{}` | `{123}` | `{id1}` |
| --- | --- | --- | --- | --- |
| `\\{[^{}]*\\}` | 能 | 能 | 能 | 能 |
| `\\{[a-zA-Z]*\\}` | 能 | 能（`*` 允许空） | 不能 | 不能 |
| `\\{[a-zA-Z]+\\}` | 能 | 不能 | 不能 | 不能 |

「必须是字母」用最后一行。

若字母包括中文这类 Unicode 字母，把 `[a-zA-Z]` 换成 `\\p{L}`：`\\{\\p{L}+\\}`。`{id}` 仍然匹配。路径变量名一般是英文，用 `[a-zA-Z]+` 即可。

### 最终建议

判断有没有「花括号里全是英文字母」，用 `"\\{[a-zA-Z]+\\}"` 再 `find()`。要拿出里面的 `id`，写成 `"\\{([a-zA-Z]+)\\}"`，读 `group(1)`。不要继续用 `[^{}]*`，那不是字母限制。

## 137. `while (m.find())` 为什么要加 while？

出现位置：`PatternTest.test5`。

```java
Pattern p = Pattern.compile(".*\\{[a-zA-Z]*\\}.*");
Matcher m = p.matcher(s);
while (m.find()) {
    System.out.println(m.group());
}
```

字符串是 `user/getUser/{id}`。

**结论：`while` 不是 `find()` 的语法要求。** `find()` 每次只找下一处匹配，找到返回 true，找不到返回 false。`while` 表示「有多少处就处理多少处」。只判断有没有一对花括号时，写成 `if (m.find())` 就够。你现在的模式前后都有 `.*`，整段字符串最多成功一次，循环体也只会进一次。

### `find()` 做一次什么

`Matcher` 内部记着上次找到的位置。第一次 `find()` 从开头找。找到就把这次匹配的范围记下来，`group()` 能读到这段文本，并返回 true。再调用 `find()` 时，从上一次匹配结束的后面继续找，不再从头找。后面没有了就返回 false，循环结束。

所以：

```text
if (m.find())     只关心有没有至少一处
while (m.find())  把每一处都走一遍
```

没有 `while` 也可以写 `if`。不调用 `find()`，`group()` 没有当前匹配，不能拿结果。

### 你这段循环实际只会进一次

模式是 `.*\\{[a-zA-Z]*\\}.*`。开头和结尾的 `.*` 会把 `{id}` 前后的字符都吃掉，一次匹配就是整个 `user/getUser/{id}`。匹配结束的位置已经是字符串末尾，下一次 `find()` 为 false。`while` 和 `if` 在这个模式上效果一样：打印一次整段字符串。

若模式收成只匹配花括号本身：

```java
Pattern p = Pattern.compile("\\{[a-zA-Z]+\\}");
```

字符串里有两处时，`while` 才看得出差别：

```text
/user/{id}/order/{name}
第 1 次 find：{id}
第 2 次 find：{name}
第 3 次 find：false，结束
```

用 `if` 就只会看到 `{id}`。

### 最终建议

只判断「有没有」时写成 `if (m.find())`。要把每一对 `{名字}` 都打出来时再用 `while`，并且模式不要用前后的 `.*` 把整段一次吃完，否则循环没有第二次机会。

## 138. 从 Map 里取值时，为什么进不了 `RequestMappingInfo.equals`？

出现位置：`RequestMappingInfo.equals`，调用点是 `HandlerMappingImpl` 里的 `requestMappingInfoMap.get(requestMappingInfo)`。`hashCode` 仍是 `Objects.hash(path, method)`。`equals` 里又用 `regexPath` 对另一个对象的 `path` 做正则。

**结论：`HashMap.get` 先用 `hashCode` 选桶，桶里对不上才不会调用 `equals`。** 请求路径是 `user/getUser/123`，表里的 key 是模板 `user/getUser/{id}` 时，两边的 `path` 不同，`hashCode` 就不同，查找停在选桶，断点打在 `equals` 上不会进来。另外，若拿去 `get` 的就是当初 `put` 进去的同一个对象，`==` 已经成立，`HashMap` 也不会再调 `equals`。

### `get` 实际做了什么

`HashMap` 不是遍历所有 key 调 `equals`。简化后的查找是：

```text
1. h = key.hashCode()，映射到某个桶
2. 看这个桶里已有的 key：
     先比 hash 是否相等
     再看是不是同一个引用（==）
     都不是，才调用 key.equals(...)
3. 桶是空的，或者这条链上没有 hash 相同的 key：直接返回 null
```

所以「进不了 equals」通常是第 1 步就走散了，不是 `equals` 写错了没被调试器看见。

你现在的 `hashCode` 只含 `path` 和 `method`，不含 `regexPath`：

```java
return Objects.hash(path, method);
```

注册时放进 Map 的 `path` 是模板，例如 `user/getUser/{id}`。请求进来时新建的 `RequestMappingInfo.path` 是 `user/getUser/123`。两个字符串不相等，`hashCode` 几乎一定不同，它们不在同一个桶里。`equals` 里的正则根本没有机会跑。

可以在 `hashCode` 里打断点，看两次调用的 `path` 是不是一个模板、一个真实路径。

### 同一个对象取值也不会进 equals

`HashMap` 的比较大致是：

```text
已有key == 传入key    或者    已有key.equals(传入key)
```

`==` 为 true 时，短路，不再调用 `equals`。用 `put` 时的那个实例再 `get`，调试器停在 `equals` 上也进不去。这不表示相等判断失败。要观察 `equals`，必须 `new` 另一个 `RequestMappingInfo`，并且它的 `hashCode` 得和表里的 key 相同。

### 正则不能写进 HashMap 的 equals

就算强行让 `equals` 被调用，这套写法也违反 `hashCode` / `equals` 的约定：

```text
若 a.equals(b) 为 true，则 a.hashCode() 必须等于 b.hashCode()
```

模板对象和 `user/getUser/123` 若靠正则算成相等，它们的 `hashCode` 仍然按不同的 `path` 计算，结果不相等。`HashMap` 允许这种 key，但 `get` 找不到。`HashMap` 适合「path + method 完全相同」这种精确 key。`/user/{id}` 对 `/user/123` 这种一对多的匹配，要自己遍历 `keySet()`，对每个模板做 `matcher.matches()`，不要指望 `map.get`。

`getHandlerMethodForPath` 里已经有一层 `for` 循环，但循环内部又 `requestMappingInfoMap.get(loop)`。那里的 `get` 用的是表里原有的 key 自己去查自己，`==` 成立，同样不会为了正则去跑你新写的 `equals`。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 重写了 `equals`，`get` 就一定会进来 | 先过 `hashCode` 选桶 |
| 断点不进就是 `equals` 返回了 false | 没被调用和返回 false 不是一回事 |
| 把正则放进 `equals` 就能匹配路径变量 | `hashCode` 仍按模板字符串算，桶对不上 |
| `hashCode` 也改成算正则就能修好 | 正则匹配不是稳定的哈希。查找时应遍历模板 |

### 最终建议

精确路径继续用现在的 `hashCode` 和 `map.get`。带 `{id}` 的模板不要放进 `equals` 里用正则比较。`get` 返回 null 时，再遍历 `requestMappingInfoMap.keySet()`，用每个 key 的 `regexPath` 去匹配请求的 `path`。调试「为什么没进 equals」时，先看两次 `hashCode` 的 `path` 是否相同。

## 139. 路径变量也写好了，怎么样？接下来呢？

**结论：一个路径变量的主路径已经接上，类前缀也一起做了。** `GET /user/getUserByPath/123` 这种请求可以命中 `getUserWithPath`，并把 `123` 转成 `Long`。精确路径仍走 `map.get`，模板不走 `equals`。可以停在这一版。下一步把 Tomcat 启动从 `PhraseTest4` 挪到 `main`，不要再加第二种路径变量。

wholeUrl.replaceFirst("\\{.*\\}", "(.*)")

`ArgumentResolver` 里还有 `System.out.println(destinationString)`，验证完可以去掉。

一个 `{id}` 加类前缀可以算写好了。精确匹配和模板匹配分开，这个方向是对的。下一步只把内嵌 Tomcat 的启动挪到 `main`。

## 140. 启动类接下来怎么写？

**结论：把 `PhraseTest4.testWithCurl` 里的启动顺序原样挪到 `src/main/java` 的一个 `main` 方法里。** 不要改 Mapping、Resolver 和异常。测试方法可以留着，但不要再靠它挂住进程。

### 写在哪

放在 `minispring-web` 的 **main** 源码，不要放在 `src/test/java`。测试里的 `main` 也能点运行，但那仍然是测试 classpath 上的类。建议：

```text
minispring-web/src/main/java/com/minispring2/web/MiniSpringApplication.java
```

类上只有 `public static void main(String[] args)`。IDEA 里对这个方法点运行。

### 方法里按这个顺序写

和现在的测试相同，一行都不要改语义：

```java
public class MiniSpringApplication {
    public static void main(String[] args) throws Exception {
        MiniApplicationContext miniApplicationContext = new MiniApplicationContext();
        miniApplicationContext.basicPackages = new String[]{
                "com.minispring2.demo", "com.minispring2.core", "com.minispring2.web"
        };
        miniApplicationContext.refresh();

        Dispatcher dispatcher = new Dispatcher();
        dispatcher.init(miniApplicationContext.defaultBeanFactory);

        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8080);
        tomcat.getConnector();

        Context context = tomcat.addContext("", new File(".").getAbsolutePath());
        DispatcherServlet dispatcherServlet = new DispatcherServlet(dispatcher);
        Tomcat.addServlet(context, "dispatcherServlet", dispatcherServlet);
        context.addServletMappingDecoded("/*", "dispatcherServlet");

        tomcat.start();
        tomcat.getServer().await();
    }
}
```

四段各自的作用：

| 顺序 | 代码 | 作用 |
| --- | --- | --- |
| 1 | `refresh()` | 扫包、创建 Bean。`Dispatcher` 要用这里的 `defaultBeanFactory` |
| 2 | `dispatcher.init(...)` | 注册 Controller 映射。必须在把 Servlet 交给 Tomcat 之前做完 |
| 3 | `new DispatcherServlet(dispatcher)` 再 `Tomcat.addServlet` | 把已经 init 好的 Dispatcher 传进 Servlet。不要在 `service()` 里再 `new Dispatcher` |
| 4 | `getConnector()`、`start()`、`await()` | 创建 8080 连接器、启动、阻塞主线程。没有 `await()`，`main` 结束进程就退出 |

`throws Exception` 交给 `main` 即可，不用在 `main` 里把异常翻译成 400。那是请求进来之后 `Dispatcher` 的事。

### 跑起来之后怎么验

先停掉还挂在 `PhraseTest4` 上的旧进程，否则 8080 会被占用。然后运行 `main`，另开终端：

```powershell
curl.exe -i http://localhost:8080/user/hello
curl.exe -i "http://localhost:8080/user/getUser?userId=12345"
curl.exe -i http://localhost:8080/user/getUserByPath/123
curl.exe -i -X POST http://localhost:8080/user/addUser -H "Content-Type: application/json" -d "{\"name\":\"Jerry\",\"age\":19}"
```

### 这一步不要写的

## 141. `main` 写好之后，然后呢？

`MiniSpringApplication` 已经在 `minispring-web/src/main/java/com/minispring2/web/MiniSpringApplication.java`，内容就是 `PhraseTest4` 的启动顺序。MVC 主线可以停。

**结论：先用 curl 确认这个 `main` 能起来，然后回到 IoC。** 下一件只做「框架代码不要再依赖 demo 包」：把 `BeanDefinition`（以及它旁边的 `RuntimeBeanReference`）从 `com.minispring2.demo.model` 挪到 core 自己的包。不要在这一步写构造器注入，也不要改 MVC。

### 先确认启动类

停掉还挂在测试上的进程，运行 `MiniSpringApplication.main`，再执行：

```powershell
curl.exe -i http://localhost:8080/user/hello
```

看到 `hello world` 和 200，入口就算换完。没看到就先修启动，不要开始改容器。

### 为什么下一刀切在 BeanDefinition

`DefaultBeanFactory` 和 `Scan` 现在 import 的是：

```text
com.minispring2.demo.model.BeanDefinition
com.minispring2.demo.model.RuntimeBeanReference
```

`BeanDefinition` 是容器的元数据，不是用户业务。它放在 `demo.model` 里，等于框架依赖演示代码。包一挪，core 可以不再认识 `User`、`UserDao` 那一层。这是加固 IoC 里最小、也最该先做的一步。

做法：

1. 把 `BeanDefinition`、`RuntimeBeanReference` 移到 `com.minispring2.core`（或 `com.minispring2.core.model`）。
2. 改 `DefaultBeanFactory`、`Scan` 和 core 测试里的 import。
3. 编译、跑原来的 Phase 测试，再跑一次 `main`，`/user/hello` 仍然是 `hello world`。

行为不变。变的只是类放在哪。

### 这之后的 IoC 顺序

一次只做一件：

```text
1. BeanDefinition 移出 demo（本步）
2. singletonBeanMap 不要再 public，外面只通过 getBean 拿
3. 构造器注入（现在只有字段上的 @Autowired）
4. 多个同类型 Bean 时的 @Primary
5. 初始化 / 销毁，以及循环依赖里提前拿到的对象和最终对象是不是同一个
```

MVC 的 `(.*)`、405、第二个路径变量都先放着。

### 最终建议

`main` 用 curl 验过之后，只把 `BeanDefinition` 和 `RuntimeBeanReference` 挪出 `demo.model`。测试和 `/user/hello` 保持原样，再谈注入方式。
