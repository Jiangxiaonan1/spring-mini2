## 1. `UserController.class.newInstance()` 和 `UserController.getClass().newInstance()` 一样吗？

**结论：不一样。** 前者合法；后者若 `UserController` 是类名，编译失败。

**出现位置：** `minispring-web/src/test/java/PhraseTest1.java`（给 `com.minispring2.web.core.HandlerMethod.object` 赋控制器实例时）。

### 对照

| 写法 | 前提 | 结果 |
|------|------|------|
| `UserController.class.newInstance()` | 类名 | 一定是 `new UserController()` |
| `UserController.getClass().newInstance()` | `UserController` 当类名 | **编译失败**：`getClass()` 是实例方法，不能用类名调用 |
| `controller.getClass().newInstance()` | `controller` 是实例 | 按**运行时类型**再 new，可能是子类 |

### 原因

- `.class`：写在**类型名**后面的类字面量，得到 `Class<UserController>`。
- `getClass()`：`Object` 的**实例方法**，必须先有对象：`某个对象.getClass()`。

### 正确写法

```java
handlerMethod.object = UserController.class.newInstance();
// 更推荐（newInstance 已过时）
handlerMethod.object = UserController.class.getDeclaredConstructor().newInstance();
```

### 相关易错写法

| 写法 | 结果 |
|------|------|
| `UserController.class` | `Class<UserController>`，对 |
| `UserController.class.newInstance()` | `new UserController()`，对 |
| `UserController.class.getClass()` | 得到 `Class.class`（`java.lang.Class` 这个类），错 |
| `UserController.class.getClass().newInstance()` | 试图 `new Class()`，运行失败 |
| `UserController.class.class` | **编译错误**：`.class` 不能跟在表达式后面 |

记法：要 `Class` 对象时，**有实例用 `getClass()`，只有类型名用 `.class`。**

## 2. `@Retention(RetentionPolicy.RUNTIME)` 里的 RetentionPolicy 是什么？

**结论：** 注解的**保留策略**：这条注解要活到源码、class 文件，还是运行时。

| 策略 | 源码 | `.class` | 运行时反射能读到 |
|------|:----:|:--------:|:----------------:|
| `SOURCE` | 是 | 否 | 否 |
| `CLASS`（默认） | 是 | 是 | 否 |
| `RUNTIME` | 是 | 是 | 是 |

扫 `@Controller` 必须用 `RUNTIME`，否则 `isAnnotationPresent` 永远是 false。  
`@Target` 管注解能标在哪，`@Retention` 管能活到何时。

---

## 3. Policy 不是保单吗？为什么不叫 Strategy？

**结论：** 这里的 policy = 规定 / 策略，不是保险单。`RetentionPolicy` 宜译为**保留策略**。

- `strategy`：可替换的算法（策略模式）。
- `policy`：事先定好的规则、档位（SOURCE / CLASS / RUNTIME）。

「文件保留多久」英语就叫 retention policy，不是 retention strategy。

---

## 4. 有包名的类为什么用不了默认包里的 `@Controller`？

**结论：** Java **禁止命名包引用未命名包（默认包）**里的类型。

- `Controller.java` 没写 `package` → 默认包。
- `UserController` 在 `package controller` → 写不出 `import`，也不能直接用。

规则认的是 `package` 声明，不是「是不是源码根目录」。  
给注解加上包名（如 `com.minispring2.web.annotation`）再 import。  
JLS §7.4.2：不能 import 未命名包中的类型。

## 5. `@Controller` 要接入 IoC 才能被扫描到吗？

**结论：** 扫描 ≠ IoC。不用容器也能扫注解再 `new`，但 Controller 一旦要注入就走死。

正确目标：`@Controller` 先当 Bean，Dispatcher 再从容器取实例建映射。  
最小闭环：扫包 → `addBeanDefinition` → `getBean` → Dispatcher 收集 Handler。  
注意：`minispring-web` 依赖 core；core 不要再依赖 web（避免循环）。`@Controller` 宜放在 core，或 core 只扫 `@Component`。

## 6. `ClassLoader.getResource` / `getResources` 是什么？

**结论：** 按 **classpath 相对路径**定位资源，不是磁盘路径。

```java
String path = packageName.replace('.', '/');  // 不要用 replaceAll(".", "/")，`.` 是正则
URL url = classLoader.getResource(path);
Enumeration<URL> urls = classLoader.getResources(path);
```

- `getResource`：第一处，返回一个 `URL` 或 null。
- `getResources`：所有 jar / 模块里的同名路径。
- `ClassLoader` 版路径**不要**前导 `/`。
- URL 只告诉「包在哪」，列 `.class` 还要按 `file:` / `jar:` 分别处理。

---

## 7. `URL url = resources.nextElement()` 这个 URL 是什么？

**结论：** 该包在 classpath 上的一个位置。

- IDE：`file:/.../target/classes/controller`
- 打成 jar：`jar:file:/.../xxx.jar!/controller`

`url.getProtocol()` 判断 `file` 还是 `jar`，再列目录或打开 jar。

---

## 8. `url.toURI()` 是什么？`new File(url.toURI())` 会新建文件吗？

**结论：** `toURI()` 把 `URL` 转成 `URI`。`new File(uri)` **只包装路径，不在磁盘上创建文件**。

`File` 是抽象路径名。`listFiles()` / `exists()` 不创建；`mkdirs()` / `createNewFile()` 才会。  
`getPath()` 可能带 `%20`，`toURI()` 解码更稳。仅 `file:` 协议可这样转 `File`；`jar:` 不行。

---

## 9. `classLoader.loadClass(className)`？A 的加载器能加载 B 吗？

**结论：** 加载器不是万能的；只能加载自己（及父加载器）看得到的类。

- `className` 必须是二进制名：`controller.UserController`，不能是磁盘路径。
- 同一应用 classpath 上的 A、B 通常共享 AppClassLoader，可以互相 `loadClass`。
- Bootstrap（如 `String`）加载不了业务类；不同 WebApp / 自定义加载器默认隔离。
- 扫描用 `Thread.currentThread().getContextClassLoader()` 或 `Scan.class.getClassLoader()`。

## 17. `git rm -r --cached .idea` 是什么？执行完然后呢？

**结论：** 从 Git 索引里拿掉 `.idea`，**不删本地文件**。

| 部分 | 含义 |
|------|------|
| `git rm` | 从 Git 移除已跟踪路径 |
| `-r` | 递归目录 |

## 18. `@RequestMapping` 里写 `String value();` 对吗？

**结论：作为迷你 MVC 的第一版，这样写是对的。**

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestMapping {
    String value();
}
```

- 属性名叫 `value`：可以用 `@RequestMapping("/hello")`，不必写 `value = "/hello"`。
- 没有 `default`：路径必填，漏写编译失败，教学上更清楚。
- `RUNTIME`：启动时才能读到。
- 只标 `METHOD`：第一版够用；官方还允许标在类上当路径前缀。

官方是 `String[] value() default {}`（多路径、可省略）。现在不必照搬。

注意：`com.minispring2.web.core.HandlerMethod` 是映射条目类，和这个**注解同名**。Dispatcher 里容易 import 错。条目类更宜改名为 `HandlerMethod`。

## 19. 注解属性为什么要写成 `String value()`，带括号？

**结论：** 注解的「属性」在语法上是**无参方法**，不是字段。规范就要求写成 `类型 名字();`。

- 定义：`String value();`（像接口方法）
- 使用：`@RequestMapping("/hello")`（赋值，不是调用）
- 读取：`mapping.value()`（这时才像方法调用）

不能写成 `String value;`。可以有 `default`，不能有参数、不能抛受检异常。

---

## 20. 注解属性必须叫 `value` 吗？能不能叫 `value1`？

**结论：可以叫 `value1`、`path` 等任意合法方法名。** `value` 只是唯一能省略属性名的那个名字。

```java
String value1();
// 使用时必须写：
@RequestMapping(value1 = "/hello")
// 不能写：
@RequestMapping("/hello")  // 只有属性名叫 value 才行
```

有多个属性时，即便有一个叫 `value`，也通常要写出所有名字（除非只给 `value` 赋值）。

## 21. `Dispatcher.init` 写得怎么样？和 Spring MVC 还差多少？

**结论：** 主循环是对的（容器里找 `@Controller` → 方法上找 `@RequestMapping` → 建成 `HandlerMethod` 放进 Map）。这是 `RequestMappingHandlerMapping` 的骨架。和官方比，还只覆盖「精确 URL + 无参方法」这一小段。

当前实现要点：遍历 `singletonBeanMap`，不是 `beanDefinitionMap`；只认已创建的单例。若只 `scan` 未 `getBean`，`init` 会是空表。

和官方的主要差距：路径模式 / 路径变量、HTTP 方法、类级别前缀、`@GetMapping`、HandlerAdapter、拦截器、代理后取目标类、重复映射检测。

## 25. `@Controller` 上再标 `@Component` 对吗？

**结论：声明方式对，和 Spring 一样；但 `isAnnotationPresent(Component.class)` 在 `UserController` 上是 false。**

## 36. `method.getAnnotation(RequestMapping.class)` 之后如何向上找元注解？

**结论：** 注解实例没有「父注解」字段。用 `annotation.annotationType()` 得到注解的 `Class`，再 `getAnnotations()` / `isAnnotationPresent`。要递归，并跳过 `java.lang.annotation`（`@Retention`、`@Target`），否则会死循环。

`RequestMapping` 上目前只有 Target/Retention，**没有** `@Component`。找组件应沿 **类上的 `@Controller`** 往上走，不是沿方法上的 `@RequestMapping`。

## 37. `Set<Class<?>> visited` 不允许重复添加吗？

**结论：** `Set` 里同一元素只能有一份。`add` 已存在时返回 `false`，集合不变。`if (!visited.add(type))` 表示「已经走过」，用来避免元注解递归死循环。

---

## 38. `Class<? extends Annotation> inner = a.annotationType();` 是什么意思？

**结论：** 从注解**实例** `a` 取出它对应的注解**类型**（一个 `Class`）。`? extends Annotation` 表示这个 Class 代表的是 `Annotation` 的某个子类型（任意 `@interface`）。有了 `inner` 才能继续 `getAnnotations()` 往上找元注解。

---

## 39. 为什么不用 `.class` / `getClass()`，非要 `annotationType()`？

**结论：** `.class` 只能写在类型名后面，不能写 `a.class`。`getClass()` 可以用，但注解实例常常是 JDK 代理，得到的是 `$Proxy`，不是 `@interface` 本身。`annotationType()` 保证返回真正的注解类型（如 `Controller.class`）。

---

## 40. 为什么反射拿到的注解会是动态代理？

**结论：** `@interface` 编译后是接口，不能 `new`。注解的值存在 `.class` 的属性里，运行时要用一个对象把 `value()` 等方法接上。JDK 用 `Proxy` + `AnnotationInvocationHandler` 按接口动态生成实现，不必为每个注解生成实体类。

---

## 41. 为什么要 `if (inner.getName().startsWith("java.lang.annotation")) continue`？

**结论：** 跳过 JDK 自带的元注解（`@Retention`、`@Target`、`@Documented`、`@Inherited` 等）。它们几乎标在每一个自定义注解上，再递归会在 JDK 注解之间绕圈或做大量无意义查找。要找的是 `@Component`、`@RequestMapping` 这类业务元注解。

## 46. `Modifier.isAbstract(aClass.getModifiers())` 是什么意思？

**结论：** `aClass.getModifiers()` 返回用位标志编码的修饰符整数；`Modifier.isAbstract(...)` 检查其中是否包含 `abstract` 标志。返回 true 表示抽象类（或抽象方法），不能直接实例化，组件扫描时应排除。

## 47. 扫描时应存 BeanDefinition、直接创建单例，还是用到时再创建？

**结论：** 扫描器只负责发现组件并注册 `BeanDefinition`，不应直接创建 Bean。创建时机由容器统一管理：纯 `BeanFactory` 可在 `getBean` 时懒创建；应用上下文启动时通常预实例化所有非懒加载单例。MVC 建映射前必须确保 Controller 已由容器创建，或遍历定义并对 Controller 调 `getBean`。

---

## 48. 现在是不是应该考虑 `refresh()` 了？

**结论：是。** 当前已有扫描、BeanDefinition、单例创建和 MVC 映射，正需要一个固定启动流程把它们串起来。第一版 `refresh()` 只做扫描注册、注册后处理器、预实例化非懒单例；MVC 的 `dispatcher.init(factory)` 应在 core 容器 refresh 完成后由 web 层调用，避免 core 依赖 web。

---

## 49. “预实例化非懒加载单例”是单独方法吗？是不是遍历 BeanDefinition 创建 Bean？

**结论：是，通常叫 `preInstantiateSingletons()`。** 遍历 BeanDefinition 名称，只处理 singleton 且非 lazy 的普通 Bean，并调用 `getBean(beanName)`，不要直接调 `createBean`。依赖会由 `getBean` 递归创建。当前迷你容器还没有 scope/lazy 元数据，可先把所有已注册定义视为非懒单例。

## 50. `Dispatcher.init` 通过构造参数还是 `@Autowired` 获取容器？

**结论：当前阶段优先显式构造器注入。** Dispatcher 属于启动基础设施，它需要容器来建立映射；若又等待容器通过 `@Autowired` 注入，会增加启动先后和循环依赖问题。建议构造器接收 BeanFactory 接口并保存，随后 `init()` 无参。等 Dispatcher 本身纳入成熟容器生命周期后，再考虑 `Aware` 接口或框架内部依赖注入。

## 54. Bean 或方法可以有多个注解，`getBeansWithAnnotation` 是否应返回 `Map<String, List<Object>>`？

### 问题背景

建议给 `ListableBeanFactory` 增加按注解查询能力：

```java
Map<String, Object> getBeansWithAnnotation(
        Class<? extends Annotation> annotationType);
```

由于一个类或方法可以同时被多个注解修饰，容易产生疑问：一个 Bean 名称是否应关联多个对象，因此返回 `Map<String, List<Object>>`。

### 关键区分

查询条件是“一个注解类型”，返回对象是“符合条件的 Bean”。一个 Bean 即使带有多个注解，也仍然是同一个 Bean 实例：

```java
@Controller
@Deprecated
public class UserController {}
```

调用：

```java
getBeansWithAnnotation(Controller.class)
```

结果仍应是：

```text
userController -> UserController 实例
```

`@Controller` 和 `@Deprecated` 是 Bean 的元数据，不会让容器产生两份 `UserController`。因此 `Map<String, Object>` 的语义正确：

- key：唯一 beanName；
- value：该名称对应的 Bean 实例。

`Map<String, List<Object>>` 表示“一个 beanName 对应多个 Bean 实例”，这与 IoC 容器中 beanName 唯一标识 Bean 的语义冲突。

### 如果要一次查询多个注解

这属于查询条件设计，不是返回值要变成 List。可以分别查询：

```java
getBeansWithAnnotation(Controller.class);
getBeansWithAnnotation(Service.class);
```

也可以以后增加 ANY / ALL 查询：

```java
Map<String, Object> getBeansWithAnnotations(
        Set<Class<? extends Annotation>> annotationTypes,
        MatchMode mode);
```

- `ANY`：带任意一个目标注解即可；
- `ALL`：必须带全部目标注解。

如果确实要按注解分组展示，可返回：

```java
Map<Class<? extends Annotation>, Map<String, Object>>
```

外层 key 才是注解类型，内层才是 beanName 到 Bean；但当前框架没有必要增加这层复杂度。

### 类注解和方法注解不能混为一谈

`ListableBeanFactory#getBeansWithAnnotation` 查询的是 **Bean 类型上的注解**。方法不是 Bean，因此方法上的 `@RequestMapping` 不应该由 BeanFactory 返回。

MVC 层应在取得 Controller Bean 后扫描其方法，并建立：

```java
Map<String, HandlerMethod>
```

一个 Controller 可以贡献多个 `HandlerMethod`：

```text
/user/get  -> UserController#get()
/user/save -> UserController#save()
```

这里的一对多关系是“一个 Controller Bean 对应多个 HandlerMethod”，而不是“一个 beanName 对应多个 Bean”。

### 最终结论

保留 `Map<String, Object>`。多个注解只会让同一个 Bean 命中多个查询条件，不会让一个 beanName 对应多个对象。类级组件查询属于 BeanFactory；方法级映射查询属于 MVC 的 HandlerMapping，两层职责应分开。

### 追问澄清：一个 `@Controller` 确实会命中多个 Bean

用户进一步指出，`@Controller` 会修饰很多不同的类，因此一次查询确实会返回多个 Bean。这个判断正确，但 `Map<String, Object>` 本身就能容纳多个查询结果：

```text
userController  -> UserController实例
orderController -> OrderController实例
adminController -> AdminController实例
```

Map 的一个 value 不是整个查询结果；Map 的所有 entry 合起来才是结果集合。每一个 Bean 使用不同的 beanName 作为 key，所以不需要让每个 key 再对应一个 `List<Object>`。

如果只关心实例、不关心 beanName，可以返回 `List<Object>`；如果以注解类型作为 key，才可能设计为 `Map<Class<? extends Annotation>, List<Object>>`。但当前方法已经把注解作为入参，返回 `Map<String, Object>` 能同时保留全部匹配 Bean 及其名称，语义最合适。

## 55. 能否同时扫描 `demo` 和 `controller` 两个包？是否合理？

### 结论

可以，容器支持多个扫描根包是合理能力。若业务类分散在两个无包含关系的包中，可以提供 `String... basePackages` 并依次扫描；若它们本来属于同一个应用，更推荐把它们放到同一个业务根包下，只扫描一次业务根包。

### 当前项目的情况

现在 Service / Dao 等 demo 类位于：

```text
com.minispring2.demo
```

Controller 位于：

```text
com.minispring2.web.controller
```

临时可以同时扫描这两个包。直接扫描共同父包 `com.minispring2` 也能工作，但会遍历框架自己的 `core`、`support`、`annotation`、`web.core` 等包；即使最终用 `@Component` 过滤掉，大范围扫描仍不够清晰。

更合理的模块与包布局是让框架和示例应用分开：

```text
minispring-core：框架 IoC
minispring-web：框架 MVC
minispring-demo：示例业务，依赖 core + web

com.minispring2.demo.controller
com.minispring2.demo.service
com.minispring2.demo.dao
```

这样只需扫描 `com.minispring2.demo`。框架模块不应该反向包含使用框架的 demo 业务类。

### 多包扫描 API

可以让上下文保存多个根包：

```java
MiniApplicationContext(String... basePackages)
```

refresh 时逐个调用 scanner。扫描器应处理重复类和重复 beanName，避免两个扫描根包重叠时静默覆盖。

当前扫描器把字段引用写成 `new RuntimeBeanReference(field.getName())`，例如字段名是 `userService`；但 Bean 注册名却把类名首字母转成大写，得到 `UserService`。两者大小写不一致会导致找不到依赖。惯例应为类名首字母小写，或真正按字段类型选择候选 Bean。

### 最终建议

当前可先显式扫描 `com.minispring2.demo` 和 `com.minispring2.web.controller` 验证跨包注入；下一阶段将 demo 业务移入独立应用模块，并统一到 `com.minispring2.demo` 根包，避免扫描整个框架命名空间。

## 56. `git push` 报 `TLS connect error` 应如何判断和处理？

### 现象

```text
fatal: unable to access 'https://github.com/Jiangxiaonan1/spring-mini2.git/':
TLS connect error: error:00000000:lib(0)::reason(0)
```

### 本机诊断结果

- Git 版本为 `2.47.1.windows.1`，版本不旧；
- `origin` 的 fetch / push URL 均正确；
- Git 没有配置 `http.proxy` / `https.proxy`；
- Git 使用 OpenSSL 和自带 CA 文件；
- `curl.exe -I https://github.com` 同样出现 `Recv failure: Connection was reset`。

这说明失败发生在 HTTPS/TLS 网络链路上，还没有到 GitHub 仓库权限或账号认证阶段。它与 `-u`、`master`、远程 URL 尾部显示的 `/` 无关，也不是提交内容的问题。

### 排查顺序

1. 用浏览器访问 GitHub，并尝试手机热点等其他网络；若换网络恢复，说明当前网络链路重置了连接。
2. 如果使用 Clash、V2Ray 等本地代理，确认代理正在运行，并把 Git 指向它的实际端口：

```bash
git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890
```

端口 `7890` 只是示例，必须换成代理软件显示的端口。SOCKS 代理可使用 `socks5h://127.0.0.1:端口`。

3. 若已不使用代理，清理残留：

```bash
git config --global --unset-all http.proxy
git config --global --unset-all https.proxy
```

4. 网络正常但仅 Git OpenSSL 失败时，才考虑切换 Windows TLS 后端：

```bash
git config --global http.sslBackend schannel
```

当前 curl 也被重置，因此这不是首选方案。

5. 使用只读命令查看更多握手信息：

```powershell
$env:GIT_CURL_VERBOSE="1"
git ls-remote origin
Remove-Item Env:GIT_CURL_VERBOSE
```

`git ls-remote` 不会推送或修改远程。

### 不应采用的处理

不要通过 `git config --global http.sslVerify false` 关闭证书校验。当前错误是连接被重置，不是证书校验失败；关闭校验既无针对性，也会降低安全性。

### 最终判断

优先检查网络或正确配置本地代理。网络恢复后，原命令 `git push -u origin master` 可以直接重试。

## 57. 项目已有自动注入能力，接下来应该做什么？

### 对当前能力的判断

项目已经跑通了最小自动注入链路：

```text
扫描 @Component / @Controller
→ 发现字段上的 @Autowired
→ BeanDefinition 记录 RuntimeBeanReference
→ BeanFactory 创建依赖 Bean
→ 通过 setter 填充属性
→ Controller 方法使用已注入的 UserService
```

`PhraseTest2` 同时扫描 `com.minispring2.demo` 和 `com.minispring2.web`，随后 refresh、初始化 Dispatcher 并断言返回 `"hello world"`，证明 IoC 与 MVC 的最小纵向链路已经建立。

但是，这只能称为“按字段名生成引用、再通过 setter 注入”的第一版能力，还不是完整的 `@Autowired`：

1. `Scan` 使用 `field.getName()` 作为 beanName，因此实际按名称注入，不是 Spring `@Autowired` 默认的按类型注入；
2. 字段必须存在对应 setter，虽然注解标在字段上，最终却不是字段注入；
3. `populate` 使用 `fieldValue.getClass()` 精确查找 setter，接口声明、父类型、代理类型会导致 `NoSuchMethodException`；
4. 找不到依赖、多实现冲突、可选依赖都没有明确语义；
5. `Scan` 同时承担资源扫描、组件识别和注入元数据解析，职责开始变重；
6. Spring 通常由 `AutowiredAnnotationBeanPostProcessor` 在 Bean 创建阶段处理注入，而不是由 classpath 扫描器直接执行注入逻辑。

### 下一步优先级一：先把自动注入做“正确”

应先补测试和语义，而不是立刻增加更多 MVC 注解：

- 按类型注入，字段名只在多个候选时作为辅助；
- 接口字段能注入实现类；
- 无候选时抛清晰异常；
- 多候选时抛 `NoUniqueBeanDefinitionException` 一类异常；
- 注入后仍保持容器单例身份；
- 循环依赖场景下引用一致；
- AOP 代理作为依赖时 setter 类型匹配正确。

建议给容器增加：

```java
Object getBean(Class<?> requiredType);
String[] getBeanNamesForType(Class<?> requiredType);
```

类型匹配应使用 `requiredType.isAssignableFrom(candidateType)`，不能用运行时对象 Class 做 setter 的精确参数匹配。

### 下一步优先级二：把注入从 Scan 中拆出去

`Scan` 最好只负责：

```text
包路径 → Class → 是否组件 → BeanDefinition 注册
```

`@Autowired` 的解析和注入属于 Bean 创建生命周期。可以先做一个简化的 `AutowiredAnnotationBeanPostProcessor`，在实例化后、初始化前处理字段；将来再抽象成 `InstantiationAwareBeanPostProcessor`。这样 XML / 手工 BeanDefinition / 注解扫描创建的 Bean 都能共享同一套自动注入能力，而不是只有扫描 Bean 才能使用 `@Autowired`。

### 下一步优先级三：补容器查询接口和封装

让 `DefaultBeanFactory` 实现 `BeanFactory` / `ListableBeanFactory`，并把公开的 `singletonBeanMap` 改回私有。对外只提供：

```java
getBean(name)
getBean(type)
getBeansWithAnnotation(annotationType)
getBeanNamesForType(type)
```

Dispatcher 构造器只依赖 `ListableBeanFactory`，不要依赖具体实现和内部 Map。

### 下一步优先级四：修正生命周期与扩展点

在继续扩展 MVC 前，应确认：

```text
实例化
→ 属性填充 / @Autowired
→ 所有 BeanPostProcessor.beforeInitialization
→ 初始化回调
→ 所有 BeanPostProcessor.afterInitialization
→ 进入单例池
```

当前 `initialize` 是每个处理器依次执行 before + after，不符合 Spring 的“两轮遍历”；三级缓存工厂也只返回原始对象，尚不能保证循环依赖中的早期引用与最终 AOP 代理一致。

### IoC 稳定后再推进 MVC

随后最有价值的 MVC 顺序是：

1. Dispatcher 构造器接收 `ListableBeanFactory`；
2. 把 Handler 查找拆成 `HandlerMapping`；
3. 重复 URL 映射启动时报错；
4. 支持类级别路径和 HTTP Method；
5. 再做参数解析、返回值处理、异常解析。

### 最终建议

当前不应马上追求更多注解数量。优先完成“按类型自动注入 + 多候选错误语义 + 注入处理器从 Scan 解耦 + ListableBeanFactory 封装”。这一阶段完成后，IoC 才能稳定承托 MVC、AOP 和后续扩展。

## 58. 按类型查询是否需要额外维护一份“类型 → BeanDefinition”集合？

### 问题背景

扫描阶段目前只把结果写入：

```java
Map<String, BeanDefinition> beanDefinitionMap;
```

创建 Bean 时也只能先根据 beanName 取 BeanDefinition。因此会产生疑问：为了支持 `getBean(UserService.class)` 或 `@Autowired UserInterface`，是否还要额外维护一份按类型组织的数据结构。

### 结论

需要提供“按类型查询 BeanDefinition / beanName”的**方法能力**，但第一版不需要维护第二份 Map。直接遍历现有 `beanDefinitionMap`，检查每个 BeanDefinition 保存的 beanClass 是否能赋值给目标类型即可。

```java
public List<String> getBeanNamesForType(Class<?> requiredType) {
    List<String> names = new ArrayList<>();
    for (Map.Entry<String, BeanDefinition> entry : beanDefinitionMap.entrySet()) {
        Class<?> candidateType = entry.getValue().getaClass();
        if (requiredType.isAssignableFrom(candidateType)) {
            names.add(entry.getKey());
        }
    }
    return names;
}
```

`isAssignableFrom` 能处理接口、父类和实现类：

```java
UserInterface.class.isAssignableFrom(UserService.class) // true
```

随后按类型取 Bean 的过程应是：

```text
requiredType
→ 遍历 BeanDefinition 找候选 beanName
→ 0 个：缺少依赖异常
→ 1 个：getBean(beanName)
→ 多个：冲突异常（以后由 @Primary / @Qualifier 决定）
```

### 为什么不是直接遍历 singletonBeanMap

按类型解析经常发生在 Bean 尚未创建时。`singletonBeanMap` 只保存已完成创建的实例，若依赖尚未实例化就查不到；`beanDefinitionMap` 才是完整候选清单。因此类型查询首先基于 BeanDefinition 的 class，再通过名称进入统一的 `getBean(name)` 创建流程。

### 为什么不急着做 `Map<Class<?>, BeanDefinition>`

一个实现类可能同时匹配多个类型：

```text
UserService
├─ UserInterface
├─ Object
└─ UserService
```

若用 Class 直接做 key，就要为接口和所有父类型建立多份索引，还要处理一个类型有多个实现、注册/覆盖后的缓存失效。第一版遍历定义更简单且正确。容器规模变大、确认存在性能问题后，可缓存成：

```java
Map<Class<?>, List<String>> typeCandidateCache;
```

缓存值应是 beanName 列表，而不是单个 BeanDefinition，因为一个接口可能有多个实现。

### 职责归属

这项能力应该属于 `ListableBeanFactory`：

```java
String[] getBeanNamesForType(Class<?> type);
Map<String, Object> getBeansOfType(Class<?> type);
```

扫描器只负责注册定义，不负责长期维护类型查询；BeanFactory 基于注册表提供列举和候选解析。

### 最终建议

保留唯一真相来源 `beanDefinitionMap`。先实现“遍历定义并返回匹配 beanName”的方法，再由 `getBean(Class)` 或自动注入处理器使用它。当前规模无须第二份类型 Map。

### 追问：找到多个 beanName 后是否全部调用 `getBean`？

不需要。必须区分“候选发现”和“Bean 实例化”：

```text
遍历 BeanDefinition
→ 得到候选 beanName 列表
→ 根据规则选出唯一名称
→ 只对最终选中的名称调用一次 getBean
```

候选数量处理：

1. 0 个：抛缺少依赖异常；
2. 1 个：直接 `getBean(names.get(0))`；
3. 多个：先按 `@Qualifier`、`@Primary`、字段名等规则选出唯一候选；仍无法唯一确定时抛多候选异常。

例如字段类型是 `PaymentService`，候选为 `alipayService` 和 `wechatPayService`，不能为了选择而先创建两个实例。可以先仅依据 BeanDefinition 元数据筛选；若字段名为 `wechatPayService`，选中该名称后只创建该 Bean。

需要区分两个 API：

```java
Object getBean(Class<?> type)
```

目标是取得一个唯一 Bean，只实例化最终选中的候选。

```java
Map<String, Object> getBeansOfType(Class<?> type)
```

目标就是取得全部匹配 Bean，因此会对每个匹配名称调用 `getBean`。Dispatcher 查询全部 Controller 属于后一种集合查询；给一个字段做类型注入属于前一种唯一候选解析。

## 59. `@Autowired` 字段没有 setter 时如何赋值？

### 当前实现为何失败

当前 `populate` 根据属性名拼出 setter，再反射调用：

```java
setter = "set" + capitalize(propertyName);
Method method = bean.getClass().getDeclaredMethod(
        setter, fieldValue.getClass());
method.invoke(bean, fieldValue);
```

这种方式属于 JavaBean 的 setter 注入。类中没有 setter 时，`getDeclaredMethod` 会抛 `NoSuchMethodException`。但注解标在字段上时，使用者通常期待字段注入，不应该被迫再写 setter。

### 字段注入如何实现

字段注入可以直接反射赋值：

```java
Field field = bean.getClass().getDeclaredField(fieldName);
field.setAccessible(true);
field.set(bean, dependency);
```

`setAccessible(true)` 使框架可以访问 private 字段，因此不需要 setter。若字段可能来自父类，需要沿继承层次逐级查找；还应拒绝 static / final 字段，并将字段不存在、访问失败和类型不兼容包装成明确的容器异常。

### 三种注入语义应分开

1. 字段注入：`@Autowired` 标在字段，使用 `Field#set`；
2. setter 注入：注解或 BeanDefinition 明确描述属性，通过 setter；
3. 构造器注入：创建 Bean 时解析构造参数，依赖明确并且支持 final 字段，通常更推荐。

Spring 的字段 `@Autowired` 主要由 `AutowiredAnnotationBeanPostProcessor` 在属性填充阶段通过反射完成，不要求 setter。当前实现把字段注解转换为普通 `PropertyValue`，随后全部走 setter，混合了字段注入和 setter 注入的语义。

### 当前 setter 查找的另一个问题

`getDeclaredMethod(setter, fieldValue.getClass())` 要求参数类型精确相同。若 setter 参数是接口 `UserServiceApi`，实际对象是实现类 `UserService` 或 JDK 代理，就会找不到。保留 setter 注入时，应根据声明字段类型查找 setter，或遍历候选方法并使用：

```java
parameterType.isAssignableFrom(valueType)
```

判断参数兼容性。

### 推荐演进

短期让字段上的 `@Autowired` 直接走 Field 反射，手工/XML式 `PropertyValue` 保持 setter 注入；中期把自动注入从 Scan 移到专门的 BeanPostProcessor；长期优先支持构造器注入。

## 60. `Class#isAssignableFrom` 是什么意思？当前类型查询写法是否正确？

### 方法语义

```java
TargetType.class.isAssignableFrom(CandidateType.class)
```

表示：`CandidateType` 类型的对象能否赋值给 `TargetType` 类型的变量。可以读成：

```text
左边类型能否接住右边类型
```

例如：

```java
UserInterface.class.isAssignableFrom(UserService.class) // true
Object.class.isAssignableFrom(UserService.class)        // true
UserService.class.isAssignableFrom(UserInterface.class) // false
```

普通赋值与该判断对应：

```java
UserInterface service = new UserService(); // 合法，所以第一项为 true
```

### 当前代码的两个错误

当前单例判断：

```java
object.getClass().isAssignableFrom(clazz)
```

方向反了。`clazz` 是调用方要求的目标类型，应该放左边：

```java
clazz.isAssignableFrom(object.getClass())
```

当前 BeanDefinition 判断：

```java
beanDefinition.getClass().isAssignableFrom(clazz)
```

`beanDefinition.getClass()` 得到的是 `BeanDefinition.class`，不是它描述的业务 Bean 类型。应该读取 BeanDefinition 保存的 `aClass`：

```java
clazz.isAssignableFrom(beanDefinition.getaClass())
```

### 类型查询的正确流程

```text
requiredType（左边）
→ 遍历已创建实例的实际类型，或 BeanDefinition 的 beanClass（右边）
→ requiredType.isAssignableFrom(candidateType)
→ 选出唯一 beanName
→ getBean(beanName)
```

最终创建时宜调用 `getBean(beanName)`，而不是直接调用 `createBean`，以继续遵守单例缓存、循环依赖和统一创建入口。

### 记忆方法

把 `A.isAssignableFrom(B)` 翻译为：

```text
A 变量 = B 对象，能不能成立？
```

能成立返回 true。不要按英文表面误读为“B 能否接住 A”。

## 61. `assign` 为什么解释成“接住”？如何从 `isAssignableFrom` 判断哪边范围更大？

### `assign` 在编程语境中的含义

`assign` 在日常英语里可以表示分配任务、资源；在程序语言中通常译为“赋值”：

```java
target = value;
```

即把右边的 value assign 给左边的 target。这里不是“分配内存”的意思。

### “接住”只是记忆说法

“A 类型能否接住 B 对象”不是 `assign` 的字面翻译，而是为了把抽象的赋值兼容关系还原成 Java 代码：

```java
A variable = new B();
```

若该赋值合法：

```java
A.class.isAssignableFrom(B.class) == true
```

### `from` 为什么容易导致方向混乱

方法名从左边接收者 A 的视角表达：

```text
Is A assignable from B?
A 能否从 B 获得一个可赋给自己的值？
```

所以数据流是：

```text
B 对象 → A 变量
```

`from B` 指来源是 B，并不表示 B 范围更大。

### 如何判断范围大小

把每个类型理解为它可以表示的对象集合：

```text
Number 可表示：Integer、Long、Double……
Integer 只表示：Integer 对象
```

因此：

```text
Integer 实例集合 ⊆ Number 实例集合
```

所以：

```java
Number.class.isAssignableFrom(Integer.class) // true
Integer.class.isAssignableFrom(Number.class) // false
```

通常左边是父类 / 接口 / 相同类型，范围更大；右边是实现类 / 子类，范围更具体。

### 三种记忆方法

1. 直接代入赋值：

```text
A.isAssignableFrom(B)
→ A x = new B() 合法吗？
```

2. 看箭头：

```text
B → A
右边的对象流向左边的变量
```

3. 看继承：

```text
父类.class.isAssignableFrom(子类.class) 通常为 true
```

接口同理：

```java
List.class.isAssignableFrom(ArrayList.class) // true
```

### 最终结论

`assign` 在这里应译为“赋值”；“接住”只是帮助判断方向的口语化比喻。`A.isAssignableFrom(B)` 判断 B 类型的值能否赋给 A 类型变量，因此一般左边范围更大、右边更具体。

## 62. `Class#getDeclaredFields()` 和 `Class#getFields()` 有什么区别？

### 核心区别

| 方法 | 当前类 public | 当前类 protected / 默认 / private | 父类继承的 public | 父类的非 public |
|------|:-------------:|:---------------------------------:|:----------------:|:----------------:|
| `getFields()` | 是 | 否 | 是 | 否 |
| `getDeclaredFields()` | 是 | 是 | 否 | 否 |

`getFields()` 关注“从外部可见的 public 字段”，会把父类继承的 public 字段算进去；`getDeclaredFields()` 关注“这个类自己声明了什么”，访问级别不限，但不查父类。

例如：

```java
class Parent {
    public String inheritedPublic;
    private String inheritedPrivate;
}

class Child extends Parent {
    public String ownPublic;
    private String ownPrivate;
}
```

`Child.class.getFields()` 能得到 `ownPublic`、`inheritedPublic`；`Child.class.getDeclaredFields()` 能得到 `ownPublic`、`ownPrivate`。

### 对当前自动注入的影响

当前代码使用：

```java
for (Field field : o.getClass().getFields())
```

它只能发现 public 字段。`UserController.userService` 是默认访问级别（即使改为 private 也一样），因此不会出现在结果中，注入循环无法命中。后面的 `field.setAccessible(true)` 只能解决“已经找到字段后的访问权限”，不能让 `getFields()` 发现非 public 字段。

字段 `@Autowired` 的第一版应使用 `getDeclaredFields()`。如果需要支持父类中声明的注入字段，应沿继承链逐层调用 `getDeclaredFields()`：

```text
当前类 → 父类 → ... → Object
```

每个找到的 private 字段在赋值前调用 `setAccessible(true)`。

### 其他细节

- 两个方法都返回数组，没有字段时返回空数组，不返回 null；
- 结果中可能包含编译器生成的 synthetic 字段，可用 `field.isSynthetic()` 排除；
- `getField(name)` 只查 public（含继承）；
- `getDeclaredField(name)` 只查当前类声明的任意访问级别字段；
- 如果 Bean 已被 JDK 动态代理，`o.getClass()` 是代理类，业务字段不在代理类上，应在代理前完成字段注入，或取得目标类。

### 最终建议

当前字段注入改用“业务类逐级 `getDeclaredFields()`”的思路；不要用 `getFields()`。`setAccessible(true)` 与字段发现是两件事：前者解决访问权限，后者由选择哪一个反射 API 决定。

## 63. 按类型注入进一步完善后，下一步做什么？

### 当前进展

当前实现已经从按字段名查依赖推进到：

```text
Scan 读取 @Autowired 字段类型
→ RuntimeBeanReference 保存 field.getType()
→ populate 调 getBeanForType(requiredType)
→ isAssignableFrom 匹配实现类
→ Field#set 完成字段注入
```

这是实质进展，接口字段也具备被实现类匹配的基础。

### 当前 `getBeanForType` 仍存在的语义问题

1. 遍历 `singletonBeanMap` 和 `beanDefinitionMap` 时遇到第一个匹配项就返回，若存在两个实现，结果取决于 `HashMap` 遍历顺序，不稳定；
2. 找不到候选时返回 null，随后可能把 null 注入字段，启动仍成功，错误会延迟到业务调用；
3. 从 BeanDefinition 命中后直接调用 `createBean`，绕过统一 `getBean` 入口，可能破坏单例、早期缓存和循环依赖处理；
4. 使用 `beanDefinition.getBeanName()` 依赖 BeanDefinition 内部名称；手工注册的定义可能没有设置该字段，更可靠的是使用 Map entry 的 key；
5. 类型候选发现主要应基于完整的 BeanDefinition 注册表，而不是优先扫描已创建单例；否则创建状态会影响解析结果；
6. 当前字段查找只用当前类的 `getDeclaredFields()`，尚未处理父类注入字段；
7. Scan 仍负责解析 `@Autowired`，使自动注入只天然服务于扫描得到的 Bean。

### 下一步一：拆分候选发现与实例创建

先提供：

```java
List<String> getBeanNamesForType(Class<?> requiredType)
```

它只遍历 BeanDefinition 并返回全部匹配 beanName，不创建对象。然后：

```java
Object getBean(Class<?> requiredType)
```

负责处理候选数量：

```text
0 个 → 抛缺少 Bean 异常
1 个 → getBean(beanName)
多个 → 抛多候选异常
```

最终只能调用统一的 `getBean(String)`。

### 下一步二：优先补失败测试

除了当前成功的 Controller → UserService 测试，还应增加：

- 按接口类型注入唯一实现；
- 没有候选时 refresh 失败；
- 两个实现时 refresh 明确失败，而不是随机选一个；
- 注入对象与容器 `getBean` 返回的是同一单例；
- private 字段无 setter 仍可注入；
- 父类字段的注入行为；
- A/B 字段循环依赖；
- AOP 代理作为依赖时类型仍兼容。

### 下一步三：把自动注入从 Scan 移出

Scan 最终只应注册 BeanDefinition。创建阶段由专门的 `AutowiredAnnotationBeanPostProcessor` 扫描实例字段、解析类型并注入。这样手工注册和扫描注册的 Bean 都能使用同一套 `@Autowired`。

### 下一步四：再补候选选择能力

确认 0/1/多候选语义后，再增加：

- `@Primary`；
- `@Qualifier("beanName")`；
- 多候选时用字段名辅助匹配；
- `@Autowired(required = false)`。

### 最终建议

紧接着先实现 `getBeanNamesForType` 与唯一候选解析，并补齐 0 个、1 个、多个候选的测试。不要立刻继续增加 MVC 功能；类型注入的确定性和失败语义稳定后，再把 `@Autowired` 迁移到 BeanPostProcessor。

### 追问：两个 Map 都以 beanName 为 key，为什么还要拆两个方法？

两个 Map 使用 beanName 作为唯一 key，只能说明“已经知道名称时，每次精确取得一个定义或实例”。按类型注入的输入不是 beanName，而是 `Class<?>`；一个类型可能对应 0、1 或多个不同 beanName：

```text
PaymentService
├─ alipayService
└─ wechatPayService
```

因此仍存在两个不同阶段：

```text
类型 → 候选 beanName 集合
选出唯一 beanName → getBean(beanName)
```

拆成两个方法不是因为 Map 的 value 会返回多个对象，而是因为“候选发现”和“实例获取”的职责、返回结果及失败语义不同。

如果当前只在一处使用，功能上可以把遍历和数量判断都写进 `getBean(Class<?>)`，不必强行公开两个方法。推荐的最小公开 API 是：

```java
Object getBean(String beanName);
<T> T getBean(Class<T> requiredType);
```

`getBeanNamesForType` 可以先作为 private 辅助方法。只有当 Dispatcher、集合注入或 `ListableBeanFactory` 需要“列出全部候选但暂不创建”时，再公开：

```java
String[] getBeanNamesForType(Class<?> requiredType);
```

另外，按类型候选应查完整的 `beanDefinitionMap`。`singletonBeanMap` 只含已创建实例，若用它发现候选，结果会随容器创建进度变化。

### 阶段性决定：暂不拆分方法

用户决定当前阶段不单独抽取 `getBeanNamesForType`。这个决定合理：目前类型查询只有一个调用点，过早拆出公开 API 会增加接口数量，却没有明显复用价值。

暂不拆分不等于省略候选解析语义。现有的按类型查询方法内部仍应保证：

1. 基于 `beanDefinitionMap` 搜集全部候选；
2. 明确处理 0、1、多个候选；
3. 选出名称后调用统一的 `getBean(beanName)`；
4. 不依赖 HashMap 的“第一个匹配项”；
5. 不直接调用 `createBean`，也不以返回 null 代替缺少依赖异常。

等出现以下需求时再拆：Dispatcher 要列出 Bean、支持 `List<T>` 集合注入、实现 `ListableBeanFactory`、多个地方复用类型候选发现。届时抽取是由真实复用推动，而不是为了形式上模仿 Spring。

## 64. 暂不拆分类型查询方法后，下一步做什么？

### 当前最小目标

继续保留现有 `getBeanForType(Class<?>)` 一个方法，但把其行为从“遇到第一个匹配项就返回”改为“先收集候选、再作唯一性判断”。这一步解决的是正确性，与是否拆方法无关。

方法内部可按以下流程：

```text
遍历 beanDefinitionMap.entrySet()
→ requiredType.isAssignableFrom(beanClass)
→ 收集匹配的 Map key（beanName）
→ 0 个：抛缺少依赖异常
→ 1 个：getBean(beanName)
→ 多个：抛依赖不唯一异常
```

应使用 Map entry 的 key，而不是依赖 `BeanDefinition#getBeanName()`；手工注册的 BeanDefinition 可能没有同步设置内部名称。最终应进入 `getBean(String)`，不能直接 `createBean`。

### 为什么这是现在最值得做的

当前 HashMap 的遍历顺序不稳定。若一个接口有两个实现，框架可能在不同运行环境中注入不同对象；若没有实现，返回 null 会让错误延迟到业务调用。让 refresh 在启动阶段明确失败，才能形成可靠容器语义。

### 紧跟着写的三个测试

1. 接口只有一个实现：成功注入，并与 `getBean(name)` 是同一对象；
2. 接口没有实现：`refresh()` 抛清晰异常；
3. 接口有两个实现：`refresh()` 抛多候选异常，不随机选择。

### 完成后的下一站

三个测试稳定后，再将 `@Autowired` 字段解析和赋值从 `Scan` 移入专门的 `AutowiredAnnotationBeanPostProcessor`。Scan 只负责注册组件，自动注入成为所有 Bean 共用的创建阶段能力。此后再推进 MVC 的 HandlerMapping 分层。

### 最终建议

现在只做“当前方法内部的 0/1/多候选处理 + 三个测试”。不要同时引入 `@Primary`、`@Qualifier` 或方法拆分；先建立确定的失败语义。

## 65. 类型候选处理完成后，下一步做什么？

### 对当前实现的复核

当前 `getBeanForType` 已经形成：

```text
getBeanNamesForType(requiredType)
→ 0 个抛异常
→ 多个抛异常
→ 唯一候选调用 getBean(beanName)
```

候选查询基于 `beanDefinitionMap`，使用 `requiredType.isAssignableFrom(candidateType)`，最终进入统一的 `getBean(String)`；这部分基本方向正确。

### 不能跳过的验证

代码库现有 core 测试中尚未发现针对新类型注入语义的测试。因此“代码写完”之后第一步不是继续扩展功能，而是补三个最小测试：

1. 接口只有一个实现，成功注入，并断言注入实例与容器实例相同；
2. 类型没有实现，refresh 明确失败；
3. 类型存在两个实现，refresh 明确失败而不是随机选取。

这三个测试验证的是容器约定，不只是当前 demo 能否输出 `"hello world"`。

### 下一项经典设计：把 `@Autowired` 从 Scan 中移出

当前 Scan 同时做：

```text
扫描 classpath
→ 判断 @Component
→ 读取 @Autowired 字段
→ 生成 RuntimeBeanReference
```

问题是只有扫描得到的 Bean 才天然拥有自动注入元数据；手工注册、`@Bean` 或其他来源的 BeanDefinition 无法复用。更合理的分工是：

```text
Scan：只发现组件并注册 BeanDefinition
Bean 创建阶段：检查实例字段上的 @Autowired 并注入
```

可新增一个简化的 `AutowiredAnnotationBeanPostProcessor`。它持有 BeanFactory，用字段类型调用 `getBeanForType`，再通过 `Field#set` 注入。

### 为什么普通 afterInitialization 不合适

自动注入应发生在：

```text
实例化
→ 属性填充 / @Autowired 注入
→ 初始化回调
→ afterInitialization / AOP 代理
```

因此不应把注入放到现有 `afterInitialization`。可以先增加一个属性处理扩展点，例如：

```java
postProcessProperties(Object bean, String beanName)
```

在 `instantiate` 之后、`initialize` 之前调用。将来可演进为 Spring 风格的 `InstantiationAwareBeanPostProcessor`。

### 推荐的小步实现顺序

1. 先补 0/1/多候选测试；
2. 创建自动注入处理器，只处理字段；
3. BeanFactory 在属性填充阶段调用它；
4. Scan 删除读取 `@Autowired` 和生成 `RuntimeBeanReference` 的逻辑；
5. 增加一个手工注册 BeanDefinition 也能 `@Autowired` 的测试，证明注入已与扫描来源解耦。

### 最终建议

下一步先写候选数量测试；测试通过后，开始复现 `AutowiredAnnotationBeanPostProcessor` / 属性填充扩展点。这比继续加 `@Primary` 或 MVC 功能更有架构价值。

## 66. 将 `@Autowired` 移出扫描器后，BeanDefinition 的 `propertyValueList` 如何组织？是否把所有字段都加入？

### 核心结论

不能把所有字段无条件加入 `propertyValueList`。`propertyValueList` 不是“类中有哪些字段”的清单，而是“外部配置明确要求给哪些属性赋什么值”的清单。扫描得到的普通组件如果没有显式属性配置，其 `propertyValueList` 完全可以为空。

### 三类信息必须区分

1. **类结构信息**：类有哪些字段、字段类型和访问级别。这些信息已经存在于 `Class` 字节码中，反射可随时读取，不需要复制到 BeanDefinition。
2. **显式属性配置**：例如手工/XML配置指定 `name = "张三"`、`userDao = ref("userDao")`。这才属于 `PropertyValue`。
3. **注解注入元数据**：哪些字段带 `@Autowired`、需要按什么类型解析。这应由自动注入处理器读取，而不是混进普通 PropertyValue。

把所有字段放入 propertyValueList 会产生问题：普通业务状态字段也会被当作容器配置；框架不知道 String、int 等字段应该填什么；字段默认值可能被覆盖；每个 BeanDefinition 重复保存 Class 已经包含的结构信息；注解注入与 XML/setter 属性注入仍然耦合。

### 扫描器移除自动注入后的行为

组件扫描只需：

```java
BeanDefinition bd = new BeanDefinition(beanClass);
beanDefinitionMap.put(beanName, bd);
```

此时：

```text
propertyValueList = 空集合
```

是正常状态，不表示 BeanDefinition 不完整。它已经描述了“要创建哪个类”；依赖将在 Bean 创建阶段由注解处理器发现。

### 自动注入处理器如何工作

可以创建简化的 `AutowiredAnnotationBeanPostProcessor`：

```text
Bean 已实例化
→ 获取 beanClass
→ 遍历当前类及父类的 declaredFields
→ 只选择带 @Autowired 的字段
→ requiredType = field.getType()
→ beanFactory.getBean(requiredType)
→ field.setAccessible(true)
→ field.set(bean, dependency)
```

它不是把所有字段加入 propertyValueList，而是在创建阶段仅处理带注解字段。

### 是否需要缓存字段元数据

第一版可以每次创建 Bean 时反射扫描字段。单例只创建一次，成本很低。后续可由处理器维护：

```java
Map<Class<?>, InjectionMetadata> injectionMetadataCache;
```

其中 `InjectionMetadata` 保存该类需要注入的 Field/Method 列表。这个缓存属于自动注入处理器，不属于 BeanDefinition 的普通 propertyValueList。Spring 的 `AutowiredAnnotationBeanPostProcessor` 也有类似注入元数据缓存。

### PropertyValue 应继续服务什么场景

已有 `PropertyValue` 可以继续服务：

- 手工注册 BeanDefinition；
- XML 属性配置；
- Java 配置中明确指定的常量；
- 显式 `RuntimeBeanReference`；
- setter 属性覆盖。

例如：

```text
BeanDefinition(UserService)
propertyValues:
  name -> "张三"
  userDao -> RuntimeBeanReference("userDao")
```

这些值由定义来源明确提供，和 `@Autowired` 按类型推断不是同一机制。

### 推荐创建顺序

为了让显式配置拥有覆盖权，可参考 Spring 的思路：

```text
实例化 Bean
→ 自动注入处理器处理 @Autowired
→ 应用 BeanDefinition 中显式 PropertyValue
→ 初始化回调
→ afterInitialization / AOP
```

第一版也可以先固定一个简单顺序，但要避免同一字段既标 `@Autowired` 又有显式 PropertyValue 时行为不确定。

### 最终设计边界

```text
Scan：发现组件、注册 BeanDefinition
BeanDefinition.propertyValueList：保存显式配置值
AutowiredAnnotationBeanPostProcessor：发现并执行注解注入
BeanFactory：安排创建阶段并解析依赖
```

因此，移出 `@Autowired` 后无需“补填” propertyValueList，更不能无条件加入所有字段。让列表为空，正是职责解耦后的正常结果。

### 实施进展：已从 Scan 移到 populate

用户已删除 Scan 中读取 `@Autowired` 和生成 `RuntimeBeanReference` 的逻辑，并将字段扫描、按类型解析、`Field#set` 放到 BeanFactory 的 `populate` 阶段。

这一调整完成了第一层职责拆分：

```text
Scan：只发现组件并注册 BeanDefinition
populate：负责依赖注入和显式属性填充
```

时机也是正确的：populate 位于实例化之后、初始化和 AOP 之前，可以支持循环依赖所需的早期引用。

但它还是过渡形态：DefaultBeanFactory 目前直接 import 并判断 `@Autowired`，自动注入策略仍硬编码在容器核心里；`AutowiredAnnotationBeanPostProcessor` 尚未承接实际逻辑。下一步是增加 `postProcessProperties` 扩展点，将 populate 中的注解字段循环迁入该处理器。

当前实现还应注意：

1. 先判断字段是否带 `@Autowired`，命中后再 `setAccessible(true)`，无需修改所有字段的访问检查；
2. `field.get(bean) == null` 形成“只有字段当前为空才注入”的自定义语义；Spring 的字段 `@Autowired` 通常按注解执行并覆盖初始引用，不以 null 为前提；
3. 父类字段需要逐级 `getDeclaredFields()`；
4. static / final 字段应拒绝或明确处理；
5. 显式 PropertyValue 与 `@Autowired` 同时作用于同一字段时，要规定覆盖顺序。

## 67. `BeanPostProfessor.super.afterInitialization(object)` 中的 `super` 为什么能这样用？它是静态调用吗？

### 语法含义

Java 8 接口可以声明 `default` 方法。实现类若覆盖了该方法，可以使用：

```java
接口名.super.defaultMethod(arguments)
```

显式调用这个接口提供的默认实现。例如：

```java
interface BeanPostProfessor {
    default Object afterInitialization(Object object) {
        return object;
    }
}

class Processor implements BeanPostProfessor {
    @Override
    public Object afterInitialization(Object object) {
        return BeanPostProfessor.super.afterInitialization(object);
    }
}
```

### 它不是静态调用

该调用仍然作用于当前对象 `this`，只是明确指定“使用 BeanPostProfessor 接口中的默认实现”。如果是静态方法，语法会是：

```java
BeanPostProfessor.someStaticMethod(...)
```

不会出现 `.super`。接口 default 方法有实例分派语义，静态接口方法则没有。

### 为什么要写“接口名.super”

一个类可能实现两个接口，而两个接口可能提供同名 default 方法：

```java
class C implements A, B {
    public void run() {
        A.super.run();
        B.super.run();
    }
}
```

使用接口名可以明确选择哪一个默认实现。通常要求该接口是当前类的直接父接口。

### 当前代码是否有必要

当前默认实现只是原样返回 object，而覆盖方法又只调用默认实现：

```java
return BeanPostProfessor.super.afterInitialization(object);
```

因此这个 override 没有实际效果。可以不覆盖，让类直接继承 default 方法；或者在方法中加入真正处理逻辑后直接返回 object。

### 与自动注入时机的关系

`AutowiredAnnotationBeanPostProcessor` 不适合在 `afterInitialization` 执行字段注入。正确顺序应是：

```text
实例化
→ @Autowired / 属性填充
→ 初始化回调
→ afterInitialization（通常用于 AOP 代理）
```

当前接口只有 before/after initialization，不足以准确表达属性注入阶段。可新增 `postProcessProperties` 扩展点，或先在 BeanFactory 的 populate 阶段显式调用自动注入处理器。

### 最终结论

`InterfaceName.super.method()` 是调用接口 default 实例方法的特殊语法，不是静态调用。当前这行只是原样委托，没有业务价值；并且自动注入不应放在 afterInitialization。

### 追问与更正：为什么前面建议创建该处理器，却没有说明不能使用 afterInitialization？

用户根据“创建 `AutowiredAnnotationBeanPostProcessor`”的建议，自然地让它实现现有 `BeanPostProfessor`，并在该接口现有的 `afterInitialization` 方法中准备实现逻辑。这个推导是合理的。前面的建议遗漏了关键前提：当前 `BeanPostProfessor` 只有初始化前后两个回调，并没有“属性填充阶段”的扩展点。仅给出处理器类名而未说明要扩展生命周期接口，容易让人误以为应使用 afterInitialization。

Spring 中的 `AutowiredAnnotationBeanPostProcessor` 虽然名字含 BeanPostProcessor，但它不依靠 `postProcessAfterInitialization` 完成字段注入。它还实现了 `InstantiationAwareBeanPostProcessor`，主要通过 `postProcessProperties` 在属性填充阶段执行注入。

迷你框架可增加：

```java
public interface InstantiationAwareBeanPostProcessor
        extends BeanPostProfessor {

    default void postProcessProperties(Object bean, String beanName) {
    }
}
```

自动注入处理器实现这个接口：

```java
public class AutowiredAnnotationBeanPostProcessor
        implements InstantiationAwareBeanPostProcessor {

    @Override
    public void postProcessProperties(Object bean, String beanName) {
        // 找 @Autowired 字段、按类型 getBean、Field#set
    }
}
```

BeanFactory 调用顺序：

```text
instantiate
→ 暴露早期引用
→ postProcessProperties / populate
→ beforeInitialization
→ 初始化回调
→ afterInitialization / AOP
→ 放入完整单例池
```

处理器需要 BeanFactory 来解析依赖，可以由构造器接收；ApplicationContext 应在 `preInstantiateSingletons` 之前注册它。短期不想增加新接口，也可以由 BeanFactory 在 `populate` 中显式调用一个 `processAutowired(bean)`，但不要塞入 afterInitialization。

因此，这里应明确更正：创建该处理器的建议本身没错，但之前没有同步说明需要属性阶段扩展点，信息不完整；当前写到 afterInitialization 不是用户的认知错误，而是现有接口能力不足导致的自然选择。

## 69. `postProcessProperties` 怎么翻译、怎么理解？

### 词义拆解

```text
post-process + properties
后置处理    + Bean 属性
```

常见翻译是“后置处理属性”或“对属性进行后处理”。`post-process` 是一个整体动词，表示框架主流程之外追加的一轮加工；不能机械理解为“属性处理完成之后再处理”。

### 在 Spring 生命周期中的位置

Spring 的 `InstantiationAwareBeanPostProcessor#postProcessProperties` 大致位于：

```text
Bean 实例化完成
→ postProcessProperties
→ BeanFactory 应用 BeanDefinition 中的显式 PropertyValues
→ 初始化回调
→ postProcessAfterInitialization
```

因此它位于“实例化之后、初始化之前”，并且通常在 BeanFactory 正式应用显式属性值之前。方法名中的 `post` 主要来自 PostProcessor 扩展机制，不表示所有属性都填完以后才调用。

### Properties 指什么

这里不是 `.properties` 配置文件，而是 Bean 的属性和依赖，例如：

```java
@Autowired
private UserService userService;
```

自动注入处理器可以在该回调中找到注解字段、解析字段类型、从 BeanFactory 取得依赖，再通过 Field 或 Method 注入。

### 与其他回调的区别

- `postProcessProperties`：属性填充阶段，适合依赖注入；
- `postProcessBeforeInitialization`：属性已经填好，即将初始化；
- `postProcessAfterInitialization`：初始化完成，适合创建 AOP 代理。

### 迷你框架中的命名选择

如果目标是复现 Spring 生命周期扩展点，使用 `postProcessProperties` 合适。如果第一版方法只负责字段自动注入，也可以先使用更直接的内部方法名：

```java
injectAutowiredFields(bean, beanName)
```

等抽象为通用属性处理器后，再使用 `postProcessProperties`。

### 最终理解

可以把它理解为：“Bean 已经 new 出来，现在允许属性处理器在属性填充阶段对它做额外加工。”它不是读取配置文件，也不是初始化完成之后的回调。

## 70. 理解 `postProcessProperties` 后，项目下一步应该做什么？

### 当前状态复核

Scan 已经只负责发现 `@Component` 并注册 BeanDefinition，不再读取 `@Autowired`，这部分拆分已完成。但字段自动注入代码仍硬编码在 `DefaultBeanFactory.populate` 中：

```text
遍历 bean.getClass().getDeclaredFields()
→ 判断 @Autowired
→ getBeanForType(field.getType())
→ Field#set
```

`AutowiredAnnotationBeanPostProcessor` 目前仍只继承默认的 `afterInitialization`，没有执行实际注入。因此下一步不是再加新功能，而是把已有注入循环真正迁移到属性处理扩展点。

### 第一步：定义属性阶段接口

```java
public interface InstantiationAwareBeanPostProcessor
        extends BeanPostProfessor {

    default void postProcessProperties(Object bean, String beanName) {
    }
}
```

它与 before/after initialization 的关系：

```text
InstantiationAwareBeanPostProcessor
→ 负责实例化后、初始化前的属性阶段

BeanPostProfessor
→ 负责初始化前后的一般加工
```

### 第二步：让自动注入处理器实现它

```java
public class AutowiredAnnotationBeanPostProcessor
        implements InstantiationAwareBeanPostProcessor {

    private final DefaultBeanFactory beanFactory;

    public AutowiredAnnotationBeanPostProcessor(
            DefaultBeanFactory beanFactory) {
        this.beanFactory = beanFactory;
    }

    @Override
    public void postProcessProperties(Object bean, String beanName) {
        // 遍历字段
        // 判断 @Autowired
        // beanFactory.getBeanForType(field.getType())
        // field.set(bean, dependency)
    }
}
```

处理器持有同一个 BeanFactory，是因为它只负责“发现注入点”，依赖解析与创建仍必须由容器完成。循环依赖时，BeanFactory 仍可通过此前放入三级缓存的早期对象返回依赖。

### 第三步：BeanFactory 只负责调用扩展点

在 createBean 中应保持：

```text
instantiate
→ 放入 singletonFactory / 暴露早期引用
→ populate
→ initialize
```

populate 内：

```text
调用所有 InstantiationAwareBeanPostProcessor.postProcessProperties
→ 应用 BeanDefinition.propertyValueList 中的显式属性
```

然后删除 DefaultBeanFactory 中直接 import `@Autowired` 并反射字段的代码。此后 BeanFactory 不认识具体注解，只认识扩展接口。

### 第四步：在 refresh 中注册基础设施处理器

必须在预实例化单例之前：

```text
创建 DefaultBeanFactory
→ 扫描并注册 BeanDefinition
→ 注册 AutowiredAnnotationBeanPostProcessor
→ preInstantiateSingletons
```

否则 Bean 已经创建完，处理器加入得太晚。

### 当前第一版不必做的复杂能力

- InjectionMetadata 缓存；
- 构造器注入；
- `@Qualifier` / `@Primary`；
- required=false；
- 方法注入。

第一版只移动现有字段逻辑，不同时扩张功能范围。

### 验收测试

1. 原有 Controller → UserService 自动注入仍通过；
2. 手工 `addBeanDefinition` 注册的带 `@Autowired` Bean 也能注入，证明能力不依赖 Scan；
3. 处理器未注册时字段保持未注入，证明扩展点确实生效；
4. 注入发生在 `beforeInitialization` 之前。

### 额外整理项

当前仓库同时存在旧包与 `core.beanPostProcessor` 包中的 `BeanPostProfessor` / Logging 实现。DefaultBeanFactory 已导入新包版本；后续应统一保留一套，避免注册了另一个同名接口实现却无法加入当前处理器列表。类名中的 `Professor` 也是拼写/语义问题，官方名称是 `Processor`，可在本阶段稳定后统一重命名。

### 最终建议

现在只完成“属性阶段接口 → 自动注入处理器 → BeanFactory 调用 → refresh 注册 → 测试”这条链。完成后，自动注入才真正从 BeanFactory 核心逻辑中解耦。

### 实施检查：已增加 `postProcess(instantiate)` 调用

用户已在 `createBean` 的 populate 之后、initialize 之前调用 `postProcess(instantiate)`。从生命周期位置看，这能够保证自动注入发生在初始化之前，方向正确。

但当前实现还没有真正完成“处理器解耦”：

1. 自动注入字段循环仍写在 `DefaultBeanFactory#postProcess` 中，BeanFactory 仍直接 import `@Autowired`；
2. `createBean` 直接调用自身的 `postProcess`，没有遍历 `beanPostProcessorList` 并筛选 `InstantiationAwareBeanPostProcessor`；
3. `AutowiredAnnotationBeanPostProcessor` 内虽然也有一份注入逻辑，但实际没有被 createBean 调用；
4. 该处理器使用 `extends DefaultBeanFactory` 获得 `getBeanForType`，这会创建另一套独立的 definition/singleton/cache Map，无法解析原容器中的依赖。这里应使用组合：构造器接收当前 BeanFactory，而不是继承 BeanFactory；
5. `preInstantiateSingletons` 一边创建所有 Bean、一边发现并注册 BeanPostProcessor，顺序受 HashMap 影响。若 Controller 先创建、处理器后创建，Controller 会错过处理。应先注册所有 BeanPostProcessor，再预实例化普通单例。

正确的调用关系应是：

```text
ApplicationContext
→ 创建 BeanFactory
→ 扫描定义
→ 先发现并注册 BeanPostProcessor
→ 预实例化普通单例

createBean
→ instantiate
→ 暴露早期引用
→ 遍历 processorList：
     仅对 InstantiationAwareBeanPostProcessor 调 postProcessProperties
→ 应用显式 PropertyValue
→ initialize
```

第一版也可以由 ApplicationContext 手工注册：

```java
factory.addBeanPostProcessor(
        new AutowiredAnnotationBeanPostProcessor(factory));
```

这样能保证使用同一个容器且顺序确定。完成迁移后，删除 DefaultBeanFactory 自身的字段注入方法与 `@Autowired` import，才算真正移出核心类。

## 71. `InstantiationAwareBeanPostProcessor` 怎么翻译和理解？为什么不直接使用 `BeanPostProcessor`？

### 名称拆解

```text
Instantiation + Aware + BeanPostProcessor
实例化          感知    Bean 后置处理器
```

可译为“具备实例化阶段感知能力的 Bean 后置处理器”或“实例化感知型 Bean 后置处理器”。

- `Instantiation`：把 Class 通过构造器变成对象，即 `new` 的阶段；
- `Aware`：表示这个扩展接口希望感知并参与该生命周期阶段；
- `BeanPostProcessor`：容器创建 Bean 时调用的扩展处理器。

`Aware` 不表示它自动知道所有事情，而是表示容器承诺在对应阶段回调它。

### BeanPostProcessor 原本覆盖的阶段

基础 `BeanPostProcessor` 主要提供：

```text
postProcessBeforeInitialization
postProcessAfterInitialization
```

其位置是：

```text
实例化
→ 属性填充
→ beforeInitialization
→ 初始化
→ afterInitialization
```

这两个回调都围绕“初始化”，字段依赖注入应发生在属性填充阶段，因此仅靠基础接口时机不准确。放在 afterInitialization 更晚，Bean 的初始化方法可能已经在依赖为 null 的情况下执行，或者对象已经被代理。

### InstantiationAware 增加了什么

官方接口在 BeanPostProcessor 基础上增加实例化和属性填充相关回调，概念上包括：

```text
postProcessBeforeInstantiation
postProcessAfterInstantiation
postProcessProperties
```

其中 `postProcessProperties` 正适合 `@Autowired`：

```text
对象已经创建
→ 扫描 @Autowired 字段
→ 解析并注入依赖
→ 再进入初始化
```

### 为什么新建子接口，而不是把方法全部塞进 BeanPostProcessor

1. **接口职责分离**：日志/AOP处理器只关心初始化后代理，不应该表现得像能参与实例化或属性填充；
2. **生命周期语义清晰**：BeanFactory 可通过 `instanceof InstantiationAwareBeanPostProcessor` 只调用需要的特殊阶段；
3. **减少无关能力**：普通处理器不必实现或继承一堆与自己无关的方法；
4. **便于演进与兼容**：在子接口增加特殊回调，不改变最基础扩展契约；
5. **避免错误时机**：若只剩 before/after initialization，开发者容易把自动注入硬塞到错误回调。

技术上可以给基础接口增加带 default 的 `postProcessProperties`，程序也能运行；但所有实现都会被声明成拥有属性阶段能力，接口边界变模糊。子接口的价值主要是架构语义，而不是 Java 做不到。

### 容器如何区别调用

```java
for (BeanPostProcessor processor : processors) {
    if (processor instanceof InstantiationAwareBeanPostProcessor) {
        ((InstantiationAwareBeanPostProcessor) processor)
                .postProcessProperties(bean, beanName);
    }
}
```

普通 Logging/AOP 处理器不会进入该分支；Autowired 处理器会。

### 对当前迷你框架是否必须完全照搬

不必须。如果目前只需要一个字段注入钩子，可以定义更小、更直白的接口：

```java
interface PropertyPopulationBeanPostProcessor {
    void postProcessProperties(Object bean, String beanName);
}
```

若目标是学习和复现 Spring 生命周期，使用 `InstantiationAwareBeanPostProcessor extends BeanPostProcessor` 更有对照价值。不要一开始复制官方所有方法，只实现当前需要的 `postProcessProperties` 即可。

### 命名提醒

官方名称是 `BeanPostProcessor`（处理器），不是当前项目中的 `BeanPostProfessor`（教授）。`Professor` 虽然能作为合法类名，但语义与官方概念不一致，后续统一包和接口时建议更正。

### 最终结论

新建接口不是因为基础 BeanPostProcessor 不能写注入逻辑，而是因为它现有回调属于初始化阶段，时机不对。InstantiationAware 子接口把实例化/属性填充这一类更早、更特殊的扩展能力单独表达出来，使不同处理器只参与自己关心的生命周期阶段。

## 72. `BeanPostProcessor.super.afterInitialization(object)` 为什么报 “not an enclosing class”？

### 当前继承关系

```text
AutowiredAnnotationBeanPostProcessor
  implements InstantiationAwareBeanPostProcessor
      extends BeanPostProcessor
```

`AutowiredAnnotationBeanPostProcessor` 的直接父接口是 `InstantiationAwareBeanPostProcessor`；`BeanPostProcessor` 是间接父接口。

### 报错原因

Java 的：

```java
InterfaceName.super.defaultMethod()
```

语法只能用于当前类直接实现的父接口，用来明确选择直接父接口的 default 实现。当前类没有直接写：

```java
implements BeanPostProcessor
```

因此不能使用 `BeanPostProcessor.super`，IDEA 提示它不是当前类可直接限定调用的 enclosing / direct superinterface。

### 三种处理方式

最简单的是删除无意义的 override。`afterInitialization` 的默认实现会通过接口继承自动可用：

```java
public class AutowiredAnnotationBeanPostProcessor
        implements InstantiationAwareBeanPostProcessor {
}
```

如果确实要在当前覆盖方法中调用继承的默认实现，可以通过直接父接口限定：

```java
return InstantiationAwareBeanPostProcessor.super
        .afterInitialization(object);
```

但该方法当前只是原样返回 object，这样写仍没有实际业务价值。更直接的是：

```java
return object;
```

### 对自动注入处理器的正确方向

Autowired 处理器不需要覆盖 `afterInitialization`。它应该覆盖：

```java
postProcessProperties(Object bean, String beanName)
```

并在其中执行字段注入。当前 `InstantiationAwareBeanPostProcessor` 中的：

```java
default void postProcess() {};
```

名称和参数还不能表达属性处理上下文；方法体后的分号虽可被 Java 当作额外空声明接受，但没有必要。

### 最终结论

此前 `BeanPostProcessor.super` 能用，是因为类当时直接实现 BeanPostProcessor；现在中间增加了 InstantiationAware 子接口，BeanPostProcessor 变成间接父接口，因此原写法失效。当前最合理的做法是删除 afterInitialization override，改为实现属性阶段方法。

## 73. `is not an enclosing class` 怎么翻译和理解？

### 字面翻译

`enclose` 表示包围、包含；`enclosing class` 通常翻译为“外围类”或“外部封闭类”。因此：

```text
BeanPostProcessor is not an enclosing class
```

字面是：

```text
BeanPostProcessor 不是一个包含当前代码的外围类
```

“不是封闭类”虽然直译，但中文不自然，容易误解为 final 或不能继承。

### Java 中真正的 enclosing class

```java
class Outer {
    class Inner {
        void test() {
            Outer.this.toString();
        }
    }
}
```

`Inner` 写在 `Outer` 内部，所以 Outer 是 Inner 的 enclosing class。`Outer.this` 表示外围 Outer 实例。

### 为什么当前接口调用也出现这条提示

Java 的 `TypeName.super.method()` 是受限制的限定 super 语法。TypeName 不能任意填写，它通常必须是合法的外围类型或当前类直接实现的父接口。

当前结构：

```text
AutowiredAnnotationBeanPostProcessor
→ 直接实现 InstantiationAwareBeanPostProcessor
→ 间接继承 BeanPostProcessor
```

`BeanPostProcessor` 既不是包含当前类的外围类，也不是当前类直接实现的接口，因此 `BeanPostProcessor.super` 不是合法限定。IDEA 复用了 “not an enclosing class” 这类诊断文案。

### 应如何理解，而不是机械翻译

在本场景中，最实用的理解是：

```text
BeanPostProcessor 不是当前代码可以直接用 “它.super” 指定的类型。
```

可使用直接父接口：

```java
InstantiationAwareBeanPostProcessor.super.afterInitialization(object);
```

或者更合理地删除没有实际作用的 override。

### 它不表示什么

该错误不表示：

- BeanPostProcessor 不能被继承；
- 接口必须改成 class；
- 类被 final 封闭；
- 包访问权限不足。

它只是在说 `TypeName.super` 的类型限定不合法。

### 最终结论

`enclosing class` 标准含义是“外围类”。但在当前接口 default 方法场景，应把整条错误理解为：“BeanPostProcessor 不是可在这里直接限定调用 super 的类型”，根因仍是它只是间接父接口。

## 74. 为 `@Autowired` 单独抽 `AutowiredAnnotationBeanPostProcessor` 是否过度设计？

### 用户的质疑

当前 `DefaultBeanFactory#postProcess` 已经能够直接扫描 Bean 字段，发现 `@Autowired` 后按类型取 Bean 并赋值。若再创建一个 `AutowiredAnnotationBeanPostProcessor`，其核心代码仍然是同一段字段扫描，看起来只是把十几行代码搬到新类，并增加接口、注册和调用逻辑，显得啰嗦。

这个质疑成立。是否抽类取决于项目当前目标，而不是因为官方 Spring 有这个类就必须照搬。

### 两种方案都可以成立

#### 方案 A：保留 BeanFactory 内部小方法

```text
createBean
→ populate
→ injectAutowiredFields
→ initialize
```

优点：

- 代码路径短，容易调试；
- 当前只有 `@Autowired` 一种自动注入策略，没有真实复用需求；
- 对学习 Bean 创建主流程更直观；
- 不需要处理 Processor 注册顺序和处理器自身如何获取 BeanFactory。

缺点：

- BeanFactory 直接认识 `@Autowired`，创建机制和注解策略耦合；
- 以后增加 `@Value`、`@Resource`、自定义注入或第三方扩展时，会不断修改 BeanFactory；
- 不容易独立启用、禁用、排序和测试某种注入策略。

如果采用这一方案，方法名应比 `postProcess` 更具体：

```java
injectAutowiredFields(bean)
```

因为它不是通用后处理器，只做字段自动注入。

#### 方案 B：抽为 AutowiredAnnotationBeanPostProcessor

BeanFactory 只定义生命周期：

```text
属性阶段到了 → 调所有属性处理器
```

具体处理器定义策略：

```text
Autowired 处理器 → 识别 @Autowired
Value 处理器 → 识别 @Value
其他处理器 → 处理自己的注解
```

抽类的价值不在于减少字段扫描代码，而在于把：

```text
BeanFactory：何时允许扩展（机制）
AutowiredProcessor：如何识别并注入（策略）
```

分开。这是 Spring 的可扩展性设计，不是实现字段注入所必需的最低结构。

### 什么时候再抽最合理

出现以下任一需求时，抽 Processor 开始有实际收益：

1. 增加第二种属性处理机制，例如 `@Value`；
2. 希望用户自定义注入注解而不修改 BeanFactory；
3. 需要处理器排序、开关或独立测试；
4. 希望 BeanFactory 核心完全不依赖具体注解；
5. 明确以复现 Spring 扩展点为当前学习目标。

若这些需求尚未出现，延后抽象是合理的 YAGNI 选择。

### 当前小方法自身还应完善

即使暂不抽类，也应处理：

- `getDeclaredFields()` 不会返回 null，外层 null 判断可去掉；
- 当前重复调用了两次 `getDeclaredFields()`；
- 应先判断 `@Autowired`，再 `setAccessible(true)`；
- `field.get(bean) == null` 是“为空才注入”的自定义语义，与 Spring 默认行为不同；
- 应支持父类字段或明确暂不支持；
- static / final 字段应拒绝；
- 方法名 `postProcess` 太宽泛，宜改为 `injectAutowiredFields`。

### 阶段性建议

当前可以不创建 `AutowiredAnnotationBeanPostProcessor`，保留一个私有、命名明确的注入方法，让最小框架继续前进。等引入 `@Value` 或主动学习 Processor 扩展体系时，再把该方法机械迁移到处理器；不应为了形式上接近 Spring 而提前增加结构。

### 最终结论

“直接小方法”和“独立处理器”完成字段扫描的核心算法确实相同。前者追求当前简单，后者追求未来扩展和职责隔离。以现阶段功能为目标，保留小方法合理；以复现 Spring 经典扩展设计为目标，独立处理器才有学习价值。可以明确延后，而不是强制绑定。

## 75. 保留 `injectAutowiredFields` 小方法后，接下来做什么？

### 当前状态

`createBean` 已按以下顺序调用：

```text
instantiate
→ 暴露三级缓存工厂
→ populate 显式 PropertyValue
→ injectAutowiredFields
→ initialize
→ 放入一级缓存
```

扫描器也已经不再解析 `@Autowired`。作为最小实现，字段自动注入主链路已建立。

### 首先清理两套并存方案

项目当前同时存在：

1. `DefaultBeanFactory#injectAutowiredFields`，它是真正被 createBean 调用的实现；
2. 标有 `@Component` 的 `AutowiredAnnotationBeanPostProcessor`，它继承 DefaultBeanFactory 并复制了同样逻辑；
3. `InstantiationAwareBeanPostProcessor` 接口，但 BeanFactory 并未调用其属性阶段方法；
4. `preInstantiateSingletons` 会先创建 BeanPostProcessor 并加入列表，但当前 Autowired processor 加入后并不会负责属性注入。

这会让代码看起来已经使用 Processor，实际仍由主 BeanFactory 注入。既然阶段性决定保留小方法，就应只保留这一条真实路径：不要把空壳 Autowired processor 标为组件，也不要为了它扫描整个 `com.minispring2.core`。若暂时保留文件用于以后学习，应明确标记未启用，避免注册。

### 下一步一：把小方法本身做稳

建议按以下顺序处理每个字段：

```text
遍历当前类及父类的 declaredFields
→ 没有 @Autowired：continue
→ static / final：明确拒绝
→ requiredType = field.getType()
→ dependency = getBeanForType(requiredType)
→ setAccessible(true)
→ field.set(bean, dependency)
```

需要调整的细节：

- `getDeclaredFields()` 永不返回 null，不需要 null 判断；
- 已保存 `declaredFields`，循环不要再调用一次；
- 不要在确认注解前对所有字段 `setAccessible(true)`；
- `field.get(bean) == null` 是自定义“空值才注入”规则，若要贴近 Spring应去掉；
- 支持父类字段需要逐级扫描 superclass；
- 异常信息应包含 beanName、字段名和 requiredType。

### 下一步二：补自动注入边界测试

必须覆盖：

1. private 字段无 setter 注入成功；
2. 接口字段注入唯一实现；
3. 没有候选时 refresh 失败；
4. 两个候选时 refresh 失败；
5. 父类 `@Autowired` 字段（若声明支持）；
6. static / final 字段的约定；
7. 循环依赖；
8. 注入对象与容器 getBean 返回同一单例。

### 下一阶段

小方法和测试稳定后，可以回到 MVC，优先拆 `HandlerMapping` 并增加重复 URL 检测；也可以在新增 `@Value` 时再正式引入属性 Processor 扩展机制。

### 最终建议

当前唯一下一步不是增加新功能，而是清除未实际生效的 Autowired Processor 路径，并把 `injectAutowiredFields` 的字段筛选、继承字段、错误语义和测试补齐。完成后再推进 MVC。

## 76. `HandlerMapping` 是做什么的？是否围绕 `requestMappingMap`？

### 核心结论

是。当前 `Dispatcher` 中的 `requestMappingMap` 是 HandlerMapping 最早期的数据结构，但 HandlerMapping 不只是给这个 Map 换一个类名。它负责完整的“处理器映射”职责：

```text
启动时：发现、解析、注册 Handler
请求时：根据请求条件查找 Handler
```

`requestMappingMap` 只是该职责当前使用的内部存储。

### 当前 Dispatcher 混合了哪些职责

当前 `Dispatcher#init`：

```text
从 BeanFactory 取得所有 @Controller
→ 扫描 @RequestMapping 方法
→ 创建 HandlerMethod
→ 放入 requestMappingMap
```

当前 `Dispatcher#doService`：

```text
根据 requestUrl 查 requestMappingMap
→ 得到 HandlerMethod
→ 反射调用
→ 写入响应
```

因此 Dispatcher 同时承担了：

1. Handler 发现与注册；
2. Handler 查询；
3. Handler 执行；
4. 返回值处理；
5. 404 处理。

Spring MVC 将第 1、2 项抽成 HandlerMapping，让 DispatcherServlet 只负责请求流程编排。

### 最小接口设计

```java
public interface HandlerMapping {
    HandlerMethod getHandler(HttpRequest request);
}
```

基于注解的实现：

```java
public class RequestMappingHandlerMapping
        implements HandlerMapping {

    private final Map<String, HandlerMethod> handlerMethods
            = new HashMap<>();

    public void init(ListableBeanFactory beanFactory) {
        // 找 @Controller
        // 扫 @RequestMapping
        // 注册 HandlerMethod
    }

    @Override
    public HandlerMethod getHandler(HttpRequest request) {
        return handlerMethods.get(request.requestUrl);
    }
}
```

Dispatcher 改成只依赖 HandlerMapping：

```text
handler = handlerMapping.getHandler(request)
→ handler 不存在：404
→ 存在：交给调用逻辑执行
```

### HandlerMapping 与 HandlerMethod 的区别

- `HandlerMethod`：一个映射结果的数据对象，保存 Controller Bean 和 Method；
- `HandlerMapping`：发现、保存并查询很多 HandlerMethod 的服务。

类比：

```text
HandlerMethod = 通讯录中的一条联系人记录
HandlerMapping = 管理和查询整本通讯录的系统
```

### 为什么 Map 应移出 Dispatcher

抽取后：

- `requestMappingMap` 应变成 RequestMappingHandlerMapping 的 private 字段；
- Dispatcher 不知道内部是 HashMap、路径树还是正则匹配器；
- 可以增加第二种 HandlerMapping，而不修改 Dispatcher；
- 映射冲突检测集中在注册阶段；
- Handler 映射逻辑可以独立测试。

### 启动与请求阶段

启动阶段：

```text
ApplicationContext.refresh
→ RequestMappingHandlerMapping.init(beanFactory)
→ 建立映射表
```

请求阶段：

```text
Dispatcher.doService
→ handlerMapping.getHandler(request)
→ 执行 HandlerMethod
```

扫描注解只做一次，不在每次请求时扫描。

### 后续 Map key 的演进

当前只按 URL 精确匹配，可以使用：

```java
Map<String, HandlerMethod>
```

加入 GET/POST、headers、params 后，key 应演进为：

```java
Map<RequestMappingInfo, HandlerMethod>
```

`RequestMappingInfo` 可包含路径和 HTTP Method。加入 `/users/{id}` 后，不能仅依赖 HashMap 精确 `get`，HandlerMapping 还需要模式匹配。

### 重复映射检测

注册时不能静默覆盖：

```text
/hello 已注册 UserController#hello
又注册 OtherController#hello
→ 启动失败并报告冲突
```

这是 HandlerMapping 应承担的职责，而不是 Dispatcher 请求执行时才发现。

### 最终结论

`requestMappingMap` 是 HandlerMapping 的核心数据雏形；HandlerMapping 是围绕它形成的“发现 + 注册 + 查询”抽象。下一步可把 Dispatcher.init 和 Map 移入 `RequestMappingHandlerMapping`，让 Dispatcher 只负责请求编排。

### 实施进展与复核

用户已经新增 `HandlerMapping` 和 `HandlerMappingImpl`，把 Controller 扫描、`@RequestMapping` 解析、映射 Map 以及 URL 查询移动到实现类。Dispatcher 目前通过 HandlerMappingImpl 获取 HandlerMethod，再负责调用和响应处理。职责拆分的主方向已经完成。

仍需做以下收尾：

1. Dispatcher 中原有 `requestMappingMap` 已不再使用，应删除，同时清理 HashMap / Map import；
2. Dispatcher 字段应声明为接口 `HandlerMapping`，不要声明为 `HandlerMappingImpl`，否则抽接口没有形成依赖倒置；
3. `doService` 连续调用两次 `getHandlerMethod`，应查询一次保存局部变量；
4. HandlerMappingImpl 的 Map 应为 private，不能让外部修改；
5. `getBeansWithAnnotation(Controller.class)` 已经筛选过 Controller，内部再次 `aClass.isAnnotationPresent(Controller.class)` 重复，而且会排除组合 Controller 注解；
6. `getDeclaredMethods()` 不会返回 null；
7. `isAnnotationPresent` 成功后 `getAnnotation` 不会在同一线程下突然返回 null，该判断可简化；
8. 重复 URL 当前仍会被 HashMap.put 静默覆盖，应在注册阶段抛冲突异常；
9. `HandlerMappingImpl` 名称过泛，若它专门处理注解 RequestMapping，更贴近职责的名称是 `RequestMappingHandlerMapping`；
10. `autoAddHandlerMethod` 可改为 `init`、`detectHandlerMethods` 或 `registerHandlerMethods`，避免 “autoAdd” 弱化生命周期语义。

下一步最小任务是：清理 Dispatcher 遗留 Map、让字段依赖 HandlerMapping 接口、一次查询 Handler，并在 HandlerMapping 注册时加入重复路径检测。完成后再考虑 HandlerAdapter。

## 77. 实现接口方法时，`throws` 异常声明也必须遵守接口吗？

### 当前报错

接口声明：

```java
void autoAddHandlerMethod(DefaultBeanFactory beanFactory);
```

实现类却声明：

```java
public void autoAddHandlerMethod(
        DefaultBeanFactory beanFactory) throws Exception
```

编译器提示 overridden method does not throw `java.lang.Exception`。

### 核心规则

`throws` 是方法契约的一部分。重写方法对于受检异常：

- 可以不抛；
- 可以抛接口声明的相同受检异常；
- 可以抛接口异常的子类（更具体）；
- 不能新增接口没有声明的受检异常；
- 不能把受检异常扩大成更宽的父类。

例如：

```java
interface A {
    void run() throws IOException;
}

class B implements A {
    public void run() throws FileNotFoundException {} // 合法，子类
}

class C implements A {
    public void run() throws Exception {} // 不合法，范围扩大
}
```

### 为什么有此限制

调用方可能只持有接口：

```java
HandlerMapping mapping = new HandlerMappingImpl();
mapping.autoAddHandlerMethod(factory);
```

接口没有声明受检异常时，调用方不需要 try/catch。如果实现类可以偷偷新增 `throws Exception`，替换实现后调用方的异常处理契约就被破坏，违反可替换性。

### 受检异常与运行时异常

`Exception`（除 RuntimeException 分支外）属于受检异常，必须在接口声明或由调用方捕获。`RuntimeException` 及其子类不受这条 throws 声明限制，实现类可以抛出而不写在方法签名。

重复 URL 映射属于框架启动配置错误，通常不适合用宽泛的受检 `Exception`。第一版可抛：

```java
throw new IllegalStateException("MVC中出现重复的URL映射: " + path);
```

更正式可定义：

```java
class DuplicateRequestMappingException extends RuntimeException
```

这样接口方法无需声明 `throws`，启动仍会立即失败，并且异常语义明确。

另一种方案是在接口也声明 `throws Exception`，但会迫使所有调用方处理过于宽泛的异常，不推荐。

### 最终结论

不是“异常信息必须继承”，而是重写方法必须遵守接口的受检异常契约。当前重复映射建议使用具体的运行时异常，而不是在实现方法上新增 `throws Exception`。

## 78. `HandlerAdapter` 是做什么的？

### 核心职责

HandlerMapping 负责回答“这次请求由谁处理”，HandlerAdapter 负责回答“这个 Handler 应该怎样被调用”：

```text
请求
→ HandlerMapping：找到 Handler
→ HandlerAdapter：适配并执行 Handler
→ 返回执行结果
```

当前 Dispatcher 中以下逻辑就是 HandlerAdapter 的雏形：

```java
Object target = handlerMethod.object;
Method method = handlerMethod.methodName;
Object result = method.invoke(target);
```

随着 Controller 方法出现参数、注解和不同返回类型，这段执行逻辑会越来越复杂，不应全部堆在 Dispatcher。

### 为什么叫 Adapter

Dispatcher 希望统一调用 Handler，但 Handler 可能有不同形态：

```text
@Controller 的 HandlerMethod
实现某个 Controller 接口的对象
函数式 Handler
Servlet 风格处理器
```

它们的调用方式不同。适配器把不同形态转换成 Dispatcher 能使用的统一调用协议，因此体现适配器模式。

### Spring 中的典型接口思想

```java
interface HandlerAdapter {
    boolean supports(Object handler);
    Object handle(HttpRequest request,
                  HttpResponse response,
                  Object handler);
}
```

- `supports`：当前适配器是否会调用这种 Handler；
- `handle`：解析参数、调用目标方法并返回处理结果。

基于注解 Controller 的实现对应 Spring 中的 `RequestMappingHandlerAdapter`。

### 对当前迷你 MVC 的第一版设计

当前只有 HandlerMethod 一种类型，可以先简化：

```java
interface HandlerAdapter {
    Object handle(HttpRequest request,
                  HttpResponse response,
                  HandlerMethod handler);
}
```

实现类：

```text
HandlerMethodAdapter
→ 取得 Controller 对象
→ 取得 Method
→ 准备参数数组
→ method.invoke(controller, args)
→ 返回 result
```

Dispatcher 变为：

```text
handler = handlerMapping.getHandler(request)
→ handler 为空：404
→ result = handlerAdapter.handle(request, response, handler)
→ 把 result 交给返回值处理
```

### HandlerAdapter 后续承接的能力

1. 根据方法参数识别 `HttpRequest` / `HttpResponse`；
2. 解析 `@RequestParam`；
3. 解析 `@PathVariable`；
4. 解析 `@RequestBody`；
5. 执行类型转换；
6. 调用 Method 并解包 `InvocationTargetException`；
7. 将返回结果交给 ReturnValueHandler。

### 它不应该负责什么

- 不负责扫描 `@Controller`；
- 不负责 URL 匹配；
- 不负责保存 requestMappingMap；
- 通常不直接决定 404；
- JSON 序列化最终可继续拆给 HttpMessageConverter / ReturnValueHandler。

### 与 HandlerMethod 的关系

```text
HandlerMethod = “目标对象 + 方法”的描述
HandlerAdapter = 读懂这个描述并执行它的人
```

HandlerMethod 是数据，HandlerAdapter 是执行策略。

### 最终结论

当前 Dispatcher 中 `method.invoke(object)` 以及未来的参数准备逻辑应移动到 HandlerAdapter。抽取后 Dispatcher 只负责总流程，HandlerMapping 负责寻找，HandlerAdapter 负责调用。

### 实施复核：HandlerAdapter 已拆出，但当前调用链会空指针

用户已经新增 `HandlerAdapter` 与 `HandlerAdapterImpl`，并把 `Method#invoke` 移入实现类。代码职责迁移了一部分，但当前结构存在关键问题：

```text
Dispatcher.init
→ 创建并初始化 HandlerMappingImpl（里面有完整映射）

Dispatcher.doService
→ 每次 new HandlerAdapterImpl
→ HandlerAdapterImpl.handlerMapping 从未赋值
→ handle 中调用 handlerMapping.getHandlerMethod
→ NullPointerException
```

即使通过构造器把 HandlerMapping 塞给 Adapter，这种职责关系仍然不理想。HandlerAdapter 不应再次寻找 Handler；“找谁处理”属于 HandlerMapping，“怎么调用已找到的 Handler”才属于 HandlerAdapter。

正确调用链：

```text
Dispatcher
→ handlerMapping.getHandlerMethod(url)
→ handler 不存在：Dispatcher 处理 404
→ handlerAdapter.handle(request, response, handler)
```

因此接口至少要接收已找到的 Handler：

```java
Object handle(HttpRequest request,
              HttpResponse response,
              HandlerMethod handler);
```

或第一版由 Adapter 直接写响应：

```java
void handle(HttpRequest request,
            HttpResponse response,
            HandlerMethod handler);
```

Dispatcher 应在初始化阶段创建一次 HandlerAdapter，并以接口类型保存：

```java
HandlerMapping handlerMapping;
HandlerAdapter handlerAdapter;
```

不应在每次 `doService` 时 new 一个适配器。这样未来可由 Dispatcher 遍历多个 Adapter 的 `supports(handler)`，选择会处理当前 Handler 类型的实现。

当前最小修正目标：

1. 从 HandlerAdapterImpl 删除 HandlerMapping 字段；
2. handle 增加 HandlerMethod 参数；
3. Dispatcher 先查询 Handler；
4. Dispatcher 判断 404；
5. Dispatcher 把 HandlerMethod 传给 Adapter；
6. Adapter 只负责反射调用；
7. Adapter 在 init 时创建一次，并以 HandlerAdapter 接口声明。

完成后才算真正形成“Mapping 负责查找、Adapter 负责执行、Dispatcher 负责协调”的三层关系。

## 79. 当前 HandlerAdapter 先保持现状，接下来做什么？

### 阶段性决定

用户决定当前 HandlerAdapter 与 HandlerMapping 的依赖关系先保持现状，不继续为职责纯度重构。这个选择可以接受：当前只有一种 Handler 类型，优先用新功能证明 Adapter 的价值，比继续调整类关系更直观。

### 下一步：让 HandlerAdapter 支持方法参数

目前 Adapter 仍然只执行：

```java
method.invoke(controller);
```

它与原 Dispatcher 中的反射调用能力相同。下一步应让它能根据 Controller 方法签名准备参数。第一版只支持框架自身的两个参数类型：

```java
@RequestMapping("/hello")
public String hello(HttpRequest request,
                    HttpResponse response) {
    return request.requestUrl;
}
```

HandlerAdapter 可读取：

```java
Class<?>[] parameterTypes = method.getParameterTypes();
```

构造参数数组：

```text
参数类型是 HttpRequest → 放入当前 request
参数类型是 HttpResponse → 放入当前 response
其他类型 → 抛 UnsupportedOperationException
```

最后：

```java
method.invoke(controller, args);
```

### 为什么现在做这个

参数适配正是 HandlerAdapter 从“搬出来的反射代码”变成“执行适配层”的第一项真实职责。它能验证抽取不是形式变化，并为后续 `@RequestParam`、`@PathVariable`、`@RequestBody` 奠定流程。

### 第一版不要急着抽 ArgumentResolver

当前只有 HttpRequest / HttpResponse 两种规则，可以先在 HandlerAdapter 中用 if 判断。等加入 `@RequestParam` 后，再抽：

```java
HandlerMethodArgumentResolver
```

每个解析器负责一种参数来源。这样抽象由第二种真实需求推动，不会重复此前为单个 Autowired 逻辑过早增加接口的问题。

### 验收测试

增加 Controller 方法：

```java
@RequestMapping("/echo")
public String echo(HttpRequest request) {
    return request.requestUrl;
}
```

发送 `/echo`，断言响应为 `/echo`。再增加一个未知参数类型方法，确认框架在调用前给出“暂不支持该参数类型”的明确错误。

### 随后路线

1. 支持 HttpRequest / HttpResponse 参数；
2. 给 HttpRequest 增加查询参数 Map；
3. 定义 `@RequestParam`；
4. 支持 String 到基础类型转换；
5. 当解析规则增多时抽 HandlerMethodArgumentResolver；
6. 再处理返回值和 JSON。

### 最终建议

现在不要再改 HandlerMapping/Adapter 的类关系。直接给 Adapter 增加最小参数组装能力，让 Controller 方法第一次可以声明请求和响应参数。

## 80. 反射得到的方法参数类型后，如何判断 Java 基本数据类型？

### 基本判断

```java
Class<?> type = parameter.getType();
boolean primitive = type.isPrimitive();
```

若参数声明为 `int`，`parameter.getType()` 返回 `int.class`；若声明为 `Integer`，返回 `Integer.class`。两者不是同一个 Class：

```java
int.class != Integer.class
Integer.TYPE == int.class
```

### 同时支持基本类型和包装类型

```java
if (type == int.class || type == Integer.class) {
    value = Integer.valueOf(text);
} else if (type == long.class || type == Long.class) {
    value = Long.valueOf(text);
} else if (type == boolean.class || type == Boolean.class) {
    value = Boolean.valueOf(text);
} else if (type == double.class || type == Double.class) {
    value = Double.valueOf(text);
} else if (type == float.class || type == Float.class) {
    value = Float.valueOf(text);
} else if (type == short.class || type == Short.class) {
    value = Short.valueOf(text);
} else if (type == byte.class || type == Byte.class) {
    value = Byte.valueOf(text);
} else if (type == char.class || type == Character.class) {
    if (text.length() != 1) {
        throw new IllegalArgumentException("无法转换为 char: " + text);
    }
    value = text.charAt(0);
} else if (type == String.class) {
    value = text;
} else {
    throw new IllegalArgumentException("暂不支持的参数类型: " + type.getName());
}
```

### `isPrimitive()` 的边界

它只告诉调用方“是不是基本类型”，不能说明具体是哪一种。Java 基本类型包括：

```text
byte short int long float double char boolean void
```

`void.class.isPrimitive()` 也为 true，但 void 不会成为普通方法参数类型。

### 转换异常

- 数字格式错误会抛 `NumberFormatException`；
- primitive 参数不能接收 null；
- `Boolean.valueOf` 只有忽略大小写等于 `"true"` 时返回 true，其他文本都返回 false，若需严格校验应主动拒绝非法值；
- 未支持类型不应默认转 String，否则 Controller 声明错误会被隐藏。

### 后续抽象

当前 if/else 适合第一版。转换类型增加后，可抽：

```java
Object convert(String text, Class<?> targetType)
```

再演进为 Converter 注册表。HandlerAdapter 负责参数来源，类型转换器负责 String 到目标 Java 类型，不应长期混成一段代码。

## 81. 如何解析 Request Body？是否需要 Map → JSON、JSON → 对象？

### 方向判断

请求体解析的主要方向是：

```text
HTTP Body 字节
→ 按 charset 解码成字符串
→ JSON 反序列化
→ Controller 参数对象
```

例如请求：

```json
{"name":"张三","age":18}
```

Controller：

```java
public String save(@RequestBody User user)
```

框架应把 JSON 直接转换成 `User`。不要求业务层先拿 Map，也不需要先做 Map → JSON。Map → JSON / 对象 → JSON 主要是响应序列化方向：

```text
Java 对象或 Map → JSON → HTTP Response Body
```

JSON 库内部可能先构建 Map / JSON Tree，但这是实现细节。

### 不建议自己手写 JSON 解析器

JSON 涉及字符串转义、Unicode、数组、嵌套对象、null、数字精度等规则。迷你 MVC 的学习重点是消息转换扩展点，不是重新实现 JSON 标准。可使用 Jackson：

```java
ObjectMapper objectMapper = new ObjectMapper();
User user = objectMapper.readValue(json, User.class);
```

### HttpRequest 需要携带的信息

第一版可增加：

```java
String requestBody;
String contentType;
String characterEncoding;
```

真实 HTTP 接入后，requestBody 来源是输入流字节；当前内存测试可直接赋 JSON 字符串。

### 定义参数注解

```java
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestBody {
    boolean required() default true;
}
```

HandlerAdapter 遍历 Method Parameter 时：

```text
有 @RequestBody
→ 检查 Content-Type 是否 application/json
→ 检查 body 是否为空
→ targetType = parameter.getType()
→ ObjectMapper.readValue(body, targetType)
→ 放入 args[i]
```

### 更合理的经典设计：HttpMessageConverter

不要让 HandlerAdapter 永久依赖 Jackson。可定义：

```java
interface HttpMessageConverter {
    boolean canRead(Class<?> targetType, String contentType);
    Object read(String body, Class<?> targetType);

    boolean canWrite(Class<?> valueType, String contentType);
    String write(Object value);
}
```

`JsonHttpMessageConverter` 内部使用 ObjectMapper。HandlerAdapter 只选择能读取当前 content type 和目标类型的 converter。

### Map 参数与泛型

若 Controller 参数是：

```java
@RequestBody Map<String, Object> body
```

可以反序列化为 Map。但 `Map<String, User>`、`List<User>` 等泛型不能只靠 `parameter.getType()`，还要读取：

```java
parameter.getParameterizedType()
```

第一版建议只支持普通 POJO 和简单 Map，泛型集合以后再做。

### 错误语义

- body 缺失但 required=true：400；
- JSON 格式错误：400；
- Content-Type 不支持：415；
- 没有可用 converter：415 或明确框架异常；
- 一个方法通常只允许一个 `@RequestBody`，因为请求输入流一般只能直接消费一次；
- 应限制最大 body 大小，避免内存风险。

### 推荐的第一版实现顺序

1. HttpRequest 增加 requestBody / contentType；
2. 新增 `@RequestBody`；
3. 引入 Jackson ObjectMapper；
4. HandlerAdapter 识别注解并调用 `readValue(body, parameter.getType())`；
5. 测试 JSON → 普通 User 对象；
6. 之后再抽 HttpMessageConverter；
7. 最后实现返回对象 → JSON。

### 最终结论

Request Body 的核心是 JSON → Java 对象；响应方向才是 Java 对象 / Map → JSON。Map 可以作为 Controller 的目标参数或 JSON 库内部结构，但不是必须中转层。

### 实施复核：RequestBody 第一版已经写出

当前实现已经具备：

```text
@RequestBody 参数识别
→ 从 HttpRequest.requestBody 读取 JSON 字符串
→ ObjectMapper.readValue
→ 放入反射调用参数数组
→ Controller 接收 UserDao 对象
```

同时已有 PhraseTest3 构造 UserDao、序列化成 JSON 并请求 `/addUser`，主方向已经跑通。

在继续下一功能前，应修正以下关键点。

#### 1. 目标类型不应由请求对象提供

当前使用：

```java
Class<?> requestBodyType = httpRequest.requestBodyType;
objectMapper.readValue(requestBody, requestBodyType);
```

目标类型应由 Controller 方法签名决定：

```java
Class<?> requestBodyType = parameter.getType();
```

客户端只提供 JSON 数据与 Content-Type，不应该告诉服务器“请反序列化成哪个 Java Class”。方法参数已经明确声明了 UserDao，额外的 requestBodyType 会造成重复信息、不一致和不必要的安全风险。因此 HttpRequest 中无需保存 Class。

#### 2. method.invoke 的位置错误

当前 `method.invoke(object, values)` 写在参数 for 循环内部，会导致：

- 无参方法的循环一次都不执行，因此 Controller 方法不会被调用；
- 多参数方法会被调用多次；
- 第一次调用时后续参数仍未填充。

正确顺序：

```text
遍历所有 Parameter，填满 values[]
→ 循环结束
→ method.invoke(controller, values) 只调用一次
```

这是当前最需要修正的逻辑错误。

#### 3. required 应在 Jackson 解析前判断

当前先 `readValue`，再判断解析结果是否 null。若 body 本身为 null 或空字符串，Jackson 往往先抛解析异常，`required=false` 没有机会生效。

应先判断：

```text
body 为空且 required=true → 请求参数错误
body 为空且 required=false → values[i] = null
body 非空 → Jackson 解析
```

#### 4. RequestBody 的 value 当前没有意义

HTTP 请求体通常只有一份，`@RequestBody(value = "userDao")` 中 value 没有参与解析。第一版只保留 required 即可；名称配置更适合 RequestParam 或 PathVariable。

#### 5. ObjectMapper 应复用

当前每次参数解析都 `new ObjectMapper()`。第一版可让 HandlerAdapter 持有一个 final ObjectMapper；后续由 JsonHttpMessageConverter 持有。

#### 6. 测试需要断言

`testGetUser3` 目前只打印响应。应断言 Controller 确实收到了 name=Jerry、age=19，并断言响应格式。否则 JSON 解析失败或返回默认 toString，测试仍可能被忽略。

### RequestBody 之后的下一步

修正上述逻辑后，最自然的下一项是响应体转换：

```text
Controller 返回 String → 原样 text/plain
Controller 返回普通对象 / Map / List → Jackson writeValueAsString
Controller 返回 null → 空响应或 204（先选定一种）
```

可先直接写在 Adapter 中跑通，再抽 ResponseBody / HttpMessageConverter。

## 82. Spring 框架解析 JSON 也是使用 Jackson 吗？

### 结论

Spring MVC 最常见的 JSON 实现确实是 Jackson，但 Spring Framework 本身没有把 JSON 能力写死为 Jackson。Spring 定义 `HttpMessageConverter` 抽象，再根据 classpath、配置、Content-Type 和目标类型选择具体转换器。

### 调用链

请求参数带 `@RequestBody` 时，大致流程：

```text
DispatcherServlet
→ RequestMappingHandlerAdapter
→ 参数解析 / RequestResponseBodyMethodProcessor
→ 查找可读取 application/json 的 HttpMessageConverter
→ Jackson 转换器调用 ObjectMapper.readValue
→ 得到 Controller 参数对象
```

Controller 返回 `@ResponseBody` / `@RestController` 对象时方向相反：

```text
Java对象
→ Jackson HttpMessageConverter
→ ObjectMapper 序列化
→ JSON Response Body
```

### 常见 Jackson 转换器

Spring MVC 中经典实现是：

```text
MappingJackson2HttpMessageConverter
```

它内部持有 Jackson `ObjectMapper`。Spring Boot Web 应用通常默认自动配置 Jackson，因此开发者感觉像是 Spring 自己天然会处理 JSON。

### 不是强制绑定

可以替换或增加其他实现：

- Gson；
- JSON-B；
- XML（JAXB 等）；
- String / byte[]；
- 自定义二进制格式；
- 自定义 HttpMessageConverter。

如果 classpath 没有 Jackson，也没有其他 JSON converter，Spring MVC 不会凭空把 JSON 转成 POJO，通常会出现不支持媒体类型或找不到转换器的问题。

### Spring 与 Spring Boot 的区别

- Spring Framework / Spring MVC：提供转换器接口和 Jackson 适配实现，是否启用取决于依赖和配置；
- Spring Boot：Web starter 通常带入并自动配置 Jackson，让默认 JSON 使用体验开箱即用。

### 对 mini-Spring 的启发

第一版直接在 HandlerAdapter 中调用 ObjectMapper 可以快速跑通；之后抽 `HttpMessageConverter`，让 HandlerAdapter 依赖抽象而非 Jackson。这样既复现 Spring 经典设计，也保留以后替换 JSON 库的能力。

## 83. mini-Spring 项目应选择哪个稳定的 Jackson Maven 版本？

### 推荐版本

当前项目使用 Java 8，可选择 Jackson `2.22.2`。该版本已发布到 Maven Central，是 2.22 系列的稳定补丁版本，并继续以 Java 8 为运行基线。

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.22.2</version>
</dependency>
```

`jackson-databind` 会通过 Maven 传递依赖带入 `jackson-core` 和 `jackson-annotations`，第一版无需分别声明。

### 放在哪个模块

JSON 请求体和响应体转换属于 Web 层，因此实际 dependency 宜放在 `minispring-web/pom.xml`，不要放进 `minispring-core`。如果希望父 POM 集中管理版本，可以在父 POM 的 `dependencyManagement` 中声明版本，再由 web 模块引用。

### 版本一致性

当前只用 databind 时直接依赖即可。以后同时引入多种 Jackson 模块，例如 `jackson-datatype-jsr310`，可考虑 Jackson BOM 统一版本，避免 core、annotations、databind 不一致。

### 安全与升级

Jackson databind 历史上会持续发布安全和兼容修复。稳定不意味着永久固定；应锁定具体补丁版本保证构建可重复，并在后续依赖维护时升级到同一维护线的新补丁版本，不建议使用动态版本范围。

### 最终结论

本项目第一版使用 `com.fasterxml.jackson.core:jackson-databind:2.22.2`，放在 minispring-web 模块即可。

## 84. 注解中的 `boolean required() default true` 和 `String value() default ""` 是什么意思？方法名固定吗？

### 注解成员不是固定函数

注解中的成员在 Java 语法上写成无参方法形式：

```java
返回类型 成员名() default 默认值;
```

成员名由注解设计者自己决定，不是 Java 固定名称。因此 `required`、`value`、`name`、`path` 都可以。调用时不能带参数，也没有方法体。

### `required`

```java
public @interface RequestBody {
    boolean required() default true;
}
```

表示 RequestBody 注解有一个 boolean 配置项，名称是 required，默认 true。

使用：

```java
@RequestBody
User user
```

等价于：

```java
@RequestBody(required = true)
User user
```

允许请求体为空：

```java
@RequestBody(required = false)
User user
```

框架反射读取：

```java
RequestBody body = parameter.getAnnotation(RequestBody.class);
boolean required = body.required();
```

`required` 只是约定出的语义：框架代码必须主动读取并执行“为空时是否报错”，Java 不会自动校验。

### `value`

```java
public @interface Xxx {
    String value() default "";
}
```

表示一个 String 配置项，默认空字符串。`value` 不是强制名称，但它在注解使用语法中具有特殊简写待遇：

```java
@Xxx("abc")
```

等价于：

```java
@Xxx(value = "abc")
```

如果成员改名为 `name()`，则必须写：

```java
@Xxx(name = "abc")
```

不能简写为 `@Xxx("abc")`。

### 多个成员组合

```java
public @interface Param {
    String value() default "";
    boolean required() default true;
}
```

用法：

```java
@Param("id")
@Param(value = "id", required = false)
@Param(required = false) // value 使用默认 ""
```

### RequestBody 是否需要 value

请求体通常只有一份，不需要通过名称选择，所以 RequestBody 一般只需要 required：

```java
@RequestBody User user
```

`value` 更适合 `@RequestParam("id")`、`@PathVariable("id")`、`@RequestMapping("/users")` 等需要指定名称或路径的注解。

### 注解成员允许的类型

主要包括基本类型、String、Class、枚举、注解及这些类型的数组。默认值必须是编译期可表示的合法注解值，不能通过普通运行时代码计算。

### 最终结论

`required()` 和 `value()` 都是注解设计者定义的配置成员，不是固定函数名。`value` 只有“使用时可省略成员名”的语法特殊性；`required` 没有语言级特殊含义，其行为完全由框架实现。

## 85. Jackson 将 Java 对象转换成 JSON 怎么写？是 `writeValue` 吗？

### 转成 JSON 字符串

使用：

```java
String json = objectMapper.writeValueAsString(user);
```

它与反序列化方向对应：

```java
User user = objectMapper.readValue(json, User.class); // JSON → 对象
String json = objectMapper.writeValueAsString(user);  // 对象 → JSON字符串
```

当前 mini-MVC 的 `HttpResponse.responseBody` 是 String，因此最适合使用 `writeValueAsString`。

### `writeValue` 的用途

`writeValue` 用于直接写到某个输出目标，不是返回 String：

```java
objectMapper.writeValue(file, user);
objectMapper.writeValue(outputStream, user);
objectMapper.writeValue(writer, user);
```

因此：

- 想得到 JSON 字符串：`writeValueAsString`；
- 想直接写文件、流或 Writer：`writeValue`；
- 想得到 UTF-8 字节：`writeValueAsBytes`。

### 示例

```java
User user = new User();
user.setName("张三");
user.setAge(18);

String json = objectMapper.writeValueAsString(user);
```

结果：

```json
{"name":"张三","age":18}
```

Map、List 也可直接序列化：

```java
objectMapper.writeValueAsString(map);
objectMapper.writeValueAsString(list);
```

### 在 HandlerAdapter / 返回值处理中的使用

如果 Controller 返回普通对象：

```java
Object result = method.invoke(controller, args);
response.responseBody = objectMapper.writeValueAsString(result);
response.contentType = "application/json";
```

后续更合理的是把这段放到 JSON HttpMessageConverter 或 ReturnValueHandler，而不是长期写死在 Adapter。

### String 返回值的注意事项

若对字符串 `"hello"` 调用：

```java
writeValueAsString("hello")
```

结果是合法 JSON 字符串：

```json
"hello"
```

其中包含双引号。若 Controller 返回 String 并希望响应正文直接是 `hello`，应按 `text/plain` 原样写出，不要再经过 Jackson。这也是返回值处理器需要根据类型和 Content-Type 选择转换器的原因。

### ObjectMapper 的复用

ObjectMapper 完成配置后可复用，通常不应每个请求都 new。第一版可以让 JSON converter 或 HandlerAdapter 持有一个共享实例。

### 异常

`writeValueAsString` 可能抛 `JsonProcessingException`。框架应将其包装为响应转换异常并最终返回 500，而不是把 Jackson 异常直接暴露给客户端。

### 最终结论

对象转 JSON 字符串用 `writeValueAsString`；`writeValue` 是直接写入文件或输出流。当前 responseBody 是 String，优先使用前者。

### 实施复核：响应对象序列化已经加入 HandlerAdapter

当前已经在反射调用后使用：

```java
httpResponse.responseBody =
        objectMapper.writeValueAsString(result);
```

对于 UserDao、Map、List 等对象，这个方向正确。

但当前 `method.invoke` 和响应序列化仍放在“遍历参数”的 for 循环内部，这是关键逻辑错误，必须先修正：

```text
当前：
每解析一个参数 → 调一次 Controller → 写一次响应

正确：
解析完所有参数 → Controller 只调用一次 → 响应只转换一次
```

后果：

- 无参方法不会进入循环，因此完全不执行；
- 多参数方法会执行多次；
- 第一次执行时后续参数尚未填充；
- 响应结果会被后一次循环覆盖。

正确结构：

```java
for (...) {
    // 只填 values[i]
}

Object result = method.invoke(controller, values);
httpResponse.responseBody = serialize(result);
```

此外还要区分返回类型：

```text
result == null → 空响应，不能 result.toString
result instanceof String → 若期望 text/plain，直接原样写
其他对象 → writeValueAsString，Content-Type = application/json
```

若所有返回值都无条件走 Jackson，String `"hello world"` 会变成包含引号的 JSON：

```json
"hello world"
```

这会使原先断言纯文本 `hello world` 的测试失败。需要明确当前框架是“所有 Controller 都返回 JSON”，还是区分文本和对象。

`HttpResponse` 后续应增加 contentType 和 status；ObjectMapper 也应作为 Adapter 的可复用字段，不要每次 handle 都 new。

RequestBody 的 `required=false` 仍需在 body 为空时直接给 values[i] = null 并跳过 readValue，否则 Jackson 仍会收到 null。

测试应将 JSON 响应再反序列化并断言字段，而不是只 println：

```java
UserDao result = objectMapper.readValue(
        response.responseBody, UserDao.class);
assertEquals("Jerry", result.getName());
assertEquals(19, result.getAge());
```

完成以上收尾后，再抽 HttpMessageConverter 才有意义。

### 第二次实施复核：参数循环和返回类型已修正，下一步是什么？

当前已将 `method.invoke` 移到参数循环之外，并区分：

```text
null → 空响应
String → 原样文本
其他对象 → Jackson JSON
```

无参方法、多参数方法重复调用以及 String 被额外加 JSON 引号的问题已在结构上修正。

仍有一个 RequestBody 边界未完成：

```text
required=false 且 body=null
```

当前仍会继续调用 `objectMapper.readValue(null, type)`。应在空 body 分支中直接设置参数 null 并跳过解析。测试也应增加 JSON 响应字段断言。

在这些收尾之后，下一项主功能建议转向 HandlerMapping 的 HTTP Method 支持，见问题 86。

## 86. Request Body 和响应 JSON 完成后，下一步做什么？

### 推荐主任务：支持 HTTP Method

当前映射只以 URL 字符串为 key：

```java
Map<String, HandlerMethod>
```

因此无法区分：

```text
GET  /users
POST /users
```

两个方法会被判定为重复路径，或后者覆盖前者。HTTP Method 是 MVC 路由的核心条件，下一步比继续增加 JSON 功能更有价值。

### 第一版模型

定义：

```java
enum RequestMethod {
    GET, POST, PUT, DELETE, PATCH
}
```

RequestMapping 增加：

```java
RequestMethod method() default RequestMethod.GET;
```

HttpRequest 增加：

```java
RequestMethod requestMethod;
```

### 映射 key 不再只是 String

定义不可变对象：

```java
class RequestMappingInfo {
    private final String path;
    private final RequestMethod method;

    // equals + hashCode
}
```

映射表：

```java
Map<RequestMappingInfo, HandlerMethod>
```

注册和查询都使用 path + method。只有两个条件都相同才属于重复映射。

### HandlerMapping 接口演进

当前：

```java
getHandlerMethod(String requestUrl)
```

可改为：

```java
getHandlerMethod(HttpRequest request)
```

因为路由选择已不只依赖 URL，后续还可能依赖 headers、params、Content-Type。

### 状态码语义

- 路径和方法都匹配：执行 Handler；
- 路径不存在：404；
- 路径存在但 HTTP Method 不匹配：405 Method Not Allowed；
- 相同 path + method 注册两次：启动失败。

### 测试

同一路径注册：

```text
GET  /users → queryUsers
POST /users → addUser
```

断言分别命中不同方法；发送 DELETE /users 时断言 405；再注册第二个 GET /users 时断言启动失败。

### 后续路线

HTTP Method 稳定后：

1. 类级别 `@RequestMapping("/users")` 路径前缀；
2. `@GetMapping` / `@PostMapping` 组合注解；
3. 路径变量 `/users/{id}`；
4. HttpMessageConverter；
5. 统一异常与状态码处理。

### 最终建议

先修 `required=false` 空 body 分支和 JSON 响应断言，然后实现 `RequestMethod + RequestMappingInfo`，让 HandlerMapping 从“字符串查表”升级为真正的 HTTP 路由匹配。

## 88. `@RequestMapping` 中能否写 `enum value()` 来区分 GET / POST？

### 为什么语法不合法

```java
enum value() default RequestMethod.Get;
```

不能这样写。`enum` 是声明枚举类型的关键字，不是“任意枚举”的通用返回类型。注解成员必须写一个确定的实际类型，例如 `RequestMethod`。

正确写法：

```java
RequestMethod method() default RequestMethod.GET;
```

枚举：

```java
public enum RequestMethod {
    GET, POST, PUT, DELETE, PATCH
}
```

### 为什么成员名应是 method 而不是 value

`value` 目前用于 URL 路径：

```java
String value();
```

GET / POST 表示 HTTP Method，使用 `method` 更清晰：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestMapping {
    String value();
    RequestMethod method() default RequestMethod.GET;
}
```

使用：

```java
@RequestMapping(value = "/users", method = RequestMethod.GET)
@RequestMapping(value = "/users", method = RequestMethod.POST)
```

若希望 `@RequestMapping("/users")` 仍可简写，路径成员继续叫 value。

### 如果想创建 GetMapping / PostMapping

可以设计组合注解：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@RequestMapping(method = RequestMethod.GET)
public @interface GetMapping {
    String value();
}
```

但这要求 RequestMapping 的 path 有默认值，并允许作为元注解使用：

```java
@Target({ElementType.METHOD, ElementType.ANNOTATION_TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestMapping {
    String value() default "";
    RequestMethod method() default RequestMethod.GET;
}
```

更重要的是，mini 框架不会自动实现 Spring 的 `@AliasFor` 属性合并。`@GetMapping("/users")` 的 value 存在 GetMapping 上，元注解 RequestMapping 的 value 仍是默认空字符串。HandlerMapping 需要专门读取具体组合注解并合并 path + method。

### 当前阶段推荐

第一版先不做 GetMapping / PostMapping 组合注解，直接使用：

```java
@RequestMapping(value = "/users", method = RequestMethod.GET)
```

先完成 `RequestMappingInfo(path, method)`、重复映射检测和 404/405。等路由稳定后，再实现组合注解属性合并。

### 最终结论

注解成员可以使用枚举，但返回类型必须写具体枚举类 `RequestMethod`，不能写关键字 `enum`。区分 GET/POST 应增加 `method()` 成员，URL 继续使用 `value()`。

## 80. 反射取到参数类型后，强转怎么自动填写？`(aClass.)` 这种写法对吗？

**结论：编译期强制转换 `(Xxx)` 不能用运行时的 `Class` / `Type` 自动填。** `parameter.getParameterizedType()` 给你的是运行时对象，不是源码里的类型名。IDE 也不会根据这个对象帮你补全 `(UserDao)`。反射场景要么用 `Class.cast()`，要么根本不强转——`Method.invoke` 吃的就是 `Object[]`。

出现位置：`HandlerAdapterImpl.handle`，当时草稿类似：

```java
if (AnnotationUtils.hasMeta(parameter.getAnnotations(), RequestMapping.class)) {
    Type parameterizedType = parameter.getParameterizedType();
    Object o = (aClass.) requestParams.get(parameter.getName());
}
```

### 为什么 `(aClass.)` 写不出来

Java 里这两种东西名字像、用法完全不同：

| 写法 | 什么时候确定 | 例子 |
|------|--------------|------|
| `(UserDao) obj` | **编译期**，括号里必须是类型名 | 编译器生成 `checkcast` |
| `UserDao.class` / `parameter.getType()` | **运行时**的 `Class` 对象 | 只是一个普通变量 |

所以：

```java
Class<?> aClass = parameter.getType();
Object o = (aClass) obj;     // 编译失败：括号里不能放变量
Object o = (aClass.) obj;    // 更不行：这不是合法语法
```

IDE 自动补全强制转换时，补的是**源码里已经写死的类型名**，例如你本地变量已经声明成 `UserDao dao = ...` 时，它才可能建议 `(UserDao)`。循环里每个 `parameter` 类型都可能不同（`Long`、`UserDao`、`String`……），编译器在写代码那一刻不知道下一次循环会是哪个类，所以**没有“按当前参数类型自动填括号”这件事**。

`Type parameterizedType = parameter.getParameterizedType();` 也帮不上忙：`Type` 是接口，运行时可能是 `Class`、`ParameterizedType`（如 `List<String>`）、`GenericArrayType` 等。你不能写 `(parameterizedType) obj`。

### 真正要用的 API：`getType()` 还是 `getParameterizedType()`

`java.lang.reflect.Parameter` 上两个方法容易混：

| 方法 | 返回值 | 适用 |
|------|--------|------|
| `parameter.getType()` | `Class<?>` | 原始类型。`Long userId` → `Long.class`；`UserDao userDao` → `UserDao.class` |
| `parameter.getParameterizedType()` | `Type` | 带泛型的完整类型。`List<String>` 时才能看到 `String` |

当前 Controller 是：

```java
public String getUser(@RequestParam Long userId)
public UserDao addUser(@RequestBody UserDao userDao)
```

这两个都没有泛型，用 `parameter.getType()` 就够。`getParameterizedType()` 留给以后 `List<UserDao>` 这类参数。

另外：参数上应判断 `@RequestParam` / `@RequestBody`，不是 `@RequestMapping`。`@RequestMapping` 标的是方法和类，用来声明 URL；`UserController` 里已经写成 `@RequestParam Long userId`、`@RequestBody UserDao userDao`。

### 写法一：根本不强转（当前 invoke 场景最合适）

`Method.invoke(Object obj, Object... args)` 的参数就是 `Object[]`。Map 里取出来已经是 `Object`，放进数组即可：

```java
Parameter[] parameters = methodName.getParameters();
Object[] args = new Object[parameters.length];
for (int i = 0; i < parameters.length; i++) {
    Parameter parameter = parameters[i];
    if (AnnotationUtils.hasMeta(parameter.getAnnotations(), RequestParam.class)
            || AnnotationUtils.hasMeta(parameter.getAnnotations(), RequestBody.class)) {
        args[i] = requestParams.get(parameter.getName());
    }
}
Object result = methodName.invoke(object, args);
```

这里**没有** `(Long)`、也没有 `(UserDao)`。JVM 在 `invoke` 里会按方法签名再检查实际类型；类型不对会抛 `IllegalArgumentException`，不是编译期强转失败。

记法：反射调用方法时，框架手里始终是 `Object`。强转是给**当前方法里后续要当具体类型用**的代码准备的，不是给 `invoke` 准备的。

### 写法二：运行时“按 Class 转换”——`Class.cast`

如果确实想根据参数类型做一次检查/转换，对应的不是 `(Xxx)`，而是 `Class` 上的实例方法：

```java
Class<?> requiredType = parameter.getType();
Object raw = requestParams.get(parameter.getName());
Object o = requiredType.cast(raw);
```

`Class.cast` 的语义接近：

```java
if (raw != null && !requiredType.isInstance(raw)) {
    throw new ClassCastException(...);
}
return (T) raw;   // 这个 T 是 Class<T> 上的泛型，对 Class<?> 来说结果仍是 Object
```

注意：`parameter.getType()` 是 `Class<?>`，`cast` 的返回值仍是 `Object`（因为 `?` 未知）。它**不会**让后面的局部变量变成 `Long` 或 `UserDao`，只是多一次运行时类型检查。对 `invoke` 来说，这一步经常是多余的。

### 写法三：字符串到目标类型——这不是强转，是转换

HTTP 查询参数通常是 `"1"` 这种字符串。下面两种完全不是一回事：

```java
Object o = (Long) "1";           // ClassCastException：String 不是 Long
Long id = Long.valueOf("1");     // 转换成功：解析字符串
```

`(Long)` 只检查“这个对象是不是已经是 Long（或其子类）”，不会把 `"1"` 解析成数字。`@RequestParam Long userId` 时，如果 `requestParams` 里存的是 `"1"`，必须自己写转换，例如：

```java
Object raw = requestParams.get(parameter.getName());
Class<?> type = parameter.getType();
Object converted;
if (raw == null) {
    converted = null;
} else if (type.isInstance(raw)) {
    converted = raw;
} else if (type == Long.class || type == long.class) {
    converted = Long.valueOf(raw.toString());
} else if (type == Integer.class || type == int.class) {
    converted = Integer.valueOf(raw.toString());
} else if (type == String.class) {
    converted = raw.toString();
} else {
    throw new IllegalArgumentException("暂不支持的参数类型: " + type.getName());
}
args[i] = converted;
```

官方 Spring 把这件事交给 `ConversionService` / `WebDataBinder`，不是靠强制转换。迷你框架第一版可以只支持 `String`、`Long`、`Integer`、`Boolean` 等有限集合。

`@RequestBody UserDao` 更进一步：请求体是 JSON 字符串，要反序列化成对象，仍然不是 `(UserDao) jsonString`。

### 和字段注入的对照

容器里按类型注入时也遇到过类似问题：`field.getType()` 得到 `Class<?>`，然后：

```java
Object dependency = beanFactory.getBeanForType(field.getType());
field.set(bean, dependency);   // Field.set 也吃 Object，同样不必 (UserService)
```

模式相同：

1. 用反射拿到 **`Class<?>`（运行时类型描述）**；
2. 按这个 `Class` 去查找或转换出 **`Object`**；
3. 再交给 `field.set` / `method.invoke`。

全程没有 `(具体类名)`。只有你在**非反射代码**里要把这个 `Object` 赋给 `UserDao dao` 这种确定类型的变量时，才写 `(UserDao)`。

### 常见误区

| 想法 | 实际 |
|------|------|
| `(parameter.getType()) obj` 或 `(aClass) obj` | 语法非法，括号里必须是类型名 |
| 拿到 `Type` 就能写成 `(Type) obj` | `Type` 是接口对象，不是强制转换语法 |
| IDE 会根据当前 `parameter` 自动填 `(Long)` | 循环里类型不固定，补全不了运行时才知道的类型 |
| `getParameterizedType()` 比 `getType()` 更“完整”，所以总该用它 | 无泛型时两者信息等价，且前者不是 `Class`，没法 `cast` |
| 强转能把 `"1"` 变成 `1L` | 不能；那是 `valueOf` / 转换器的工作 |
| `invoke` 前必须先强转成方法参数类型 | 不必；`invoke` 的参数就是 `Object...` |
| 参数上判断 `RequestMapping` | URL 映射看方法/类；参数绑定看 `RequestParam` / `RequestBody` |

### 推荐的最小实现顺序（仍不必现在改代码）

1. 组 `Object[] args`，按参数下标填值，然后 `invoke(object, args)`；
2. `@RequestParam` 用参数名从 `requestParams` 取值；值已经是目标类型就直接放，是字符串再按 `parameter.getType()` 做有限转换；
3. `@RequestBody` 以后再接 JSON 反序列化；
4. 需要泛型（`List<UserDao>`）时再解析 `ParameterizedType`。

### 最终建议

把 `(aClass.)` 丢掉。当前这一层要的是：

```java
args[i] = requestParams.get(parameter.getName());
```

需要按类型处理时用 `parameter.getType()`（`Class<?>`），检查用 `type.cast(raw)` 或 `type.isInstance(raw)`，字符串变数字用 `Long.valueOf` 这类转换。**不要试图让强制转换括号“自动填写”。**

## 81. 怎么给 Controller 方法入参赋值？Long/String 能手写转换，UserDao 能在 Adapter 里写死吗？

**结论：`invoke` 时参数对象的运行时类型必须对得上方法签名，但 Adapter 里不要写死 `UserDao`。** Long/String 这种 JDK 标量可以维护一张有限转换表；`UserDao` 这类业务类型必须走通用绑定：目标类型从 `parameter.getType()` 读出来，数据从请求里读，用反射或 JSON 库填属性。框架代码一旦出现 `new UserDao()`，每加一个业务类就要改 Adapter，这就不是框架了。

出现位置：`HandlerAdapterImpl.handle` 组 `method.invoke` 的参数；对照 `UserController`：

```java
public String getUser(@RequestParam Long userId)
public UserDao addUser(@RequestBody UserDao userDao)
```

### 需要“调配成这个方法的参数类型”吗？

需要，但是运行时对齐，不是编译期强转。

```java
Object[] args = new Object[parameters.length];
// 把每个 args[i] 填成“能赋给第 i 个参数”的对象
methodName.invoke(object, args);
```

JVM 会检查：`args[0]` 实际是不是 `Long`（或其兼容类型）。对不上就 `IllegalArgumentException`，对上了 Controller 方法内部就能当 `Long userId` / `UserDao userDao` 用。

对齐有两条完全不同的路，由**注解**决定数据从哪来，由 **`parameter.getType()`** 决定要变成什么：

| 注解 | 数据从哪来 | 典型目标类型 | Adapter 里怎么做 |
|------|------------|--------------|------------------|
| `@RequestParam` | 查询串 / 表单，一个名字对应一个值 | `String`、`Long`、`Integer`、`Boolean` | 有限转换表：`"1"` → `1L` |
| `@RequestBody` | 整个请求体（通常是 JSON） | `UserDao` 等业务对象 | 通用反序列化：JSON + `Class<?>` → 对象 |
| 无注解且类型是 `HttpRequest` / `HttpResponse` | 当前这次调用的框架对象 | 框架类型 | 直接放入 `args` |

不要把 `@RequestParam` 和 `@RequestBody` 合成一条 `requestParams.get(name)` 再强转。`userId=1` 是一个字符串；`UserDao` 是多个字段组成的对象，通常根本不在 query Map 里。

当前 `HttpRequest.requestParams` 是 `Map<String, Object>`，只适合 `@RequestParam`。`@RequestBody` 以后应另有字段，例如 `String requestBody` 或原始字节，而不是指望 `requestParams.get("userDao")` 已经是 `UserDao`。

### Long / String：可以在代码里写死，但写死的是类型表，不是某个业务方法

标量类型是封闭集合。框架写下面这种 if 是合理的，官方 Spring 的 `ConversionService` 默认转换器也是这个思路：

```java
Object convertSimple(Object raw, Class<?> type) {
    if (raw == null) {
        return null;
    }
    if (type.isInstance(raw)) {
        return raw;
    }
    String text = raw.toString();
    if (type == String.class) {
        return text;
    }
    if (type == Long.class || type == long.class) {
        return Long.valueOf(text);
    }
    if (type == Integer.class || type == int.class) {
        return Integer.valueOf(text);
    }
    if (type == Boolean.class || type == boolean.class) {
        return Boolean.valueOf(text);
    }
    throw new IllegalArgumentException("暂不支持的简单类型: " + type.getName());
}
```

`@RequestParam` 分支可以写成：

```java
if (AnnotationUtils.hasMeta(parameter.getAnnotations(), RequestParam.class)) {
    Object raw = requestParams.get(parameter.getName());
    args[i] = convertSimple(raw, parameter.getType());
}
```

这里写死的是 `Long.class`、`String.class`，**不是** `getUser` 这个方法，也不是 `userId` 这个名字。下一个 Controller 如果是 `@RequestParam Integer age`，同一张表就能用。

### UserDao：不能、也不该在 Adapter 里写死

错误方向：

```java
// 框架代码里不要这样
if (parameter.getType() == UserDao.class) {
    UserDao userDao = new UserDao();
    userDao.setId(Long.valueOf(requestParams.get("id").toString()));
    userDao.setName(requestParams.get("name").toString());
    args[i] = userDao;
}
```

问题：

1. 再来 `OrderDao`、`BookDao` 就要继续加 if，Adapter 变成业务代码；
2. 字段名、类型都和 `UserDao` 绑死，Controller 改个属性框架跟着改；
3. JSON 体、表单、query 三种来源被揉进同一段硬编码。

正确方向：Adapter **不知道** `UserDao` 这个类名。它只知道“第 i 个参数要一个 `parameter.getType()` 描述的对象”。构造过程必须对任何有 setter / 可 JSON 映射的类都成立。

#### 做法 A：JSON 反序列化（对应 `@RequestBody`，和 Spring 更接近）

请求体：

```json
{"id":1,"name":"tom","age":18}
```

框架：

```java
if (AnnotationUtils.hasMeta(parameter.getAnnotations(), RequestBody.class)) {
    String json = httpRequest.requestBody;   // 以后给 HttpRequest 加这个字段
    Class<?> type = parameter.getType();     // 运行时是 UserDao.class
    args[i] = objectMapper.readValue(json, type);
}
```

`readValue(json, type)` 内部会：`new UserDao()`（通过无参构造），再按 JSON 字段名调 `setId` / `setName` / `setAge`。**UserDao 的知识在 UserDao 自己的字段和 JSON 里，不在 Adapter 里。** 换成 `OrderDao` 只要 JSON 结构和类对得上，Adapter 一行都不用改。

迷你框架第一版甚至可以先手写一个极简版，仍然通用：

```java
Object bindJsonObject(String json, Class<?> type) throws Exception {
    Object target = type.getDeclaredConstructor().newInstance();
    // 解析出 Map<字段名, 字符串值> 后：
    for (Field field : type.getDeclaredFields()) {
        Object raw = map.get(field.getName());
        if (raw == null) {
            continue;
        }
        field.setAccessible(true);
        field.set(target, convertSimple(raw, field.getType()));
    }
    return target;
}
```

这里循环的是 **`type.getDeclaredFields()`**，`type` 是参数上读到的 `UserDao.class`。没有 `UserDao` 这个标识符。字段类型 `Long` / `String` / `Integer` 再复用上面那张标量转换表。

#### 做法 B：按属性名绑表单（对应 Spring 的命令对象 / `@ModelAttribute`）

如果以后支持 `id=1&name=tom&age=18` 填进对象，也是同一套路：

```java
Object target = parameter.getType().getDeclaredConstructor().newInstance();
for (Field field : parameter.getType().getDeclaredFields()) {
    Object raw = requestParams.get(field.getName());
    if (raw != null) {
        field.setAccessible(true);
        field.set(target, convertSimple(raw, field.getType()));
    }
}
args[i] = target;
```

仍然没有写死 `UserDao`。当前项目里 `addUser` 标的是 `@RequestBody`，优先走做法 A，不要和 `@RequestParam` 混用同一张 query Map。

### 一张图看清“谁知道 UserDao”

```text
HTTP 进来
  ├─ query: userId=1          → @RequestParam → convertSimple → Long
  └─ body:  {"id":1,...}      → @RequestBody  → 通用绑定(type) → UserDao 实例
                                                      ↑
                                        type = parameter.getType()
                                        运行时才是 UserDao.class
                                        源码里不出现 UserDao 这个词

然后：
args[i] = 上面得到的 Object
method.invoke(controller, args)
```

Controller 作者写死 `UserDao` 是对的：那是业务方法签名。框架作者写死 `UserDao` 是错的：框架只写“按 Class 构造 + 按字段填充”。

### 和 IoC 注入的对照

`@Autowired UserService userService` 时也没有在注入器里写 `new UserService()`：

```text
requiredType = field.getType()
→ getBeanForType(requiredType)
→ field.set(bean, dependency)
```

Web 参数绑定是平行故事：

```text
requiredType = parameter.getType()
→ 从 HTTP 构造出该类型的对象（转换或反序列化）
→ args[i] = 该对象
→ method.invoke(controller, args)
```

区别只是对象从哪来：容器里已有 Bean，还是从这一次请求的字符串现场造出来。

### 常见误区

| 想法 | 实际 |
|------|------|
| Adapter 必须 `new UserDao()` 才能给 `addUser` 传参 | 必须造出 UserDao 实例，但要用 `type.getDeclaredConstructor().newInstance()`，`type` 来自参数 |
| 业务类型太多，只能一个个 if | 业务类型走同一条通用绑定；if 只留给 JDK 标量 |
| `requestParams.get("userDao")` 再强转成 UserDao | query Map 里通常没有现成对象；body 是 JSON 字符串 |
| `@RequestParam` 和 `@RequestBody` 用同一套取值 | 一个是按参数名取单值，一个是整段 body |
| 先把 JSON 转成 UserDao 再放进 requestParams，Adapter 只 get | 把业务反序列化提前到进框架之前，等于测试里手填对象，框架没有学到绑定 |
| 转换表要覆盖所有业务类 | 转换表只覆盖 String/数字/布尔；业务类用字段循环 + 这张表 |

### 当前建议的实现顺序（仍可先讨论、后改代码）

1. 组 `Object[] args`，`invoke(object, args)`。无参方法（`/hello`）数组长度为 0。
2. `@RequestParam` + `convertSimple`，先打通 `/getUser?userId=1`。
3. `HttpRequest` 增加原始 body；`@RequestBody` 用 `parameter.getType()` 做通用绑定，不要出现 `UserDao` 字面量。
4. 规则变多后再抽 `HandlerMethodArgumentResolver`。

### 最终建议

入参必须对上方法签名，但**对上的方式按注解分流**：标量用手写转换表，业务对象用“目标 Class + 通用填充”。`HandlerAdapterImpl` 里可以出现 `Long.class`，**不可以**出现 `UserDao.class` / `new UserDao()`。

## 82. `Object[] values` 里放 Integer、String、UserDao，它们还保留原来的类型吗，还是都变成了 Object？

**结论：对象本身不会变成 Object。** `Object[]` 只表示“这个格子能指向任何对象”；格子里的引用仍指向原来的 `Integer` / `String` / `UserDao` 实例。编译期看到的是 `Object`，运行时 `getClass()` 仍是原来的类。`Method.invoke` 正是靠运行时类型去对方法签名，所以放进 `Object[]` 不会把类型信息弄丢。

出现位置：`HandlerAdapterImpl.handle` 中的 `Object[] values = new Object[parameters.length];`

### 两套类型，不要混

Java 每个值都有两层类型：

| 层次 | 是什么 | 例子 |
|------|--------|------|
| 编译期类型（引用的静态类型） | 变量/数组元素在源码里声明的类型 | `values[i]` 的类型是 `Object` |
| 运行时类型（对象的真实类型） | 堆上那个对象 `new` 出来时的类 | `values[i].getClass()` 可能是 `Integer`、`String`、`UserDao` |

放进数组 = **换了一个更宽的引用去指向同一个对象**，不是拷贝成 Object、也不是改对象的类。

```java
Integer n = Integer.valueOf(1);
String s = "hello";
UserDao u = new UserDao();

Object[] values = new Object[3];
values[0] = n;
values[1] = s;
values[2] = u;

values[0].getClass();   // Integer
values[1].getClass();   // String
values[2].getClass();   // UserDao
values[0] instanceof Integer;  // true
```

内存上可以想成：

```text
values ──► [ 格子0 | 格子1 | 格子2 ]     ← 数组的编译期类型是 Object[]
               │       │       │
               ▼       ▼       ▼
            Integer  String  UserDao     ← 三个对象各自还是原来的类
```

三个格子的“牌子”都写着 Object（所以你不能直接 `values[0].intValue()`，编译器只承认 Object 上的方法）。牌子后面挂的人没变。

### 为什么还要写成 Object[]

因为一次调用的多个参数类型通常不同：第 0 个是 `Long`，第 1 个是 `UserDao`。Java 数组元素类型必须统一，能装下所有这些引用的最小公共类型就是 `Object`。`Method.invoke` 的签名也是：

```java
public Object invoke(Object obj, Object... args)
```

框架在组参时本来就不知道（也不该在源码里写死）下一格是 Integer 还是 UserDao，所以用 `Object[]` 当托盘。托盘是 Object，托盘上的菜还是各自的菜。

这和已经用过的结构完全一样：

```java
Map<String, Object> requestParams;   // get 出来编译期是 Object
field.set(bean, dependency);         // set 吃的是 Object
Object o = singletonBeanMap.get(key);
```

`requestParams.get("userId")` 若实际放进去的是 `Long`，取出来编译期是 `Object`，运行时仍是 `Long`。

### 编译期变 Object 意味着什么

因为 `values[i]` 静态类型是 `Object`，**当前方法里**不能当 Integer 用：

```java
values[0].intValue();        // 编译失败：Object 没有 intValue
Integer x = values[0];       // 编译失败：需要强转
Integer x = (Integer) values[0];  // 可以，但这是给“你自己后续当 Integer 用”的
```

`invoke` **不需要**你先转回 Integer。它拿到 `Object[]` 后，用方法元数据里的参数类型去做运行时检查：第 i 个参数声明是 `Long`，则要求 `values[i]` 的运行时类型能赋给 `Long`（或装箱兼容）。检查的是对象真实类型，不是数组格子的静态类型。

所以：

- 放进 `Object[]`：静态类型变宽，真实类型不变；
- 再 `invoke`：按真实类型对签名，不要求你先强转。

### 会“变成 Object”的只有一种情况：你自己 new 了别的东西

```java
values[0] = n.toString();           // 现在格子里是 String "1"，不再是 Integer
values[0] = new Object();           // 现在是光秃秃的 Object 实例
```

单纯赋值 `values[0] = n` 不会发生这种事。

装箱要注意：`values[i] = 1;`（int 字面量）会变成 **`Integer`**，不是 `int`，也不是 `Object`。`Object[]` 装不了真正的 `int`/`long` 这种基本类型，只能装它们的包装类。Controller 写 `long userId` 时，`invoke` 会把 `Integer`/`Long` 再拆箱；若你放进去的是 `Integer` 而方法要 `Long`，可能对不上，所以转换表应产出 `Long.valueOf`，不要只产出 `Integer`。

### 和强制转换那一轮的关系

上一问里 `(aClass.)` 写不出来，原因正在这里：

- 你手里的变量类型是 `Object`（从数组或 Map 取出）；
- 对象真实类型是 `UserDao`；
- 编译器只看变量类型，所以不会自动填 `(UserDao)`；
- `invoke` 不看你有没有写 `(UserDao)`，只看真实类型对不对。

`getClass()` / `instanceof` 看的是真实类型；`(Xxx)` 和局部变量声明看的是编译期类型。

### 常见误区

| 想法 | 实际 |
|------|------|
| 放进 `Object[]` 后对象就变成 Object 类了 | 引用变宽，对象类不变 |
| `values[i].getClass()` 一定是 `Object.class` | 一般是 Integer / String / UserDao |
| 所以必须先强转再 invoke | 不必；invoke 吃 Object[]，自己按签名检查 |
| `Object[]` 和 `new Object()` 一样 | 前者是“装引用的格子”，后者才是一个真正的 Object 实例 |
| 数组元素静态类型是 Object，invoke 会失败 | 失败只发生在真实类型与方法参数不兼容时，例如方法要 Long 你放了 String |
| `int` 放进 Object[] 还是 int | 会装箱成 Integer |

### 最终建议

把 `Object[] values` 理解成**参数托盘**：格子统一标成 Object，是为了把不同类型的实参排成一列交给 `invoke`。Integer、String、UserDao 放进去后**原来的类型还在**。组参时保证每个格子指向的对象真实类型对得上 Controller 参数即可，不要为了“变成 Object”再包一层，也不要为了“还原类型”在 invoke 前强转。

## 83. `requestParams.get(parameter.getName())` 按参数名匹配，为什么拿不到名字？

**结论：方法参数名默认不进字节码。** `parameter.getName()` 在未加 `-parameters` 编译时返回 `arg0`、`arg1`，不是源码里的 `userId`。`requestParams` 的 key 若是 `userId`，`get("arg0")` 就是 null。这和字段不同：`Field.getName()` 一定能拿到字段名，因为字段名是 class 文件的正式成员。框架侧可靠做法是给 `@RequestParam` 加 `value()`，用注解里的名字去 Map 里取；`-parameters` 只是可选的便利，不能当唯一来源。

出现位置：`HandlerAdapterImpl.handle`

```java
values[i] = requestParams.get(parameter.getName());
```

对照：

```java
public String getUser(@RequestParam Long userId)
```

以及当前空注解：

```java
public @interface RequestParam {
}
```

父 POM 只有 `maven.compiler.source/target`，没有 `-parameters`。`minispring-web` 还把 compiler 设成了 8。

### 反射里“名字”分两种

| API | 默认能否拿到源码名 | 原因 |
|------|-------------------|------|
| `Field.getName()` | 能 | 字段名写在 class 的 Field 表里，加载、链接都要用 |
| `Method.getName()` | 能 | 方法名同样是成员标识 |
| `Parameter.getName()` | **默认不能** | 参数名对 JVM 执行不是必需的；javac 默认不写入 |

方法参数在字节码里默认只保留类型和顺序：`getUser(Ljava/lang/Long;)Ljava/lang/String;`。叫 `userId` 还是 `id`，运行时不需要知道。所以 `getName()` 的约定是：

```java
parameter.isNamePresent()   // 没开 -parameters 时是 false
parameter.getName()         // false 时返回 "arg0"、"arg1"...
```

调试时如果看到 key 对不上，多半就是拿着 `"arg0"` 去查 `"userId"`。

本地变量表（`-g` / IDEA 默认调试信息）里其实可能有 `userId`，但那是给调试器看的 `LocalVariableTable`。`Parameter.getName()` **不读**这张表，只认 Java 8 起的 `MethodParameters` 属性，必须显式 `-parameters` 才会生成。

### 为什么字段注入没踩这个坑

`@Autowired` 扫的是字段：

```java
@Autowired
UserService userService;
```

`field.getName()` → `"userService"`，稳定。方法参数没有同等待遇。按参数名匹配 HTTP 查询串，等于依赖一件编译器默认不保证的事。

### 三条路，框架该走哪条

#### 1. 注解写明名字（Spring 的主路径，应作为迷你框架的主路径）

```java
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestParam {
    String value() default "";
}
```

Controller：

```java
@RequestMapping("/getUser")
public String getUser(@RequestParam("userId") Long userId) {
    return userService.getUser(userId).toString();
}
```

Adapter：

```java
RequestParam requestParam = parameter.getAnnotation(RequestParam.class);
String name = requestParam.value();
values[i] = requestParams.get(name);
```

查询串 `?userId=1` 的 key 来自**注解字符串**，与 Java 参数叫什么无关，也不依赖编译参数。`value` 还可以和参数名不同：`@RequestParam("id") Long userId` 去取 `id`。

这正是注解属性写成 `String value()` 的典型用途：运行时能读到的、作者显式提供的名字。

#### 2. 编译保留参数名（便利，不能当唯一依赖）

javac：

```text
javac -parameters ...
```

Maven：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
    </configuration>
</plugin>
```

IDEA：Settings → Build → Compiler → Java Compiler → Additional command line parameters 填 `-parameters`，然后 Rebuild。只改 Maven 不够，若测试是 IDEA 直接 javac 出来的 class，仍然没有 `MethodParameters`。

之后 `parameter.getName()` 才是 `userId`。官方 Spring 在 `@RequestParam` 的 `value` 为空时会尝试用这个名字；拿不到就抛类似：

```text
Name for argument of type [java.lang.Long] not specified,
and parameter name information not available via reflection.
Ensure that the compiler uses the '-parameters' flag.
```

迷你框架也可以学：`value` 非空用 value；为空则 `isNamePresent()` 为 true 才用 `getName()`，否则明确报错。不要静默 `get("arg0")`。

#### 3. 按参数下标、不按名字（只适合教学试跑，不适合当 API）

只有一个 `@RequestParam`、Map 里也只有一个值时，可以 `values[i] = 唯一那个 value`。多参数、名字对不上就会乱。不要作为设计。

### 推荐的取值顺序（对齐 Spring）

```text
1. @RequestParam.value() 非空 → 用它当 requestParams 的 key
2. 否则若 parameter.isNamePresent() → 用 parameter.getName()
3. 否则抛异常，提示补 value 或加 -parameters
```

第一版甚至可以**只做第 1 步**：强制 `@RequestParam("userId")`。少一个编译开关，行为确定，也顺便巩固“注解属性 `value()` 是给运行时读的”。

### 和 `@RequestBody` 的关系

`RequestBody` 现在元注解了 `@RequestParam`，`hasMeta(..., RequestParam.class)` 对 `@RequestBody UserDao` 也会为 true，然后又去 `requestParams.get(参数名)`。body 对象本来就不在 query Map 里，再加上参数名是 `arg0`，这条分支会更乱。`@RequestBody` 不应标成 `@RequestParam` 的元注解；参数绑定应按**直接注解**分流：有 `RequestParam` 走 query，有 `RequestBody` 走 body。

### 常见误区

| 想法 | 实际 |
|------|------|
| `parameter.getName()` 和 `field.getName()` 一样可靠 | 字段名在 class 里；参数名默认不在 |
| 调试能看到 `userId`，反射就一定能拿到 | 调试读 LocalVariableTable；`getName()` 读 MethodParameters |
| 开 IDEA 调试信息就够了 | 不够，要 `-parameters` |
| 只改 Maven，IDE 运行立刻生效 | IDE 自己编译时也要加同样的参数并 Rebuild |
| 框架必须用 Java 参数名去对 query | 更稳的是注解 `value`；参数名只是缺省 |
| 拿到 `arg0` 说明 Parameter API 坏了 | 这是未保留真实名字时的占位名，工作正常 |

### 最终建议

`get(parameter.getName())` 这条路在当前编译配置下会稳定失败。不要继续抠 `getName()`。给 `@RequestParam` 加上 `String value()`，Controller 写成 `@RequestParam("userId")`，用注解值去取 Map。若以后想像 Spring 那样省略名字，再同时加编译器 `-parameters` 和 `isNamePresent()` 判断。

## 84. 想让 `@RequestParam` 的 `value` 不声明时自动用参数名，注解里能写成带方法体的 default 吗？

**结论：不能。** 注解属性没有方法体，默认值必须是编译期常量，写不出“没填就用参数名”。`default ""` 只表示空字符串，不会 magically 变成 `userId`。省略 `value` 时改用参数名，是 **HandlerAdapter 里的 if**：`value` 非空用注解，为空再用 `parameter.getName()`。而 `getName()` 仍要求编译加 `-parameters`，否则还是 `arg0`。另外这里是**方法参数名**，不是字段名。

出现位置：当前 `RequestParam` 草稿为

```java
public @interface RequestParam {
    default String value() {
        return "";
    };
}
```

Adapter 已写成：

```java
RequestParam annotation = parameter.getAnnotation(RequestParam.class);
values[i] = requestParams.get(annotation.value());
```

Controller 仍是 `@RequestParam Long userId`（没写 `"userId"`）。

### 注解属性的正确语法

注解里的 `value()` 不是普通方法，不能有 `{}` 方法体，也不能 `return`。编译器会报类似 “annotation members cannot have bodies” / “应该为 ;”。

正确写法（此前问题 18、19 已出现过这种形态）：

```java
public @interface RequestParam {
    String value() default "";
}
```

对照：

| 写法 | 是什么 | 结果 |
|------|--------|------|
| `String value();` | 注解属性，必填 | 使用处必须写 `@RequestParam("userId")` 或 `@RequestParam(value = "userId")` |
| `String value() default "";` | 注解属性，缺省为空串 | `@RequestParam` 可以不写括号；运行时 `annotation.value()` 是 `""` |
| `default String value() { return ""; }` | 普通接口 default 方法 | **不是合法注解属性** |

`default` 在注解里的位置在 **方法签名后面**，表示这个属性的缺省常量；在接口里的 `default` 在 **返回类型前面**，表示接口实现。两者只是同一个英文单词。

缺省值必须是编译期常量：字符串字面量、基本类型、枚举、`Class`、嵌套注解、以及它们的数组。不能调用 `parameter.getName()`，不能读被标注元素，不能写表达式去“发现当前参数叫什么”。注解类型在定义时根本看不到 `userId` 这个词。

### 为什么注解自己没法“自动用参数名”

`@RequestParam` 贴在参数上时，发生了两件独立的事：

```text
源码：  getUser(@RequestParam Long userId)
         │                 │
         │                 └─ 参数名叫 userId（默认不进 class）
         └─ 注解实例：value = ""（因为 default ""）
```

运行时你分别去取：

```java
parameter.getAnnotation(RequestParam.class).value();  // ""
parameter.getName();                                  // 有 -parameters 才是 "userId"，否则 "arg0"
```

注解对象不知道自己贴在哪个参数上。`value()` 只返回注解里存的那份常量。要把两件事接起来，只能在读注解的代码里写规则——也就是 Adapter，不是注解定义。

这和 Spring 完全一致：`@RequestParam` 的 `value` 默认 `""`（另有 `name` 作别名），`RequestParamMethodArgumentResolver` 发现为空才去解析参数名。

### Adapter 里该怎么写“没声明就用参数名”

```java
RequestParam annotation = parameter.getAnnotation(RequestParam.class);
if (annotation == null) {
    continue; // 或走别的解析器；hasMeta 为 true 不代表本参数上直接有 @RequestParam
}
String name = annotation.value();
if (name == null || name.isEmpty()) {
    if (!parameter.isNamePresent()) {
        throw new IllegalStateException(
            "请在 @RequestParam 中写明名字，或使用 javac -parameters 编译: "
                + parameter.getType().getSimpleName());
    }
    name = parameter.getName();
}
values[i] = requestParams.get(name);
```

语义：

```text
@RequestParam("id") Long userId  → 用 "id"
@RequestParam Long userId        → value 为 ""，改用参数名 "userId"（需 -parameters）
```

没有 `-parameters` 时，第二行仍会变成 `get("arg0")` 或走到上面的异常。想让省略写法真正可用，还要：

1. Maven `maven-compiler-plugin` 设 `<parameters>true</parameters>`；
2. IDEA Compiler 增加 `-parameters` 并 Rebuild；
3. Adapter 用 `isNamePresent()` 判断，不要把 `arg0` 当业务名。

这不是注解 `default` 能单独完成的，是 **注解缺省空串 + 运行时回退 + 编译保留参数名** 三件套。

### “字段名”和“参数名”不要混

用户说“自动使用字段名字”，当前场景是方法参数：

```java
public String getUser(@RequestParam Long userId)
```

能回退的是 **`userId` 这个参数名**，不是某个字段。字段名（`Field.getName()`）只在 `@Autowired` 注入、或以后按属性绑 `UserDao` 时稳定可用。`@RequestParam` 标在参数上，回退只能找 `Parameter.getName()`。

`@RequestParam` 的 `@Target` 目前含 `ElementType.TYPE`，标在类上也没有“字段名”可对。第一版应只保留 `ElementType.PARAMETER`。

### 若暂时不想开 `-parameters`

省略 `value` 这条便利就先不要做。强制：

```java
@RequestParam("userId") Long userId
```

`annotation.value()` 一定是 `"userId"`，和编译开关无关。等参数绑定跑通再加回退。两种能力可以并存，但回退不是靠把 `default` 写成方法体。

### 顺带：`getAnnotation` 和 `hasMeta` 不一致

当前循环条件是 `hasMeta(..., RequestParam.class)`，取值却是 `parameter.getAnnotation(RequestParam.class)`。

- `@RequestParam Long userId`：两者都有，`getAnnotation` 正常；
- `@RequestBody UserDao userDao`：`RequestBody` 上有元注解 `@RequestParam`，`hasMeta` 为 true，但参数上没有 `@RequestParam` 本身，`getAnnotation` 为 **null**，下一行 NPE。

`@RequestBody` 不应元注解 `@RequestParam`。判断时用 `parameter.isAnnotationPresent(RequestParam.class)` 或 `getAnnotation != null`，与取值同一口径。

### 常见误区

| 想法 | 实际 |
|------|------|
| `default String value() { return ""; }` 能当注解缺省 | 非法；注解属性不能有方法体 |
| `String value() default "";` 会自动填参数名 | 只会得到空串 `""` |
| 注解定义里能读到被标注的 `userId` | 不能；默认值是常量 |
| 空 value 时 Adapter 里 `get("")` 能命中 | Map 的 key 是 `userId`，不是空串 |
| 回退用字段名 | `@RequestParam` 在参数上，用 `parameter.getName()` |
| 只改注解、不改编译参数，省略写法就能用 | 省略依赖 `-parameters`，否则仍是 `arg0` |

### 最终建议

把注解改成 `String value() default "";`，不要写方法体。所谓“不声明就用名字”，写在 Adapter：`value` 非空用注解，为空且 `isNamePresent()` 再用参数名，否则报错。这不是注解语言能自动完成的功能。若现在编译还没加 `-parameters`，Controller 先显式写 `@RequestParam("userId")`。

## 85. Spring 里 `@RequestParam` 不写 value 时，参数名是怎么补上的？

**结论：注解本身不会自动填参数名。** Spring 和上一问说的三件套一样：`value`/`name` 默认 `""`；解析器发现为空再去反射取方法参数名；取不到就抛异常，提示加 `-parameters`。补名字的代码在 `AbstractNamedValueMethodArgumentResolver.updateNamedValueInfo`，不在 `@RequestParam` 定义里。取到名字之后，再用这个名字去 `request.getParameterValues(name)`，最后用 `WebDataBinder` 把字符串转成 `Long` 等目标类型。

对照当前迷你代码：`HandlerAdapterImpl` 里 `requestParams.get(annotation.value())`；注解是 `String value() default "";`。Spring 把“读注解 → 空则补名 → 按名取值 → 类型转换”拆成了独立解析器，但规则与问题 84 建议的 if 相同。

### 调用链（MVC）

```text
RequestMappingHandlerAdapter
  → InvocableHandlerMethod.invokeForRequest
    → 对每个 MethodParameter：
         HandlerMethodArgumentResolverComposite
           → 第一个 supportsParameter == true 的解析器
           → RequestParamMethodArgumentResolver.resolveArgument
             → 父类 AbstractNamedValueMethodArgumentResolver
```

`@RequestParam`、`@PathVariable`、`@RequestHeader`、`@CookieValue` 都走同一套“按名字取值”的父类。迷你框架现在把这些 if 写在 Adapter 循环里，官方是每个来源一个 Resolver。

### 1. 注解：默认空串，不做魔法

```java
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequestParam {

    @AliasFor("name")
    String value() default "";

    @AliasFor("value")
    String name() default "";

    boolean required() default true;

    String defaultValue() default ValueConstants.DEFAULT_NONE;
}
```

要点：

- 只允许标在 **PARAMETER** 上，没有 TYPE；
- `value` 和 `name` 互为别名（`@AliasFor`），写 `@RequestParam("userId")` 或 `@RequestParam(name = "userId")` 一样；
- 缺省都是 `""`，**不是**参数名；
- `required` / `defaultValue` 是取值之后的策略，与“名字从哪来”无关。

`@RequestParam Long userId` 运行时 `ann.name()` 仍是 `""`。

### 2. 解析器先把注解抄进 NamedValueInfo

`RequestParamMethodArgumentResolver.createNamedValueInfo`：

```java
RequestParam ann = parameter.getParameterAnnotation(RequestParam.class);
return (ann != null
    ? new RequestParamNamedValueInfo(ann)
    : new RequestParamNamedValueInfo());
```

有注解时：

```java
super(annotation.name(), annotation.required(), annotation.defaultValue());
```

此时 `NamedValueInfo.name` 可能仍是 `""`。无注解但处于 default resolution 模式（简单类型也当 request param）时，名字同样先留空，留给下一步补。

判断是否由自己处理用的是 **参数上是否直接有** `@RequestParam`：

```java
parameter.hasParameterAnnotation(RequestParam.class)
```

不是 `hasMeta`。`@RequestBody` 不会被这个解析器当成 RequestParam。

### 3. 空名字才回退到方法参数名（关键）

父类 `AbstractNamedValueMethodArgumentResolver.updateNamedValueInfo`：

```java
private NamedValueInfo updateNamedValueInfo(MethodParameter parameter, NamedValueInfo info) {
    String name = info.name;
    if (info.name.isEmpty()) {
        name = parameter.getParameterName();
        if (name == null) {
            throw new IllegalArgumentException("""
                Name for argument of type [%s] not specified, and parameter name information not \
                available via reflection. Ensure that the compiler uses the '-parameters' flag."""
                    .formatted(parameter.getNestedParameterType().getName()));
        }
    }
    String defaultValue = (ValueConstants.DEFAULT_NONE.equals(info.defaultValue) ? null : info.defaultValue);
    return new NamedValueInfo(name, info.required, defaultValue);
}
```

这就是 Spring 的“不声明就用参数名”：**写在解析器里，不写在注解里。** `getNamedValueInfo` 还会把结果缓存在 `ConcurrentHashMap<MethodParameter, NamedValueInfo>` 里，每个参数只算一次。

和迷你框架建议写法的对应：

| Spring | 迷你框架对应 |
|--------|----------------|
| `info.name.isEmpty()` | `annotation.value().isEmpty()` |
| `parameter.getParameterName()` | `parameter.getName()`（在 `isNamePresent()` 为 true 时） |
| `name == null` 抛异常并提示 `-parameters` | 不要 `get("arg0")`，同样抛错 |

### 4. 参数名怎么发现：ParameterNameDiscoverer

`MethodParameter.getParameterName()` 不直接调 `Parameter.getName()`，而是走策略接口：

```java
public String getParameterName() {
    ParameterNameDiscoverer discoverer = this.parameterNameDiscoverer;
    if (discoverer != null) {
        String[] parameterNames = discoverer.getParameterNames(method);
        if (parameterNames != null) {
            this.parameterName = parameterNames[this.parameterIndex];
        }
        this.parameterNameDiscoverer = null; // 只发现一次
    }
    return this.parameterName;
}
```

现行默认实现 `DefaultParameterNameDiscoverer`：

```text
若有 Kotlin → KotlinReflectionParameterNameDiscoverer
然后 → StandardReflectionParameterNameDiscoverer
```

`StandardReflectionParameterNameDiscoverer` 就是对 Java 8 `Parameter` API 的包装：

```java
for (Parameter param : parameters) {
    if (!param.isNamePresent()) {
        return null;          // 整组作废，不要留下 arg0
    }
    parameterNames[i] = param.getName();
}
```

**任意一个参数没有真实名字，就返回 null。** 于是 `updateNamedValueInfo` 走进那条著名异常。Spring **不会**把 `arg0` 当成 query 名去用。

历史变化（便于理解网上旧文章）：

| 时期 | 发现参数名的手段 |
|------|------------------|
| Spring 5 / Boot 2 | 反射 `-parameters` **加上** ASM 读 `LocalVariableTable`（调试信息里的局部变量名） |
| Spring 6.1+ / Boot 3.2+ | 去掉 `LocalVariableTableParameterNameDiscoverer`，Java 侧只认 `-parameters` |

所以升级 Boot 3.2 后，以前“开了 debug 就能省略 `@RequestParam("userId")`”的项目会突然报错。官方要求：要么写明名字，要么编译加 `-parameters`。Spring Boot 父 POM 一般已打开 compiler `parameters`。

### 5. 有了名字之后：取值 + 转换

父类 `resolveArgument` 大纲：

```text
name = NamedValueInfo.name（已可能从参数名补上）
arg  = resolveName(name, ...)     // 子类按来源取原始值
若 arg == null 且有 defaultValue → 用默认值
若仍 null 且 required → 缺参异常
然后 binder.convertIfNecessary(arg, parameterType, parameter)
```

`RequestParamMethodArgumentResolver.resolveName` 取的是 Servlet 参数（query + form）：

```java
String[] paramValues = request.getParameterValues(name);
if (paramValues != null) {
    arg = (paramValues.length == 1 ? paramValues[0] : paramValues);
}
```

此时 `arg` 通常是 **String**（或 String[]）。方法参数若是 `Long`，不是强转，而是：

```java
arg = binder.convertIfNecessary(arg, parameterType, parameter);
```

`WebDataBinder` / `ConversionService` 把 `"1"` 变成 `1L`。这对应问题 81 里的标量转换表；官方把表做成了可扩展的 ConversionService。

`@RequestBody UserDao` **不走**这条解析器，而走 `RequestResponseBodyMethodArgumentResolver` + `HttpMessageConverter`（Jackson 等），按 `parameter.getParameterType()` 反序列化整段 body。名字回退与 body 无关。

### 6. 和当前迷你实现的差距

```text
Spring:
  注解 value/name == "" 
    → MethodParameter.getParameterName()
      → isNamePresent ? 真实名 : null
    → null 则明确失败
    → 用最终名字 request.getParameterValues
    → ConversionService 转到 Long

当前 HandlerAdapterImpl:
  注解 value == "" 
    → requestParams.get("")
    → 静默拿不到
```

要对齐 Spring，Adapter（或以后抽出的 Resolver）应做 `updateNamedValueInfo` 那 10 行，而不是改注解语法。`@RequestBody` 继续单独分支，不要 `hasMeta(RequestParam)`。

### 常见误区

| 想法 | Spring 实际 |
|------|-------------|
| `@RequestParam` 的 default 会填入 `userId` | default 是 `""`；补名在解析器 |
| Spring 总能读到源码参数名 | 现行只认 `-parameters`（及 Kotlin 反射） |
| `getName()` 得到 `arg0` 时 Spring 会拿去查 query | 发现 `!isNamePresent()` 直接返回 null 并抛错 |
| 调试信息 / `-g` 在新版本仍够用 | 6.1 起不够 |
| `@RequestBody` 也靠参数名 | body 走 MessageConverter，用的是 `Class` 不是名字 |
| 强转 String 为 Long | `convertIfNecessary`，不是 `(Long)` |

### 最终建议

读 Spring 时抓住三层即可：注解只存常量名；`updateNamedValueInfo` 在名为空时用 `getParameterName()`；`StandardReflectionParameterNameDiscoverer` 用 `isNamePresent()` 拒绝 `arg0`。迷你框架第一版若不想引入 Discoverer 接口，把这三步写成 Adapter 里的 if 就已经是同一算法。省略 `@RequestParam("userId")` 之前，先保证编译带 `-parameters`，否则会遇到和官方一模一样的那句异常。

## 86. 方法的入参名字能通过反射拿到吗？

**结论：能，但不是默认就能。** Java 8 起可以用 `Method.getParameters()` → `Parameter.getName()`。没加 `-parameters` 编译时，这个名字是占位符 `arg0`、`arg1`，不是源码里的 `userId`。先看 `parameter.isNamePresent()`：`true` 才是真名。类型、注解、下标随时能拿到，只有“源码参数名”依赖编译器是否写入 class。

这是问题 83–85 的底层事实，单独成条便于复习。出现位置：`getUser(@RequestParam Long userId)` 与 `HandlerAdapterImpl` 里对 `Parameter` 的使用。

### 反射对一个方法参数能拿到什么

```java
Method method = UserController.class.getMethod("getUser", Long.class);
Parameter[] parameters = method.getParameters();
Parameter p = parameters[0];

p.getType();                 // Long.class        —— 一定有
p.getParameterizedType();    // 同左（无泛型时）  —— 一定有
p.getAnnotations();          // @RequestParam     —— Retention 为 RUNTIME 时有
p.getName();                 // "userId" 或 "arg0" —— 看编译
p.isNamePresent();           // true / false       —— 是否写入了真实名
```

JVM 执行 `invoke` 只需要类型和顺序，不需要参数叫什么。所以 javac 默认生成的描述符是：

```text
getUser(Ljava/lang/Long;)Ljava/lang/String;
```

里面没有 `userId`。Java 8 增加了可选属性 `MethodParameters`；加上 `-parameters` 才会写入，`getName()` 才能返回 `userId`。

对照其他“名字”：

| 反射 API | 默认能否拿到源码名 |
|----------|-------------------|
| `Class.getName()` / `Method.getName()` / `Field.getName()` | 能，成员名是 class 的正式标识 |
| `Parameter.getName()` | **默认不能**，要 `-parameters` |
| 构造器参数 | 同一套 `Parameter` API，同样要 `-parameters` |

字段注入能 `field.getName()`，方法参数不能同等对待，原因就是这张表。

### 怎么判断拿到的是不是真名

```java
if (parameter.isNamePresent()) {
    String name = parameter.getName(); // "userId"
} else {
    String name = parameter.getName(); // "arg0"：API 仍返回字符串，但不是源码名
}
```

注意：`isNamePresent() == false` 时 `getName()` **不会**返回 `null`，而是 `arg0`。直接 `requestParams.get(parameter.getName())` 会去查 `"arg0"`，看起来像“反射拿不到”，其实是拿到了占位名。Spring 因此在 `!isNamePresent()` 时整组返回 null，绝不使用 `arg0`。

用 `javap -v UserController.class` 可以自查：有 `MethodParameters` 且 `name=userId` 才算编译成功带上了名字；只有 `LocalVariableTable` 是调试信息，`Parameter.getName()` 不读它。

### 怎样让反射拿到真名

javac：

```text
javac -parameters ...
```

Maven：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
    </configuration>
</plugin>
```

IDEA：Settings → Compiler → Java Compiler → Additional command line parameters 填 `-parameters`，然后 Rebuild。当前仓库父 POM 没有这项，IDE 直接运行测试时通常仍是 `arg0`。

Spring Boot 父 POM 一般已打开，所以很多业务项目里 `@RequestParam Long userId` 能工作，容易误以为“反射默认就能拿名字”。

### 和框架绑定的关系

反射拿到名字，只解决“这个参数叫什么”。还要：

1. 请求 Map 的 key 正好是这个名字（或注解 `value` 另指定）；
2. 值再按 `parameter.getType()` 转换。

官方路径是：注解 `value` 优先，为空才 `getParameterName()`。迷你框架同样可以，但不要把 `arg0` 当业务名。

### 常见误区

| 想法 | 实际 |
|------|------|
| 反射拿不到参数名 | 能拿，默认是 `arg0`；真名要 `-parameters` |
| `getName()` 为 `arg0` 说明 API 坏了 | 未写入 `MethodParameters` 时的规定行为 |
| 调试能看到 `userId`，`getName()` 就一定是 | 调试读 LocalVariableTable，反射读 MethodParameters |
| 和方法名、字段名一样稳 | 只有参数名是可选元数据 |
| 拿到名字就能当 `@RequestParam` 用 | 还要和 query key 对齐，并做类型转换 |

### 最终建议

把问题记成一句：**反射可以读方法入参名，条件是 class 里有 `MethodParameters`。** 先 `isNamePresent()`，再 `getName()`。当前项目没开 `-parameters` 时，不要用参数名去匹配 `requestParams`；用 `@RequestParam("userId")` 的注解值更稳。

## 87. `@RequestParam` 写好了，接下来做什么？

**结论：注解写好不等于绑定完成。下一步不是抽 Resolver，也不是立刻做 `@RequestBody`，而是让 `/getUser` 端到端跑通，并补上 String → Long 的标量转换。** 当前 Adapter 只是 `requestParams.get(annotation.value())` 原样塞进 `invoke`；测试里塞的是已经装箱好的 `12345L`，还没有证明框架会处理真实 HTTP 里的字符串 `"12345"`。先把这一条路径做实，再谈 body / JSON。

### 现在实际到哪一步

已有：

```java
public @interface RequestParam {
    String value() default "";
}

public String getUser(@RequestParam("userId") Long userId)

values[i] = requestParams.get(annotation.value());
```

`PhraseTest2.testGetUser` 已指向 `/getUser`，但 Map 里放的是：

```java
put("userId", 12345L);  // 已经是 Long，invoke 碰巧能对上
```

还缺：

| 缺口 | 为何现在就要管 |
|------|----------------|
| 没有按 `parameter.getType()` 转换 | 真实 query 是 `"12345"`，`(Long)` 强转会失败，`invoke` 也会 `IllegalArgumentException` |
| 测试没有断言 | `testGetUser` 只打印，绿不了也看不出来 |
| `hasMeta(RequestParam)` | `@RequestBody` 元注解了 `@RequestParam`，打 `/addUser` 时 `getAnnotation` 为 null，NPE |
| `value` 为空时的行为 | 仍会 `get("")`；回退参数名和 `-parameters` 都可以再往后放 |
| `requestParams == null` | `/hello` 现在能过是因为无参；有参方法 NPE |

问题 79 的路线里「定义 `@RequestParam`」已经跨过；下一项本来就是「支持 String 到基础类型转换」。HttpRequest/HttpResponse 作为方法参数可以继续不做——Controller 还没用它们当入参。

### 下一步（只做这一件）：打通 `@RequestParam` + 标量转换

Adapter 里对直接标注了 `@RequestParam` 的参数：

```text
1. 用 parameter.getAnnotation(RequestParam.class)，不要 hasMeta
2. name = annotation.value()；为空则明确报错（先不要 getName()）
3. raw = requestParams.get(name)
4. values[i] = convertSimple(raw, parameter.getType())
5. invoke(object, values)
```

`convertSimple` 第一版只覆盖当前需要的类型即可：

```text
null → null
已经是目标类型 → 原样返回
String → Long / Integer / Boolean / String
其他 → 明确抛“暂不支持”
```

不要在 Adapter 里写 `UserDao`。`@RequestBody` 先跳过：循环里遇到未支持的参数类型应报错，而不是当 RequestParam 处理。

验收（改测试，不必先抽类）：

```java
httpRequest.requestUrl = "/getUser";
httpRequest.requestParams = new HashMap<>();
httpRequest.requestParams.put("userId", "12345");  // 故意用字符串
dispatcher.doService(httpRequest, httpResponse);
assertEquals("{id:12345, name:'Tom', age:20}", httpResponse.responseBody);
```

`UserService.getUser` 是按 id 现场 new 一个 Tom，所以这个断言稳定。若仍 `put("userId", 12345L)`，测不到转换。

`/hello` 无参应继续通过，防止组参循环把无参方法弄坏。

### 这一步里顺手修、但不要扩大范围

1. **判断改成直接注解**：`parameter.isAnnotationPresent(RequestParam.class)` 或 `getAnnotation != null`。并从 `RequestBody` 上拿掉元注解 `@RequestParam`。否则下一步一碰 `/addUser` 就会炸。
2. **`@RequestParam` 的 `@Target` 只留 `PARAMETER`**，和 Spring 一致；标在类上没有 query 可绑。
3. **value 为空抛错**，提示写成 `@RequestParam("userId")`。省略写法等转换跑通再加 `-parameters`。

不要在这一步做：ArgumentResolver 接口、ConversionService、JSON、`@RequestBody` 反序列化、编译器 `-parameters`。第二种参数来源还没出现，抽接口会重复 `@Autowired` 过早抽象的问题。

### 再往后的顺序（转换测试绿了才进入）

```text
1. 现在：@RequestParam + convertSimple + /getUser 断言（字符串入参）
2. 然后：HttpRequest 增加 requestBody；@RequestBody 用 parameter.getType() 通用绑定
3. 两种来源都有了：再考虑 HandlerMethodArgumentResolver
4. 返回值：现在 result.toString() 够用；JSON 输出跟 body 输入一起做更自然
5. 最后才是：value 为空回退参数名、-parameters、required/defaultValue
```

`@RequestBody` 是下一项功能，不是现在立刻写。它依赖「按 Class 构造对象」，和标量转换表是两条路（问题 81）。先把表做小、做对。

### 常见误区

| 想法 | 实际 |
|------|------|
| 注解和 `get(value)` 写完就齐了 | 还缺转换和验收；当前测试用 Long 绕过了转换 |
| 接下来抽 Resolver | 只有一种来源，Adapter 里 if 足够 |
| 接下来做 UserDao / JSON | `/getUser` 还没按字符串证明绑定 |
| 同时做参数名回退 | 已显式 `"userId"`，回退不是阻塞项 |
| 转换时写死 `if (name.equals("userId"))` | 按 `parameter.getType()` 转，不要按业务参数名 |

### 最终建议

下一步只做：`@RequestParam` 按注解 `value` 取值，再用 `parameter.getType()` 做有限标量转换，用 `userId="12345"` 的测试锁住 `/getUser`。这才是 RequestParam 从“注解存在”变成“MVC 能绑简单参数”。转换绿了再碰 `@RequestBody`。

## 88. `parameter.getType()` 和 `parameter.getParameterizedType()` 有什么区别？

**结论：一个给擦除后的 `Class`，一个给带泛型的 `Type`。** `getType()` 返回 `Class<?>`，永远是原始类型（`Long.class`、`List.class`）。`getParameterizedType()` 返回 `java.lang.reflect.Type`，无泛型时往往就是那个 `Class` 本身；有泛型时才是 `ParameterizedType`（如 `List<String>` 能看到 `String`）。第二行 `Class<?> aClass = parameter.getParameterizedType();` **编译失败**，因为右边不是 `Class`。当前 `Long userId` / `UserDao userDao` 没有泛型，转换表用 `getType()` 即可。

出现位置：`HandlerAdapterImpl` 草稿

```java
Class<?> aClass = parameter.getType();
Class<?> aClass = parameter.getParameterizedType();
```

对应 `Method` 上的一对兄弟方法：`getParameterTypes()` ↔ `getType()`，`getGenericParameterTypes()` ↔ `getParameterizedType()`。

### 返回值先不同

| 方法 | 声明返回值 | 实际常见结果 |
|------|------------|--------------|
| `parameter.getType()` | `Class<?>` | `Long.class`、`UserDao.class`、`List.class` |
| `parameter.getParameterizedType()` | `Type` | 无泛型时就是上面那个 `Class`；有泛型时是 `ParameterizedType` 等 |

`Type` 是接口，实现者包括：

```text
Class                 无泛型，或泛型擦除后的原始类型
ParameterizedType     List<String>、Map<String, UserDao>
GenericArrayType      T[]、List<String>[]
TypeVariable          方法上的 <T> T param
WildcardType          List<? extends Number>
```

`Class` 实现了 `Type`，所以无泛型时两个方法常常返回**同一个** `Long.class` 对象。有泛型时 `getParameterizedType()` 不再是 `Class`，不能赋给 `Class<?>`。

### 用同一个参数对照

```java
void demo(Long userId,
          UserDao userDao,
          List<String> names,
          Map<String, UserDao> map,
          List<UserDao>[] groups) {}
```

| 参数 | `getType()` | `getParameterizedType()` |
|------|-------------|--------------------------|
| `Long userId` | `Long.class` | `Long.class`（同一个 Class） |
| `UserDao userDao` | `UserDao.class` | `UserDao.class` |
| `List<String> names` | `List.class` | `ParameterizedType`：raw=`List`，实际参数=`String.class` |
| `Map<String, UserDao> map` | `Map.class` | `ParameterizedType`：`String`、`UserDao` |
| `List<UserDao>[] groups` | `List[]` 对应的 Class | `GenericArrayType`，分量仍带 `UserDao` |

`List<String>` 为何 `getType()` 只剩 `List`：泛型擦除。运行时 `List` 实例里不带着 `String` 这个 Class；源码里的 `<String>` 只留在**方法签名的泛型信息**里，必须用 `getParameterizedType()` / `getGenericParameterTypes()` 读。

读 `List<String>` 里的 `String`：

```java
Type type = parameter.getParameterizedType();
if (type instanceof ParameterizedType parameterizedType) {
    Type raw = parameterizedType.getRawType();                 // List
    Type[] args = parameterizedType.getActualTypeArguments();  // [String]
    Class<?> elementType = (Class<?>) args[0];                 // 仅当实参本身是 Class
}
```

`List<List<String>>` 时 `args[0]` 仍是 `ParameterizedType`，要再拆一层。这就是 Spring `ResolvableType` / `MethodParameter.getNestedGenericParameterType()` 要处理的事。

### 当前项目该用哪一个

```java
public String getUser(@RequestParam("userId") Long userId)
public UserDao addUser(@RequestBody UserDao userDao)
```

都没有类型参数。`getType()` 就是 `Long.class` / `UserDao.class`，可以：

```java
Class<?> type = parameter.getType();
if (type == Long.class || type == long.class) {
    return Long.valueOf(raw.toString());
}
```

`getParameterizedType()` 在这里多出来的信息为零，还不能直接 `== Long.class`（除非先判断它是 Class）。标量转换、`Class.cast`、`type.getDeclaredConstructor().newInstance()` 都要 `Class`，用 `getType()`。

以后若出现 `@RequestBody List<UserDao>` 或 `@RequestParam List<Long>`，才需要 `getParameterizedType()`：外层是 List，元素类型用来逐个转换或反序列化。

### 名字容易误导

`getParameterizedType()` 直译像“只有参数化类型才调用”。实际语义是：**这个参数在源码里的完整类型（可能带泛型）**。不是 ParameterizedType 时，它照样返回 `Class`。JDK 用这个名字，是相对 `getType()`（擦除后的 Class）而言的“可能参数化的那份 Type”。

若参数类型是 `Long`，两个方法等价；若是 `List<String>`，只有后者能看到 `String`。

### 和强制转换、invoke 的关系

`invoke` 只认擦除后的 `Class`：方法描述符是 `(Ljava/lang/Long;)` 或 `(Ljava/util/List;)`，没有 `<String>`。所以组 `Object[]` 时，运行时检查的是 `getType()` 那一层。

泛型信息只影响**你怎么构造这个对象**（List 里每个元素转成 String 还是 UserDao），不影响 `invoke` 的 checkcast 目标。这和字段注入一样：`field.getType()` 是 `UserService.class`；若将来有 `List<UserService>`，才需要 `field.getGenericType()`。

### 常见误区

| 想法 | 实际 |
|------|------|
| `Class<?> aClass = parameter.getParameterizedType()` | 编译失败，返回值是 `Type` |
| `getParameterizedType()` 更完整，所以总该用它 | 无泛型时与 `getType()` 相同；有泛型时不能当 `Class` 用 |
| `getType()` 对 `List<String>` 能得到 String | 只能得到 `List.class` |
| 两个方法返回不同类型的对象，所以 `Long` 时也不同 | 无泛型时经常是同一个 `Class` 实例 |
| 名字带 Parameterized 就只适用于 `List<T>` | 任何参数都能调；不是参数化类型时返回 Class |
| 强转 / convert 必须用 `getParameterizedType()` | `Long.valueOf`、`Class.cast` 需要 `Class`，用 `getType()` |

### 最终建议

当前绑定 `Long` / `UserDao` 只用 `parameter.getType()`。把 `getParameterizedType()` 留给以后的 `List<...>` / `Map<...>`。不要把返回值写成 `Class<?>`；若要用，先 `instanceof ParameterizedType` 再取 `getActualTypeArguments()`。

## 89. String → Long 转换写好了，这一步算完成吗？接下来做什么？

**结论：主路径已经打通，`/getUser` 用字符串 `"12345"` 能进到 `Long userId`。** `PhraseTest2` 三个用例均通过，`testGetUser2` 打印 `{id:12345, name:'Tom', age:20}`。方向对：按 `parameter.getType()` 分支，用 `Long.valueOf(raw.toString())`，不是 `(Long)` 强转。接下来不要继续扩转换表，转向 `@RequestBody`：给 `HttpRequest` 加原始 body，按 `parameter.getType()` 做通用对象绑定。转换代码还有几处小缺口，进 body 之前顺手收一下即可，不必再抽 ConversionService。

出现位置：`HandlerAdapterImpl.handle`

```java
values[i] = requestParams.get(annotation.value());
Class<?> aClass = parameter.getType();
if (aClass == Integer.class) {
    values[i] = Integer.valueOf(requestParams.get(annotation.value()).toString());
} else if (aClass == Long.class) {
    values[i] = Long.valueOf(requestParams.get(annotation.value()).toString());
} else {
    values[i] = requestParams.get(annotation.value()).toString();
}
```

测试：`testGetUser` 放 `12345L`，`testGetUser2` 放 `"12345"`。

### 为什么说主路径对

- 用了 `getType()` 而不是 `getParameterizedType()`，和问题 88 一致。
- `"12345"` 和 `12345L` 都能变成 `Long`：`toString()` 后再 `valueOf`，Long 入参也会变成 `"12345"` 再解析回来，碰巧兼容。
- `/hello` 无参仍通过，组 `Object[]` 没有把无参方法弄坏。
- 没有在 Adapter 里写 `UserDao`。

这已经满足问题 87 说的「RequestParam 从注解存在变成能绑简单参数」。

### 还值得收的小缺口（不必单开一大步）

1. **第一行赋值是死的。** 后面 if/else 一定会覆盖 `values[i]`。留着容易让人以为“先放原值再转换”。
2. **`get` 了四次。** 抽成 `Object raw = requestParams.get(name);`，null 时不要调 `toString()`（现在缺参会 NPE）。
3. **else 一律 `toString()`。** 参数若是 `Boolean`、或已经是目标类型以外的对象，会被拧成 String，`invoke` 再失败。更稳的是：已是目标类型则原样返回；`String.class` 才 `toString()`；其余明确抛“暂不支持”。
4. **没有 `long.class` / `int.class`。** 当前 Controller 是包装类 `Long`，够用；若写成 `long userId` 会掉进 else 变成 String。
5. **`hasMeta(RequestParam)` 仍在。** `@RequestBody` 元注解了 `@RequestParam`，一打 `/addUser`，`getAnnotation(RequestParam.class)` 为 null。进 body 之前必须改成直接注解判断，并去掉 `RequestBody` 上的 `@RequestParam`。
6. **测试只打印、没有 `assertEquals`。** 回归时绿不成“锁住”。`testGetUser2` 建议断言 `{id:12345, name:'Tom', age:20}`。

这些是打磨，不是推翻。不要为此引入 ConversionService 或 Resolver。

### 接下来做什么：`@RequestBody`

问题 87 的顺序里，标量转换之后就是第二种参数来源。`UserController.addUser(@RequestBody UserDao userDao)` 已经写在那里，请求体不是 query Map 里的一个 key。

建议最小增量：

1. `HttpRequest` 增加 `String requestBody`（或以后再改成字节）。不要把 JSON 先解析成 UserDao 再塞进 `requestParams`。
2. Adapter 循环里单独判断 `parameter.isAnnotationPresent(RequestBody.class)`（或 `getAnnotation != null`）。
3. 目标类型用 `parameter.getType()`（运行时是 `UserDao.class`），**源码不要出现 `UserDao` 字面量**。极简绑定即可：无参构造 `newInstance`，再按字段名从 JSON/Map 取值，字段类型复用刚写的 Integer/Long/String 转换。
4. 测试：`/addUser` 给一段 `{"id":1,"name":"tom","age":18}`（或测试里先放 Map，但 Adapter 仍按 Class 通用填充），断言返回里出现 `19787263`（`UserService.addUser` 会 `setId`）。

JSON 解析第一版可以很简陋，甚至测试暂时用“已经拆好的 Map + 通用 bind”验证“按 Class 填充”，真正的字符串 JSON 解析可以紧随其后。关键是 Adapter 不知道 `UserDao` 这个类名。

两种来源都跑通之后，再考虑是否抽 `HandlerMethodArgumentResolver`。现在不要抽。

### 不要在这一步做的事

- 扩转换表覆盖所有 JDK 类型；
- `value` 为空回退参数名 / `-parameters`；
- 返回值 JSON 序列化（现在 `result.toString()` 对 UserDao 的手写 toString 够验收）；
- HttpRequest/HttpResponse 作为 Controller 方法参数。

### 最终建议

String → Long 可以视为 RequestParam 主路径完成。进 `@RequestBody` 前先把判断改成直接注解、去掉 RequestBody 上的元注解 `@RequestParam`，避免 NPE。然后给请求加 body，用 `parameter.getType()` 通用构造业务对象，不要在 Adapter 里 `new UserDao()`。

## 90. request 路由做好了，支持 GET 和 POST，接下来怎么做？

**结论：GET/POST 能查到，但路由这一层还没收口。下一步不要抽 ArgumentResolver，也不要做 PathVariable / 真实 HTTP，只把「path + method」收成唯一路由表。**

出现位置：`HandlerMappingImpl`、`HandlerAdapterImpl`、`Dispatcher`、`RequestMappingInfo`、`UserController`、`PhraseTest4`。

### 当前已经做到哪

- `@RequestMapping` 增加了 `requestMethod()`，默认 `RequestMethod.Get`。
- 有了 `RequestMappingInfo(path, method)` 和 `requestMappingInfoMap`。
- `getHandlerMethod(RequestMappingInfo)` 按 path + method 比较后返回 Handler。
- `PhraseTest4` 用 `RequestMappingInfo(path=/getUser, method=Get)` 能打到 `getUser`。

这说明「按 HTTP Method 选 Handler」这条主路径通了，方向对。但还不能算路由阶段完成。

### 为什么说还没收口

看现在的实现，新旧两套查找同时活着：

```java
// HandlerMappingImpl
public final Map<String, HandlerMethod> requestMappingMap = new HashMap<>();
public final Map<RequestMappingInfo, HandlerMethod> requestMappingInfoMap = new HashMap<>();
```

```java
// HandlerAdapterImpl
if (httpRequest.requestUrl != null) {
    handlerMethod = handlerMapping.getHandlerMethod(httpRequest.requestUrl);
} else {
    handlerMethod = handlerMapping.getHandlerMethod(httpRequest.requestMappingInfo);
}
```

`PhraseTest2` / `PhraseTest3` 仍只填 `requestUrl`，完全绕开 method。所以现有测试绿，并不证明 GET/POST 路由已经接进主链路。

更关键的是重复校验仍按「只有 path」：

```java
if (requestMappingMap.get(annotation.value()) != null) {
    throw new RuntimeException("MVC中出现重复的URL映射");
}
```

同一路径的 GET 和 POST 现在会被判成重复映射。这正好把刚做的 HTTP Method 能力卡死了。`/getUser` GET 再加 `/getUser` POST，启动就会炸。路由升级的核心价值是「同路径不同方法可以并存」，这一条目前不成立。

另外几处会让后续越写越拧：

1. **`RequestMappingInfo` 没有 `equals` / `hashCode`。** 所以不能 `map.get(info)`，只能遍历 `keySet` 比字段。能跑，但是 O(n)，也解释不了「为什么它能当 Map key」。HashMap 用 key 查找靠的就是这两个方法；缺了它们，两个「path、method 都相同」的对象对 Map 来说是两个 key。
2. **404 和 405 没分开。** 找不到 Handler 一律写 `"404"`。路径存在但 method 不对，官方语义是 405 Method Not Allowed。
3. **`/addUser` 没标 POST。** `requestMethod` 默认 Get，带 `@RequestBody` 的接口现在登记成 GET，语义反了。
4. **`RequestMethod` 大小写不统一。** `Get` 和 `POST` 混用。建议一律 `GET` / `POST`，和 HTTP 方法名对齐。
5. **Dispatcher 每请求 `new HandlerAdapterImpl()`，再把 mapping 塞进去。** Adapter 又自己查 Mapping。前面约定过：Dispatcher 负责找 Handler，Adapter 只负责调。Lookup 和 invoke 还粘在一起。
6. **没有「同路径不同方法」的测试。** `PhraseTest4` 只验证了 GET `/getUser`。没测 POST 同路径、没测 405、没测重复注册应启动失败。只 println，没有断言。

`HandlerMethodArgumentResolver` 现在还是空壳静态方法，先别往里面搬代码。Resolver 解决的是「参数从哪来」，不是「哪个方法该被调用」。路由没收口就抽解析器，等于同时开两摊。

### 这一步只做：收口 HTTP Method 路由

目标可以写成一句话：

```text
整个 MVC 只认一张表：Map<RequestMappingInfo, HandlerMethod>
查找条件永远是 path + method
同 path 不同 method 可以并存
同 path 同 method 启动失败
路径没有 → 404
路径有、method 没有 → 405
```

建议按这个顺序改，一次只动路由，不动参数绑定：

**1. `RequestMappingInfo` 做成可当 Map key 的值对象**

字段可以继续 public，但必须补 `equals` / `hashCode`，只比较 `path` 和 `method`。两个字段都确定后再放进 Map。查找改成：

```java
return requestMappingInfoMap.get(requestMappingInfo);
```

不要再 `for (RequestMappingInfo loop : keySet())` 手比。手比能工作，但等于自己实现了一遍 HashMap 已经提供的事，也掩盖了「缺 equals/hashCode」这个漏洞。

**2. 删掉 path-only 的 `requestMappingMap` 和 `getHandlerMethod(String)`**

`HttpRequest` 也不再靠 `requestUrl` 走旁路。请求进入 Dispatcher 时，必须带 path 和 method。旧测试 `PhraseTest2` / `PhraseTest3` 一起改成填 `RequestMappingInfo`，不要保留「没写 method 也能查到」的兼容分支。兼容分支一留，两套表会一直活着。

**3. 重复校验改成 path + method**

注册时：

```text
RequestMappingInfo info = (path, method)
if (map.containsKey(info)) 启动失败
else map.put(info, handler)
```

只有 path 相同、method 也相同，才是冲突。`GET /users` 和 `POST /users` 必须都能注册。

**4. Dispatcher 先查 Handler，再交给 Adapter**

```text
Dispatcher.doService
  → handler = handlerMapping.getHandler(request)
  → 没有 handler：写 404 或 405，直接返回
  → 有 handler：handlerAdapter.handle(handler, request, response)
```

`HandlerAdapter` 不再持有 `HandlerMapping`，也不再自己 `getHandlerMethod`。`HandlerAdapter` 在 `init` 里创建一次，不要每个请求 new。接口可以改成：

```java
void handle(HandlerMethod handler, HttpRequest request, HttpResponse response)
```

**5. 区分 404 和 405**

`getHandler` 返回 null 时，不要立刻当 404。先判断「这个 path 是否在表里出现过」：

- 整个 path 都没见过 → 404
- path 见过，但当前 method 对不上 → 405

第一版不必做 Allow 头，`HttpResponse.status = 404` 或 `405` 即可。`responseBody` 写 `"404"` / `"405"` 也能验收，但 status 要填上，后面接真实 HTTP 才接得上。

实现上可以另备一个 `Set<String> registeredPaths`，注册时把 path 放进去；也可以遍历 `requestMappingInfoMap.keySet()` 看有没有相同 path。教学阶段遍历可以，表变大后再优化。

**6. 把 demo 接口的 method 写对**

```text
GET  /hello
GET  /getUser
POST /addUser
```

`/addUser` 必须显式 `requestMethod = RequestMethod.POST`（或你统一后的 `POST`）。默认 GET 只留给确实是查询的方法。

**7. 用测试锁住语义，不要只 println**

最少四条：

| 场景 | 期望 |
| --- | --- |
| `GET /getUser` + `userId` | 命中 `getUser`，body 里能看到用户信息 |
| `POST /addUser` + JSON body | 命中 `addUser`，不要再走 GET 默认 |
| 同一路径再注册一个不同 method，例如 `GET /users` 和 `POST /users` | 分别命中两个方法 |
| `DELETE /getUser`（或未注册的 method） | status 405，不调用 Controller |
| 启动时再注册一个 `GET /getUser` | 抛「重复映射」 |

现有 `PhraseTest2`（`/hello`）和 `PhraseTest3`（param / body）改完 RequestMappingInfo 后行为应保持不变，并补 `assertEquals`。`PhraseTest4` 适合专门锁 method 语义。

### 这一步不要做的事

- 不要抽 `HandlerMethodArgumentResolver`。Adapter 里的 `@RequestParam` / `@RequestBody` 分支先原样留着。
- 不要写 `@GetMapping` / `@PostMapping`。它们只是 `@RequestMapping(method=GET/POST)` 的语法糖，路由表没收口时加组合注解，等于再引入一层元注解解析。
- 不要做 `/users/{id}`、`@PathVariable`。路径变量是「path 怎么匹配」，现在连「path 是否相等」都还和旧 String key 混在一起。
- 不要做类级别 `@RequestMapping("/users")` 前缀。那是注册时把 class path + method path 拼起来，属于路由表稳定之后的增量。
- 不要接 Tomcat / ServerSocket。真实 HTTP 会把「谁解析 method」和「谁查表」搅在一起，现在还看不清。
- 不要扩 ConversionService、不要动 `@Autowired`、不要改 Scan。

### 收口完成后，下一层才是 ArgumentResolver

路由收口的验收通过后，再单独开一步：

```text
把 HandlerAdapter 里 RequestParam / RequestBody 两个分支
迁成两个 HandlerMethodArgumentResolver
```

那时 Adapter 只遍历参数、选 resolver、invoke、写响应。ObjectMapper 下沉到 RequestBody resolver。现有 Web 测试行为不变。那是问题 87 里说过的阶段，现在提前做会和路由收口抢同一块 Adapter。

### 和问题 86、87 的关系

问题 86 把 HTTP Method 定为 RequestBody 之后的主任务；问题 87 的总路线里把它放在 ArgumentResolver 后面。你实际先做了 Method 路由，这个顺序也可以：路由是「找谁」，Resolver 是「参数怎么填」，两者独立。但 86 里写过的验收还没齐：

- 映射 key 是不可变的 `RequestMappingInfo`，带 equals/hashCode；
- 只有一张表；
- 同 path 不同 method 可并存；
- 404 / 405 分开；
- 重复 path+method 启动失败。

先把 86 的验收做完，再回到 87 的 Resolver。不要因为「PhraseTest4 能打印出结果」就认为路由阶段结束。

### 判断依据

- Spring MVC 的 `RequestMappingInfo` 是条件对象，不是单纯 URL 字符串；`RequestMappingHandlerMapping` 用它做 key。
- `HashMap` 的 get/containsKey 依赖 key 的 `equals`/`hashCode`。值对象不当值对象用，就只能手写循环，后续加 consumes/produces/params 会更难。
- Dispatcher 的职责是「找到 Handler + 处理映射失败」；Adapter 的职责是「调用 Handler」。Lookup 留在 Adapter 里，405 也只能挤在 Adapter 的 else 里写成 404。
- 同一 URL 上 GET 查、POST 增是 REST 的基本形态。重复校验若仍按 path，这个形态无法表达。

### 常见误区

| 说法 | 问题 |
| --- | --- |
| PhraseTest4 通了，路由就做完了 | 旧测试仍走 `requestUrl`，同 path 不同 method 还不能注册 |
| 两张表先并存，兼容旧测试 | 兼容分支会变成永久双轨，method 永远是可选的 |
| 没有 equals/hashCode，遍历也能比 | 能跑，但 RequestMappingInfo 不能当 Map key，和「升级 key」这个目标相反 |
| 找不到就统一 404 | 丢掉了「资源在、动词不对」这个信息，后面接 Servlet 时 status 会对不上 |
| 接下来抽 Resolver / 写 GetMapping | 路由表还是双轨，抽解析器解决不了「谁被调用」 |
| `/addUser` 不写 method、靠默认 GET | body 接口登记成 GET，测试和真实 HTTP 语义都会歪 |

### 最终建议

下一步只做一件事：**删掉按 URL 字符串查表的旧路，让 `RequestMappingInfo(path+method)` 成为唯一 key，并补上 404/405 和同路径双方法测试。** Adapter 里的参数绑定先不动。等这些测试用断言锁住之后，再抽 ArgumentResolver。

## 91. 怎么重写 equals？

**结论：不要 `return super.equals(obj)`。** `Object.equals` 比的是「是不是同一个对象」（`==`）。`RequestMappingInfo` 要当 HashMap 的 key，必须自己比 `path` 和 `method` 两个字段；同时必须重写 `hashCode`，两个方法用同一组字段。

出现位置：`RequestMappingInfo.equals`，当前是：

```java
@Override
public boolean equals(Object obj) {
    return super.equals(obj);
}
```

这等于没重写。`super` 是 `Object`，`Object.equals` 的实现就是 `return this == obj`。注册时 `new` 出来的 info，和查找时 `new` 出来的另一个 info，即使 path、method 完全一样，`equals` 也是 false，`map.get` 找不到。

### 为什么默认 equals 不够

Java 里每个对象都从 `Object` 继承了 `equals`。默认语义是**引用相等**：

```text
info1 == info2          // 是不是堆里的同一个实例
info1.equals(info2)     // 没重写时，和 == 一样
```

路由表需要的是**值相等**：

```text
path 相同 且 method 相同  →  同一个映射条件
```

注册：

```java
RequestMappingInfo key = new RequestMappingInfo();
key.path = "/getUser";
key.method = RequestMethod.Get;
requestMappingInfoMap.put(key, handler);
```

查找：

```java
RequestMappingInfo query = new RequestMappingInfo();
query.path = "/getUser";
query.method = RequestMethod.Get;
requestMappingInfoMap.get(query);
```

`key` 和 `query` 是两个对象。不重写 equals，HashMap 认为它们不是同一个 key，只能像现在这样遍历 `keySet` 手比字段。重写之后，`get(query)` 就能直接命中。

### 标准写法

`equals` 的入参必须是 `Object`，不能改成 `RequestMappingInfo`，否则不是重写（override），是重载（overload）。HashMap 调用的是 `equals(Object)`，你那个 `equals(RequestMappingInfo)` 它根本不会走。

推荐按这个顺序写，少一步都容易埋坑：

```java
@Override
public boolean equals(Object obj) {
    if (this == obj) {
        return true;
    }
    if (!(obj instanceof RequestMappingInfo)) {
        return false;
    }
    RequestMappingInfo other = (RequestMappingInfo) obj;
    return Objects.equals(this.path, other.path)
            && Objects.equals(this.method, other.method);
}
```

各行在干什么：

| 步骤 | 作用 |
| --- | --- |
| `this == obj` | 同一个引用，直接 true，省一次字段比较 |
| `instanceof RequestMappingInfo` | null 或别的类型直接 false。`instanceof` 对 null 就是 false，不必再写 `obj == null` |
| 强转 | 入参是 Object，要比字段必须转成自己的类型 |
| `Objects.equals(a, b)` | 两个字段都比。它内部会处理 null：两边都 null 为 true，一边 null 为 false，都非 null 再调 `a.equals(b)` |

不要写成：

```java
return this.path.equals(other.path) && this.method.equals(other.method);
```

`path` 或 `method` 为 null 时会 NPE。`Objects.equals` 就是为了避开这个。Java 7 起就能用；项目若是 JDK 8，没问题。

如果不用 `Objects`，等价手写是：

```java
return (path == other.path || (path != null && path.equals(other.path)))
        && (method == other.method || (method != null && method.equals(other.method)));
```

更长，也更容易漏。教学上理解即可，实现用 `Objects.equals`。

### 必须同时重写 hashCode

`equals` 和 `hashCode` 是一对契约，不是两个独立功能：

```text
如果 a.equals(b) == true
那么 a.hashCode() 必须等于 b.hashCode()
```

HashMap 的查找顺序是：

```text
1. 算 key.hashCode()，定位到某个桶
2. 在桶里用 equals 找相等的 key
```

只重写 equals、不重写 hashCode，会落到这种坑：

```text
put 时用的是对象 A，hashCode 是 System.identityHashCode(A) 一类的默认值
get 时用的是对象 B，hashCode 是另一份默认值
A.equals(B) 已经是 true
但 A、B 的 hashCode 不同 → 进了不同的桶 → get 仍是 null
```

所以 `RequestMappingInfo` 里应同时写：

```java
@Override
public int hashCode() {
    return Objects.hash(path, method);
}
```

`Objects.hash` 用的字段必须和 `equals` 里比的字段完全一致。少一个或多一个，契约就破了。

IDEA 可以生成这两方法：`Alt+Insert`（Mac 是 `Command+N`）→ `equals() and hashCode()` → 勾选 `path`、`method`。生成结果和上面等价，可以看一眼再留着。

### equals 契约（HashMap 依赖这三条）

1. **自反**：`x.equals(x)` 为 true。
2. **对称**：`x.equals(y)` 和 `y.equals(x)` 同真同假。
3. **传递**：`x` 等于 `y`、`y` 等于 `z`，则 `x` 等于 `z`。
4. **一致**：字段没变，多次调用结果不变。
5. **对 null**：`x.equals(null)` 必须是 false，不能 NPE。

值对象还要注意：放进 HashMap 之后，**不要再改 path / method**。HashMap 按放入时的 hashCode 分桶；改字段后 hash 变了，对象还停在旧桶里，之后 `get` 会丢。这就是上一问说「做成值对象」的原因：字段最好在构造时定死，或者至少约定放入 Map 后不再改。

第一版可以继续 public 字段，但一旦 `put` 进 `requestMappingInfoMap`，就别再赋值。更稳的是以后改成 `final` 字段 + 构造方法。

### 和现在手写循环的关系

现在的查找：

```java
for (RequestMappingInfo loop : requestMappingInfoMap.keySet()) {
    if (loop.path.equals(requestMappingInfo.path)
            && loop.method.equals(requestMappingInfo.method)) {
        return requestMappingInfoMap.get(loop);
    }
}
```

这两行字段比较，就是你应该写进 `equals` 的内容。重写之后查找收成：

```java
return requestMappingInfoMap.get(requestMappingInfo);
```

`get` 内部会先 hashCode 定位桶，再 equals 比字段。你不用再遍历。

重复校验同样变成：

```java
if (requestMappingInfoMap.containsKey(info)) {
    throw new RuntimeException("MVC中出现重复的URL映射");
}
```

`containsKey` 也走同一对 equals/hashCode。这样「同 path 不同 method」是两个 key，「同 path 同 method」才是冲突。

### 常见误区

| 写法 | 问题 |
| --- | --- |
| `return super.equals(obj)` | 仍是引用比较，等于没重写 |
| `public boolean equals(RequestMappingInfo obj)` | 这是重载，不是重写。HashMap 不会调用它 |
| 只写 equals，不写 hashCode | `equals` 为 true 的两个对象可能进不同桶，`get` 仍失败 |
| hashCode 用了字段，equals 少比一个 | 契约破裂，HashMap 行为未定义 |
| `this.path.equals(other.path)` | path 为 null 时 NPE |
| `if (obj == null) return false;` 后再 `instanceof` | 多余；`instanceof` 已覆盖 null |
| 用 `getClass() != obj.getClass()` 还是 `instanceof` | 当前没有子类，两种都行；有子类时 `getClass()` 更严。第一版 `instanceof` 足够 |
| 把 HandlerMethod 或其他可变状态算进 equals | key 会变，Map 会丢 |
| 重写了 equals 却继续手写 for 循环比字段 | 能跑，但看不出重写的意义 |

### 最小可验收

写完后不必先改整张路由表。用两个不同实例就能验：

```java
RequestMappingInfo a = new RequestMappingInfo();
a.path = "/getUser";
a.method = RequestMethod.Get;

RequestMappingInfo b = new RequestMappingInfo();
b.path = "/getUser";
b.method = RequestMethod.Get;

assert a.equals(b);
assert a.hashCode() == b.hashCode();

Map<RequestMappingInfo, String> map = new HashMap<>();
map.put(a, "hit");
assert "hit".equals(map.get(b));
```

`equals` 为 true、`hashCode` 相同、`map.get(b)` 能拿到 `put(a)` 的值，这三个同时成立，才算重写成功。只有 `equals` 为 true、`get` 仍是 null，就是漏了 hashCode。

### 最终建议

把现在的 `super.equals(obj)` 换成「先判同一引用，再 `instanceof`，再 `Objects.equals(path)` + `Objects.equals(method)`」，并立刻补 `hashCode()` 用 `Objects.hash(path, method)`。字段集合必须两边一致。不要改方法签名。改完用两个 `new` 出来的 info 做 `map.put` / `map.get`，能取到值再去删 `HandlerMappingImpl` 里的手写循环。

## 92. 什么是 405，和 404 有什么区别？

**结论：404 是「这个路径不存在」；405 是「这个路径存在，但当前 HTTP 方法不允许」。** 对客户端来说，一个是「你找错地方了」，一个是「地方对了，动词用错了」。

### 名字和官方含义

| 状态码 | 英文全称 | 常见中文 | 核心意思 |
| --- | --- | --- | --- |
| **404** | Not Found | 未找到 | 服务器找不到与请求 URI 对应的资源 |
| **405** | Method Not Allowed | 方法不允许 | 请求的 URI 识别到了，但该资源不支持这次用的 HTTP Method |

两者都属于 4xx「客户端错误」：不是服务器崩了（那是 5xx），而是请求本身有问题。差别在于**错在哪一层条件**：

```text
404 → path 这一层就没命中
405 → path 命中了，method 没命中
```

### 用你现在的路由表理解

假设注册了：

```text
GET  /getUser  → getUser()
POST /addUser  → addUser()
```

| 请求 | 应返回 | 原因 |
| --- | --- | --- |
| `GET /getUser` | 200（成功） | path + method 都匹配 |
| `GET /noSuchUrl` | **404** | 整个 path 从未注册过 |
| `DELETE /getUser` | **405** | `/getUser` 有人管，但只允许 GET，不允许 DELETE |
| `POST /getUser` | **405** | 同上：路径在，动词不对 |
| `GET /addUser` | **405** | `/addUser` 在，但登记的是 POST |

如果一律写成 404，客户端分不清：

- 是不是 URL 写错了（该改 path）；
- 还是 URL 对了，该改成 GET / POST（该改 method）。

REST 客户端、浏览器、网关、OpenAPI 工具都依赖这个区分。Spring MVC 在 `RequestMappingHandlerMapping` 里也会：先按路径等条件找，路径有但 method 不对时走 405，而不是假装资源不存在。

### 正式协议里 405 还多了什么

HTTP 规范对 405 还有一条常见要求：响应最好带 **`Allow` 头**，列出该资源实际支持的方法。例如：

```http
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
```

意思是：「你发了 DELETE，但这条路径只接受 GET 和 HEAD。」

404 一般**不**需要 Allow：资源都不存在，谈支持哪些方法没有意义。

你现在的 mini 框架第一版可以先只设：

```java
httpResponse.status = 405;
httpResponse.responseBody = "405";
```

`Allow` 头可以以后接真实 HTTP 再补。教学上先把「404 / 405 分支」分清即可。

### 和 400、401、403 别混

容易和 405 搅在一起的还有：

| 状态码 | 含义 | 和 405 的差别 |
| --- | --- | --- |
| **400** Bad Request | 请求格式/参数不合格 | 方法对了，但 body、query、JSON 坏了 |
| **401** Unauthorized | 未认证 | 身份未知 |
| **403** Forbidden | 已认证但无权限 | 身份知道，但不许做 |
| **404** Not Found | 资源不存在 | path 没命中 |
| **405** Method Not Allowed | 方法不被该资源接受 | path 命中、method 没命中 |

例如：`POST /addUser` 的 JSON 解析失败 → 更接近 **400**，不是 405；发到根本没有的 `/addUsr` → **404**；发 `PUT /addUser` 而你只注册了 POST → **405**。

### 在 Dispatcher 里怎么判断

查找 `Map<RequestMappingInfo, HandlerMethod>` 得到 null 时，不要立刻写 404。拆成两步：

```text
1. 用 (path, method) 精确查 → 命中则执行 Handler
2. 未命中时，问：这个 path 是否在表里出现过？
   - 从未出现过 → 404
   - 出现过，只是 method 对不上 → 405
```

实现上可以：

- 注册时另维护 `Set<String> registeredPaths`；或
- 遍历 `requestMappingInfoMap.keySet()`，看有没有相同 `path`。

教学阶段遍历可以；表大了再优化。关键是语义先对。

你现在的 `HandlerAdapterImpl` 找不到就写 `"404"`，等于把 405 也吞进了 404。路由收口时要把这个分支拆开（见问题 90）。

### 为什么不能「找不到就全是 404」

| 做法 | 问题 |
| --- | --- |
| 一律 404 | 客户端无法区分改 URL 还是改 Method；缓存/代理也可能按「不存在」处理 |
| 一律 405 | 不存在的 URL 也会被说成「方法不对」，误导更大 |
| 只有 path 当 key、method 事后再比 | 同路径多方法不好表达；和现在的 `RequestMappingInfo` 方向不一致 |

正确模型是：映射条件 = path + method；失败时再根据「path 是否存在」在 404 与 405 之间选择。

### 常见误区

| 说法 | 澄清 |
| --- | --- |
| 405 是服务器内部错误 | 否，4xx 是客户端错；5xx 才是服务器错 |
| 路径不对也可以返回 405 | 否，路径都不存在应 404 |
| 参数缺了返回 405 | 否，那是 400（或你框架自定义的业务码） |
| 没登录返回 405 | 否，那是 401 / 403 |
| mini 框架不写 Allow 就不算 405 | Allow 是规范推荐；status=405 已经表达了核心语义，Allow 可后补 |

### 最终建议

记两个短句就够用：

- **404 = 没有这个 URL**
- **405 = 有这个 URL，但不接受你用的 GET/POST/…**

落到代码：`(path, method)` 查不到时，先判断 path 是否注册过，再分别写 `status = 404` 或 `405`。不要再统一返回 `"404"` 字符串。

## 93. 关于 405 的逻辑也写好了

**结论：404 / 405 分支的主路径是对的，可以算「状态码语义」这一小步打通。** 路由阶段还没收完：旧的 path-only 表和「按 path 判重复」还在，同路径 GET+POST 仍注册不了；`status` 没填；查找失败仍写在 Adapter 里。下一步先把路由收口做完，再抽 ArgumentResolver。

出现位置：`HandlerAdapterImpl.handle`、`HandlerMappingImpl.getHandlerMethodForPath`、`RequestMappingInfo`、`HttpRequest`、`UserController`、`PhraseTest3`。

### 已经做对的部分

1. **`RequestMappingInfo` 的 equals / hashCode 写好了**，精确查找改成了 `requestMappingInfoMap.get(info)`，不再手写遍历比字段。这和问题 91 一致。

2. **精确未命中后，用「同 path、不同 method」区分 405 和 404**：

```java
HandlerMethod handlerMethod = handlerMapping.getHandlerMethod(httpRequest.requestMappingInfo);
if (handlerMethod != null) {
    // 执行
} else {
    if (handlerMapping.getHandlerMethodForPath(...) != null) {
        httpResponse.responseBody = "405";
    } else {
        httpResponse.responseBody = "404";
    }
}
```

语义对：`(path, method)` 都对 → 调 Handler；path 有、method 不对 → 405；path 也没有 → 404。和问题 92 一致。

3. **`getHandlerMethodForPath` 的判断条件方向正确**：

```java
path 相同 && method 不同 → 视为「资源在、动词不对」
```

4. **`HttpRequest` 去掉了 `requestUrl`**，测试改成填 `RequestMappingInfo`。`/addUser` 标了 `POST`，`RequestMethod` 统一成 `GET` / `POST`。这些都是问题 90 里点过的。

### 还没收口的点

**1. 两张表还在，重复校验仍按 path**

```java
public final Map<String, HandlerMethod> requestMappingMap = ...;
public final Map<RequestMappingInfo, HandlerMethod> requestMappingInfoMap = ...;

if (requestMappingMap.get(annotation.value()) != null) {
    throw new RuntimeException("MVC中出现重复的URL映射");
}
```

只要注册第二个同 path、不同 method 的映射，启动仍会炸。405 的前提是「同路径可以挂多个 method」；现在表结构还不允许这件事。`requestMappingMap` 和 `getHandlerMethod(String)` 可以删了，重复校验改成 `requestMappingInfoMap.containsKey(info)`。

**2. `getHandlerMethodForPath` 返回 HandlerMethod 当布尔信号**

名字像「按 path 取一个 Handler」，实际用途是「这个 path 是否存在别的 method」。调用方也不打算 invoke 返回值，只看 `!= null`。更直白的是：

```java
boolean hasPath(String path);
// 或
boolean hasHandlerForPath(RequestMappingInfo info); // 只比 path
```

现在这样能跑，但接口语义容易误导后来人去「执行那个错误 method 的 Handler」。

**3. 只写了 `responseBody = "405"`，没填 `HttpResponse.status`**

`HttpResponse` 已有 `Integer status`。正式语义应是：

```java
httpResponse.status = 405;
httpResponse.responseBody = "405"; // 可选
```

404 同理。以后接 Servlet / 浏览器时，靠的是 status，不是 body 字符串。

**4. 404 / 405 仍在 Adapter 里，Adapter 仍持有 Mapping**

查找失败属于「没找到可调用的 Handler」，更适合放在 `Dispatcher.doService`：

```text
handler = mapping.getHandler(info)
if (handler == null) {
  if (mapping.hasPath(info.path)) status=405; else status=404;
  return;
}
adapter.handle(handler, request, response);
```

Adapter 只负责参数绑定和 invoke。Dispatcher 仍每个请求 `new HandlerAdapterImpl()`，也可以顺手改成 `init` 里创建一次。

**5. 缺少锁住 405 的测试**

`PhraseTest3` 覆盖了 GET `/getUser` 和 POST `/addUser`，但没有：

- 对已注册 path 发错误 method → body/status 为 405；
- 对未注册 path → 404；
- 同 path 注册 GET + POST 都能命中（当前注册阶段会先失败）。

只 `println`、没有 `assertEquals`，回归时绿不成「锁住」。

### 对 `getHandlerMethodForPath` 实现的细评

当前：

```java
for (RequestMappingInfo loop : requestMappingInfoMap.keySet()) {
    if (path 相同 && method 不同) {
        return map.get(loop);
    }
}
return null;
```

在「精确 get 已经为 null」的前提下，这个循环等价于「是否存在相同 path」。能工作。注意：

- 若将来同一 path 有 GET 和 POST，请求是 PUT：循环会返回其中一个（比如 GET 的 Handler），调用方只看非 null → 405，结果仍对。
- 精确匹配已由 `equals`/`hashCode` 的 `get` 负责，这里不要再写「method 也相同」的分支，否则和精确查找重复。

不必为了 405 再维护第二张 `Map<path, HandlerMethod>`；维护 `Set<String> paths` 或遍历 keySet 比 path 都可以。教学阶段遍历即可。

### 这一步算完成吗？

| 验收项（问题 90） | 现状 |
| --- | --- |
| equals/hashCode + `map.get` | 已完成 |
| 请求只走 `RequestMappingInfo` | 已完成 |
| 404 / 405 分开 | 主路径已完成（body 字符串） |
| 唯一一张 `Map<RequestMappingInfo, HandlerMethod>` | 未完成，旧表还在 |
| 同 path 不同 method 可并存 | 未完成，重复校验按 path |
| 同 path 同 method 启动失败 | 未完成（现在是同 path 就失败） |
| `status` 字段 | 未填 |
| Dispatcher 查 Handler，Adapter 只调用 | 未完成 |
| 405 / 同路径双方法测试 + 断言 | 未完成 |

所以：**405 判断逻辑写对了，路由收口还差最后一截。**

### 接下来怎么做（仍不要开 ArgumentResolver）

按优先级，一次只收这些：

1. **删 `requestMappingMap` 和 `getHandlerMethod(String)`**，注册/查重只认 `requestMappingInfoMap`。
2. **重复校验改成 `containsKey(RequestMappingInfo)`**，允许 `GET /users` + `POST /users`。
3. **`HttpResponse.status` 在 404/405/成功时都填上**（成功可先写 200）。
4. **把「查 Handler + 404/405」挪到 Dispatcher**；Adapter 入参带上已解析的 `HandlerMethod`，不再持有 Mapping。

做完以上，问题 90 的路由阶段才算收完。然后再做：

```text
把 HandlerAdapter 里 RequestParam / RequestBody 两个分支
迁成两个 HandlerMethodArgumentResolver
```

### 常见误区

| 说法 | 问题 |

### 最终建议

## 94. 这个 Status 枚举怎么写？

用户草稿：

```java
public enum Status {
    private String success = "1";
    private String fail = "0";
    public Status(String status) {
        this.
    }
}
```

**结论：枚举常量必须写在类体最前面；`SUCCESS` / `FAIL` 是常量名，`"1"` / `"0"` 是构造参数，不能写成字段初始化。** 另外：若这是给 `HttpResponse.status` 用的，更不该用 `"1"`/`"0"`，应直接用 HTTP 数字 `200` / `404` / `405`，或做一个 `HttpStatus` 枚举；业务成功失败码和 HTTP 状态码不要混成一个 `Status`。

### 你这段为什么编译不过

Java 枚举有固定结构，和普通 class 不一样：

```text
enum 名字 {
    常量列表,     ← 必须最先出现
    ;           ← 后面还有字段/方法时，常量列表要以分号结束
    字段
    构造方法
    普通方法
}
```

草稿里的问题：

| 写法 | 问题 |
| --- | --- |
| `private String success = "1"` | 你把「枚举常量」写成了普通字段。常量应是 `SUCCESS("1")` |
| 常量写在字段后面 | 非法。枚举体第一项必须是常量列表 |
| `public Status(String status)` | 枚举构造器只能是 `private`（或不写修饰符，默认 private）。不能 `public`，外面不能 `new Status(...)` |
| `this.` 没写完 | 应赋给字段，例如 `this.code = status` |

枚举的本质可以想成：编译器帮你生成了几个**预先 new 好的单例对象**，名字就叫 `SUCCESS`、`FAIL`。你不能在外部再 `new`。

### 若目标是业务成功/失败码

正确写法：

```java
package com.minispring2.common;

public enum Status {
    SUCCESS("1"),
    FAIL("0");

    private final String code;

    Status(String code) {
        this.code = code;
    }

    public String getCode() {
        return code;
    }
}
```

用法：

```java
Status s = Status.SUCCESS;
String code = s.getCode();          // "1"
Status fail = Status.valueOf("FAIL"); // 按常量名解析，不是按 "0"
```

要点拆开：

1. **`SUCCESS("1")`**：调用私有构造器，把 `"1"` 传进去，创建名为 `SUCCESS` 的枚举实例。
2. **多个常量用逗号分隔**，最后一个常量后面若还有字段/方法，加 **`;`**。
3. **字段用 `final`** 更稳，构造后不再改。
4. **构造器不要写 `public`**。
5. **对外读值用 getter**，不要把字段弄成 public 再到处改。

只有两个常量、暂时不需要 `"1"`/`"0"` 字符串时，还可以更简单：

```java
public enum Status {
    SUCCESS,
    FAIL
}
```

需要和前端约定数字码时，再带 `code` 字段。

### 若目标是 HttpResponse 的 HTTP 状态

你刚在做的是 200 / 404 / 405。HTTP 状态码是**三位数字**，不是 `"1"` / `"0"`。混用一个叫 `Status` 的枚举，后面会和业务结果码打架。

更合适的两条路：

**路 A：继续用 Integer（当前 `HttpResponse.status`）**

```java
httpResponse.status = 200;
httpResponse.status = 404;
httpResponse.status = 405;
```

第一版够用，不必强行上枚举。

**路 B：单独做 `HttpStatus`，不要叫 `Status`**

```java
package com.minispring2.web.core;

public enum HttpStatus {
    OK(200),
    NOT_FOUND(404),
    METHOD_NOT_ALLOWED(405);

    private final int value;

    HttpStatus(int value) {
        this.value = value;
    }

    public int value() {
        return value;
    }
}
```

用法：

```java
httpResponse.status = HttpStatus.METHOD_NOT_ALLOWED.value();
// 或以后把字段改成 HttpStatus 类型
```

`RequestMethod` 你已经用枚举表达 GET/POST；HTTP 状态用枚举同理，但是**另一套概念**，不要和业务 `SUCCESS`/`FAIL` 塞进同一个 enum。

### 和 `RequestMethod` 对照记忆

你已经写过：

```java
public enum RequestMethod {
    GET, POST
}
```

这是「无附加数据」的最简枚举。`Status` 若要带 `"1"`/`"0"`，只是在常量后面多了构造参数和字段，骨架一样：

```text
RequestMethod:  GET, POST
Status:         SUCCESS("1"), FAIL("0");  + 字段 code + 构造器
HttpStatus:     OK(200), NOT_FOUND(404);  + 字段 value + 构造器
```

### 常见误区

| 说法/写法 | 澄清 |
| --- | --- |
| 枚举里先写字段再写 `SUCCESS` | 常量必须在最前 |
| `new Status("1")` | 枚举禁止外部 new |
| `public` 构造器 | 枚举构造器只能 private |
| `Status.valueOf("1")` | `valueOf` 认的是常量名 `SUCCESS`，不是 code |
| 一个 `Status` 既表示成功失败又表示 404 | 概念混了；HTTP 用 `HttpStatus` 或 Integer |
| `HttpResponse.status = Status.SUCCESS` | 类型对不上（Integer vs enum），语义也不对 |

### 最终建议

- 若只是练枚举语法：按上面的 `SUCCESS("1"), FAIL("0")` 写。
- 若服务于当前 MVC：`HttpResponse` 用 **200/404/405**（Integer 或单独的 `HttpStatus`），不要用 `"1"`/`"0"` 的 `Status`。
- 业务接口返回「成功/失败」码时，再单独保留 `common.Status`，和 HTTP 状态分开。

当前路由收口优先填的是 `httpResponse.status = 404/405/200`，不必先引入业务 `Status` 枚举。

## 95. 三件路由收口（除断言测试）都写好了，怎么样？

用户完成项：删 path-only 旧表并按 `RequestMappingInfo` 查重；填 status（用 `HttpStatus` 枚举）；查找 + 404/405 挪到 Dispatcher。断言测试尚未写。

**结论：三件大事的方向都做对了，HTTP Method 路由骨架可以收口。** 但有一个会直接弄坏后续成功请求的 bug：`405` 时把 `failStatus` 写进了**映射表里那个真正的 HandlerMethod**，下一次正确 method 打过来仍会被当成失败。先修这个，再写断言测试；测绿之后再抽 ArgumentResolver。

### 已经做对的部分

1. **只剩一张表**

```java
Map<RequestMappingInfo, HandlerMethod> requestMappingInfoMap
```

`requestMappingMap` 和 `getHandlerMethod(String)` 已去掉。查重变成：

```java
RequestMappingInfo info = new RequestMappingInfo(path, method);
if (requestMappingInfoMap.get(info) != null) {
    throw new RuntimeException("MVC中出现重复的URL映射");
}
```

这和 `containsKey(info)` 等价，同 path 不同 method 可以并存。`RequestMappingInfo` 构造器、`equals`/`hashCode` 也齐了。

2. **Adapter 不再查 Mapping**

```java
void handle(HttpRequest, HttpResponse, HandlerMethod)
```

Dispatcher 先拿 Handler，再交给 Adapter。职责拆开了，和问题 90、93 的目标一致。

3. **有了 `HttpStatus` 枚举**

`OK(200)` / `NOT_FOUND(404)` / `METHOD_NOT_ALLOWED(405)`，写法正确（见问题 94）。比到处写魔法数字清晰。

4. **404/405 判断离开了 Adapter 的参数循环**

失败时 Dispatcher 直接 return，不会误 invoke。大方向对。

### 必须先修的 bug：`failStatus` 污染了注册表里的 Handler

当前 `getHandlerMethod`：

```java
HandlerMethod handlerMethod = requestMappingInfoMap.get(requestMappingInfo);
if (handlerMethod == null) {
    HandlerMethod forPath = getHandlerMethodForPath(requestMappingInfo);
    if (forPath == null) {
        HandlerMethod miss = new HandlerMethod();
        miss.failStatus = HttpStatus.NOT_FOUND;
        return miss;                    // 404：新建对象，还好
    } else {
        forPath.failStatus = HttpStatus.METHOD_NOT_ALLOWED;
        return forPath;                 // 405：改的是表里那个真 Handler！
    }
}
```

`getHandlerMethodForPath` 返回的是 `requestMappingInfoMap` 里**已经注册的实例**。给它设 `failStatus`，等于改了单例映射上的字段。

时间线：

```text
1. POST /getUser（只注册了 GET）
   → 拿到 GET 对应的 HandlerMethod，failStatus = 405
   → Dispatcher 返回 405

2. GET /getUser（正确请求）
   → map.get 命中同一个 HandlerMethod
   → failStatus 仍是 METHOD_NOT_ALLOWED
   → Dispatcher 看到 failStatus != null，再次当失败返回
   → Controller 永远不会再被调用
```

404 分支用了 `new HandlerMethod()`，所以没这个问题；**只有 405 会污染**。

#### 怎么改（推荐从简到稳）

**方案 A（最小改动，和你现在结构兼容）**

405 也 `new` 一个壳，不要改表里的对象：

```java
HandlerMethod miss = new HandlerMethod();
miss.failStatus = HttpStatus.METHOD_NOT_ALLOWED;
return miss;
```

**方案 B（更清晰，推荐）**

查找失败就返回 `null`，404/405 的区分留在 Dispatcher，不要把错误码塞进 `HandlerMethod`：

```java
// HandlerMapping
HandlerMethod getHandler(RequestMappingInfo info); // 没有就 null
boolean hasPath(String path);

// Dispatcher
HandlerMethod handler = mapping.getHandler(info);
if (handler == null) {
    if (mapping.hasPath(info.path)) {
        httpResponse.status = 405;
        httpResponse.responseBody = "405";
    } else {
        httpResponse.status = 404;
        httpResponse.responseBody = "404";
    }
    return;
}
adapter.handle(request, response, handler);
```

`HandlerMethod` 只表示「能调用的处理器」，不应兼任「错误结果」。`failStatus` 字段可以删掉。

### 另外几处小缺口（断言前顺手收）

**1. 写了 body，没写 `HttpResponse.status`**

```java
httpResponse.responseBody = String.valueOf(handlerMethod.failStatus.value());
```

`HttpResponse.status` 仍是 null。成功路径也没设 200。应同时：

```java
httpResponse.status = handlerMethod.failStatus.value(); // 或 404/405
// 成功时
httpResponse.status = HttpStatus.OK.value();
```

body 写 `"404"` 可以保留方便 println，但断言应优先锁 `status`。

**2. Adapter 仍每个请求 `new`**

能跑。可在 `init` 里创建一次 `HandlerAdapter`，和 Mapping 对称。非阻塞。

**3. 查重用 `get != null` 可以，`containsKey` 更直白**

语义一样，不必强改。

**4. `getHandlerMethodForPath` 仍返回 Handler 当布尔信号**

在方案 B 里改成 `hasPath` 更干净；若暂留方案 A，至少 405 不要返回表内实例。

### 断言测试写什么（下一小步）

路由阶段最后一块砖。建议最少四条，全部 `assertEquals`，不要只 `println`：

| 用例 | 期望 |
| --- | --- |
| `GET /getUser` + userId | `status == 200`，body 含用户信息 |
| `POST /addUser` + JSON | `status == 200`，JSON 能反序列化 |
| `POST /getUser`（path 在、method 错） | `status == 405` |
| `GET /noSuchUrl` | `status == 404` |
| （加分）同 path 再挂一个 POST，分别命中 | 证明查重按 path+method |

写 405 用例时，**先发错误 method，再发正确 method**，正好能暴露上面的 `failStatus` 污染；修完后两条都应过。

现有 `PhraseTest3` 的 GET/POST 成功路径补上 `assertEquals` 即可复用。

### 常见误区

| 说法 | 问题 |
| --- | --- |
| 失败也返回 HandlerMethod，靠 failStatus 区分 | 容易改到表内对象；Handler 语义被污染 |
| body 写了 "405" 就算填了 status | `HttpResponse.status` 仍是 null |
| 三件做完就可以抽 Resolver | 污染 bug + 无断言，回归锁不住 |
| 405 返回「错误 method 那个 Handler」给 Adapter 调 | 绝对不要 invoke；你现在 Dispatcher 已 return，这点是对的 |

### 最终建议

三件收口的骨架分可以打高分。立刻改的是：**405 不要修改映射表里的 HandlerMethod**（新建壳，或改成 Dispatcher 里 `null + hasPath`）。然后补 `status` 字段和断言；断言里特意加「先 405 再正确 GET」，绿了再进 ArgumentResolver。
